## 一、目标回顾

过程层计划步骤条从「button 行条」升级为**多级折叠树**（用户拍板）：

```
[过程层总折叠条 process_summary]（一级）
├── 文本段(assistant)                ← 不入组合，独立行
├── [组合行段 ▸ N 段执行]            ← 二级小折叠条：连续非文本行段(think/tool)，自动分段
├── [计划步骤折叠区 ▸ N 待办]        ← 区级折叠头（效果同总折叠条，职责=待办项），跟随首个待办项原位
│     ├─ [待办项 1 · 序 · 状态 · 标题 ▸]   ← 文字折叠条（非 button）
│     │     ├─ [组合行段 ▸ 子动作]
│     │     └─ 产出区（description + result/output + reason）
│     └─ [待办项 2 …]（项 1 完成自动折叠后才出现）
```

核心语义：**待办项串行时序**——项运行中子动作陆续进入其组合；完成后自动折叠；下一项 UI 才出现；动作行段永不先于其待办项头出现。

## 三、关键设计决策（下一会话勿偏离）

1. **状态在数据层，折叠条不新增虚拟行**：区级折叠 `Turn.planCollapsed`（跨切窗持久）；项级复用 `stepCollapsed`；组合行段用组件内 ref `comboCollapsed`（切窗重挂重置为展开，可接受）。遵循项目既有"渲染层聚合 + 状态数据化"模式。
2. **pending 项不渲染**：`planStatus==='pending' && childRefIds 空` → 隐藏（`visibleBlocks` 过滤）。`planStatus` 是扁平透传字段（`tc.status` 仅三态无 pending/skipped）：`flatRowToStreamItem` 对 `isPlanStep` 行透传 `row.status`。
3. **回源幂等**：`restorePlanStepsIntoFlow` 逐项 `action_start`（id=`plan-${item.id}` 去重）+ `plan_step_status(autoCollapse:true)`；`in_progress` 按 `completed` 处理（后端无持久 running）；`pending` 不发状态保持隐藏。
4. **zone 头"N 待办"数** = 可见项数（不含未露头 pending，`planItemCount`）。
5. **窗口化**：块头是合成 DOM 无独立行账本，单头偏差 ≤4px 由 RO 实测兜底；区折叠引发的行高变化由既有"v-show 隐藏行缓存置 0"机制驱动；`structuralSignature` 未扩展（分析结论：无需）。
6. 产出区判定 `outputText`：`tc.result ?? item.result`；`plan_replanned` 段的产出来自 `items[].result`（plan\_replanned 注入重建段带 result）。

## 四、真机走查指引（浏览器 <http://localhost:5175/> 或桌面端）

1. **串行时序**：发起带计划任务 → 待办项 1 出现 → 子动作随运行进入其组合（组合行段）→ 完成自动折叠 → 待办项 2 才出现；未来 pending 项不提前露头
2. **三级折叠**：点待办项头 / 组合条 / 区级折叠头（"N 待办"）各自展开收起；滚动离开再滚回（切窗）区级与项级折叠态保持、不拉扯
3. **回源还原**：刷新 / 切会话 → 计划区、待办项（含产出区）、子动作、顺序完整还原，完成项保持折叠
4. **总折叠不冲突**：一级 process\_summary 仍能收敛全部行段
5. **普通任务回归**：无计划任务时 think/tool 收进"组合行段"折叠条，文本段独立显示
