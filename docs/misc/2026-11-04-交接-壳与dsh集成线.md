## 二、本会话做完的三件事

### 2.1 SSE 流式透传 + `client-hmr` 重开（`a65a025` → `c1f712e`）

**解决了什么**：插件启停后侧栏入口必须刷新页面才生效。

**根因**：Tauri 自定义协议的应答是**一次性缓冲体**（`UriSchemeResponder::respond`
只收 `Into<Cow<'static,[u8]>>`，无流式写回通道），而 SSE 要求边收边吐 → 必然 502。

**落法**：`sse:` 端点前缀分流 → 宿主 `readSseResponse` → 壳 `cmd_sse_open` 经管道
流 lane 推 `Channel` → 页面 `__WORLDSEA_SSE__.sse()` / `.fetch()`。

**⚠ 最大教训（会重犯，务必记住）**：走查前我两轮判「仍未生效」，真因是
**tsdown 打包产物 `lib/index.js` 未同步**。`dsh` 包有**两套产物**：

| 产物 | 生成者 | 运行时是否加载 |
|---|---|---|
| `lib/types/*.js` | `tsc -b` | **否** |
| `lib/index.js` | **`tsdown`** | **是** |

**核对 `dsh/` 链路时只读 `src/` 与 `lib/types/` 会假阳性**，必须 grep 运行时产物
`lib/index.js`。完整修复动作见 §3.2。

### 2.2 pipe 崩溃修复（`6facfac`）

**症状**：启用 wallpaper-engine 系列插件后宿主直接死，全站 502，页面「dsh 已退出」。

**根因**：壳的管道载体用手搓的合成响应对象，只实现了 `on`/`off`/`once`，
缺 `removeListener` 与 `emit`。而 Node 的 `Readable.pipe(dest)` 完整依赖这些：

```
dest.once('close'|'finish', …)  → onfinish() → dest.removeListener(…)  ← 崩溃点
unpipe() → dest.emit('unpipe', src)                                    ← 第二个缺失
```

官方走真实 `node:http` `ServerResponse`，天然齐全；**只有壳内会崩**，且是
「任何插件对 `res` 调 `.pipe()`」都必崩。

**修法**：按 Node 目的地契约补齐（`removeListener`/`off`/`removeAllListeners`/
`emit`/`listenerCount`/`writableNeedDrain`），并把 `once` 改成真正的单次语义
（原先是 `once = on`，会重复触发）。顺带补 `getHeader`/`getHeaders`/`hasHeader`/
`removeHeader`。

**回归锁**：`dsh/packages/bundle/web-app/tests/pipe-response-contract.spec.ts`（2 例，
真实管道 + 真 `Readable.pipe`）。反证已做：删掉 `removeListener`/`emit` → 抛 6 个
未捕获错误、退出码 1。

### 2.3 宿主崩溃自愈 P0（`1c7d310` → `974f177` → `54e3433`）

**解决了什么**：宿主进程死亡后页面只显示「请退出应用后重新启动」，**无任何恢复手段**。

**官方机制边界（已核实源码，别再查一遍）**：官方有 `installFailLoud`
（`dsh/packages/boot/app-boot/src/index.ts:884`，由 `apps/cli/src/profile-boot.ts:309`
安装），但它只做「捕获 → 写 stderr 诊断 → 等 2s release → `exit(1)`」：

| 能力 | 官方 |
|---|---|
| 捕获 `uncaughtException`/`unhandledRejection` | ✅ |
| 定位是哪个插件 | ❌ |
| 写崩溃报告到文件 | ❌（`startup-*.log` **仅启动失败**才写） |
| 自动重启 | ❌ |
| 停用/卸载问题插件 | ❌ |

即官方设计是「**fail loud 而非自愈**」。Electron 桌面端同样会死，只是用户关掉
重开即可；我们的壳没有等价托管 → 表现为「无操作」。**这是壳的集成缺口，不是 dsh 缺陷。**

**用户拍板三项**：① 退避重试最多 3 次（1s/2s/4s）② 整页 reload ③ 保留手动入口。

**为什么必须整页 reload 而非重连 transport**：宿主重启后 `__DSH_BOOT__`
（release / token / client 图）全变，`client-modules` 的 `ReleaseChangeGate`
（`dsh/packages/client/modules/src/client/release-change.ts`）会**拒绝旧页应用新图**。
这是既有语义，不是可选项。

## 四、下一步：P1（停用/卸载问题插件）

### 4.1 用户原话（意图）

> 「壳侧能有个停止插件运行的重试方法，以及能根据情况由壳侧主动卸载出问题的插件的方法；
> 这两个方法都能有个手动确认的控件，同时停止或卸载后能够尝试重新连接，由用户决定用哪个方法，
> 不至于启动后断开连接时是无操作的，这两个方法都仅限 dsh 侧宿主内安装的外部插件，
> 而不染指官方内置插件」

### 4.2 已查清的关键事实（省你重复排查）

**壳不能直接动插件**：壳是 Tauri 进程，插件跑在 dsh 宿主子进程里。两条路：

1. 杀宿主重启（粗粒度，P0 已做）
2. **调宿主的插件管理 API**（细粒度，P1 要做的）

**好消息：插件管理 API 已存在**。`dsh/packages/boot/plugin-manager/src/index.ts`
有一整套 `@Remote` 方法：`listPlugins` / `setPluginEnabled` / `setVersionExemption` /
`change` / `inspect` …宿主已经能禁停插件。

**坏消息：得先知道是哪个插件**。崩溃是进程级死亡，插件标识可能来不及上报。
**这一轮已埋好线索**（见 §4.3）。

### 4.3 已备好的前提：`last route:` 线索

`dsh/packages/host/webserver/src/index.ts` 新增只读 `lastActivity()`：
`route()` 在**调 handler 之前**记下命中路由（path / kind / method / url / 自增序号）。

`installFailLoud` 增第四参 `activity`，崩溃时 stderr 补写一行：

```
dsh: last route: GET /wallpaper-engine/media/x → prefix route /wallpaper-engine
```

- `prefix` 路由报**注册路径**（如 `/wallpaper-engine`）而非请求路径——要指名的是插件，不是资源
- 供应商抛错被吞掉，绝不替换真正的失败原因

**P1 可直接消费这行**：壳捕获宿主 stderr → 解析出插件命名空间 → 调插件管理 API 禁用它。

### 4.4 建议的施工顺序（我的判断，供参考）

| 优先级 | 项 | 理由 |
|---|---|---|
| **P1-a** | 壳解析 `last route:` → 报出「疑似问题插件」 | 这是 P1 一切的前提 |
| **P1-b** | 错误页/菜单给出「停用该插件后重启」选项 | 用户原话的核心诉求 |
| **P1-c** | 停用后自动重连 | 用户原话「停止或卸载后能尝试重新连接」 |

**约束**：只动**外部插件**，不染指官方内置插件（用户明确要求）。
判断「外部 vs 内置」可查 `plugin-manager` 的 `listPlugins()` 返回（含 `readOnlyReason`）。

## 五、本线历史坑位（按需查）

### 5.1 三个 `hmr` 概念（极易混淆）

| 概念 | 位置 | 作用 |
|---|---|---|
| `client/hmr` | `dsh/packages/client/hmr/` | 浏览器侧：轮询 bundle mtime → `rebuilt` |
| `boot/hmr` | `dsh/packages/boot/hmr/` | 宿主侧：chokidar，提供 `hmr` 服务 |
| `plugin-manager` | `dsh/packages/boot/plugin-manager/` | 启停插件，查 `ctx.get('hmr')` |

### 5.2 `client-hmr` 的 stat-poll 开销（已实测量化）

默认 **500ms**（上游 `Config` 的 `.default(500)`，**不是壳引入的**）——
官方 desktop profile 加载同一个 `web-app` bundle、无 config 覆写，故**官方与我们同值**。

实测本壳 profile：graph **80 行全部带 client bundle URL** → **160 次 stat/秒**。
单次 `statSync` 本机约 **160µs**（远高于正常 SSD 的 1–10µs，系 Defender 所致）
→ 估算 **≈25ms/s ≈ 单核 2.5%**；正常机器约 **0.2%**。

**结论：不改**。这是上游既有设计，改它只会增加追版 fork 冲突面。
若将来确认空闲 CPU 偏高，**优先怀疑 Defender**；确需降频则在
`apps/tauri/dsh-overlay.yml` 加 `config: { pollIntervalMs: 5000 }`
（热更新延迟 0.5s→5s，但**插件启停的 UI 响应走 SSE graph 推送，不受影响**）。

### 5.3 Tauri 硬约束（踩过就会再踩）

**`app.manage` 同类型二次注册会 panic**（tauri-2.11.5 `app.rs:1948` 断言
`state for type ... is already being managed`）。重启/热替换必须把可变状态包进
`RwLock<Option<Inner>>`——`DshBridge` 已按此改（见 `dsh_bridge.rs`）。

**`data:` URL 不在 `is_local_url` 白名单**（`webview/mod.rs:1698`）→ 页面拿不到
`__TAURI_INTERNALS__`，也**收不到壳注入的脚本**（含窗口栏）。壳自有页面一律走
`worldsea://` 协议伺服。**改载体时要核对「这条链上还有谁依赖注入」**——
这一条让走查 #4 失败过一次。

**Tauri ACL 是显式白名单**：新命令必须登记 `permissions/worldsea-shell.toml`
+ `capabilities/default.json`，否则 invoke 被静默拒绝。**永远不要 `.catch(() => {})`**。

## 六、探针技法（验证宿主行为时很有用）

壳默认管道模式无 TCP 监听，外部探测不到。做法：

1. 复制 profile 到临时目录，`node_modules` 用 **junction**（`cmd /c mklink /J`，秒级）
2. `DSH_HOME=<临时>` 起独立宿主：`node apps/cli/lib/bin.js web --no-open --ipc-pipe <管道名>`
3. Node 探针连管道：帧格式 `u32be 长度 + u8 kind + payload`（`0x4a`=JSON、`0x42`=二进制）
   - 先收 `hello` 帧
   - 发 `{ t:'stream-open', id, endpoint:'sse:/plugins/events', payload:null }`
   - 收 `stream-item`（每项一条 SSE `data:` 载荷）
4. 改 profile 的 `package.json` bundles → 观察 graph 帧变化

**验完必须清理**：探针文件、临时 profile、后台宿主进程。
