### 2.1 SSE 流式透传 + `client-hmr` 重开（`a65a025` → `c1f712e`）

**解决了什么**：插件启停后侧栏入口必须刷新页面才生效。

**根因**：Tauri 自定义协议的应答是**一次性缓冲体**（`UriSchemeResponder::respond`
只收 `Into<Cow<'static,[u8]>>`，无流式写回通道），而 SSE 要求边收边吐 → 必然 502。

**落法**：`sse:` 端点前缀分流 → 宿主 `readSseResponse` → 壳 `cmd_sse_open` 经管道
流 lane 推 `Channel` → 页面 `__WORLDSEA_SSE__.sse()` / `.fetch()`。

**⚠ 最大教训（会重犯，务必记住）**：走查前我两轮判「仍未生效」，真因是
**tsdown 打包产物 `lib/index.js` 未同步**。`dsh` 包有**两套产物**：

| 产物 | 生成者 | 运行时是否加载 |
|---|---|---|
| `lib/types/*.js` | `tsc -b` | **否** |
| `lib/index.js` | **`tsdown`** | **是** |

**核对 `dsh/` 链路时只读 `src/` 与 `lib/types/` 会假阳性**，必须 grep 运行时产物
`lib/index.js`。完整修复动作见 §3.2。

**补充（2026-11-04 新发现）**：`apps/cli` 的产物是**按内容哈希分片**的
（`profile-boot-<hash>.js`），改了内容会换新文件名。按旧文件名 grep 也会假阳性，
要 grep 目录而非固定文件名。

### 2.2 pipe 崩溃修复（`6facfac`）

**症状**：启用 wallpaper-engine 系列插件后宿主直接死，全站 502，页面「dsh 已退出」。

**根因**：壳的管道载体用手搓的合成响应对象，只实现了 `on`/`off`/`once`，
缺 `removeListener` 与 `emit`。而 Node 的 `Readable.pipe(dest)` 完整依赖这些：

```
dest.once('close'|'finish', …)  → onfinish() → dest.removeListener(…)  ← 崩溃点
unpipe() → dest.emit('unpipe', src)                                    ← 第二个缺失
```

官方走真实 `node:http` `ServerResponse`，天然齐全；**只有壳内会崩**，且是
「任何插件对 `res` 调 `.pipe()`」都必崩。

**修法**：按 Node 目的地契约补齐（`removeListener`/`off`/`removeAllListeners`/
`emit`/`listenerCount`/`writableNeedDrain`），并把 `once` 改成真正的单次语义
（原先是 `once = on`，会重复触发）。顺带补 `getHeader`/`getHeaders`/`hasHeader`/
`removeHeader`。

**回归锁**：`dsh/packages/bundle/web-app/tests/pipe-response-contract.spec.ts`（2 例，
真实管道 + 真 `Readable.pipe`）。反证已做：删掉 `removeListener`/`emit` → 抛 6 个
未捕获错误、退出码 1。

### 2.3 宿主崩溃自愈 P0（`1c7d310` → `974f177` → `54e3433`）

**解决了什么**：宿主进程死亡后页面只显示「请退出应用后重新启动」，**无任何恢复手段**。

**官方机制边界（已核实源码，别再查一遍）**：官方有 `installFailLoud`
（`dsh/packages/boot/app-boot/src/index.ts:896`，由 `apps/cli/src/profile-boot.ts:309`
安装），但它只做「捕获 → 写 stderr 诊断 → 等 2s release → `exit(1)`」：

| 能力 | 官方 |
|---|---|
| 捕获 `uncaughtException`/`unhandledRejection` | ✅ |
| 定位是哪个插件 | ❌ |
| 写崩溃报告到文件 | ❌（`startup-*.log` **仅启动失败**才写） |
| 自动重启 | ❌ |
| 停用/卸载问题插件 | ❌ |

即官方设计是「**fail loud 而非自愈**」。Electron 桌面端同样会死，只是用户关掉
重开即可；我们的壳没有等价托管 → 表现为「无操作」。**这是壳的集成缺口，不是 dsh 缺陷。**

**用户拍板三项**：① 退避重试最多 3 次（1s/2s/4s）② 整页 reload ③ 保留手动入口。

**为什么必须整页 reload 而非重连 transport**：宿主重启后 `__DSH_BOOT__`
（release / token / client 图）全变，`client-modules` 的 `ReleaseChangeGate`
（`dsh/packages/client/modules/src/client/release-change.ts`）会**拒绝旧页应用新图**。
这是既有语义，不是可选项。

### 2.4 崩溃线索 + 插件停用（P1-a / P1-b，`ccc64a1`）

**P1-a：报出崩溃时正在服务哪个插件**

宿主崩溃是进程级死亡，插件来不及上报自己是谁。宿主的 `last route:` 行只到路由路径，
而**路径前缀 ≠ 包名**（`/wallpaper-engine` vs `dsh-plugin-wallpaper-engine`），
壳若靠映射表猜必然脆弱。

**关键机制**：cordis 的服务方法体内 `this.ctx` 会被重绑定为**调用方**（shadow 机制，
`vendor/cordis/src/utils.ts` 的 `createTraceable`），故 `webServer.register()` 注册那一刻
就知道归属。实测真 Loader 下三者一致：

| 字段 | 值 | 用途 |
|---|---|---|
| `fiber.name` | `wallpaper-engine` | 写入 `last route:` |
| `entry.options.name` | `wallpaper-engine` | `listPlugins()` 的 `moduleName` |
| `entry.id` | `bc982e72:…` | 早期 `setPluginEnabled` 用的 id |

**落法**：路由表值改 `WebRouteEntry{route, plugin?}`；`last route:` 行追加 ` → plugin <名>`
（根 fiber 注册的路由不记归属——报出来会误导用户去停用一个不存在的「插件」）；
壳新增 `dsh_crash_attribution.rs` 解析该行。

**P1-b：停用后重启**

壳经 `dsh_bridge::call_api`（已存在，自动带 cookie，与页面同链路）直调宿主
`pluginManager` Remote。信封形状：`{type:'client-request', rpcId, method, payload:{args}}`
——**缺 `args` 会报 `Remote payload must contain exactly one plain-object args field`**（踩过）。

### 2.5 bundle 粒度重构 + 卸载（P1-c，`36d71fc`）

**发现了什么**：P1-b 的**粒度选错了**。

| 方式 | 停 `wallpaper-engine` |
|---|---|
| 逐 entry（P1-b 原实现） | 调 **8 次**；子 entry 仍 `enabled:true`，只变 `fiberPhase:pending` |
| `setBundleEnabled(name)`（现用） | 调 **1 次**；8 个 entry 全从 `listPlugins()` 消失 |
| `removeBundle(name)`（卸载） | 1 次；包真被 pnpm 移除 |

`dsh-plugin-wallpaper-engine` **一个 npm 包**在 `listPlugins()` 里展开成 **8 个 entry**
（主入口 + about-notice / mascot-avatar / media-bridge / pet-link / fx / parallax / fonts），
但在 `listBundles()` 里只有 **1 个**。这就是 bundle 粒度更优的原因。

**收益**：整套家族归并逻辑（`family_root` / `external_families` / 逐个停用）被删掉，
净 **-20 行**，行为更彻底。

**两个实测结论（已写进注释与测试）**：

1. **卸载不用自己「先停再卸」**——宿主对运行中的 bundle 内部已处理（直接返回
   `changed:true` 并真跑 pnpm remove）。多调一次只会多一次 profile 重载。
2. **`setBundleEnabled` / `removeBundle` 只认 `name`**——写成 `id` 是 entry 粒度字段。

**菜单形态**：「视图」下两项并列，由用户二选一（回应原话「由用户决定用哪个方法」）：

- 停用「X」后重启（保守，包还在）
- 卸载「X」后重启（彻底，包被移除）

两项只在**有崩溃线索**时可点，且严格只作用于**外部插件**。

### 2.6 归因精度——记最近 N 条路由（P1-d，`93231a2`）

**问题**：单点线索只回答「崩溃那一刻谁在服务」，而那可能只是恰好在飞的无关请求。
实测过插件自崩、该行却记着无关官方插件 `client-connection` 的情形，单点无法区分
「某插件密集刷同一路由时崩」与「一堆无关请求里夹了这一次」。

**落法**：宿主 webserver 增环形缓冲 `recentActivity()`（`ACTIVITY_HISTORY = 5`），
`FailLoudActivity` 返回类型改 `readonly string[]` 逐行写出。壳 `Suspect` 增 `trail`，
错误页只在「崩溃前换过插件」时展示轨迹（单插件压缩后不显示，避免撑长正文）。

**⚠ 一个必须同步的常量**：壳侧 `ACTIVITY_TRAIL_LIMIT` 必须与宿主侧 `ACTIVITY_HISTORY`
对齐——它不只用于展示，还是「上一轮崩溃的记录是否已收满、这条属于下次崩溃」的判定依据。

**探测坑**：用 `fetch('http://127.0.0.1:<port>/…')` 自造路由活动**无效**——管道模式宿主
不监听 TCP。须用 `ctx.webServer.dispatch()` 直接喂合成请求。

### 2.7 卸载二次确认（P1-e，`58bb03d`）

判据是**可逆性**而非「操作重不重要」：停用可再启用 → 不加摩擦；卸载要重新安装 →
必须确认（给可逆操作也弹框只会训练用户习惯性点是）。

落法：`tauri_plugin_dialog` 原生模态（`OkCancelCustom("卸载","取消")`），经回调 +
`mpsc` 拿结果；**拿不到结果一律按取消**（超时 300s 或通道断开），绝不默认执行破坏性动作。

确认判据落在 `Remediation::needs_confirmation()` 上而非调用点临时判断——将来加第三个
动作时会先被迫回答「它要不要确认」。测试钉住这条差异。

### 2.8 重启链改「先 kill 后 spawn」（P1-f，`422bba0`）

**调研推翻了命题**：「补手动重连入口」这个需求描述不准确——菜单已有「重新启动 Agent
内核」，它做的就是完整重启 + 换桥 + 重载页面。

**实测发现**：两个宿主能同跑一个 DSH_HOME 且互不报错（dsh 的设计如此，便于多客户端），
但它们共享 `storages/`，重叠存活期间并发写有损坏风险。

**落法**：`restart_host()` 每次尝试前先 `reap_for_restart()` 收旧宿主，成功后 `adopt()`。
`replace()` 拆成两法。**关键约束：reap 不得置 `shutting_down`**——那是 `kill()` 的语义
（壳要退出），会让心跳守护永久静默，新宿主之后再崩就没人接。故不能直接复用 `kill()`。

**走查要点**：证「第一次重启成功、之后再崩仍能自动救回」——若 reap 误置了关停标志，
症状正是「第一次能救、之后再也救不回来」。

### 2.9 「外部插件」子菜单（P1-g，`3201005`）

**解决什么**：截至 P1-f 所有处置入口都**依赖崩溃线索**。线索指偏、或宿主崩在非路由路径时，
用户完全失去手动入口，只能去改 profile 文件。

**形态**：「视图 → 外部插件」，按**包名**列（与 bundle 粒度一致），每项「停用后重启 /
卸载后重启」。已停用的标 `（已停用）`，不可移除的置灰。**每次弹出前按真实清单重建**——
插件运行期可变，缓存只会说旧话。

**两个入口共用一条流程**：`remediate_named_and_restart`（按包名）与
`remediate_suspect_and_restart`（按线索）只在「目标从哪来」不同，确认/执行/通知/重启
全走同一个 `finish`。

**动态 id**：`worldsea.plugin.<动词>.<包名>`。静态 `match` 无法枚举运行时包名，故
`handle` 用前缀兜底 + `parse_plugin_action()` 解析（只按**第一个**点切动词，其余整体是包名）。

### 4.2 崩溃线索的**固有边界**（重要，别高估它）

`last route` 是「崩溃瞬间在服务的路由」，**不等于崩溃元凶**。

实测反例（2026-11-04）：植入的插件在启动 8 秒后自行抛错，但期间页面恰好在调
`/api/settings/describe`，那行记的是 `client-connection`——无关的官方内置插件。

**故文案一律用「崩溃时正在服务的插件」而非「疑似元凶」**，并明说「不一定是崩溃原因」。
`stop_page_does_not_claim_the_plugin_caused_the_crash` 守着这条线。

**安全防线**：处置只作用于外部插件（`moduleName` 不以 `@deepseek-ai/` 开头、不是 `cordis:`），
官方内置一律拒绝——上面那个反例正是被这条防线挡住的。

**⚠ 不要用 `readOnlyReason` 判内置**：实测官方 `llm`/`session`/`storage` 全都没有该字段，
它只表示「不能经 profile patch 管理」。拿它判会把官方插件当成可停用的外部插件。

### 4.3 已查清的关键事实（省你重复排查）

**壳不能直接动插件**：壳是 Tauri 进程，插件跑在 dsh 宿主子进程里。两条路：
① 杀宿主重启（粗粒度，P0 已做）② 调宿主的插件管理 API（细粒度，P1 已做）。

**插件管理 API 一览**（`dsh/packages/boot/plugin-manager/src/index.ts`，全是 `@Remote`）：

| 方法 | 粒度 | 用途 |
|---|---|---|
| `listPlugins()` | entry | 每个 entry 一行，含 `fiberPhase` / `readOnlyReason` |
| `listBundles()` | **bundle（包）** | 含 `enabled` / `installed` / `removable` |
| `setPluginEnabled(id, enabled)` | entry | 早期用，已被 bundle 粒度取代 |
| `setBundleEnabled(name, enabled)` | **bundle** | **现用**，一次停整包 |
| `removeBundle(name)` | **bundle** | **现用**，卸载（内部已处理先停再卸） |

- 归因**不覆盖非路由崩溃**（启动期、后台任务、定时器）——那时没有 `last route:` 行，
  错误页保持原文案、不臆造插件名
- **双宿主共存未被禁止**：dsh 本身允许多宿主同跑一个 home（官方设计，便于多客户端）。
  P1-f 只保证**我们的重启链**不留重叠窗口，不去改 dsh 的这个行为



## 五、本线历史坑位（按需查）

### 5.1 四个 `hmr` 相关概念（极易混淆）

| 概念 | 位置 | 作用 |
|---|---|---|
| `client/hmr` | `dsh/packages/client/hmr/` | 浏览器侧：轮询 bundle mtime → `rebuilt` |
| `boot/hmr` | `dsh/packages/boot/hmr/` | 宿主侧：chokidar，提供 `hmr` 服务 |
| `plugin-manager` | `dsh/packages/boot/plugin-manager/` | 启停插件，查 `ctx.get('hmr')` |
| `client-modules` | `dsh/packages/client/modules/` | client bundle 图；`ReleaseChangeGate` 在 `release-change.ts` |

### 5.2 `client-hmr` 的 stat-poll 开销（已实测量化）

默认 **500ms**（上游 `Config` 的 `.default(500)`，**不是壳引入的**）——
官方 desktop profile 加载同一个 `web-app` bundle、无 config 覆写，故**官方与我们同值**。

实测本壳 profile：graph **80 行全部带 client bundle URL** → **160 次 stat/秒**。
单次 `statSync` 本机约 **160µs**（远高于正常 SSD 的 1–10µs，系 Defender 所致）
→ 估算 **≈25ms/s ≈ 单核 2.5%**；正常机器约 **0.2%**。

**结论：不改**。这是上游既有设计，改它只会增加追版 fork 冲突面。
若将来确认空闲 CPU 偏高，**优先怀疑 Defender**；确需降频则在
`apps/tauri/dsh-overlay.yml` 加 `config: { pollIntervalMs: 5000 }`
（热更新延迟 0.5s→5s，但**插件启停的 UI 响应走 SSE graph 推送，不受影响**）。

### 5.3 Tauri 硬约束（踩过就会再踩）

**`app.manage` 同类型二次注册会 panic**（tauri-2.11.5 `app.rs:1948` 断言
`state for type ... is already being managed`）。重启/热替换必须把可变状态包进
`RwLock<Option<Inner>>`——`DshBridge` 已按此改（见 `dsh_bridge.rs`）。

**`data:` URL 不在 `is_local_url` 白名单**（`webview/mod.rs:1698`）→ 页面拿不到
`__TAURI_INTERNALS__`，也**收不到壳注入的脚本**（含窗口栏）。壳自有页面一律走
`worldsea://` 协议伺服。**改载体时要核对「这条链上还有谁依赖注入」**——
这一条让走查 #4 失败过一次。

**Tauri ACL 是显式白名单**：新命令必须登记 `permissions/worldsea-shell.toml`
+ `capabilities/default.json`，否则 invoke 被静默拒绝。**永远不要 `.catch(() => {})`**。

### 5.4 `dsh/` 是 vendored fork

- 门禁 `pnpm fork:check`，基线提交 `a71b4ba`，**台账 16 = 16**
- 任何 `dsh/` 改动**必须在同一提交内**更新
  [dsh-fork台账.md](../details/架构/dsh-fork台账.md)，否则被门禁拦下
- 台账格式：`文件路径 | 状态 | 摘要与理由 | 上游对照`
- 本轮 `dsh/` 改动登记为 **G6**（`host/webserver` + `apps/cli/profile-boot`）

### 5.5 dsh CLI 参数位置的坑（本轮踩过）

`--patch` / `--dump-config` 等是 **launcher 标志，必须排在子命令之前**：

```powershell
# 对
node dsh\apps\cli\lib\bin.js --profile web --patch <overlay.yml> --dump-config
# 错（报 unknown option）
node dsh\apps\cli\lib\bin.js web --patch <overlay.yml>
```

且**已用 `--profile web` 选过 profile 后，不能再给 `web` 子命令**
（报 `too many arguments. Expected 0 arguments but got 1: web`）。

`--dump-config` 是诊断 overlay 是否生效的捷径——能看到最终组合里有哪些 `- id:`。

## 六、探针技法（验证宿主行为时很有用）

壳默认管道模式无 TCP 监听，外部探测不到。做法：

1. 复制 profile 到临时目录，`node_modules` 用 **junction**（`cmd /c mklink /J`，秒级）
2. `DSH_HOME=<临时>` 起独立宿主：`node apps/cli/lib/bin.js --profile web --no-open --port <端口>`
3. 拿 token：抓 stdout 的 `dsh web: http://127.0.0.1:<port>/?token=…`
4. 换 cookie：GET 该 URL（不跟随重定向）→ 取 `set-cookie` 首段
5. 调 API：POST `/api/pluginManager/<方法>`，body 是
   `{"type":"client-request","rpcId":"任意","method":"pluginManager/<方法>","payload":{"args":{…}}}`，
   头带 `cookie` 与 `content-type: application/json`

**验完必须清理**：探针文件、临时 profile（先 `rmdir` 断 junction 再删目录）、后台宿主进程。

**⚠ 验证卸载务必用隔离 profile**——真实 profile 上试会真删用户插件。

## 十、本轮方法论沉淀（值得复用）

**「先验证可行性再动手」救过两次**：

- P1-b 开工前先用 `curl`/`Invoke-WebRequest` 打通 `pluginManager` API，
