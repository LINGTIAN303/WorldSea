### 2.2 三条硬约束（改设计前必须遵守）

1. **维度内可叠加**：同一维度允许多取值（如「标题式 + 图解式」），存数组不存单值——理论基线 §一 第 22 行。
2. **维度间近似正交**：不做「取值组合」的白名单/预设包（组合数 = 10×8×14×16×11×4×3×3×3 ≈ 2.6 亿，必然爆炸）——§一 第 36 行。
3. **投影不是开关**：九维的每维投影只读同一份节点数据，**不得因切换投影而改写数据**——§一 第 36 行 + 既有「白板=结构容器、组件由 nodeId 派生」的硬决策。

## 三、Q3 · 三条横向关系（方案已定）

### 3.1 关系类型

| 语义 | 建议类型名 | 说明 |
| --- | --- | --- |
| 并列 | `outline_parallel` | 同层级、无先后（对应逻辑结构维的「并列」） |
| 递进 | `outline_progressive` | 有推进方向（对应「递进/因果/时间」） |
| 对比 | `outline_contrast` | 互斥或对照（对应「对比/问题—解决」） |

- 三型均为**节点 ↔ 节点**，与既有三条跨芽关系（`outline_mentions` / `outline_located_in` / `outline_covers`）**并存且不重叠**。
- 注册走既有 `RelationshipRegistry.register`（与 `outlineLinks.ts` 同口径），**不启用 `registerCustom`**（Q3-B 已裁定不做）。

### 3.2 呈现形态：标记，不画连线

- 节点详情面板增加「横向关系」区（选择对端节点 + 关系类型，可多选）。
- 白板/树视图以**图标徽章**表达（与既有 `link_entity` 徽章同层），不引入边渲染与布局语义。
- 理由：连线要求位置语义，而白板位置的真相源是 `order`（施工分解 §8.3 已论证），画线会重蹈「双写」覆辙。

### 3.3 施工步骤

1. `apps/tauri/src/entity/outlineLinks.ts` 增补三型（含反向注册与守卫用例）
2. 关系注册载入校验（`inverseRegistrySync.spec` 同类守卫）
3. 节点详情面板「横向关系」编辑区（唯一写入口，复用 `relationship` 服务）
4. 树/白板徽章呈现（读侧，纯派生）
5. 测试：关系 CRUD + 反向 + 徽章派生 + 删除节点级联

## 六、门禁与风险

- **门禁**：`vue-tsc` 0 · `arch:check` 0 违规（file-size 已清零，新增文件须 < 400 行）· vitest 全量 · 断链 0。
- **风险 1**：文档级 profile 与节点级字段同时存在 → 必须明确「节点未设置时是否继承」，否则同一维度出现两个真相（Q8 要解决）。
- **风险 2**：Q3 三型与逻辑结构维的 14 个取值语义重叠（并列/递进/对比是其中 3 个）→ 落地时须约定：**关系表是关系的真相源，逻辑结构维只做展示映射**，不反向写入。
- **风险 3**：投影若被误当作「可编辑视图」，会诱发按视图改写数据 → 投影必须只读，编辑入口只在节点详情与白板既有路径。
