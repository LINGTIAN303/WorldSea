# P1-f：重启链改「先 kill 后 spawn」（2026-11-04）

> 起于「补手动重连入口」的调研。调研结论推翻了原命题，最终改的是重启链的顺序。

## 一、调研：三个发现，其中一个推翻了命题

用户选的选项是「补手动重连宿主入口」，我的推荐理由写着「宿主因其他原因断连时无手动
重连入口」。**动手前核实，发现这句话不准确**：

| 发现 | 结论 |
|---|---|
| 菜单已有「重新启动 Agent 内核」 | 它做的正是完整重启 + 换桥 + 重载页面，**手动重连并非缺失** |
| 两个宿主能否同跑一个 DSH_HOME | **能**，实测都正常就绪、互不报错 |
| 代价是什么 | 它们共享 `storages/`（会话、插件数据），重叠存活期间并发写有损坏风险 |

故命题应从「补入口」改为「消除重启期间的双进程重叠」。

## 二、改动

`restart_host()` 原本是「spawn 新 → 成功 → `replace()`（内部 kill 旧）」。改为
**每次尝试前先 `reap_for_restart()` 收掉旧宿主**。

同时把 `DshProcess::replace()` 拆成两个语义明确的方法：

| 方法 | 语义 | 关键约束 |
|---|---|---|
| `reap_for_restart()` | kill + wait + 清句柄 | **不得置 `shutting_down`**——那是 `kill()` 的语义（壳要退出），会让心跳守护永久静默，新宿主之后再崩就没人接 |
| `adopt(child)` | 装上句柄 + 清关停标志 | 与守护同锁，故接管原子 |

**为什么不用现成的 `kill()`**：它会置 `shutting_down`，重启场景下等于自断守护。

## 三、验证

| 项 | 结果 |
|---|---|
| `cargo test --lib` | **189 passed**（+1 净增，含重写 1 例） |
| `cargo check` | 零警告 |
| `pnpm gate` | 4 项全过 |

两个新测试各自守一条线：

- `reap_then_adopt_swaps_the_handle_and_keeps_the_watchdog_alive` —— reap 不得让守护静默
- `reap_kills_a_still_running_host_before_restart` —— **半死状态下（进程活着但桥断了）
  手动重启必须真把旧进程收掉**，否则双宿主共用 storages

**反证**：给 `reap_for_restart` 加上 `shutting_down.store(true)` → 两例同时失败。

## 四、又一次构建缓存假失败

改完后测试报 2 例失败，但源码核对无误。`cargo clean -p worldsea-tauri-app` 后全绿。

**这是本轮第二次踩到**（前一次在 P1-c 重构时）。症状固定：**源码正确、测试报旧值**。
判断方法：`Select-String` 核对源码后若与报错不符，先清包缓存再怀疑代码。

已写入交接文档 §3.1。

## 五、真机走查清单（用户手测）

| # | 操作 | 预期 |
|---|---|---|
| 1 | 正常使用中，「⋯」→「视图 → 重新启动 Agent 内核」 | 应用日志出现「重启前收掉旧宿主（pid=…）」→ 新宿主就绪 → 页面恢复 |
| 2 | 同上，但任务管理器观察 `node.exe` | 任意时刻**最多一个**「命令行含 `bin.js web --ipc-pipe`」的 node 进程（不再有旧新并存） |
| 3 | 杀宿主让其自动重启 3 次 | 行为与以前一致（自动重启仍能救回），第 2 项的「最多一个」同样成立 |
| 4 | 重启成功后继续用一会 | 心跳守护仍有效：再杀一次宿主，仍会自动重启（证明 reap 没把守护弄死） |

**第 4 项是关键**——若 `reap_for_restart` 误置了关停标志，症状就是「第一次重启成功、
之后再崩就再也救不回来」。这是本次改动最容易犯的错。

## 六、遗留

- **未加独立「手动重连」入口**：调研表明现有「重新启动 Agent 内核」已覆盖该需求，
  再加一个只会让菜单里出现两个行为几乎相同的项。
- **双宿主共存未被禁止**：本次只是让**我们的重启链**不留重叠窗口。dsh 本身允许多宿主
  同跑一个 home（官方设计如此，便于多客户端），我们的壳不需要也不应该去改它。
