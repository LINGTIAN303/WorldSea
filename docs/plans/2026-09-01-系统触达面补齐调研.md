### 2.2 沙箱：Claude Code 结构洞察（对本项目定位最关键）

- **核心原则：写文件不走 Bash，走 Write/Edit 工具**（沙箱外、白名单限定路径）；Bash 才被关进笼子（OverlayFS 假文件系统 + network namespace + PID namespace）。一条 Bash 命令可删文件/改权限/下载执行/发网络，图灵完备无法穷举 → 必须笼子；Write 只能"往指定路径写指定内容" → 白名单即可。[参考](https://deepseek.csdn.net/6a3a4de910ee7a33f28129a6.html)

- 原生沙箱 = **拿隔离换自由度**（解决逐条审批疲劳）；macOS Seatbelt 开箱即用、Linux/WSL2 bubblewrap+socat 需安装、**Windows 官方仍在 planned**。[参考](https://github.com/Ayodet/Claude-Code/blob/main/guide/security/sandbox-native.md)

- Roblox 企业级：Kernel/Process/Network/Filesystem 四层隔离 + deny-by-default + 网络 egress 白名单。[参考](https://i.blackhat.com/BH-USA-26/Presentations/US-26-Kumar-Caging-The-Agent-Thur.pdf)

- 子 Agent 隔离：Claude Code SubAgent = 独立进程 + pivot\_root 文件系统隔离 + 最小权限执行边界（`/mnt/sandbox/{skill}` 只读代码/只读配置/临时读写区 tmpfs）。

## 三、三项展开（做什么 → 为什么 → 展开内容 → 做到什么程度）

### 方向 1：PTY 伪终端（最高优先，最接近 Claude Code 能力落差）

**做什么**：将持久化 Shell 从管道仿真升级为真伪终端，Agent 能运行交互式命令、TUI 程序、长驻进程，输出为原始 VT 字节流。

**为什么**：Agent 无法跑 `vim`、REPL、交互式 CLI（git interactive、`pip install` 交互确认）等于残缺链路——这是当前与市面产品最直接的能力落差。

**展开内容**：

1. **底层**：新增 ConPTY backend（含 PASSTHROUGH\_MODE 0x8），保持 portable-pty 的 `PtyPair` 抽象与现有 `ExecuteCommandTool`/`ShellSessionManager` 接口兼容（下沉到 `agent-commands` 的 terminal.rs，不破坏现工具契约）
2. **会话**：`shell_session_create` 升级为 PTY 会话（cols/rows 可调、resize、原始字节流读 + 写入）；现有管道实现保留为无 PTY 兜底
3. **输出处理**：输出保留原始 ANSI/VT（不 clean\_ansi 抹平），前端渲染由当前文本块升级为带颜色/光标语义（复用已有行段渲染体系，非终端模拟器全量实现）
4. **超时/回收**：沿用既有 timeout + KillGuard 模式；PTY 会话统一收口（Job object 杀整树，防子进程残留）

**做到什么程度**：Agent 可在会话中运行 `vim`/`htop`/`node` REPL 并交互；TUI 输出正确渲染；现有 execute\_command 行为零回归（e2e LLM 加 `#[ignore]` 真机验证）。

### 方向 3：隔离沙箱（安全水位线，可分期）

**做什么**：为 Bash/execute\_command 加进程级受限执行环境，缓解"逐条审批疲劳"并防误伤宿主机。

**为什么**：当前写保护是词法软守（变量/别名可绕过），Agent 拥有宿主机全权限；沙箱是 permission 体系的补充（Claude Code 定位：沙箱成为安全边界，而非审批系统）。

**展开内容**：

1. **原则先定**：写文件继续走 Write/Edit 工具（沙箱外白名单），**只有 Bash 进笼子**——这是 Claude Code 验证过的最优结构，避免"API 面沙箱"的复杂性
2. **Windows 落地形态**：OS 官方沙箱仍在 planned → 现实方案 = **受限目录 + 受限进程**（Job object + 工作目录限定 + 环境清理 + 禁危险内建），而非完整容器；网络/文件系统强制隔离留远期（对应 Roblox 四层模型前两层）
3. **确认语义**：保留危险命令三键确认（通过/取消/拒绝）；沙箱内命令自动放行、沙箱外命令仍走确认——分级审批
4. **观测**：沙箱违规（越界写/接触敏感路径）立即上报动作段，可审计

**做到什么程度**：Bash 默认在受限目录执行（`agent-tmp` 优先），越界尝试被拦截并留痕；审批疲劳显著下降（安全命令免确认）；宿主关键目录（用户目录/系统目录）不可被 Agent 裸写。

### 7.1 终端面板升级为真终端界面（对齐 VSCode IDE 终端）

- **调研完成（2026-09-01，P2-1 收尾）**：

  - **依赖确认**：PassthroughMaster `try_clone_reader` 已返回原始流；会话级 writer 已可写输入；resize 通道已真实接线——前端接入与后端新增增量读取/事件命令即可，无阻塞。

### 7.2 Agent 会话层迭代上限 → 总步骤预算（total\_steps）——**已施工（2026-09-01，二轮演进）**

- **背景**：GUI 真机验证中 Agent 会话层触发「超过最大迭代次数: 25」（`AgentLoopConfig.max_iterations` 默认 25），WSL 引号排查这类长任务被 25 轮卡断，不符合主流 Agent 产品（Claude Code / Codex）「长任务不设硬上限」的直觉。

- **主流做法调研（2026-09-01，用户拍板先调研再落地）**：

  - **Anthropic Agent SDK / Claude Code**：`maxTurns` 计数口径 = **工具使用往返次数**（一轮含多个工具算 1 轮；纯文本收尾轮不计），收敛 =「无工具调用的文本轮」——与项目既有收敛分支一致；默认无限制，`max_budget_usd` 成本兜底；到上限返回 `error_max_turns_reached` 独立错误（与崩溃/超时可区分）。

  - **OpenHands**：`max_iterations` 是 LLM 调用次数上限（默认 100/新版 500），触发=硬错误 `MaxIterationsReached`（与 OOM 同 ERROR 状态）——公认缺陷 issue #2406：LLM 无预算感知 + 无优雅收尾，临近截止动作被掐断、已做工作浪费。共识方案 = 预算写入 system prompt + 80%/95% 警告注入 +「最终一步收尾」。

  - **Claude Code 失控案例**：$400 账单事故 → 必须有 combo 兜底（turn 数 + budget + 可观测），而非裸数轮数。

  - **结论**：计「工具使用轮数」而非「LLM 调用次数」；预算对模型可见 + 软提醒；到顶给最终收尾步；错误类型可区分。

- **已施工设计**：

  - **删除** `AgentLoopConfig.max_iterations`（LLM 轮数口径），**新增** `total_steps: u32`（默认 200，建议 1\~500），计数口径 = 工具调用轮数（`state.total_steps_used` 每轮含工具调用 +1，纯文本收尾轮不计）。

  - **预算感知（对齐 OpenHands #2406 共识）**：80%/95% 注入「剩余 N 步，开始收尾」系统提示 + 广播新增事件 `StepBudgetWarning{used, limit, percent}`；100% 注入「最终收尾步」并放行本轮；>100% 仍未收口 → 返回 `AgentError::TotalStepsReached`（错误类型与崩溃/超时可区分）。

  - **退役** **`rate_limit.max_turns`**（默认 Some(100) → None）：轮数维度不再双轨；`max_tool_calls=200`（动作数）/ `max_tokens` / `max_duration=6h` 保留为系统级资源兜底。显式配置 max\_turns 仍生效（向下兼容）。

  - **子 Agent 链**：`SubAgentSpec.max_iterations` 字段名保留（pattern\_registry/store/前端定义引用面大），取值映射到 `child_config.total_steps`；SubAgentPool 默认步数预算 = 主 Agent 同值（supervisor 复用默认 config）。

  - **实现位置**：kernel 主循环替换迭代检查（agent/mod.rs \~L827）+ 工具执行后计数 + 预算检查方法（agent/loop\_control.rs `apply_step_budget`）+ 用户消息/clear\_history/dispose 重置。

  - **前端落地（2026-09-01 三轮）**：

    - **可配置 UI**：模型参数配置对话框（AgentSettingsPanel → 模型编辑 → ModelParamsDialog）新增「工具调用轮数上限 (Total Steps)」滑块（1\~500 默认 200），按模型 id 键存 localStorage（`agent_model_params_{id}`）；保存链接通 `updateModel`（补此前「仅落 localStorage、后端传导待 CONTRACT」缺口——temperature/topP/topK/maxTokens/totalSteps 一并传导 Rust）。

    - **后端透传**：`UpdateModelParams.total_steps` → 命令层 → kernel `AgentLoop.update_model` 写 `config.total_steps`（clamp 1\~500，热切换/保存即时生效）。

    - **满额横幅**：`StepBudgetWarning` 经 tauri 事件桥（commands.rs `TauriAgentEventEmitter` 独立分支，不落动作段持久化）推流通道 → `useAgentRust` 存 `latestStepBudget` → `AgentMessageList` 流区底部「模型调用工具轮数达到 X 上限（已用 Y 轮）」横幅 + 「继续↗」按钮。

    - **「继续↗」= 接续占位**：点击调 `clearStepBudgetHint` + 发送「继续执行」——新用户消息会重置 `total_steps` 计数（agent/mod.rs 新用户消息重置），模型在既有上下文继续行动。

  - **验证**：kernel 147 / patterns 151 / commands 113 全绿；tauri-app 编译过；vue-tsc 0 错误。

### 7.3 Win10 side-load 官方 conpty.dll 动态加载（P2-1 遗留项评估）

- **背景**：`conpty_passthrough.rs` 当前**静态链** windows-sys 的 `CreatePseudoConsole/ResizePseudoConsole/ClosePseudoConsole`（kernel32 导入）。Win10（1809+，build<22000）系统自带 ConPTY v1 API 但内核**忽略 0x8 flag** → `passthrough_enabled()=false`，flags 不带 PASSTHROUGH（退化为虚拟屏渲染，功能可用非 raw）。

- **目标**：Win10 上通过 side-load 官方 ConPTY 包（Microsoft.Windows.Console.ConPTY，含 conpty.dll + OpenConsole.exe）获得 passthrough（raw VT）行为，对齐 Win11 22H2+ 原生效果。

- **方案（评估定稿）**：

  1. 实现 `conpty_loader`：优先 `LoadLibraryW(exe 旁 conpty.dll)`（对齐 running-process#443 探测模式），`GetProcAddress` 取 Create/Resize/Close 三函数指针表；失败回落 kernel32 静态导入。
  2. `PsuedoCon::new/resize/Drop` 改经指针表调用（三处调用点见 `conpty_passthrough.rs` L27/L133/L141/L118）。
  3. 打包：tauri `bundle.resources` 内置官方 ConPTY native（conpty.dll + OpenConsole.exe 随 exe 部署）。

- **工作量**：≈50-100 LoC（loader + 指针表）+ 打包配置调整。**仅 Win10 受益**，当前虚拟屏模式功能可用，优先级低。

- **决策**：保持 ⏸ 待立项——出现 Win10 部署/使用目标需要 raw passthrough 时再施工；Win11 22H2+（原生 0x8）与虚拟屏回退均不受影响。
