## 一、已拍板结论（2026-09-28）

### 1.1 为什么做（用户确认的五条理由）

1. 交界配置在积累但无家可归（环境变量 / 硬编码 / patch 文件三处散落）；
2. 设置页 = 交界行为的一等公民管理面（可发现 / 可开关 / 可扩展）；
3. 放 dsh 侧设置路径最短（行为多发生在 Agent 面；延续「产品跟随 dsh」哲学）；
4. 为后续工具面配置（分页上限、ACL 调整等）预留入口；
5. **隔离**：产品域配置与 dsh 通用设置互不污染（用户补充）。

| 半侧 | 纯宿主侧 | 客户端半侧为主（宿主侧空 apply 占 Loader 行，对齐 `ui-settings-shell` 先例） |
| 装配 | dsh 全局插件（不动） | dsh 全局插件（link: + bundle insert + junction 三坑先例） |

### 1.3 首期范围与真相源（四组全选）

| 配置组 | 真相源 | 桥 |
|---|---|---|
| 说明书与指针（WORLDSEA.md 生成开关 / AGENTS.md 薄指针开关） | **壳侧偏好**（app_prefs 扩展） | console 页 ↔ 壳命令 get/set；壳启动按偏好生成 |

## 五、走查修复（2026-09-28，首轮走查通过后两项）

**首轮走查结论**：设置页出现、三组读写闭环、薄指针生成——全部通过。两项后续：

1. **console 卡片 UI 对齐 dsh 原生**：裸 HTML 控件改为 `ui-primitives` 的 **Switch / SegmentedControl**（种子表可 require，与设置分区同质感），布局改分区行式。
2. **「用 文件资源管理器 打开」点击无效（D3 范围外的既有缺陷，一并修复）**。CDP 探针逐层定位：壳白名单含 `/open-in-app/` ✓ · 页面直连 `POST /open-in-app/open` 200 `{"ok":true}` ✓ · 真实点击链路 ✓（fetch 发出、无报错）· Shell COM 枚举实锤**窗口其实开了**（探针期间堆了 7 个工作区窗口用户未察觉）· 前台检测实锤新窗口**不是前台窗口**。根因 = 宿主（后台进程）detached spawn 无前台权，资源管理器窗口永远垫底。修复 = 壳 proxy 接管 `POST /open-in-app/open` 的 explorer 分支（`dsh_proxy.rs` `try_open_explorer_from_shell`：壳是用户点击时的前台应用，子进程继承前台权；路径校验对齐宿主 wire 语义：绝对路径 + 目录存在，否则 400 走失败 toast；其余 app 如 vscode 照旧转发宿主 argv 链）。验证：新增 2 用例（cargo 108/0）+ CDP 真实点击窗口数 14→15。**前台弹出效果留用户复验**。

**数据面升级项的可行性结论（2026-09-28，configForms 机制通读后登记）**：`ctx.configForms.get(entryId)` 语义 = 按宿主插件条目 id 取共享表单（bash-sandbox 先例），写走 `remote.settings.mutate(namespace, ops, revision)` 持久化到宿主；但 `decode` 强制 **schema envelope 校验**（schemastery rehydrate + validate）——worldsea 插件为手写零依赖、未声明 config schema，命名空间无法通过解码。**数据面编辑升级的前置 = 给 worldsea 插件声明 config schema**（宿主半引 schemastery + 条目重载语义验证）——独立小批（D3-c2 候选），非顺手可带；v1 只读指引维持。

**D3-c2 探查补充（同日）**：dsh 插件 config schema 约定实锤 = 宿主模块 `export const Config = z.object({...})`（schemastery，open-in-app 先例）；schemastery 为 dsh 树内 vendored 包（`dsh/vendor/schemastery`，本仓内部）。**待映射链路**：① link: 外部插件的裸包名解析（两锚解析 + LinkedRoot 真实祖先链 + 各层 peer 映射——`profile.ts` 两锚注释；仓库根 node_modules 无 schemastery，需 peer 声明或内链 junction 二选一，均待实测）；② `Config` 导出 → settings describe 命名空间的接线（settings 服务提供点未在一轮搜索内定位）；③ 条目 config 变更对已装载插件的生效语义（热更新 or 重启）。三者需专门映射轮，不宜在功能批内顺手带。

## 六、G4 重估：D3-c2 可行性按 0.2.0（rc.1/rc.2）取证（2026-09-29）

**结论：可行性翻不了——前置仍成立；但前置现在可以精确清单化，故性质从「可行性待重估」变为「前置已明确、可立批」。**

**证据链**：
1. **硬约束原文仍在**（`dsh/packages/settings/settings/src/index.ts:383-385`）：`if (entry === undefined || schema === undefined) throw new Error(`No configurable plugin entry "${ns}"`)`；随后 `const form = volatileForm(schema); if (form === undefined) throw new Error(`Plugin entry "${ns}" has no volatile fields`)`。即**两道门**：条目必须有 Config schema，且 schema 里必须有 volatile 字段。
2. **三种写入 mode 全走同一 `write()`，无旁路**：`settings.update` / `settings.replace` / `settings.mutate`（宿主 `settings/src/index.ts:347/357/367`）都调私有 `write()`；上游 `api/settings-controller` 的 `mode: update|replace|mutate` 也只是分派到这三个。
3. **volatile 判定**（`settings/src/schema.ts:37-47` `volatileForm`）：字段自身或**某级祖先**标了 `meta.volatile` 即可编辑（注释：*editable without remounting*）；一处都没有 → 抛错。
4. **该文件从 D3 下结论时的基线到 rc.2 一字未改**：`git diff --stat cde62e7 096a48c -- dsh/packages/settings/settings/src dsh/packages/boot/config-editor/src` 只列出 `boot/config-editor/src/index.ts | +14 −2`（正是 [F2](2026-09-29-F2-追版0.2.0-rc.1批计划.md) 记的 `inherited`/override **显示语义**修复）。rc.2 只动了 `settings/settings/package.json`（版本号）。
5. 故 0.2.0 的两件有利事实（显示语义修复 + 「插件配置保存等待时间缩短」）属**体验层**：让「做出来好用」更有底，**不解除前置**。

**前置清单（立批时可直接照做）**：
- **(a) 声明 Config**：给 `apps/dsh-plugin-worldsea` 加 `static Config = z.object({ ... })`（宿主模块级，schemastery），把要**运行期可编辑**的字段标 `.volatile()`；粒度可到字段或某级祖先。
- **(b) 响应变更**：需对变更做出反应时 `ctx.on("loader/volatile-update", …)`——上游先例 `dsh/packages/client/product-analytics/src/index.ts:30,37`（`static Config = z.object({ enabled: z.boolean().default(true).volatile(), appVersion: z.string() })` + `loader/volatile-update` 订阅）是最小样板。
- **(c) ★ 新依赖 `@deepseek-ai/schemastery`**——本题**唯一的实质成本点**：该插件目前是**手写零依赖**（`lib/index.js` 只 import `node:fs` / `node:path`，无 `src/`、无 dependencies），且经 profile manifest 的 `"dsh-plugin-worldsea": "link:D:/WorldSea/apps/dsh-plugin-worldsea"` 链进 profile（profile 用 hoisted 链、插件自身无 `node_modules`）→ 需先验证 profile 侧能否解析到 `dsh/vendor/schemastery`。**引入新依赖按规矩需用户确认。**
- **(d) 客户端侧**：console 的「插件数据面」组从 v1 只读指引升级为 `ctx.configForms.get(<命名空间>)` 绑定的可编辑表单；先例 `dsh/packages/client/locale/src/client/index.ts:577`。

**一条可选项（供拍板时对照）**：console 的另两组（说明书与指针 / 快照策略）已走**壳命令**即时读写且实测可用——说明产品域设置**并不必须**走 configForms。configForms 的独有价值是「上游认可的**插件自身配置**编辑面」（改的是插件 config 而非壳的 prefs），且写盘落在 profile 补丁层、与插件生命周期自洽。若只为「能用」，壳命令路线已够；若为「归位到插件配置体系」，则需先付 (a)~(c)。
