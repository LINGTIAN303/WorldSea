# SSE 流式透传批计划（2026-11-04）

> **动机**：`client-hmr` 因壳协议不支持 SSE 而长期关闭（`apps/tauri/dsh-overlay.yml` 第 2 条）。后果是**插件启停后必须刷新页面才生效**——真机走查反复观察到的现象，也是白名单批「走查项 #2 设计错误」的根因（想用「插件启用→UI 出现」验证闸门，但该路径本就受 HMR 制约）。
>
> **用户裁定**（2026-11-04）：① 只拦 `/plugins/events` ② polyfill 只还原基本事件分发 + error ③ 本批只做通道，`client-hmr` 另批重开。

## 一、链路取证（逐段读过源码）

```
页面 EventSource('/plugins/events')
 │  worldsea:// 自定义协议（页面只认这个 origin）
 ▼
壳 dsh_bridge::handle_request          ← UriSchemeResponder::respond 一次性应答
 │  后台线程阻塞转发
 ▼
壳 dsh_proxy::fetch_upstream
 │  检出 text/event-stream → 502 + eprintln（现状）
 ▼
壳 dsh_pipe::request → JSON 帧
 ▼
宿主 pipe-transport  FrameParser
 │  dispatch(exchange.req, exchange.res)
 ▼
宿主 createSyntheticExchange
 │  res.write() → sink.chunk() → { t:'res-chunk' } 帧
 ▼
壳 dsh_pipe_io "res-chunk" 分支
 ⚠  **把分块 append 进 body: Vec<u8>，直到 "res-end" 才 complete()**
 ▼
壳 PipeResponse { status, headers, body: Vec<u8> }
 ▼
dsh_proxy 组装 http::Response<Vec<u8>> → responder.respond(...)
```

### 1.1 三层能力盘点（关键：缺口只有一处）

| 层 | 现状 | 结论 |
|---|---|---|
| 宿主 `res.write()` → `sink.chunk()` | ✅ 已逐块推送 `res-chunk` 帧 | **本就支持流式** |
| pipe 帧协议 | ✅ 有 `res-head` / `res-chunk` / `res-end` 三段式 | **本就支持流式** |
| 壳 `dsh_pipe_io` | ⚠️ 收下 `res-chunk` 但**累积进 Vec，`res-end` 才交付** | **唯一缺口** |
| 壳→页面 | ❌ `UriSchemeResponder::respond` 只收 `Cow<'static,[u8]>` | **硬约束，无法绕** |

```rust
// tauri-2.11.5/src/protocol/tauri.rs
impl UriSchemeResponder {
  pub fn respond<T: Into<Cow<'static, [u8]>>>(self, response: http::Response<T>) { ... }
}
```

### 1.2 由此确定的方案约束

**只把壳内缓冲改成流式没有用**——末端 `respond()` 仍要一次性交出完整 body。必须**绕开 `worldsea://` 协议**另走一条能推的通道。

而 Tauri **command 有 `Channel<Value>` 逐条推送能力**，且 `dsh_stream.rs` 已有同构实现（`cmd_stream_open` 正是收 `Channel<Value>` 逐条推）。

## 二、方案

### 2.1 总体

```
页面 EventSource('/plugins/events')
 ▼ 【改】index 注入脚本拦截 EventSource（只命中 /plugins/events）
Tauri command  cmd_sse_open(path, channel)
 ▼ 【改】新增 dsh_sse.rs：走 pipe 的 stream lane
pipe stream-open（端点 = sse path）
 ▼
宿主 serveStream() → 【改】新增 SSE 分支：按 path 合成 req/res，取 res 的 write 分块
 ▼ 逐帧 stream-item
壳 StreamSink → Channel 推给页面
 ▼
页面 polyfill 逐条 dispatch（message / error）
```

**复用现有流 lane 而非新建**：`stream-open`/`stream-item`/`stream-end`/`stream-error` 全套已在，`dsh_stream.rs` 的 `cmd_stream_open` 可直接参考（它是给 `typertGateway.wireStream` 用的，本批新增一个给 HTTP 响应用的入口）。

### 2.2 三处改动

| # | 位置 | 改什么 | 归属 |
|---|---|---|---|
| A | `dsh/packages/bundle/web-app/src/pipe-transport.ts` + `src/index.ts` | `serveStream` 现在只接 `typertGateway.wireStream.open`。新增按 path 打开的方式：用 `createSyntheticExchange` 合成 req/res、`dispatch()` 后把 `res.write` 的分块转成 async iterable | **dsh fork**（需同步台账） |
| B | `apps/tauri/src-tauri/src/dsh_sse.rs`（新）+ `lib.rs` | `cmd_sse_open` / `cmd_sse_close`，把 pipe 流帧转 `Channel` 推送；≤400 行 | 壳 |
| C | `apps/tauri/src-tauri/src/dsh_inject.rs` | 注入脚本加 EventSource 拦截（只命中 `/plugins/events`），其余路径不动 | 壳 |
| D | `apps/tauri/permissions/worldsea-product.toml` | 登记新命令（**ACL 是显式白名单，漏登记 = invoke 被拒**） | 壳 |

> **D 是硬经验**：`cmd_workspace_first_paint` 曾漏登记，导致 invoke 被拒、被 `.catch(() => {})` 静默吞掉，潜伏一个多月。

### 2.3 关键设计取舍

1. **不复用 `cmd_stream_open`**：它面向 `typertGateway.wireStream`（endpoint + payload 语义）。SSE 要的是「按 HTTP path 取响应」，语义不同，混用会让两边都变难懂。新增 `cmd_sse_open` 更清楚。
2. **保留 502 降级**：command 通道不可用时（旧宿主 / 非管道模式）仍走原逻辑，避免整页崩。
3. **`client-hmr` 不在本批重开**：通道先独立验证。HMR 上游是给 Electron 壳设计的，壳内从未跑过，两个变量混在一起排障困难。

### 3.2 原型阶段抓到的真缺陷

先写探针单独验 `readSseResponse` 的分帧逻辑（不碰真机、不依赖 HMR），抓到一个真实 bug：

> **`abort` 只调了 `exchange.abort()`，没唤醒循环**。生成器此刻正挂在 `wake` 上等待，
> 没有 `notify()` 就永远不会返回 → 消费方的 `for await` 悬挂、SSE 永不收尾。
> 修法：`onAbort = () => { exchange.abort(); notify() }`。

这个缺陷靠读代码很难发现（两个函数各自都对），只有跑起来才会暴露"永不结束"。**先探针后落地**的裁定在这里直接兑现了价值。

## 四、给「重开 client-hmr」那批的关键情报

施工中读到 `packages/client/hmr/src/client/index.ts`，它**本身就有两条路径**，这点决定了下一批怎么接：

```ts
ctx.effect(() => {
  const transport = (globalThis as PageTransportGlobal).__DSH_TRANSPORT__
  if (transport?.fetch !== undefined) {
    // 路径 A：用壳注入的 fetch 读 response.body（能流式）
    void readPageTransportEvents(transport.fetch, controller.signal, receive)
    return () => { controller.abort() }
  }
  // 路径 B：退回原生 EventSource
  const source = new EventSource(EVENTS_ROUTE)
  return () => { source.close() }
}, 'client-hmr: event source')
```

- **路径 A 需要 `__DSH_TRANSPORT__.fetch`**，且它内部用 `response.body.pipeThrough(new EventSourceParserStream())` —— 要的是一个**真 `Response` 对象**，不是字符串迭代器。
- **壳目前注入的是 `openStream` / `sse` / `streamBaseUrl`，没有 `fetch`** → HMR 只能落到路径 B（原生 EventSource）→ 走 `worldsea://` → 502。

**这意味着下一批有两条路**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲** | 把本批的 `sse(path, signal)` 包成 `fetch()` 兼容形态：返回 `new Response(ReadableStream(\{ 把字符串按原样写入 \}), { status: 200 })` | 需在页面侧构造真 `Response` + `ReadableStream`，但**不动 dsh 树**，且复用本批通道 |
| 乙 | 壳注入 `fetch` 直接走 `cmd_fetch` 一类命令 | 要新做一条「按 path 取缓冲响应」命令，但 SSE 仍需流式 → 又回到读 `response.body` |

**甲更省**：本批的 `sse()` 已产出「每条 SSE data 载荷」的迭代器，而 `EventSourceParserStream` 期望的是**原始 SSE 文本流**（含 `data:` 前缀与空行）。故接线时要么让 `sse()` 产出原始文本块、要么在包装层重新加回 `data: ` 前缀与 `\n\n`。

> 本批把 `readSseResponse` 设计成**只吐 data 载荷**（去掉前缀），是因为壳侧 `Channel` 传字符串最直接。若下一批走方案甲，接线层需要补回前缀——这是刻意的取舍点，不要误以为漏了。

## 五、风险与边界

1. **`dsh` fork 面加深**：`pipe-transport.ts` / `index.ts` 是台账已登记的条目，本批再改 → 追版（F7）冲突面略增，已同步台账（11 → 12 条）。
2. **每连接一条 pipe 流**：SSE 长连占一个流 id，`stream_open` 的 id 由 `next_id` 单调递增（`u32`）。页面刷新/导航时靠 `pagehide` 批量 `cmd_sse_close`，与既有 stream bridge 同机制。
3. **`arch:check` 不管 `dsh/`**（不在 discoveryRoots），但新 Rust 文件 `dsh_sse.rs`（约 90 行）受 400 行限制，远未触线。
