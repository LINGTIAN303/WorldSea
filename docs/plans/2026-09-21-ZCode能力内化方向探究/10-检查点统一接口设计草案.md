## 一、现状：两套「检查点」（2026-09-22 取证）

| 维度 | 会话检查点（S3-b2/d 已落地） | 长任务检查点（既有，B9 底线） |
|---|---|---|
| 语义 | **锚点指针**：视图回到哪个请求边界 | **断点快照**：任务执行到哪、能否续跑 |
| 载体 | `agent-commands`：`session_checkpoints` 表（id / session_id / request_seq / kind / created_at） | `agent-kernel`：`LongTaskCheckpoint { agent_messages, last_user_text, skill_names, chat_mode, locked_chat_mode }`（内存）→ `long_tasks` 表整条落库（commands `long_task_store`） |
| 接口 | `create_checkpoint` / `list_checkpoints` / `prune_checkpoints` + `checkpoint_now`（括号版） | `trait CheckpointProvider { async fn get_checkpoint(&self) -> LongTaskCheckpoint }` + `LongTaskManager::checkpoint(...)`（脏标记）+ `CheckpointFlush`（心搏 5s / stale 30s 触发） |
| 触发 | 手动 + 每 10 请求自动 | 事件驱动 + 心跳节流（脏才 flush） |
| 消费方 | 分叉 / 回滚锚点候选；面板（待接线） | 长任务断点恢复（续跑）；前端心跳状态展示 |
| 保留策略 | 手动 + 自动合并，保留 50 | 随任务记录（任务结束即失效） |

**共同点**：都是「可回溯时点」+ 需要落库 + 需要枚举面（列表）。
**不同点**：指针（轻、无边载荷）vs 快照（重、含整段 messages）；保留策略的语义不同（锚点按数量淘汰安全；任务断点被淘汰 = 恢复链断裂）。

## 二、「合并为同一接口」的三种读法

| 读法 | 含义 | 对应方案 |
|---|---|---|
| ① 概念与类型统一（接口层单一） | 一个「检查点」概念 + 一套类型/枚举 + 一个查询入口；存储各归其位 | **A** |
| ② 存储统一（承载形态统一） | 任务断点也写进 `session_checkpoints`（payload 承载快照）——任务检查点成为会话检查点的一种 | **B** |
| ③ 仅 trait 形状统一 | 会话侧也实现 `CheckpointProvider`（同一 trait） | **C** |

## 三、候选方案

### 方案 A：类型层统一 + 单查询入口（存储不动）

**设计**：
1. 契约类型落 `agent-engine::contracts`（单一定义处，对齐 07 落点策略）：
   ```rust
   pub enum CheckpointKind { SessionAnchor, TaskResume }
   pub enum CheckpointAnchor {
       RequestBoundary { request_seq: i64 },      // 会话锚点（轻）
       TaskProgress { task_id: String },          // 任务断点引用（快照仍在 long_tasks）
   }
   pub struct CheckpointRef { id, session_id, kind, anchor, created_at }
   pub trait CheckpointStore {                     // 一套接口；两侧各自实现
       async fn put_anchor(&self, session_id: &str, request_seq: i64, kind: &str) -> Result<String>;
       async fn list(&self, session_id: &str, limit: i64) -> Result<Vec<CheckpointRef>>;   // 合并视图
       async fn prune(&self, session_id: &str, keep: i64) -> Result<u64>;
   }
   ```
2. 会话侧：`session_checkpoints` 现状不变，实现 `CheckpointStore`（`list` 返回 SessionAnchor 项；`prune` 只淘汰锚点类）。
3. 任务侧：`LongTaskManager` 以 `TaskProgress` 形式**投影**进统一列表（读取 `long_tasks` 的活跃任务断点，不搬迁数据）；`CheckpointProvider::get_checkpoint` 保持（它是快照供给接口，不重复造）。
4. 消费面：面板 / 恢复入口统一调 `list()`——一次拿到「会话锚点 + 活跃任务断点」。

- **成本**：中低（新增契约类型 + 两侧适配 + facade 查询；无 schema 变更、无数据搬迁）。
- **风险**：低（保留策略分治天然成立：锚点按 50 淘汰、任务断点随任务生命周期）。
- **满足度**：读法 ①③；读法 ② 不满足（存储仍两张表）。

### 方案 B：存储统一（任务断点写入 `session_checkpoints`）

**设计**：
1. `session_checkpoints` 增列：`payload TEXT`（任务断点快照 JSON）、`task_id TEXT`；`kind` 取值扩为 `manual / auto / task`。
2. `long_tasks` 表**移除 checkpoint 列**（只留心跳 / 状态 / 元数据）；`CheckpointFlush` 改为写统一表。
3. `prune_checkpoints` 改按 kind 分治：锚点类保留 50；任务类**只随任务结束清理**（不参与数量淘汰——否则淘汰即恢复链断裂）。
4. 断点恢复路径改从统一表读回（`LongTaskCheckpoint` 反序列化）。

- **成本**：高（kernel 侧 flush/resume 路径改造 + commands schema + 保留策略 + 双侧测试）。
- **风险**：中高——(a) 保留策略与恢复链耦合（错配即静默丢断点）；(b) kernel 侧任务流程直接写 commands 的表，**层界被打破**（现由 store 抽象承接）；(c) 心跳高频路径与锚点低频路径共表，写放大与语义混杂。
- **满足度**：读法 ①②（字面最彻底）。

### 方案 C：仅 trait 形状统一

**设计**：会话侧新增一个 `impl CheckpointProvider`（返回把锚点包装成 `LongTaskCheckpoint` 的假快照），共用同一 trait。

- **成本**：低，但**语义错配**——`LongTaskCheckpoint` 要求整段 `agent_messages`，会话锚点没有也不应有（锚点之所以轻，正因为内容由日志 + 快照链承载）。
- **风险**：造出**无消费方**的抽象（会话侧没有"周期上报快照"的需求），违反施工纪律「无立项理由不做」。
- **满足度**：读法 ③ 的字面，但为合并而合并。

## 四、建议与待确认点

**建议：方案 A**。理由：满足「同一接口、不新建第二套」的实质（一个概念 + 一套类型 + 一个查询入口），同时保住两侧的工程边界与保留策略分治；B 的额外收益（存储合并）不足以抵偿恢复链耦合与层界破坏的风险。

**待确认**：
1. 方案选型（A / B / C）。
2. 批次归属：方案 A 落地与 **S3-e2 命令面接线**的关系——建议 **A 先落（小批）**，S3-e2 的手动打点命令直接基于统一接口；若选 B，则 S3-e2 需等 schema 变更后接线（避免二次改命令面）。
3. （若选 A）`CheckpointStore` 契约落点复核：`agent-engine::contracts` 为类型定义处；trait 方法含 async + 实现面依赖 sqlx —— trait 本体放 contracts（纯形状）还是 commands（实现侧聚合），实施时按 07 的落点规则二次确认。
