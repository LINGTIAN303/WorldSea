## 一、立项理由

新内核的工具元数据（[06 草案](06-工具元数据契约草案.md)）必须有一个读声明的**权限消费方**；现状判定散落在 `confirmation.rs`（1185 行）+ `permission_rules.rs`（320 行）+ 调用点，且「alwaysAsk 不可绕过」与「会话级授权」两条语义未契约化。

## 二、现状取证（本项目）

| 项 | 现状 |

| 档位 | **三档**：`Plan`（只读研究，写/命令全拒）/ `Interact`（默认逐条确认）/ `Autopilot`（免逐条，白名单 + 锁兜底） |
| 名单 | `Lock`（内置敏感目录 + 数据区 E1 硬判定；用户名单内 LOCK 为硬约束）> `Allow`（用户白名单）> 档位默认 |

| 缺口 | 判定顺序未单点化；alwaysAsk 类操作未显式名单化；会话级授权无结构化记录；「项目规则层」不存在 |

## 三、ZCode 判定顺序（逐行取证，service.ts）

```
plan 迁移特例
→ requiresUserInteraction（disallowedTools 即 deny；否则 ask，ruleId=tool.userInteraction）
→ alwaysAsk（checkAlwaysAsk：不可被模式的放行分支绕过）
→ yolo（且非 planEnabled）→ allow
→ auto → deny（保留未实现）
→ disallowedTools → deny
→ 项目规则 deny → 项目规则 ask
→ plan 分支（checkPlanMode：只放行 allowedInPlanMode 工具）
→ 项目规则 allow
→ WebFetch 预批 → workflow 草稿预批
→ allowedTools → allow
→ edit 分支 / build 分支（默认末位）
```

关键语义（照抄为评审词汇）：
- **fail-closed**：requiresUserInteraction 一律 ask；`alwaysAsk` 工具必过确认，模式不得绕过；
- **会话级 sessionRules 只服务 alwaysAsk gate**——「会话内允许」不等于全局放行（普通工具的模式语义不认它）；
- `edit` 与 `build` 是**两个末位分支**（编辑免确认面 vs 默认确认面）；其具体放行面待补证（若采用该档先补一轮取证）。

## 五、设计要点

1. **判定顺序单点化**：把现散落判定收为一个纯函数（`decide(context, capability, rules) → {behavior, ruleId}`），顺序对齐上表并**保留本项目强化项**（内置锁硬判定在 denylist 之前/之内；数据区保护优先）。
2. **alwaysAsk 名单化**：由工具元数据 `alwaysAsk` 字段声明（与 06 草案联动），核心清单建议：数据区写/删、未预批的外发（MCP 调用 / WebFetch）、进程执行、破坏性工具（destructive=true）。结构化标记（不靠文案匹配）。
3. **会话级授权结构化**：`grantSessionPermission(updates)` 语义——会话内 allowOnce/allowAlways 记录；**只服务 alwaysAsk gate**（对齐 ZCode）；full-access 持久化沿用现有 keyring/secure_store 通道（范围见 ZD2-3）。
4. **规则层级**（建议四层，自上而下）：内置锁（不可编辑）→ 用户 Lock/Allow → **项目规则（新，可选层）** → 档位默认。项目规则 = 写作项目目录可携带的 `permissions` 声明（deny/ask/allow 三值 + 通配符），随项目走。
5. **领域写保护并入**：数据区（E1）与敏感目录保留为内置锁条目；芽写面以工具元数据声明承接（`sideEffectScope` + `riskLevel`），领域约束不再散落调用点。
6. **交互面**：审批统一为交互请求三型（permission / userInput / hookReview）之一（S5 承接）；四值结果与超时语义**不变**（B7 回归底线）。

## 八、验收口径（施工时）

- 反证（逐条注入）：① 模式放行分支不得绕过 alwaysAsk（构造 yolo + alwaysAsk 工具 → 仍 ask）；② 内置锁不得被 Allow 名单或档位翻案（单调 guard）；③ 判定顺序表逐位构造用例（12 位次一行一例，错位即红）；④ 四值回归（B7 全绿）。
- 真机走查：三档切换 + 一键加入白名单既有能力不回归；项目规则层（若引入）在真实目录验证。
