## 一、P 线（工程机器）

### P1 架构策略文件 + 检查脚本（先建存量基线）

- **立项理由**：内核重写是「拆楼重建」，没有边界策略与自动检查，重写期就是新一轮腐化期；ZCode 用一份 `architecture-policy.yaml` + `--changed` 检查把「新行为放哪里」变成可执行规则（其 `AGENTS.md` 治理流程的机械底座）。
- **内容**：
  1. `architecture-policy.yaml`（WorldSea 版）：模块清单（crates/* 与 packages/*、apps/tauri）+ roots + layers/layerOrder + publicEntrypoints + owner；全局上限（`maxFileLines` / `maxPublicMethods` / `forbidCycles` / `forbidDeepImports`）。
  2. 检查脚本 `scripts/architecture/check.mjs`（**零新依赖**，node 原生）：TS 侧 import 图（循环、跨层、深层导入、公开入口）；Rust 侧 crate 边界（`cargo metadata` 判依赖方向）+ 文件规模与公共方法数。
  3. `--changed` 模式：只对「本次变更文件」报红（存量违例进基线豁免，**默认不追溯**）。
- **验收（反证式）**：注入三类违例各报红一次（循环依赖 / 越层导入 / 超限文件），正确代码零报红；错误版与正确版两份输出留档。
- **不做项**：不引入 knip / dependency-cruiser 等新工具（新增依赖需单独拍板，见 §四 D3）；不追溯清理存量违例。

### P2 模块阅读包

- **立项理由**：ZCode 的 `architecture:context <module-id>` 是「给 Agent 读的模块说明包」——本项目是 Agent 重度工作流，阅读包直接降低每次开工的取证成本（也回应 09-21 世界观线发现路径轮的教训：模型会扒源码代偿）。
- **内容**：`pnpm arch:context <module>`（node 脚本）生成：模块 roots 文件清单 + 公开契约面（导出的类型与函数签名）+ 依赖与被依赖 + 相关文档指针（docs/details/注释/）+ 测试位置。
- **验收**：任选 2 个模块（建议 agent-kernel 与 entity-core）生成阅读包，人工核对内容准确、体积可控（目标 < 400 行/包）。
- **不做项**：不做自动摘要（LLM 生成物不进门禁）。

### P3 治理流程落地（文档层）

- **立项理由**：ZCode 的治理是「流程 + 机械门禁」双件套；本项目已有 7 点检查清单与文档体系，缺的是「模块级边界变更的常规动作」。
- **内容**：在项目 `AGENTS.md`/docs 增补三条增量规则（不重写既有规则）：① 改跨包/跨 crate 边界前先跑架构检查并读阅读包；② 新文件/新模块在 policy 中登记（无登记即检查报红）；③ 行为变更先写/更新对应 spec 或计划文档（与既有「计划文档」惯例对齐）。
- **验收**：规则可执行（对照 P1 脚本的报红路径走一遍）。
- **不做项**：不改用户级全局规则；不引入新流程工具。

### P4 存量基线登记

- **立项理由**：P1 阈值若对存量硬报红，门禁会被噪声淹没（R6）。
- **内容**：全仓跑一次检查 → 违例清单入基线文件（`architecture-baseline.json`）→ 校验「基线内不报、基线外报」；记录各阈值下的存量分布（文件行数分位数等）供 D3 拍板。
- **验收**：基线文件与实测可重复（两次运行结果一致）；对基线内文件做一次「真实变更」验证其进入报告。

## 二、S 线（会话与权限）

### S1 设计评审（无码，先出三份一页草案 + 裁定表）✅ 草案已出（2026-09-21）

- **立项理由**：C4/C3/C2 三族都是「语义重排」——不先裁定就动代码必然返工（09-16 靠 06/08 两份草案把 D 系列裁定收敛后才开工，本线沿用）。
- **内容（三份草案）**：
  1. **会话模型草案**：事件溯源 + `replace` 遮蔽语义在新内核的归一（承接 04-§一 A2 修正：现有折叠/锚点与 replace 同构）；**分叉/回滚**（对话面）与**工作区检查点**（文件面，git 快照或自建）的载体与写路径；崩溃冷修复规则。
  2. **权限模式机草案**：三档（Plan/Interact/Autopilot）→ ZCode 五档（plan/build/edit/yolo/auto）的**映射表**与判定顺序契约（alwaysAsk 不可绕过 / 单调 guard）；会话级授权与 full-access 的持久化；`disallowedTools` 语义。
  3. **工具元数据契约草案**：C2 全字段在 Rust 内核的落型；双执行栈正式化（「客户端工具」= 前端桥工具的一等身份）；大结果落盘/artifact 的落点（与现有原文外置机制合并）。
- **验收**：三份草案各有裁定表（D 系列，编号续 09-16 的 D 前缀改为 ZD 前缀防混淆）；用户逐份拍板。
- **不做项**：不动代码；不等同实现排期。

### S2 内核契约冻结

- **立项理由**：整体重写第一步必须钉住「内核对外面」，否则前端/命令层/领域层三面全动（R2/R3）。
- **内容**：冻结 AgentLoop 对外四契约——事件契约（总线 key 表与模式，承接 B1）、工具契约（元数据 + 注册面）、输入契约（准入与取消）、审批契约（四值 + 交互三型）；产出契约文档 + 类型落点清单；**生成物**（如 bridge-spec）随契约更新。
- **验收**：契约文档与现有实现逐条对照（缺项入挂账）；前端与 tauri 命令层的改动面清单产出。
- **不做项**：不实现新内核主体。

### S3 会话分叉 / 回滚 / 工作区检查点（新增能力）

- **立项理由**：C4 差距项（WorldSea 无会话分叉/回滚；写作场景「试写一版→不满意→回到分叉点」是真实高频需求——比编程场景更贴产品）。
- **内容**：按 S1 裁定落地：对话面 fork/rewind（scope：conversation/workspace/both）+ 文件面检查点（与写作数据 owner 的边界须经 S1 裁定——**实体 store 的写面归领域层，内核只做会话面**）；崩溃后可检出。
- **验收（反证式）**：分叉后原会话不受影响；回滚后视图与文件两侧一致；注入崩溃点验证检出；回归底线 B5/B6/B9 全绿。
- **不做项**：不做多端 replayable 投影（C9 低优先）。

### S4 权限模式机与规则升级

- **立项理由**：C3 差距项；且新内核工具元数据（needsApproval/riskLevel）必须有权判读取方。
- **内容**：五档模式 + 判定顺序契约（alwaysAsk 不可绕过）+ 会话级授权持久化 + Lock/Allow 名单保留；三档到五档的映射与 UI 入口（设置面板改动属 UX 决策，需确认）。
- **验收（反证式）**：判定顺序逐条注入反例（模式不得绕过 alwaysAsk；yolo 仍受内置锁约束）；真机走查覆盖三档↔五档映射与「一键加入白名单」既有能力。
- **不做项**：不做沙箱强化（sandbox.rs 现状保留）。

### S5 交互三型呈现（permission / userInput / hookReview）

- **立项理由**：C3 交互面差距；也是「会话内事件呈现」族的第一块（为后续 C5/C6 交互面打样）。
- **内容**：三型交互请求的协议面（前端呈现 + 回传）+ 现有确认弹窗升级为交互请求族。
- **验收**：三型各一条真机走查；既有确认流程不回归（B7）。
- **不做项**：不做 hooks 体系本身（C7 排后批次）。

## 三、验收口径（全线统一）

1. **反证式**：每道新门/每条新能力，注入错误看报红（或看行为异常），正确路径零报红；**两份输出留档**（错误版 + 正确版）。
2. **回归底线**：每批完成时 [02-§三 B1-B10](02-差异矩阵与内核重写范围.md) 对账 + 测试基线不得下降（kernel 311 / commands 180 / patterns 117 / memory 119 / vitest 988 / vue-tsc 0 / src-tauri check + test --no-run）。
3. **真机走查**：由用户亲自手测（交付时给预期效果与测试步骤）；未经走查不得标记完成。
4. **文档同步**：每批同步 `docs/index/README.md` + 本目录滚动进展 + `.workbuddy/memory/`。
