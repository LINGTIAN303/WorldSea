## 一、现状取证（本项目，2026-09-22）

**两条平行通道 + 一条缺席**：

| 型 | 内核入口 | 事件（key） | Tauri 通道 | 回传命令 | 前端 |
|---|---|---|---|---|---|
| permission | `ConfirmationBroker::request(bus, tool, args)`（60s 超时） | `confirmation_requested` / `confirmation_resolved` | `agent:confirm:{session_id}` | `cmd_agent_confirm(outcome: approved\|denied\|skipped)` | `setupConfirmListener` → `useConfirm` 三键 + 白名单附加动作（`buildAllowAction`） |
| userInput | `ConfirmationBroker::ask(bus, questions)`（600s 兜底） | `ask_requested` / `ask_resolved` | `agent:ask:{session_id}` | `cmd_agent_ask_answer(answers: Option<Vec<AskAnswer>>)` | `setupAskListener` → `useAsk` 面板 |
| hookReview | **无** | — | — | — | — |

（取证落点：`confirmation.rs:564-740` 双 pending 注册表 / `event.rs:634-672` 四事件 / `commands.rs:603-647` 转发四臂 / `commands.rs:1369-1404` 两回传命令 / `useAgentRust.ts:1453-1610` 两监听器）

### 缺口（四条）

1. **无统一模型**：两型各自持事件对 / 命令 / 监听 / 取消语义；「三型为外层统一模型」仅存于 07 冻结纸面。新增一型 = 新通道 + 新命令 + 新监听（三处并改）。
2. **取消语义不一致**：提问有随轮取消（`cancel_pending_asks` → `AskOutcome::Cancelled`，`agent/mod.rs:568`），**确认没有**——`abort` / `dispose` 后待确认工具须等满 60s 超时才返回（**既有缺口**，统一注册表顺带修复）。
3. **第三型缺席且钩子决策面窄**：既有 A6 `ToolLifecycleHook` 仅二值 `Allow(args) / Deny(reason)`（`tool_hook.rs:20-25`）；ZCode 为三值——缺「转人工复核」升级路径。钩子在权限门**之后**执行（`maybe_require_confirmation` → `execute_tool_with_retry` → `run_tool_with_retry` pre，`tools.rs:696-704`）。
4. **契约副本漂移**：`ConfirmationOutcome` / `InputKind` 在 `agent-engine::contracts`（S3-a 骨架，07 指定单一定义处）与 `agent-kernel`（运行事实源）**双份并存**（engine 副本仅自测引用）；`AskOutcome` / `AskAnswer` 只存在于 kernel——**交互族的类型面尚未单点化**。

## 二、设计（统一交互请求族）

### 2.1 契约层（S5-a，`agent-engine::contracts::interaction`）

```rust
pub enum InteractionKind { Permission, UserInput, HookReview }   // serde snake_case

#[serde(tag = "kind", rename_all = "snake_case")]
pub enum InteractionRequest {                                    // 事件载荷（判别即 kind）
    Permission { tool_name: String, args: Value },
    UserInput  { questions: Value },
    HookReview { hook_name: String, tool_name: String, args: Value, reason: String },
}

pub enum HookReviewOutcome { Approved, Denied, TimedOut, Cancelled }   // 前端只回前二值；后二仅内核侧

pub enum InteractionOutcome {                                    // 统一结果（判别即 kind）
    Permission(ConfirmationOutcome),   // 四值不变（B7）
    UserInput(AskOutcome),             // 四态不变（answered/denied/cancelled/timed_out）
    HookReview(HookReviewOutcome),
}
```

- **单点化**（顺带收口缺口 4）：`ConfirmationOutcome` / `InputKind` 收敛到 engine（补 `parse` 行为面），kernel 改只读引用；`AskOutcome` / `AskAnswer` 自 kernel 迁入。**零改名零删除**：kernel `confirmation.rs` 以 `pub use` 保持 `agent_runtime::confirmation::*` 下行路径不变。

### 2.2 内核层（S5-a，`InteractionBroker` 取代 `ConfirmationBroker`）

- **统一注册表**：`HashMap<String, Pending { kind, tx }>`（id 统一前缀 `ix-`）；`resolve(id, outcome)` 校验 kind 相符（不符即拒、不唤醒）。
- **三型入口**：`request_permission` / `request_user_input` / `request_hook_review`（超时表见 2.5）。
- **统一收口**：`cancel_all()`（随轮取消）→ 三型各自内核侧终值：permission→`Timeout`、user_input→`Cancelled`、hook_review→`Cancelled`。
- **行为变化（随批登记）**：`abort` / `dispose` 现在**也**取消待确认（此前等满 60s）——收敛方向 = 更快收口；四值语义不变（仍是「未执行」），B7 不破。
- **hookReview 生产路径**：`ToolHookAction::Review { reason }`（`tool_hook.rs` 三值化）→ `run_tool_with_retry` pre 命中 → broker 发起 hookReview → `Approved` 继续执行（沿原 args）；`Denied` / 超时按 `ToolError::Execution` 返回（错误码 `HOOK_REVIEW_DENIED` / `HOOK_REVIEW_TIMEOUT`，与现有 `Deny(reason)` 路径并列、可区分）。**钩子仍不越过权限门**（位次不变）。

### 2.3 事件层（S5-b）

- keys **增补 2 个**：`interaction_requested` / `interaction_resolved`（62 → 64，增补式；见 07 §一冻结口径）。
- `OrchestratorEvent` 增补 `InteractionRequested { interaction_id, request }` / `InteractionResolved { interaction_id, outcome }`。
- 旧 4 key + 旧 4 事件变体处置 → **Q3 裁定**。

### 2.4 命令层与前端（S5-b）

- **单通道**：`agent:interaction:{session_id}`；**单回传**：`cmd_agent_interaction_respond(session_id, interaction_id, response)`——`response` 为带 `kind` 判别的载荷（`{kind:"permission", outcome}` / `{kind:"user_input", answers?}` / `{kind:"hook_review", outcome}`）；http_bridge RPC 同步。
- **前端单监听**：`setupInteractionListener` + kind 分派——permission → 现 `useConfirm` 弹窗（三键 + 白名单附加动作**原样**）；user_input → 现 `useAsk` 面板**原样**；hook_review → 新复核弹窗（hook 名 / 工具 / 原因 + 通过 / 拒绝）。`setupConfirmListener` / `setupAskListener` 退役。
- **同批交付约束**：事件面与前端消费不可分离（S5-b 一次提交；否则确认弹窗断裂）。

### 2.5 超时与结果值表（汇总）

| 型 | 超时 | 用户值 | 内核侧值 | 超时/取消结局 |
|---|---|---|---|---|
| permission | 60s（不变） | approved / denied / skipped | timeout | 不执行（B7） |
| user_input | 600s（不变） | answered / denied | cancelled / timed_out | 按跳过（B7） |
| hook_review | **60s（Q4 待裁）** | approved / denied | cancelled / timed_out | **按拒绝（fail-closed）** |

## 五、验收口径（反证式）

1. **kind 错配注入**：`resolve` 不校验 kind（permission 结果塞给 user_input 等待方）→ 用例红（复原后绿）。
2. **统一取消摘除**：摘 `cancel_all` 接线 → 随轮取消用例红（**permission 型也必须被取消**——本批修复的既有缺口）。
3. **hookReview 路径摘除**：摘 `ToolHookAction::Review` 分支 → 装配级用例红（hook 转复核 → 放行/拒绝两分支；拒绝须回 `HOOK_REVIEW_DENIED` 且工具未执行）。
4. **B7 回归全绿**：四值 + 超时单列 + 三档 + Lock/Allow 语义不变；既有确认/提问用例零改名迁移（迁移即对账）。
5. **前端**：三型各一条真机走查（hook_review 见 Q2 裁定口径）；既有确认流程不回归（B7）。
6. **基线**：kernel / commands / vitest 用例数不降；`arch:check` 零违规；`check-doc-links` 断链 0。
