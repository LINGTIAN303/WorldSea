# C5 · 凭证与模型配置批计划（小批）

> 承接：裁定 ③（模型凭证首期 env 注入；归属随凭证批立项）与 R11（「用户可能需两处配置」）。
> 插查结论：壳**从未注入过 Key**（`apps/tauri` 全树搜不到 `DEEPSEEK_API_KEY`）——今天靠**启动环境继承**；
> 而 dsh 的凭证分层是 **`继承环境（最高优先）` > `$DSH_HOME/.credentials.yaml`（页面「设置 → 模型」写入的库）> 项目 `.env` > home `.env`**
>（`packages/credentials/credentials-local/src/index.ts` 头注）。于是「两处配置」的具体危害＝**只要启动环境里有 Key，它就永远盖住界面里配置的 Key（改了不生效）**。

## 一、裁定记录（2026-09-24 拍板）

| # | 裁定点 | 结果 |
|---|---|---|
| ① | Key 唯一真源 | **dsh 的 `$DSH_HOME/.credentials.yaml`**（页面「设置 → 模型」可写）；**旧 Key 不迁移**（用户经页面引导重填一次） |
| ② | 继承的 Key（2026-09-24 晚**改判**） | **库优先 + env 兜底**：壳 spawn 前判一次库——库里已有该凭据 → **剥离**继承的环境变量（界面配置生效）；库里没有 → **保留**继承的环境变量作零配置兜底。改判理由：裁定 ③ 的「env 注入」语义保留（用户 2026-09-24 提醒），只把优先级从「env 恒优先」降为「库优先、env 兜底」 |
| ③ | 首启引导 | **用页面自带的凭证引导**（`credentialOnboarding` 默认开；壳零 UI 改动） |

## 二、批次划分（单步，小批）

### C5-a · 壳侧剥离 + 验收

- **实现**（`dsh_shell.rs`）：spawn 前对凭据环境变量逐条判定（当前名单：`DEEPSEEK_API_KEY`，逐条留痕日志）——`credential_store_has()` 读 `$DSH_HOME/.credentials.yaml` 的 **`refs:` 段**（该文档是**带版本结构**：`refs` 按环境变量名存密钥值、`records` 按 `<owner>/<id>` 存插件凭据；见 dsh `credentials-local` README），只跟踪 `refs:` 段内更深缩进的行，不做完整 YAML 解析。**判据纠正（实测逮到）**：初版按「顶层键」判会**漏判**（真存了 Key 也认不出 → 等于没修）；B 段用扁平样例误打误撞通过，D/E 段改用真实形状复验。
- **验收（真机，五段）**：A 库文件不存在 → `库中无 …：保留继承的环境变量作兜底…`；B 扁平样例（初版判据）→ `库（.credentials.yaml）已有 …：剥离继承的环境变量，以界面配置为准`；C `WORLDSEA_KEEP_ENV_KEYS=1` → `凭据环境剥离已按 … 关闭`；D **真实现场**（仅 `records`、无 `refs`）→ 兜底；E 追加真实 `refs:` 段 → 剥离。每轮跑完按备份复原 `.credentials.yaml`（该文件同时承载 dsh 的 browser-session 授权记录）。
- **反证**：C 段即反证（同一环境下行为随开关翻转）。
- **边界（如实登记）**：① 剥/不剥只影响**壳 spawn 那一次继承**；`DSH_HOME/.env`、项目 `.env` 仍按 dsh 自身分层（语义属 dsh，不在壳改）。② 「界面配置生效」的端到端观感（改 Key 后立刻生效）作为**用户走查项**：本机探针走 `/api` 需 RPC 信封，裸 fetch 会被 `gateway/bad-request` 拒（已实测），故自动化只验日志差分与库文件判定，界面级效果由走查确认。③ 打包形态下壳无启动环境继承，天然只走库。
