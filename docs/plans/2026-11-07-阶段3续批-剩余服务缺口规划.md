## 二、规划前的关键调查结论

### 2.1 `uiStore.viewComponent` 是全仓冗余，不该照搬进服务

**取证**：全仓 13 处写 `viewComponent`，**每一处都紧跟 `setView(id)`**，形如：

```ts
uiStore.setView(view.id)
uiStore.viewComponent = view.component   // 必然成对
```

只有 2 处显式置 `null`（`SidebarV2.vue:264` / `Sidebar.vue:423`），且都在 `setView('')` 之后。

**消费侧**（`ViewContainer.vue:62-79`）本身就会兜底：

```ts
const viewComp = computed(() => {
  const comp = uiStore.viewComponent
  if (comp) return comp              // 优先缓存
  const view = pluginStore.getView(uiStore.currentView)   // 兜底解析
  return view?.component ?? null
})
watch(() => uiStore.currentView, (viewId) => {          // 自动同步
  if (viewId && !uiStore.viewComponent) uiStore.viewComponent = ...
})
```

**结论**：`viewComponent` 是 `setView` 的固有副作用被外置成了调用方义务。这既造成 13 处样板，也让「把导航做成服务」卡住——因为 `Component` 对象不适合当服务数据。

**规划动作**：把 `viewComponent` 的维护收进 `setView` 内部（store 层），调用方只写 `setView(id)`。之后 `world.ui` 只需暴露纯数据 + 动作，不含组件引用。

> 这是**架构变更**（改 uiStore 语义 + 13 处调用点），需用户确认后才动手。

### 2.2 `world.ui` 的真实消费面很窄

即：**4 个动作 + 4 个字段**，无一个是组件引用（`viewComponent` 按 §2.1 收进 store 内部后）。

### 2.5 `settings` 插件是最大难点，不是「再补几个服务」能解决

它依赖 11 个 store，其中 `IconAsset`(8) / `IconOverride`(4) / `FieldOrder`(3) / `HomeProfile`(2) / `DetailLayout`(6) 全部无服务。若要推它，服务目录要从 8 项扩到 15+ 项。

**规划判断**：`settings` 插件本身是**设置面 UI**，它是「配置的编辑器」而非「配置的消费者」。把它也改成读服务，收益存疑——应单独立项评估，不并入本批。

### 批次 1：`world.ui`（含 `viewComponent` 收敛，已落地）

| 步骤 | 内容 |
|---|---|
| 1a | `uiStore` 新增 `showView({id, component})` / `clearView()`；清掉 13 处调用方的成对赋值 |
| 1b | 新增 `world.ui` 服务（6 方法，见下） |
| 1c | 迁移 `custom` / `theme-editor` / `mindmap` |
| 1d | 守卫扩清单 + 反证 |

**1a：为什么用 `showView` 而不是让 `setView` 自己查组件**

`setView` 要查「viewId → component」就得依赖 `pluginStore`，而成环风险真实存在
（`pluginStore` 现只依赖类型，但加依赖后 `uiStore` 与它将互相引用）。故取
`showView({ id, component })`——**由调用方传入组件，store 只负责同时写两个字段**。

**1a 顺带修了两个既有缺陷**：

1. **`ViewContainer` 的同步 watch 只在 `viewComponent` 为空时补齐** —— 于是
   「`showView(A)` 后紧跟 `setView(B)`」会让 `viewComponent` 停在 A，而 `viewComp`
   优先取它 → 渲染出错视图。改为**无条件同步**。
2. **`shallowRef` 缓存了代理对象而非原组件** —— 调用方常从 `pluginStore.views`
   （pinia 深代理数组）取 view，其上 `.component` 读出的是**代理对象**。旧代码在
   调用方外部取值恰好拿到原对象，收敛进 `showView` 后变成代理 → `boot.spec` 的
   「并带上组件」严格相等断言失败。解法：`showView` 内 `toRaw(view.component)`。

**1b：`world.ui` 只暴露导航意图，不传组件**

| 方法 | 消费方 |
|---|---|
| `navigateTo(viewId)` | `custom` / `mindmap` |
| `currentView()` | 预留 |
| `selectedEntityId()` / `selectEntity(id)` | `characters`（下批次） |
| `setSettingsTarget(target)` | `theme-editor` |
| `setJumpBackViewId(viewId)` | `custom` |

**刻意不含 `showView(view)` / `viewComponent`**：`Component` 是渲染对象，不该跨服务传递。
`custom` 原本写 `uiStore.showView(pluginStore.getView(id))`，改造后为
`uiSvc().navigateTo(view.id)`——行为等价，因 `ViewContainer` 有按 `currentView` 解析的兜底，
且 1a 修正后的 watch 会自动补齐缓存。守卫含反向断言：不得出现 `viewComponent` / `showView`。

**1c：`custom` 保留一处 `pluginStore` 读取，是有意的**

`custom` 是「视图容器」——职责就是动态渲染**其他视图的组件**（`getViewComp` 拿
`getView(id).component` 交给 `<component :is>`）。这是它的核心功能，不是漏迁：
组件引用不跨服务传，故这处读取留在芽内，`serviceAccess.ts` 顶部已注明。

**验收**：三插件源码零 `useUIStore` / `useSettingsStore` 直连 · 全仓测试零失败 ·
服务目录 8 → **9 项** · 守卫 109 → **130 例**（清单 35 → 42 文件）· 反证 3 轮
（`showView` 删组件赋值 → 2 例红；`mindmap` 还原直连 → 2 例红；去掉 `toRaw` → 1 例红）。

**遗留**：`uiStore` 引用现为 5 插件（`characters` / `manuscript` / `settings` / `timeline`
及壳层自身），待后续批次。

## 四、每批的固定流程

沿用前四批已固化的做法：

1. **接口设计**：只暴露已证实被消费的具名方法/字段，不转发 store 实例
2. **实现**：`services.ts` 加接口 + `createWorldServices` 加实现 + `WORLD_SERVICE_NAMES` 加名
3. **服务自测**：`world-services.spec.ts` 断言方法表、计数、不暴露敏感面
4. **迁移插件**：`svcOf<T>(name)` 单一泛型 + 具名 getter；服务缺席抛错不降级
5. **守卫**：加入 `lightPluginDataPath.spec.ts` 的 `MIGRATED` 清单（现 26 个文件 / 79 例）
6. **反证**：至少 2 轮（改错服务名 / 还原直连），确认守卫会红
7. **门禁**：`pnpm typecheck:tauri` + `node scripts/gate.mjs` + 全量 `npx vitest run`
8. **文档**：更新主计划 §十二、索引、`project_memory.md`
