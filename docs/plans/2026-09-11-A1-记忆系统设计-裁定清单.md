## 〇、本轮新取证：长期记忆在生产上从未被真正使用

这是**改变全部成本判断**的一条实测结果，先摆出来。

### 0.1 memories.db 实况（2026-09-11 只读查询）

路径：`C:\Users\LINGTIAN303\AppData\Roaming\com.worldsea.app\worldsea\memory\projects\_default\memories.db`（72 KB，无 `-wal` / `-shm` 伴生文件）

### 0.2 四条判定

1. **生产上从未真正使用。** 全部数据 = 2 条、2 个会话、集中在 2026-09-10 同一天、`raw_contexts` 与 `session_meta` 从未写入 → 这是开发试跑痕迹，不是积累。**结论：schema 变更的迁移成本 ≈ 0，当前是唯一的自由窗口。**
2. **`project_id` 全 null 得到实锤**（此前仅由代码推断）。所有会话共用 `_default`，记忆隔离确实未启用 —— 对应 [workspace-unification-plan.md](workspace-unification-plan.md) L11/L100 的「项目 id 消费缺位」。
3. **storage schema 与 trait 契约有 5 处不对齐**（见 0.3）。更准确地说：trait 声明的若干能力在库里**根本没有落脚处**。
4. **只跑过阈值归档路径，周期合并从未运行。** `period` 只有 `daily`，无 `weekly` / `monthly`；`Compactor` 的周合并与月淘汰零应用层调用。

### 0.3 schema 与 trait 契约的 5 处不对齐（新发现）

| trait / 结果类型声明的字段 | 声明位置 | SQLite 实况 | 后果 |
|---|---|---|---|

## 二、新增影响面（己组 · 2 条裁定）

> 用户追加要求：评估「session 日志系统（完整记录会话轨迹）」与「上下文压缩系统（压缩时要保留的上下文类型）」对 A1 的影响。两项均为**代码取证**（非文档转述）。
>
> 这两条不是旁支：**己1 决定 A1 有没有「不可变底座」可依赖；己2 是「什么值得沉淀」的镜像问题——凡能被安全丢弃的，就是不该写入长期记忆的；凡丢了会导致目标漂移的，就是必须沉淀的。**

#### ★ 己1 · session 日志系统 —— 轨迹的记录能力

**1）持久化载体**

| 载体 | 位置 | 内容 |
|---|---|---|
| `sessions` 表 | 会话库 `.db`（sqlx SQLite，WAL） | id · system_prompt · created_at · message_count · updated_at · title · pinned · kind · router_enabled（**已废弃，仅物理保留**）· plan · workdir · workspace_id · project_id · scene_id |
| `messages` 表 | 同上 | `(session_id, seq, msg_json)`，整条 `OrchestratorMessage` 的 JSON（crates/agent-commands/src/session_store.rs:284-294） |
| `group_chat_sessions` / `workdirs` / `workspaces` | 同上 | 群聊参与者映射 / 目录实体 / 工作区实体 |
| 编排事件 | **另一套存储** | `RunStore`（crates/agent-commands/src/run_store.rs）—— run_*、路由决策、交接产物 |
| 动作段事件 | **不是独立日志** | merge 进「最后一条 assistant 消息」的 `meta.action_events`（crates/agent-commands/src/lib.rs:3240-3250） |

**2）消息模型只有 4 种 role**（crates/agent-kernel/src/types.rs:93-98）：`User` / `Assistant` / `ToolResult` / `System`。
`thinking` 存在 `meta.thinking`（crates/agent-kernel/src/agent/mod.rs:920-925），**不进 LLM 上下文**。

**3）落盘粒度逐项核实**

| 内容 | 是否落盘 | 载体 | 是否截断 |
|---|---|---|---|
| user 消息 | ✅ | messages.msg_json | 无（但注入 `[时间戳]` 前缀，mod.rs:580-587） |
| assistant 正文 | ✅ | messages.msg_json | 无 |
| thinking 推理 | ✅ | messages.meta.thinking | 无 |
| `tool_call`（名称 + **参数原文**） | ✅ | messages.tool_calls | 无上限（截断只作用于结果） |
| `tool_result` | ✅ | messages（ToolResult） | ⚠ **入库前截断 12 000 字节、只保头部**（crates/agent-kernel/src/agent/tools.rs:53-70） |
| 计划步骤 / 待办项 | ✅ | sessions.plan 单列（JSON） | 无 |
| 动作段事件 | ✅ | 最后 assistant 的 meta.action_events | 无（但**异常中断不落库**，待测试清单已登记） |
| 编排事件（run_*） | ✅ | RunStore（另一库） | — |
| 错误与重试 | ❌ | **未见专用载体** | — |

**4）三条硬结论**

- **不能凭落盘数据完整回放会话轨迹。** 三处内容不可恢复：
  ① **tool_result 超 12 000 字节 → 尾部永久丢失**。截断发生在**入库前**（dsh §6.3 已证），即原始内容**从未进入过任何存储**。
  ② **被裁历史 → 物理删除**（`replace_messages` 全量替换，见丙2 回写修正）。
  ③ **归档的「记忆」不含工具交互**——`record_turn` 构造 `MessageTurn` 时 `tool_calls: Vec::new()`、`thinking: None`、`attachments` / `file_changes` 全空（crates/agent-memory/src/lib.rs:260-283），`load_chunk` 还原时只产出 user / assistant 两条纯文本（:299-319）。
- **`messages` 表是「可变快照」，不是「事件日志」。** 每次持久化整体重写历史 → **全仓没有 append-only 事件溯源能力**。
- **`raw_contexts` / `session_meta` / `raw_context_path` 不是"设计占位"，是未接线的既有能力。** vendor 里躺着**完整的「压缩前保存原文」机制**：
  - `Storage::write_raw_context` / `read_raw_context`（crates/vendor/memory-center-core/src/sqlite.rs:1077-1155，落 `raw_contexts` 表）
  - `memories.raw_context_path` 列（:138-160）
  - `context_parser.rs` —— 把 pre_compress_hook 收到的 `full_context` 解析成 `Vec<MessageTurn>`
  - `Archiver` 的 hook_id 对齐 API（vendor/memory-center-core-logic/src/archive.rs:74-76 / 151-153 / 297）
  - 用途注释写明：「在 Trae 客户端压缩上下文前，由 **pre_compress_hook** 将**完整原始上下文**」持久化（vendor/memory-center-core-logic/src/storage.rs:480-482）
  - **全仓零应用层调用**（grep 仅命中 vendor 自身与其测试）→ 修复不是从零造，而是**接线 + 补一个 pre-compress 触发点**。

**5）需裁定**

- ① **轨迹的目标保真度**：要求原文永久保留（含 tool_result 全文），还是接受"截断 + 不可回溯"？
- ② 若要求原文：**接线 vendor 的 `raw_contexts`**，还是另立 session 级 append-only 日志？
- ③ `TOOL_RESULT_STR_LIMIT` 现为**保头不保尾**（:57-70）——正文细节常在尾部，是否改**保头 + 保尾**（dsh 阶段 D 主张）？

#### ★ 己2 · 上下文压缩系统 —— 必须保留的上下文类型

**1）唯一自动裁剪点：`enforce_context_budget`（crates/agent-kernel/src/agent/mod.rs:745-792）**

- 判据 = 逐条累加 `content.len() + 32` 超 **160 000 字节**（量纲错误，见丙1）
- 算法 = **从头部逐条丢弃**，保留最近 12 条；`trim_context` 同步 state + backend（crates/agent-kernel/src/agent/interaction.rs:69-87）
- **不看 role、不看类型、不成对、不留痕** —— 类型化保留规则：**完全没有**。

**2）关键三问的答案**（本条核心）

| # | 问题 | 答案 |
|---|---|---|
| ① | 系统提示词与记忆注入会被裁吗？ | **不会被裁，但它们根本不在 messages 里。** `build_prompt_options`（crates/agent-kernel/src/agent/memory.rs:84-166）把 scenario_prompt + `config.system_prompt` + memory_context + pipeline_context 拼成 `system_prompt_override`，**独立于 messages 数组逐轮传入** → 记忆注入天然免受裁剪 |
| ①附 | 但有一条例外 | `state.messages[0]` 有一条 `System` 消息承载 system_prompt（mod.rs:563-575，仅推一次）。**它恰好在被裁的最头部，第一个被丢掉**。LLM 侧因 override 存在而跳过该消息（crates/agent-kernel/src/llm/genai_backend.rs:223-226），功能无损；但**类型上毫无保护**，且丢掉后下一轮会「重新推入」到数组中部 → **system 消息位置漂移**。这是类型盲裁剪的直接症状 |
| ② | `tool_call` / `tool_result` 成对裁剪吗？ | **否。** 切点落在两者之间即产生悬空 `tool_call_id` → 400。dsh 硬伤 2 **确认成立**——代码就是逐条从头减，不看 role / 配对（mod.rs:769-781） |
| ③ | 最近一轮 user 输入保证不被裁吗？ | **无保证。** 只保证「最近 12 条」。单轮若含 ≥6 次工具调用（= 1 user + 6×(assistant + toolResult) = 13 条），**该轮 user 输入即落在保留窗口之外被裁掉**。真实可达组合，非理论边缘 |

**3）被裁消息无任何痕迹**：不留摘要、不留边界事件、不留原文。
`get_archive_boundary` 返回的是「累计已消费**轮次**数」（crates/agent-memory/src/lib.rs:220-222），**与裁剪完全无关，从未被裁剪消费**。
手动入口 `trim_context`（lib.rs:3204-3214）已封装并导出（useAgentRust.ts:2774 / 3147），但**无调用方、无 UI 控件**。

**4）归档兜不住被裁内容**

`run_memory_archive` 的注释声称「语义安全：被裁轮次必然已归档进记忆」（mod.rs:743-744）——**但归档只存纯文本轮次**（详见 己1 结论③）。
→ **被裁掉的工具交互 = 两头都没有**：入库前已被截断 12 000 字节，归档再丢弃 tool_calls / thinking，裁剪又物理删除 messages 行。

**5）dsh 已备主张**（保留策略，可直接采纳）

- 阶段 B：`replace` 语义——在不可变事件日志上追加 replace 记录，复用 `meta` 扩展位（**零迁移**）
- 阶段 D：`clamp_tool_result` 改**保头 + 保尾**；溢出错误分类 + 重试
- 外部调研：摘要须含 **Objective / State / Constraints / Next steps** 四段否则目标漂移；「修剪到最近 5 组工具调用对 + 摘要」= **91.6% 完成率 vs 全量 71%**

**6）需裁定**

- ① **保留优先级排序**（建议稿）：系统提示词 > 最近一轮 user 原始输入 > 未完成的计划步骤 > **工具配对完整性** > 最近 N 轮对话 > 陈旧工具结果
- ② **配对保护**：切点是否强制对齐到 tool 配对边界（dsh 用 `toolPairingBalancedBefore/After`）
- ③ **是否引入「摘要替代」**：被裁区间生成摘要替身（需 LLM 调用，成本 / 延迟），还是纯丢弃
- ④ **压缩的可见性**：是否给用户「检查点」标记（＝ dsh R3 待定项）
- ⑤ **压缩前是否快照原文** —— 与 己1 ① ② **同源**，建议一并裁定

### 甲组 · 范围与记忆本体（A1 的「机制化」主体）

#### ★ 甲0 · A1 的「长期记忆」范围界定

- **现状**：存在一处**文档与代码的认知冲突**。[2026-08-31-Agent底层能力与三阶段成熟度.md](2026-08-31-Agent底层能力与三阶段成熟度.md) L136 称现状是「长期记忆只有**图谱化实体载体**」；但代码里真实生效的长期记忆是 `MemoryCenter` 的 **SQLite**。本轮调研另行确认：**未找到「实体/关系存储」被直接当长期记忆使用的代码路径**，实体与记忆之间只有三个弱连接（KB 实体关联 / `memory-archive` 的 `entityIds` 字段 / 场景 prompt 的实体摘要）。
- **选项**：
  - ① 只覆盖 `MemoryCenter`，知识图谱实体记忆另立设计
  - ② 覆盖两者，明确二者的分工与桥接（实体记忆 = 结构化事实，MemoryCenter = 对话沉淀）
  - ③ 覆盖两者且合并为单一机制
- **建议**：**②**。理由：底能文档把「长期实体记忆（图谱化记忆的读写、沉淀与召回）」明确写进了 A1 的三项展开内容（L140-148），但代码侧两者目前毫无桥接。若选 ①，需同步修正底能文档 L136 的表述，否则文档会持续误导。
- **影响面**：**这是第一条要定的**——它决定甲1-甲4 的对象是哪一个库、也决定 A1 文档要不要包含"实体↔记忆桥接"章节。

#### ★ 甲1 · 写入操作集：append-only 是否升级为四操作

- **现状**：`record_turn(user_message, assistant_message)` 只做追加（crates/agent-memory/src/lib.rs:255-286），达阈值才 `archive()` 落盘。**无 UPDATE / DELETE / NOOP**；`delete_by_session_id`（:224-253）仅按会话整删。
- **选项**：
  - ① 维持 append-only（零改动，接受陈旧累积）
  - ② 引入 **ADD / UPDATE / DELETE / NOOP** 四操作
  - ③ 分期：先补 **NOOP（写前去重）+ DELETE（纠正）**，UPDATE 后置
- **建议**：**③ → ②**。依据：外部调研硬数据——扁平 append-only 结构累积 **38% 陈旧率**，Mem0 在 LongMemEval 从基准 93.4% 跑 30 天掉到 **49.0%**。但 UPDATE 依赖矛盾调和策略（甲2）先定，且引入 LLM 调用成本，故拆期。
- **影响面**：`MemoryAccessor` trait 需扩展（现 7 方法无 update / delete-by-id）；schema 需支持 supersede 标记。**甲1 / 甲2 / 丙2 是同一条链**，建议连着定。

#### ★ 甲2 · 更新与矛盾调和策略

- **现状**：无任何更新路径。冲突信息只会作为不同行并排堆在库里，永不调和。
- **选项**：
  - ① 覆盖（新覆盖旧）—— 最简单，但丢历史、丢时序
  - ② **调和摘要**：生成一条显式记录矛盾与时序的新记忆（如「用户 2025-11 前用 React，之后转 Vue」），**不覆盖原始双方**
  - ③ 双时间线：保留双方 + 标注生效区间
- **建议**：**②**，并明确「**矛盾不覆盖**」为硬规则。依据：外部调研的 temporal arbiter 实践；且②与 D1 咬合——调和结论正是最该进 MEMORY.md 的那类内容。
- **影响面**：需新增 LLM 摘要调用（成本 / 延迟，属 dsh R2 同类风险，建议默认 auto 可关）；schema 需 supersede 链。

#### 甲3 · 遗忘与淘汰

### 丙组 · 计量与压缩

#### ★ 丙1 · 上下文 token 计量与阈值三档

> **量纲前提（2026-09-11 用户明确）**：本条的计量与阈值讲的**都是「上下文 token」**——即 LLM 上下文窗口占用，**不是字节**。现行的字节实现属于**实现与语义不一致**，不是"两种可选口径"。A3 已澄清同一语义（[2026-08-31-Agent底层能力与三阶段成熟度.md](2026-08-31-Agent底层能力与三阶段成熟度.md) L181「全项目以窗口占用为唯一计量语义」）。

- **现状**：实现层用了三种互不相同的近似，**没有一种是真实的上下文 token 数** ——
  - 主链路按**字节**：`HISTORY_BUDGET_BYTES = 160_000`、`HISTORY_KEEP_MESSAGES = 12` @ crates/agent-kernel/src/agent/mod.rs:752-753（注释自标「⚠ 占位待定」，其上 L738 明写「全链路无 token 计量」），计量 = `content.len()+32` 求和 —— **量纲错误**：同样 160 000 字节，全是中文时≈5.3 万汉字、全是 ASCII 时≈16 万字符，换算成 token 相差近一倍
  - Rust `estimate_tokens`（CJK 1/字、ASCII 1/4）@ crates/agent-memory/src/lib.rs:410-421 —— 量纲对（token），但是粗估
  - TS `ShortTermMemoryHelper.estimateTokens`（字符 × 0.25）@ packages/agent-core/src/orchestrator/short-term-memory.ts:66-78 —— 量纲对，但系数与上一处不一致
  - 真 tokenizer（gpt-tokenizer）存在于 packages/memory-archive/src/utils/tokenCounter.ts，但**该包未接入**
- **选项**：① 沿用粗估（零依赖，接受偏差）／② 接入真 tokenizer（准确，引入依赖与计算成本）／③ 近似为主 + 真计数校准（按模型校准系数）
- **建议**：**② 或 ③**，并把量纲**硬性统一为「上下文 token」**——清除一切以字节为阈值单位的写法（`HISTORY_BUDGET_BYTES` 这个名字本身就是错误的量纲声明）。
- **影响面**：**直接解 A3**；丙2 与 己2 的触发时机均依赖它；**归档阈值（2000）与上下文预算（160 000）同属上下文 token 语义，须一并归一**；`estimate_tokens` 与 TS 版本需收敛为一处。

#### 丙2 · Compaction 压缩语义与恢复策略

- **现状**：[deepseek-harness-调研与借鉴方案.md](../misc/deepseek-harness-调研与借鉴方案.md) §六列出四个硬伤——① 裁剪是内存态头部硬丢弃、不持久不可回溯（L344-354）② 无 `tool_call` / `tool_result` 配对保护，切点可能落在两者之间（L356-370，真实 BUG 风险）③ 全链路无 token 计量（L372-376）④ 阈值标记为占位待定（L378-387）。方案提出阶段 A-D 四步（L422-474）。

> **⚠ 回写修正（2026-09-11 代码取证）**：硬伤 ① 的**后半段与代码实况不符**，须更新本文档作为丙2 的方案基线。
>
> 原文称「裁剪只动内存不持久化 → `session_store` 里的历史不会被同步裁剪 → 刷新页面回源后，被裁掉的旧消息又完整回来了」。
>
> **实况：链路是写穿的。** `run()` 内 AfterRun 裁剪 → `run()` 返回 → 广播 `AgentEnd`（crates/agent-kernel/src/agent/mod.rs:627 / 634）→ Tauri 侧 `flush_buffered_action_events`（apps/tauri/src-tauri/src/commands.rs:321-325）→ `flush_action_events` → `persist_messages`（crates/agent-commands/src/lib.rs:3240-3250）→ `store.replace_messages`（:3217-3233）。而 `replace_messages` 是**全量替换**（`DELETE FROM messages WHERE session_id` + 逐条 INSERT，crates/agent-commands/src/session_store.rs:509-525）。
>
> **实际后果比 dsh 描述的更严重**：被裁消息**被物理删除**，刷新后不会回来，而且**不可恢复**。
>
> **对方案的影响**：阶段 B 的必要性反而更强——原表述像是在防"复活"，实际要解决的是"**把可变快照改成不可变追加**"。详见 己2。
- **选项**：
  - ① 只做阶段 A 止血（配对保护 + 裁剪同步持久化）
  - ② 阶段 A + B（引入 `replace` 语义：在不可变事件日志上追加 replace 记录，而非删历史）
  - ③ 全量 A-D
- **建议**：**②**。其一是硬伤 ② 是**当前真实的 400 错误风险**，属 P0；其二是 B 的「replace 语义」与甲1 的四操作同源，一起做省一次返工。
- **待你另定的 3 个风险点**（dsh §九 L478-487）：
  - **R3**：阶段 B 会让会话出现"检查点"消息，**前端如何呈现需你定**
  - **R4**：触发时机从 AfterRun 挪到派生前（影响 `RunPhase` 语义，**架构变更需确认**）
  - **R5**：阶段 C 需模型 `context_window` 声明（涉及 `ProviderConfig` 数据结构变更，**需确认**）
- **影响面**：解锁 WORKSTREAMS 的「Compaction 施工」下游线；R4 触及编排运行时骨架，建议单独拉一条施工项。

| 4 | dsh 硬伤 ①：「裁剪只动内存不持久化 → 刷新后旧消息又完整回来了」 | **不成立**：`AgentEnd` → `flush_action_events` → `persist_messages` → `replace_messages` **全量替换**，被裁消息被**物理删除**、不可恢复 | 丙2 回写修正已写入；方案基线应改为「把可变快照改成不可变追加」 |

第 3 条的取向本身也是个小裁定：**以 trait 为准补 schema，还是以 schema 为准精简 trait？**
第 4 条的性质不同——它不是"文档过时"，而是**原结论方向反了**（不是"会复活"而是"被销毁"），对方案的影响是加强而非削弱。
