### 0.2 四条判定

1. **生产上从未真正使用。** 全部数据 = 2 条、2 个会话、集中在 2026-09-10 同一天、`raw_contexts` 与 `session_meta` 从未写入 → 这是开发试跑痕迹，不是积累。**结论：schema 变更的迁移成本 ≈ 0，当前是唯一的自由窗口。**
2. **`project_id` 全 null 得到实锤**（此前仅由代码推断）。所有会话共用 `_default`，记忆隔离确实未启用 —— 对应 [workspace-unification-plan.md](workspace-unification-plan.md) L11/L100 的「项目 id 消费缺位」。
3. **storage schema 与 trait 契约有 5 处不对齐**（见 0.3）。更准确地说：trait 声明的若干能力在库里**根本没有落脚处**。
4. **只跑过阈值归档路径，周期合并从未运行。** `period` 只有 `daily`，无 `weekly` / `monthly`；`Compactor` 的周合并与月淘汰零应用层调用。

#### ★ 己1 · session 日志系统 —— 轨迹的记录能力

**1）持久化载体**

| 载体                                                | 位置                         | 内容                                                                                                                                                                          |
| ------------------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessions` 表                                      | 会话库 `.db`（sqlx SQLite，WAL） | id · system_prompt · created_at · message_count · updated_at · title · pinned · kind · router_enabled（**已废弃，仅物理保留**）· plan · workdir · workspace_id · project_id · scene_id |
| `messages` 表                                      | 同上                         | `(session_id, seq, msg_json)`，整条 `OrchestratorMessage` 的 JSON（crates/agent-commands/src/session_store.rs:284-294）                                                           |
| `group_chat_sessions` / `workdirs` / `workspaces` | 同上                         | 群聊参与者映射 / 目录实体 / 工作区实体                                                                                                                                                      |
| 编排事件                                              | **另一套存储**                  | `RunStore`（crates/agent-commands/src/run_store.rs）—— run\_*、路由决策、交接产物                                                                                                       |
| 动作段事件                                             | **不是独立日志**                 | merge 进「最后一条 assistant 消息」的 `meta.action_events`（crates/agent-commands/src/lib.rs:3240-3250）                                                                                |

**2）消息模型只有 4 种 role**（crates/agent-kernel/src/types.rs:93-98）：`User` / `Assistant` / `ToolResult` / `System`。  
`thinking` 存在 `meta.thinking`（crates/agent-kernel/src/agent/mod.rs:920-925），**不进 LLM 上下文**。

**3）落盘粒度逐项核实**

| 内容                         | 是否落盘 | 载体                                | 是否截断                                                                     |
| -------------------------- | ---- | --------------------------------- | ------------------------------------------------------------------------ |
| user 消息                    | ✅    | messages.msg_json                 | 无（但注入 `[时间戳]` 前缀，mod.rs:580-587）                                         |
| assistant 正文               | ✅    | messages.msg_json                 | 无                                                                        |
| thinking 推理                | ✅    | messages.meta.thinking            | 无                                                                        |
| `tool_call`（名称 + **参数原文**） | ✅    | messages.tool_calls               | 无上限（截断只作用于结果）                                                            |
| `tool_result`              | ✅    | messages（ToolResult）              | ⚠ **入库前截断 12 000 字节**（crates/agent-kernel/src/agent/tools.rs:53-70）——**2026-09-11 起改为保头 3/5 + 保尾 2/5**（原为只保头部，见己1③） |
| 计划步骤 / 待办项                 | ✅    | sessions.plan 单列（JSON）            | 无                                                                        |
| 动作段事件                      | ✅    | 最后 assistant 的 meta.action_events | 无（但**异常中断不落库**，待测试清单已登记）                                                 |
| 编排事件（run\_*）               | ✅    | RunStore（另一库）                     | —                                                                        |
| 错误与重试                      | ❌    | **未见专用载体**                        | —                                                                        |

**4）三条硬结论**

- **不能凭落盘数据完整回放会话轨迹。** 三处内容不可恢复：  
  ① **tool_result 超 12 000 字节 → 尾部永久丢失**。截断发生在**入库前**（dsh §6.3 已证），即原始内容**从未进入过任何存储**。  
  ② **被裁历史 → 物理删除**（`replace_messages` 全量替换，见丙2 回写修正）。  
  ③ **归档的「记忆」不含工具交互**——`record_turn` 构造 `MessageTurn` 时 `tool_calls: Vec::new()`、`thinking: None`、`attachments` / `file_changes` 全空（crates/agent-memory/src/lib.rs:260-283），`load_chunk` 还原时只产出 user / assistant 两条纯文本（:299-319）。
- **`messages` 表是「可变快照」，不是「事件日志」。** 每次持久化整体重写历史 → **全仓没有 append-only 事件溯源能力**。
- **`raw_contexts` / `session_meta` / `raw_context_path` 不是"设计占位"，是未接线的既有能力。** vendor 里躺着**完整的「压缩前保存原文」机制**：
  - `Storage::write_raw_context` / `read_raw_context`（crates/vendor/memory-center-core/src/sqlite.rs:1077-1155，落 `raw_contexts` 表）
  - `memories.raw_context_path` 列（:138-160）
  - `context_parser.rs` —— 把 pre_compress_hook 收到的 `full_context` 解析成 `Vec<MessageTurn>`
  - `Archiver` 的 hook_id 对齐 API（vendor/memory-center-core-logic/src/archive.rs:74-76 / 151-153 / 297）
  - 用途注释写明：「在 Trae 客户端压缩上下文前，由 **pre_compress_hook** 将**完整原始上下文**」持久化（vendor/memory-center-core-logic/src/storage.rs:480-482）
  - **全仓零应用层调用**（grep 仅命中 vendor 自身与其测试）→ 修复不是从零造，而是**接线 + 补一个 pre-compress 触发点**。

**5）需裁定**

- ① **轨迹的目标保真度**：要求原文永久保留（含 tool_result 全文），还是接受"截断 + 不可回溯"？
- ② 若要求原文：**接线 vendor 的 `raw_contexts`**，还是另立 session 级 append-only 日志？
- ③ ~~`TOOL_RESULT_STR_LIMIT` 现为**保头不保尾**（:57-70）——正文细节常在尾部，是否改**保头 + 保尾**（dsh 阶段 D 主张）？~~ ✅ **已施工（2026-09-11）**：改为保头（3/5）+ 保尾（2/5），中段省略并标注省略字节数，仍在 UTF-8 字符边界切分。原文本**仍不可恢复**（截断在入库前），但尾部结论不再丢失。

#### ★ 己2 · 上下文压缩系统 —— 必须保留的上下文类型

**1）唯一自动裁剪点：`enforce_context_budget`（crates/agent-kernel/src/agent/mod.rs:745-792）**

- 判据 = 逐条累加 `content.len() + 32` 超 **160 000 字节**（量纲错误，见丙1）
- 算法 = **从头部逐条丢弃**，保留最近 12 条；`trim_context` 同步 state + backend（crates/agent-kernel/src/agent/interaction.rs:69-87）
- **不看 role、不看类型、不留痕**；配对保护已于 **2026-09-11 施工**（见己2②）——**类型化保留规则：仍然完全没有**。
- **预算口径漏算 `system_prompt_override` 体积**：判据只累加 `state.messages` 的字节，而系统提示词 / 记忆注入 / 规则拼接 / 管线指引每轮经 `build_prompt_options` 重拼为 `system_prompt_override`（crates/agent-kernel/src/agent/memory.rs:84-150），**不计入预算** → 真实窗口占用被系统性低估（与规则体系文档 L63「规则段是否计入预算」悬置项同源）。

**2）关键三问的答案**（本条核心）

| #  | 问题                                 | 答案                                                                                                                                                                                                                                                   |
| -- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①  | 系统提示词与记忆注入会被裁吗？                    | **不会被裁，但它们根本不在 messages 里。** `build_prompt_options`（crates/agent-kernel/src/agent/memory.rs:84-166）把 scenario_prompt + `config.system_prompt` + memory_context + pipeline_context 拼成 `system_prompt_override`，**独立于 messages 数组逐轮传入** → 记忆注入天然免受裁剪   |

**5·补）压缩的用户可见性现状（己2④ 的前置事实）**

  - TS `ShortTermMemoryHelper.estimateTokens`（字符 × 0.25）@ packages/agent-core/src/orchestrator/short-term-memory.ts:66-78 —— 量纲对，但系数与上一处不一致

> ### 🔴 量纲冲突（2026-09-11 核出，**必须先解**）
>
> 把「四层阶梯按窗口比例」与「MemoryCenter 归档阈值按比例」叠在一起，出现**两条硬冲突**：
>
> | 项 | 占窗口比例 | 与 MemoryCenter 归档机制的关系 |
> |---|---|---|
> | MemoryCenter 归档阈值（内置 15 型号专家区间） | **0.20 – 0.50** | — |
> | MemoryCenter 归档**协商硬上限** | **0.80**（`min(threshold, window × 0.8)`） | — |
> | 第一层 Snip | **0.60** | ✅ 可达，但**已高于归档阈值区间**（0.20–0.50） |
> | 第二层 MicroCompact | **0.75** | ⚠ 仅落 0.75–0.80 窄带内可达 |
> | 第三层 Collapse | **0.85** | ❌ **超过 0.80 上限 → 永不触发** |
> | 第四层 AutoCompact | **0.95** | ❌ **超过 0.80 上限 → 永不触发** |
>
> **冲突一 · 时序矛盾**：归档阈值（0.20–0.50）**低于所有压缩层**（0.60–0.95）。若按「① 完整归档 → ② 四层压缩」执行，归档会先发生并清空上下文，**四层永远够不到**。
>
> **冲突二 · 死结**：第三、四层（0.85 / 0.95）**高于 MemoryCenter 的 0.80 协商上限**，即使在「先压缩、后归档」的时序下也**触发不了**。
>
> **按你 PS 描述的时序（「在后三层执行后……达到归档阈值后，才最终完整归档将上下文清空」），正解是**：
> - **归档比率必须设在最高压缩层之上**（> 0.95，例如 0.97）——即「阶梯在下、归档在最顶」；
> - **必须显式取消或上移 MemoryCenter 的 0.80 协商上限**（`token-system-roadmap-v2.54.md:314-316` 的 `model_ceiling = context_window × 0.8`），否则上面两层失效。
>
> **⚠ 这两条都是对上游既有参数的「主动偏离」**：归档比率 >0.95 已超出 MemoryCenter 的 0.20–0.50 专家区间，0.80 上限也要被覆盖。**需你确认接受这一偏离**（我倾向接受——理由：归档是"沉淀+清空"的兜底动作，压缩是"手术式腾挪"；让归档兜在最顶、压缩先行，才符合你 PS 的时序与 Claude Code 的实践）。
>
> **另一条已知的上游缺陷需引以为戒**：WorldSea 必须保证**阈值单一来源**——上游曾出现 `get_archive_threshold` 兜底 120K 而 `ArchiveConfig::default()` 兜底 400K 的**反馈断裂**（LLM 建议归档、Archiver 不触发），已修（`token-system-roadmap-v2.54.md:142-149/176-177`）。
>
> **③ 「预填充」机制在 MemoryCenter 不存在，但你的直觉有真实先例——在 Claude Code 里。**
> - MemoryCenter grep `prefill` / `预填充` → **0 命中**；`位置链接 / 落位 / 坐标`（技术义）→ **0 命中**。
> - MemoryCenter 的真实机制是 **`pre_compress_hook` 双轨归档**：一处是 raw_context 全文，一处是解析出的 turns；两者靠 **`hook_id`（UUID v4）** 关联——raw_context 落 `sessions/{session_id}/raw_contexts/{hook_id}.txt` 并回写 `IndexHook.raw_context_path`（`crates/memory-center-mcp/src/lib.rs:2662-2665`、`crates/memory-center-core/src/storage.rs:842-853`）。**定位靠 UUID，不是位置坐标**；且 raw_context 是**一次性完整写入**，**没有「先留空容器位、后顺序回填」的两阶段机制**。
> - **但你描述的那套确实存在——在 Claude Code**：**Snip「用一个占位符替换旧工具结果内容」**（纯本地、零 API），而 **Context Collapse 更关键：「读时投影（read-time projection）——原始消息**永不修改**，折叠决策记在一份独立 commit log 里，每次读时重放」**，因此**可逆**且不失效 prompt cache。
> - → **你的「空容器位 + 顺序回填完整原文」在架构上成立，其权威先例是 Claude Code 的 Snip 占位符 + Context Collapse 读时投影**；MemoryCenter 无先例可搬。这条若要做，是**独立新设计**。
>
> **④ 归档与压缩的先后关系（按澄清重述）**
> - 「① MemoryCenter 理念内的**完整归档（阈值）**」→ **属实**（`archive` 达 `archive_threshold` 触发；另有 `pre_compress_hook` 压缩前完整归档）。
> - 「② **已归档后的四层压缩**」→ 按用户澄清，这是**要求 WorldSea 新增的一层**，不是对 MemoryCenter 现状的描述。就 MemoryCenter 现状而言：它归完档只做「**调用方从 LLM 上下文丢弃该批次**」（`crates/memory-center-core-logic/src/archive.rs:22`、`:227-228`），**不负责清空整个上下文、也不做四层压缩**。→ **四层压缩是 WorldSea 要补的那一段，落在 MemoryCenter 之外。**
> - 「交由 MemoryCenter 完成索引、钩子」→ **属实**（archive 时生成 `IndexHook` 并追加索引，`archive.rs:315-330`）。
>
> **⑦ 三者关系（按用户澄清修正本文档的表述）**
> 本文档此前把 MemoryCenter 表述为「权威源头」，**不准确**。正确关系是：

#### 丙2 · Compaction 压缩语义与恢复策略

- **现状**：[deepseek-harness-调研与借鉴方案.md](../misc/deepseek-harness-调研与借鉴方案.md) §六列出四个硬伤——① 裁剪是内存态头部硬丢弃、不持久不可回溯（L344-354）② 无 `tool_call` / `tool_result` 配对保护，切点可能落在两者之间（L356-370，真实 BUG 风险）③ 全链路无 token 计量（L372-376）④ 阈值标记为占位待定（L378-387）。方案提出阶段 A-D 四步（L422-474）。

> **⚠ 回写修正（2026-09-11 代码取证）**：硬伤 ① 的**后半段与代码实况不符**，须更新本文档作为丙2 的方案基线。
>
> 原文称「裁剪只动内存不持久化 → `session_store` 里的历史不会被同步裁剪 → 刷新页面回源后，被裁掉的旧消息又完整回来了」。
>
> **实况：链路是写穿的。** `run()` 内 AfterRun 裁剪 → `run()` 返回 → 广播 `AgentEnd`（crates/agent-kernel/src/agent/mod.rs:627 / 634）→ Tauri 侧 `flush_buffered_action_events`（apps/tauri/src-tauri/src/commands.rs:321-325）→ `flush_action_events` → `persist_messages`（crates/agent-commands/src/lib.rs:3240-3250）→ `store.replace_messages`（:3217-3233）。而 `replace_messages` 是**全量替换**（`DELETE FROM messages WHERE session_id` + 逐条 INSERT，crates/agent-commands/src/session_store.rs:509-525）。
>
> **实际后果比 dsh 描述的更严重**：被裁消息**被物理删除**，刷新后不会回来，而且**不可恢复**。
>
> **对方案的影响**：阶段 B 的必要性反而更强——原表述像是在防"复活"，实际要解决的是"**把可变快照改成不可变追加**"。详见 己2。

- **选项**：
  - ① 只做阶段 A 止血（配对保护 + 裁剪同步持久化）
  - ② 阶段 A + B（引入 `replace` 语义：在不可变事件日志上追加 replace 记录，而非删历史）
  - ③ 全量 A-D
- **建议**：**②**。其一是硬伤 ② 是**当前真实的 400 错误风险**，属 P0；其二是 B 的「replace 语义」与甲1 的四操作同源，一起做省一次返工。
- **待你另定的 3 个风险点**（dsh §九 L478-487）：
  - **R3**：阶段 B 会让会话出现"检查点"消息，**前端如何呈现需你定**
  - **R4**：触发时机从 AfterRun 挪到派生前（影响 `RunPhase` 语义，**架构变更需确认**）
  - **R5**：阶段 C 需模型 `context_window` 声明（涉及 `ProviderConfig` 数据结构变更，**需确认**）
- **影响面**：解锁 WORKSTREAMS 的「Compaction 施工」下游线；R4 触及编排运行时骨架，建议单独拉一条施工项。
- **用户选择**：② 阶段 A + B（引入 `replace` 语义：在不可变事件日志上追加 replace 记录，而非删历史）
- **用户留言**：**R3**：前端尚未做session日志(历史)的面板，或许需要后续立项；如果是对话流中的，则增加一个行段？**R4**：确认；**R5**：确认；
