status: 执行中（2026-10-02 复核通过；批次 1a 地基段已落＝见 §七，1a 余下段与 1b/2 待续）

> （同类型共享，`__customFieldDefs` 停止写入并退役）；⑪ **`multiSelect` / `tags` 落库为数组存 `properties`**，
> 与 Rust `validate/entity.rs:149-200` 的 `"multi-select"` 分支对齐（`tags` 仍走实体顶层 `tags`）。

> 用户提案（2026-10-02）：工作台侧**实体类芽的详情页**两条方向——① 优化现有实体详情表单（现状右栏抽屉）
> ② 新增实体详情表单的**形态种类**（多类可配置）。范围非全部芽（部分芽不涉实体）。
>
> 八项裁定（AskUserQuestion）：
> ① **分工＝我连做两方向**，切成三批（1a 地基 → 1b 内容形态 → 2 载体形态），每批独立走查；
> ② **架构＝B**，详情段从 GEV 外移为**载体无关的 `EntityDetailForm`**；
> ③ **编辑态三轨→行内单轨**（允许改变操作路径）；
> ④ **首批痛点＝四项全含**（静默降级 / 无分组找不到字段 / 四套实现收敛为一 / 关系区三套重叠），
>    但**关系区「需慎重」**→ 本批只出事实清单，不动结构；
> ⑤ **配置权＝芽声明默认 + 用户按实体类型覆写落盘 + 设置面板加配置项**；
> ⑥ **范围＝只统一 GEV/SchemaRenderer 面**（9 个子视图硬编码 detail 卡、Graph/战术板自有面板不动）；
> ⑦ **载体首批＝栏式整页 / 沉浸页 / 居中弹层 / 浮层小窗全要**，但可分批落；
> ⑧ **缺省载体＝抽屉**（未声明的芽零行为变化）。

## 一、动机

详情页是产品域使用频次最高的面（18 个实体芽全靠它承载「看一个设定」），但它的实现现状是
**四套字段控件 + 两条写路径 + 零配置消费**，导致「字段读不准、字段找不到、改一处要改四处」。
ROADMAP §三.7「18 个实体类插件的实体详情优化」正待启动，且明写「需先确定统一的设计规范再逐个优化」
（该文引用的 `src/ui/entity/InfoPanel.vue` 等路径是旧 Web 时代，已失效）。

## 三、设计

### 3.1 两级形态模型（共用同一内容件）

| 级 | 含义 | 取值 | 落批 |
|---|---|---|---|
| **L1 载体形态** | 详情装在哪种容器、占多大空间、怎么进出 | 右栏抽屉（保底 / 全局默认）· 栏式整页 · 居中弹层 · 沉浸页 · 浮层小窗 | 批次 2 |
| **L2 内容形态** | 同一份字段数据在容器里怎么编排 | 分组式（默认）· 表格式 · 段落式（文档型）· 卡片摘要式 · 时间轴式 | 批次 1b |

两级都挂在 **`EntityDetailForm`（载体无关内容件）** 上：换容器不动编排，换编排不动容器。

### 3.2 字段控件层（批次 1a 的地基）

```ts
// packages/plugin-sdk/src/detail/fieldType.ts —— 命名漂移的唯一吸收点（不改 Rust schema）
export type NormalizedFieldType =
  | 'text' | 'textarea' | 'number' | 'boolean' | 'date' | 'select' | 'multiSelect'
  | 'tags' | 'color' | 'image' | 'entityRef' | 'formula' | 'url' | 'email'
export function normalizeFieldType(raw: string): NormalizedFieldType   // 别名表 + 未知类型显式标记（不得静默转 text）

// packages/plugin-sdk/src/detail/fieldControls.ts
export interface FieldControlDef {
  type: NormalizedFieldType
  view?: Component        // 只读态（缺省回落到 edit 的 disabled 形态）
  edit: Component         // 编辑态
  fullWidth?: boolean     // 取代 DetailField.vue:187 的本地 FULL_WIDTH_TYPES
}
```

`entityRef` 的 view 态**必须**显示实体名并可点跳转（这条单独立测，正对 2.2 的裸 ID 缺陷）。

### 3.3 详情布局层与配置合并

```ts
// packages/plugin-sdk/src/detail/detailLayout.ts（纯函数，可单测）
export interface DetailGroup { key: string; label: string; fieldKeys: string[] }
export interface DetailLayout {
  groups: DetailGroup[]        // 未分组的字段自动归入「其它」
  order: string[]              // 字段顺序
  hidden: string[]             // 可见性
  contentForm: string          // L2 形态 id（批次 1b 起有实效）
}
export function mergeLayout(sproutDefault, userOverride, liveState): DetailLayout  // 三级合并，后者覆盖前者
```

持久化（**不进实体 `properties`**）：

| 键 | 形状 | 批次 |
|---|---|---|
| `worldsea_detail_layouts` | `Record<entityType, Partial<DetailLayout>>` | 1a |
| `worldsea_detail_carriers` | `Record<entityType, carrierId>` | 2 |

与 `worldsea_field_orders` **分键**（弹窗预设语义不受扰动）；自定义字段改走**类型级 `fieldRegistry`**
（裁定 ⑩：`addUserField/removeField/setOrder`，同类型共享，落 `worldsea_field_registry`），
`properties.__customFieldDefs` 停止写入并退役（裁定 ⑩；WorldSea 无在用用户，零迁移成本）。

### 3.4 编辑态收敛为行内单轨

- 抽屉：`✏️ 全局编辑` 与 `双击单字段` 合并为**同一套行内机制**（共用 `useEntityEdit` 的 `editForm/saveEdit`），保存写路径全仓唯一。
- 弹窗 `EntityFormModal`：**只承担新建**（含模板预填）——解除 `editingEntity` 的「预填新建 / 编辑存量」双义（见 §2.1 末），
  编辑存量实体的唯一入口归抽屉。
- 弹窗独有的「字段预设拖拽排序」（`useFieldPresets.ts:88-120`）在抽屉侧以布局层承接（见 §六 风险点 3）。

删件 + `Shell.vue:22,53` 挂载 + `ui-kit/index.ts:52,168` 导出 + `docs/details/架构/快捷键系统.md:47,132,137` 三处提及
+ `architecture-baseline.json:71` 条目（属减行，按实况更新并逐条解释）。
