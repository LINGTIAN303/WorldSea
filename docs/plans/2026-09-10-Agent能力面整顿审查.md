## 一、背景与范围

对 Agent 能力面做系统性体检。**概念修正（2026-09-10 用户澄清）**：项目内现存的"世界观插件"（entity-core PluginAPI 体系 + 26 个内置业务模块桥）是**内置工具系统中的一环**，不属于本文所指的"插件系统"；真正的 **Agent 插件系统**（能力打包/分发/安装层）**尚未开始**，本章基于外部参照给出立项坐标系。

| 模块 | 载体 | 一句话定性 |
|------|------|-----------|
| Skills | crates/worldsea-skills-store + packages/agent-runtime/src/skills | 前端重后端轻（Rust 仅文件搬运，schema/执行全在 TS） |
| MCP | crates/agent-kernel/src/mcp.rs + apps/tauri/src-tauri/src/mcp_client.rs | 后端重前端轻（rmcp 完整，UI 极简） |
| 内置工具（含世界观插件体系） | crates/agent-kernel/src/tool.rs + agent-commands 工具实现 + 前端 ALL_TOOLS_MAP；世界观插件 = entity-core PluginAPI + plugin-tools 26 模块桥 | 双栈缝合（一半 Rust 原生、一半前端执行，FrontendToolBridge 缝合）；世界观插件是其中"数据域/视图扩展"一环 |
| **Agent 插件系统（未开始）** | 无代码 | 能力打包与分发层：将 Skills / Agents / Hooks / MCP servers 等打包为可安装、可版本化、可跨场景分发的扩展包——外部生态已收敛出开放标准（Agent Plugins 1.0.0），本项目尚无任何对应物 |

> 注：外部 trae-remote-official 20+ 插件为 IDE 端插件（skill/命令/agent/MCP 打包形态），恰是 Agent 插件系统的现实范例之一，可作为形态参照但非本项目代码。

## 二、总体判断

四大已实现能力面目前是**三套各自为政的小系统 + 一个空缺**（Skills / MCP / 内置工具各自成岛，Agent 插件系统整体缺位）：概念文档层面边界清晰（Skill=能力包 / Tool=原子操作 / MCP=外部工具源 / **Plugin=打包分发层**），但代码层主要靠命名约定维系，无统一 capability provider 抽象。核心债务集中在三类：

1. **双份维护会漂移**——schema/标签/别名/权限在前后端各存一份，靠人工对齐
2. **死代码与残留**——旧结构、测试残留、断线路径未清
3. **同一概念多处命名**——"插件"一词多义并存且正面临第五义（真 Agent 插件）入场压力，ToolBus 双语义，agent-runtime 同名异构

| **pi Agent 扩展系统**（设计文章） | 契约接口 + IoC/DI + 适配器 + 事件驱动；Hook（扩展功能，返回值被忽略，无序）与 Interceptor（控制流，可短路，有序）分离；两阶段初始化 + 哨兵函数（加载期调用未就绪能力→显式报错）；插件崩溃不伤核心与其他插件；热重载 | 运行时宿主侧的设计原则，尤其"崩溃隔离 + 两阶段初始化"对桌面单二进制应用直接适用 |
| **Agent 运行时容器与插件机制设计**（CSDN 系列文） | 插件系统五要素：动态注册 / 能力声明（类型·输入输出·权限）/ 版本控制（多版本共存）/ 安全隔离（运行路径受限·防注入）/ trace 可控（执行行为全落 trace） | 验收维度 checklist，可直接当设计评审清单用 |

**与四能力面的关系（目标态）**：插件系统是**打包分发层**，不是新的能力类型——把 Skills（已有）+ MCP 配置（已有）+ Agents/编排模板 + Hooks（未开始）打包成一个可版本化分发的单元。WorldSea 现有资产与标准的对应：skills-store≈skills/ 分发通道（缺 manifest 聚合）、mcp.json≈.mcp.json 组件位、场景 Scenario≈预置插件组合的静态硬编码版（scenario.rs 硬编码 builtin_skills 正是"没有插件层导致场景只能硬编码组合能力"的症状）。
