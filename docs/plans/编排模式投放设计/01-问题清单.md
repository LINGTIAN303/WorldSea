### 议题一：前端体验研究 —— 样式、交互、形态、体验

> 起步问题："前端该长什么样、用户该获得什么体验"本身是待研究的开放题，先把它拆成可探索的子面；每条是研究问题而非解答，讨论中持续追加。

#### 形态域（信息如何组织）

- **A0-1** 编排过程信息与"对话流"的关系：同一消息流内嵌（编排段作为特殊消息）vs 附着右侧独立面板 vs 二者分层？主对话区承担多少过程信息的底线（消息流宽度/阅读动线约束）？（已定案 2026-08-27，随 A2/A3：**对话流内嵌编排段**为主（一次请求一个编排段，特殊消息单元）；右侧面板承载详图（A4/A0-6 细化）；主对话区底线 = 只放迹线（索引级）不放详图（内容级）——分层原则 = 迹线在流内、详图在侧栏）
- **A0-2** 叙事形态：一次请求的"处理故事"是否应成为一条完整的视觉叙事线（请求 → 处理轨迹 → 结论）？与当前"面板承载过程、对话承载结论"的现状相比，叙事线是否会重建用户心智？（D21 定案：叙事定调为阶段推进——请求→判型→阶段链→结论，树段收为入口卡）
- **A0-3** 过程信息的生命周期：轨迹何时展开、何时收拢、是否可回看？折叠态保留什么信息（阶段摘要？最终任务流？），展开态再提供什么？（已定案 2026-08-27，C20 分级透明 + 03 参照 §三.4 时态规则：**运行中逐步展开、完成后自动收拢为折叠任务流 + 最终输出、历史可重新展开**（符合用户一贯展示偏好：任务流逐步渲染、最终折叠、不丢弃中间结论）；折叠态保留 = 判型结论 + 阶段摘要行 + 统计（N 步骤/M 工具/耗时，Cursor 范式）；展开态提供 = 阶段详情 + 物摘要 + 详图入口；跨态一致且可持久化（反模式 7）——展开状态记入会话视图状态）

#### 交互域（用户如何操作"过程"）

- **A0-4** 用户与"过程"的交互层级：仅观看（只读轨迹）vs 可操作（展开/折叠/暂停/中止/重跑）vs 可干预（指定下一步/回退）。各级的实现成本与体验收益边界在哪？（已定案 2026-08-27，随 A5/D21：v1 = 观看 + 可操作（展开/折叠/中止/插话）；可干预（指定下一步/回退/重跑指定步骤）= v2+ 门机制与步骤级状态机；收益边界 = 中止保命、插话纠偏已覆盖 80% 干预需求，步骤级干预是"把控"能力单独设计）
- **A0-5** 展开/折叠的触发语义：自动展开（有过程就展开）vs 默认折叠（有摘要即可）vs 惯性响应？触发是否可配置？（已定案 2026-08-27：**运行中自动展开 + 完成后自动收拢 + 手动选择优先**——运行中实时看到阶段推进（ChatGPT Activity 模式），完成后收拢为折叠任务流（A0-3 时态规则）；用户手动展开/收拢优先于自动（记忆用户选择至会话视图状态，反模式 7 跨态一致）；不做设置项（触发语义由编排事实驱动，无需配置面））
- **A0-6** 复杂视图（树/图/黑板）的承载形态：浮层 / 右侧抽屉 / 独立页 / 嵌套在轨迹内可滚区域？与现有面板组件的复用程度（而不是重写）决定了成本量级。（已定案 2026-08-27：**右栏面板驱动**——复用现有右栏 ExecPanel 区域，从"11 个平行 tab 手动切换"改为"迹线驱动"：点击迹线入口卡 → 右栏自动切到对应详图（ThoughtTree / 黑板 / 子 run 树）；组件零重写（OrchestratorPanel/MultiAgentPanel 已事件驱动），心智从"挑面板"变"点迹线"；现有 tab 保留为过渡期直达入口（散点已列，遥测后定去留））
- **A0-7** 可访问性与键盘可达：项目硬约束（可点击元素需 role/tabindex/键盘事件）投影到 SVG 树/图/黑板这类非 DOM 图形上的成本？复杂图形是否有简化交互路径（如仅关键节点可聚焦）？（已倾向 2026-08-27：**关键节点可聚焦的简化路径**——SVG 图形不整体键盘可达（成本爆炸），聚焦单元 = 迹线阶段卡（DOM，全键盘可达）+ 详图内关键节点（最优路径/当前活跃节点，tabindex + Enter 展开详情）；整图浏览靠鼠标/触摸，键盘用户经迹线摘要 + 关键节点详情获得等价信息——与项目"可点击元素键盘可达"约束的合规落地（聚焦单元均为 DOM 元素））

#### 样式域（视觉语言）

> 2026-08-27 收敛注记：本域四条属"实现细节可自主"边界（不改用户操作路径，只改呈现），按决策边界规则给倾向后由实现期自主落定。

- **A0-8** 视觉语言统一性：现有极简基调（三区布局、双线分隔、克制动效）与"过程可视化"所需的信息密度之间如何调和——是扩展现有语言（加图形元素但保持气质）还是引入新的图形子系统（树/图节点样式与对话气泡并存的规则）？（已倾向 2026-08-27：**扩展现有语言**——树/图/黑板组件沿用三区布局 + 双线分隔 + 克制动效规则，图形元素（节点/连线/评分色）作为新元素融入而非新子系统；依据：03 参照 §一.1（Claude 迹线行 + 折叠块与对话流同语言）+ 现有 ThoughtTree 已验证可行）
- **A0-9** 信息密度分层：索引级（轨迹）与内容级（详图）在字号/线宽/留白/色彩上的差异如何表达，使"可扫读"与"可深读"不互相干扰？（已倾向 2026-08-27：迹线 = 索引级视觉（单行阶段摘要 + 状态点 + 统计，12-13px）；详图 = 内容级视觉（完整树/图/黑板，正常字号）；干扰隔离靠 A0-1 分层承载（迹线在流内窄、详图在侧栏宽）而非同区域内调字号）
- **A0-10** 时序与状态的可视化语言：进度用时间轴 / 瀑布 / 步骤卡哪种？状态（运行中/成功/失败/降级/等待）用色、形、还是图标表达（项目禁 emoji 图标，需 SVG 或图标库）？流转中的视觉动效阈值（避免闪动/跳动，perf-kit 动效克制约束）。（已倾向 2026-08-27：**纵向步骤卡序列**（与"阶段推进"叙事同构，TracePanel 现状即雏形）；状态 = 状态点（色）+ WsIcon（形）双编码（运行中=旋转环/成功=对/失败=叉/降级=下箭头/等待=时钟，色弱化形主担纲——色盲可辨）；动效 = 仅状态点流转 + 新阶段滑入（200ms 内），无全卡动效——perf-kit 克制约束）
- **A0-11** 主题适配成本：树/图/黑板等图形组件在深色/浅色两套主题下的可读性维护成本；是否约束图形组件的用色集（与编排迹线同一 token 体系）。（已倾向 2026-08-27：**图形用色入 token 体系**（评分色阶/状态色/连线色定义为 CSS 变量，随 data-theme 切换）；单一定义点 + 两主题各调一版色值；禁止图形组件内写死颜色——与现有主题系统统一三态控制约束一致）

#### 体验域（用户获得什么感受）

- **A0-12** 过程透明度上限：把轨迹完全交给用户是"可审计的诚实"还是"认知负担"？哪些信息适合直接呈现、哪些应折叠到"详情"里？透明与无感之间的灰区如何切（快问答完全无感 vs 复杂任务透明，阈值怎么定）？（已定案 2026-08-27，C20 锁定：**分级透明——透明度跟随实际发生的编排量**；阈值 = run 形状自动定（退化 run 无感不渲染编排段 / 单链编排段默认折叠态起步 / 深水区收为入口卡）；不靠用户设置，靠编排事实驱动（03 §四.4：呈现由"是否实际发生编排"驱动）；认知负担防线 = A0-1 分层（详图永不进对话流）+ A0-3 折叠统计行）
- **A0-13** 长管线的等待感管理：多步委派/深水区探索耗时较长，用户期待管理靠什么（阶段标签 / 进度提示 / 当前子任务名 / 中途摘要）？是否有 ETA 或百分比的空间（无可靠预估时不承诺）？（已定案 2026-08-27，03 参照 §三.3 + D0-24 联动：**可预测性四件套**——① 迹线阶段卡实时推进（当前阶段高亮 = 进度感）② 阶段内"已学到 + 下一步"双行叙事（Gemini 范式，折叠态内容模板）③ 子 run 名 + 耗时（委派可见"谁在干什么多久了"，B22 子 run 数据）④ 统计行（N/M 步骤）；不做 ETA/百分比（无可靠预估不承诺，D0-24 同则））
- **A0-14** 出错的体验口径：失败/降级以什么语态、什么位置呈现（轨迹内标灰 + 一句原因 vs 弹窗）？是否给"重试/换一种方式"？用户被中断的认知如何衔接。（已定案 2026-08-27，随 B9/D23/B0-4：**迹线内呈现，永不弹窗**——失败/降级 = 阶段卡状态点变红/降级色 + 一句原因（物 summary 数据源）；部分进度可见保留（"10 步做了 7 步显示那 7 步"，03 §三.6 错误透明四要素）；出口永远给路——命令覆盖提示（"用 /plan 重试"类引导文案）；无中断突袭（降级物可见 = 认知衔接））
- **A0-15** 新手与老手：默认形态偏向哪类用户？（新用户需要理解"为什么这样处理"；老用户要快捷键/命令直达）。默认体验与高级入口的平衡。（已定案 2026-08-27，随 A1：**默认形态即新手形态**——自动判型零学习成本（新手无需理解"为什么这样处理"，迹线首段的判型理由自解释）；老手入口 = `/` 命令菜单（A1）+ 迹线快速浏览；无新手/老手模式切换（自动为主模型天然兼容两类））
- **A0-16** 沉默期与首次印象：用户第一次看到轨迹时的第一眼（首屏该有什么）与使用三天后的形态是否需要不同？初始引导的必要性。（已定案 2026-08-27：**无引导 + 首次弱提示**——首屏 = 干净对话流（快问答无感即首印象，产品性格从第一次交互就是"它自己会安排"）；不做初始引导弹层（与极简基调冲突）；迹线首次出现时编排段头部附一行弱提示（"这是你的请求被处理的过程，点击可展开"）仅首次显示（localStorage 记忆）——弱提示符合 UI 反馈偏好；三天后形态 = 同一形态（无新手期特殊态，分级透明自动适配任务复杂度））

#### 参照与基准域（用什么验证"好"）

- **A0-17** 基准任务集：选取哪些"表示性任务"作为体验走查基准（如 快问答 / 规划型 / 委派型 / 探索型 各一条），用它们检验形态是否成立？（已定案 2026-08-27，随 E19/C0-20：基准任务 = **五条覆盖四链族**——① 快问答（Query 退化 run 无感验证）② 规划型（Research/Compose 链：计划→执行→评审全迹线）③ 委派型（Supervisor 链：子 run 树可视化）④ 探索型（ToT 链：入口卡 + 详图）⑤ 降级路径（ToT 超时→Degraded 物可见）——与 E19 验证基准五条一一对应）
- **A0-18** 竞品参照：主流产品的过程可视化形态（对话式 AI 的画布/工件、编码助手的 Agent 视图、各家的思维链展开）中，哪些形态值得借鉴、哪些暴露了反模式（信息过载/剧场感）需要避免？（已完成 2026-08-27 → [03-外部参照.md](03-外部参照.md)：7 产品形态卡 + 12 反模式 + 8 设计原则；本清单后续引用均指向该文档）

### 议题二：后端运行研究 —— 运行、次数、决策、边界、职责、时态、稳定

> 起步问题："后端以什么姿态运行、对什么负责、如何形成稳定"是开放题；按用户给出的七个关键词拆为研究子面（以下每条是研究问题，非解答）。

#### 运行域（执行如何组织）

- **B0-2** 宿主与循环的驱动关系：图宿主（DefaultOrchestrator）与 AgentLoop（ReAct）谁驱动谁？同 run 内节点并发（ToT 分支 / 黑板多 Agent）与跨 run 并发的边界在哪，现有 mpsc/锁模型是否够用。（B22 定案：并发分三层——顶层 run 串行 / 节点内并发随节点语义 / 子 run 树账本嵌套）
- **B0-3** 生命周期与中止：run 的完整状态出口（出生/完结/中断/超时/重入）；用户中止如何穿透到最深的子任务/委派；孤儿 run（会话删除、进程重启、前端关闭）如何收敛。（B22 定案：五出口状态机 + abort 递归穿透 run 树；孤儿 run = 重启蒸发）

#### 次数域（量的语义与治理）

- **B0-4** 次数清单与统一定义：迭代上限、ReAct 轮次、ToT beam/深度、MultiAgent 轮次、Refine 迭代、委派深度、重试次数——各自约束什么，超限的统一语义（弃权 / 降级 / 报错）是否应一致。（已定案 2026-08-27：**超限 = 正常收敛的一种**——run 出口 Completed + reason=limit_reached + 当前最优/部分结果；只有不可恢复故障才是 Error；ToT/MultiAgent 现状语义即规范，**编排器超限报 Error 属 v1 顺手修项**；亦为 D0-4 收敛谱系给框架——收敛原因枚举 goal_reached / threshold_met / limit_reached / no_progress / aborted / degraded）
- **B0-5** 次数来源与用户干预：次数在静态配置还是请求级声明里？"再试一次 / 加深探索 / 减小范围"等用户动作如何映射为次数变更。（已倾向 2026-08-27：静态默认 + 请求级覆盖 = 现状 options 机制即规范；用户干预 v1 = 命令覆盖重发（A1），参数级调整 v2）
- **B0-6** 资源预算：单 run 的 Token / LLM 调用次数是否有预算；超出是软提醒还是硬截断；与 Loop Engineering（限流/超时）如何缝合。（已定案 2026-08-27：**v1 不做 Token 预算**——LoopEng 的 turns/duration 限流已兜底，多供应商下 Token 计数不准；Token 超支防线 = 队列限流（已有）+ v2 预算系统一并设计）
- **B0-7** 重跑语义：同一请求重跑是全新 run 还是可续跑（检查点恢复）？重跑对记忆/会话状态的副作用如何隔离。（已倾向 2026-08-27：重跑 = 全新 run（旧 run 收拢、新 run 按指定形状重建，A1 判型可纠同机制）；重跑无记忆副作用（run 间独立，记忆归档按会话不按 run）；检查点续跑 v2（B22 快照 API 为种子））

#### 决策域（决策点与依据）

- **B0-8** 决策点全清单：判型（走哪条管线）、拆分（计划怎么切）、委派（给谁/任务怎么改写）、评审（几分合格）、回炉（重拆 or 精修）、降级（放弃探索）、兜底（默认行为）——各自是确定规则还是模型判断，哪些可被用户否决。（已倾向 2026-08-27：七类决策点全部留痕——载体 = D23 物（kind 载荷内含理由字段）+ run 决策记录（B22）；铁轨类决策（条件边 if）= 确定规则，判型/委派/评审 = 模型判断（D21 可变点定义）；可否决 = 门（v1 中止+插话，v2 批准/否决门））
- **B0-9** 决策留痕与改判：每个决策是否留痕（ID/输入/输出/理由）？用户能否事后改判（如强制重试/否定评审）？（已倾向 2026-08-27：留痕载体已定（D23 物 + B22 决策记录，含 ID/理由）；事后改判 v1 = 命令覆盖重发（A1 同机制），v2 = 门上否决 + 指定步骤重跑（依赖 A5 v2））
- **B0-10** 决策依据边界：模型判断的输入面（仅本请求上下文 vs 可读既往状态/记忆）；判错后的可纠正闭环（谁发现、谁负责修）。（已倾向 2026-08-27：判型可读会话上下文 + 记忆检索结果（A3 现状），判型过程不写记忆（无副作用，判型缓存仅驻请求级）；纠错闭环 = 理由迹线可见（用户发现）+ 命令覆盖（用户纠正），自动纠错不进 v1）

#### 边界域（职责划界）

- **B0-11** 前后端契约边界：事件模型之外，后端是否还承担"视图组装"（把原始结果拼成用户易读形态）？字段序列化（camelCase/时间格式）与契约版本演进规则。（已倾向 2026-08-27：后端供事实（物 + 事件，含 summary），前端做披露分级与视图组装（C20 锁定）；v1 后端不做视图组装（迹线拼装在前端，数据已够）；序列化规则实现期随 C13 前端模型一并定）
- **B0-12** 内核/模式/命令层边界复核：底座与扩展的违约现象是否清零；未来接入面（skills 插件等）的接口边界；Supervisor 双入口（图节点显式调度 vs 委派工具隐式委派）的决策归属是否需统一到一处。（已倾向 2026-08-27：[02-现状事实.md](02-现状事实.md) §九已证生产代码零跨模式违约（仅模式→shared 合法共享）；Supervisor 双入口保留（触发语义不同：显式调度 = 图节点、隐式委派 = delegate 工具，创建已统一收口 SubAgentPool）；skills 接口边界归 C 议题 C0-15/16 一并定）
- **B0-13** 数据边界：哪些状态驻内存、哪些落 SQLite、哪些仅经事件流瞬态？run 的轨迹是否持久化、归属会话级还是全局？（已定案 2026-08-27，钥匙推论：内存 = run 实体 + OrchestratorState（B22）；懒持久 SQLite = 交接物 + run 元数据（仅多阶段/深水区 run，表结构 v1.5 定）；瞬态 = 轨迹事件（迹线回看 v2 与持久化捆绑）；归属 = 会话级（run 树挂 session，D0-18 联动））

#### 时态域（时间与状态）

- **B0-14** 阶段状态与时序保证：管线阶段的状态定义与变迁规则；事件时序保证（先 phase_entered 后 phase_result？）与乱序/丢失的处理。（已倾向 2026-08-27：phase_entered → phase_result 严格配对（B7 事件族）；同 run 内事件有序——EventBroadcaster 同步 fan-out 天然保证（[02-现状事实.md](02-现状事实.md) §三）；乱序/丢失 v1 不处理（通道可靠，跨进程 WebSocket 断连属连接层重连问题非时序问题））
- **B0-15** 时间粒度与"长"的界定：单步/单段超时（现有 SoftTimeout）粒度；现有 LongTask 阈值是否适用管线级；"等待用户确认/工具挂起"期间的状态怎么表达。（已倾向 2026-08-27：沿用现有阈值体系（软超时 30min/2h + 看门狗 5min/30min + 管级 timeout_ms，[02-现状事实.md](02-现状事实.md) §五）；LongTask 阈值适用 run 级（run 本质是长任务）；门等待（v2 计划批准门）不计 run 时长——门实现时再细化）
- **B0-16** 一致性时态：事件流与最终落库的时序（前端看到的事件 vs 最终状态）；run 完成后事件还能否改写已展示的轨迹（回写边界）。（已定案 2026-08-27，钥匙推论（B22）：事件先落迹线（前端实时聚合）、run 终态后写会话消息（final_message）；完成后不改写已展示轨迹——迹线是 append-only 账本，纠错走新 run（B0-7 重跑语义））
- **B0-17** 历史与恢复：进程重启/会话重建对运行中 run 的时态归属（丢失 / 标记中断 / 可恢复）；"回到某阶段时间点"类需求的支持深度。（已定案 2026-08-27，钥匙推论（B22）：重启 = 运行中 run 蒸发（会话历史只剩消息，无回写）；"回到时间点"= v2+（迹线回看先做展示级重放，非执行级回滚））

#### 尽责域（对什么负责）

- **B0-18** 责任清单与免责：后端承诺什么（结果可信、长任务连续、故障可恢复、过程可解释、资源不耗尽），不承诺什么（模型幻觉、工具外部副作用、用户意图误读、对生成内容的保证）？责任边际如何被轨迹与降级显性化。（已定案 2026-08-27：**v1 三项承诺**——① 过程可解释（每个 run 有迹线：phase + 物 + 理由，E19-① 验收）② 长任务连续（LoopEng 兜底：超时/看门狗/重试，已有）③ 故障可见（降级必出物，D23，E19-② 验收）；**明确免责**：模型幻觉（内容质量）、工具外部副作用、意图误读（可纠但需用户确认）；**保证 vs 尽力**：链路完整性 = 保证（构图期校验可验证），内容质量 = 尽力而为）
- **B0-19** 承诺的可测化：每项承诺的验收/回归基准；"保证"与"尽力而为"如何区分并各自可验证。（已定案 2026-08-27，随 B0-18：三项承诺各配验收基准——可解释 → E19-①（三条真实任务迹线渲染正确）；连续 → LoopEng 现有测试；可见 → E19-②（降级路径可触发且可见）；承诺清单进 E19 验证基准一并执行）

#### 稳定域（如何形成稳定）

- **B0-20** 确定性与可重入：同一输入+环境是否可复现编排（日志重放/种子）；节点是否可安全重入（幂等）。（已倾向 2026-08-27：分两层——链形状可复现（同输入同判型同管线，判型缓存后更强）+ LLM 输出天然不可复现（不追求执行级重放）；"重放"= 迹线展示级重放（v2 回看），非执行重放；节点幂等不做强制（重入走新 run，B0-7），条件边回炉循环已由无进展检测兜底）
- **B0-21** 故障域与管线冻结检测：单点失败（单个子 Agent/工具/模型）是否被圈在故障域内；现有循环检测/看门狗升级到"整条管线无响应"的判定（管线冻结=请求失效）。（已定案 2026-08-27：单点失败圈在节点内（NodeStatus::Error 隔离 + 降级支路接管，D23）+ 无进展循环检测已有（10 次阈值）；**run 级冻结检测 v1 接**——编排器加 run 级看门狗：节点执行超时兜底 + run 无事件超 N 分钟发冻结警告事件 + 产出 Degraded 物降级（覆盖编排节点内部 prompt 挂起场景，LoopEng 看门狗覆盖不到的盲区））
- **B0-22** 可观测性三层：轨迹事件 / 日志 / 指标各自记什么、在哪层收；运行中 run 的探活手段。（已倾向 2026-08-27：两层先行——轨迹事件（用户可见，B7 家族）+ tracing 日志（开发排查，现状已有）；指标层 v2 不做（单机桌面应用，日志够用）；探活 = 迹线实时事件即心跳（phase 推进可见），无事件超时 = B0-21 冻结检测的事）
- **B0-23** 演进稳定：契约（事件模型/命令面/字段）的版本策略；未来加模式/加支路时，管线定义单点 vs 判断散落的回归防线（与 D15 的联动确认）。（已倾向 2026-08-27，C20"契约稳组合演"落地：轨迹事件族与 ArtifactKind 只加不改（additive 版本化，废弃用 deprecated 标注）；管线拓扑单点 = D15 声明式定义（唯一拓扑源，A1 已定）；回归防线 = 构图期 kind 校验（D23）+ 每条支路一条枚举测试（D0-3））
- **B0-24** 资源治理：并发上限/队列/背压；循环之外的高危资源场景（并发委派风暴 / Token 超支 / 并行探索爆炸）的防线在哪。（已定案 2026-08-27：**v1 防线齐备，无新增**——顶层 run 串行（B11）= 最强并发防线；委派并发由 SubAgentPool 收口 + run 树深度 ≤3（B22）；探索爆炸由 beam_width ≤3 已限；Token 超支 = 队列限流（已有）+ v2 预算系统（B0-6 定案）；背压/队列细化 v2 随并发 run 一起设计）

### 议题三：模式与框架研究 —— 定义、形式、深广、接触、耦合、特征

> 起步问题：模式/框架"是什么、以何形式存在、该多深多广、怎么被触碰、如何互相耦合、最终如何变成产品特征"；按关键词拆为研究子面（以下每条是研究问题，非解答）。本议题与前两个不同：它从"实现"跃迁到"能力的产品性格"。

#### 定义域（什么算"一个模式"）

- **C0-1** 模式的判定标准：现判定线（"删掉它 AgentLoop 能否跑"）是否够用？"底座能力 / 底座服务 / 扩展模式"三分是否已覆盖所有语义，还是需要在产品语义层重构分类（如按任务形态分组：规划型/委派型/探索型/评审型）？（已定案 2026-08-27：判定线够用（NodeType 2026-08-25 清理后产品语义 13 模式与架构两层归属已代码级一致）；产品语义层**不重构**分类——按任务形态分组只出现在 UI 命令菜单（A1/C14 能力语义分组），不回写架构；五件套立项标准已定（C0-3））
- **C0-2** 模式与能力的边界：Tool Use / Memory / Loop Engineering 已归为底座服务而非模式；"产品能力清单"是否应以新的两层归属重写，用户看得到的能力表述与架构层如何对齐（与 C14 联动）。（已定案 2026-08-27：能力清单以 matrix 两层归属为唯一权威（matrix §13 模式表）；用户表述层 = 迹线 + 能力语义分组命令菜单（C14），不另造清单；三层表述各归其位：架构归属（matrix）/ 用户感知（迹线）/ 高级入口（命令分组））
- **C0-3** 模式的最小完整形态：一个新模式立项应满足什么五件套（策略实现 / 配置 / 事件 / 错误 / 测试）？先定义"模式 SDK"边界，防止半成品模式混入目录。（已定案 2026-08-27：**五件套 = 立项标准**（multi_agent 为样板）；**v1 建轻量注册表而非完整 SDK**——每模式一条静态注册项（名称/命令/事件族/ArtifactKind/配置默认值），后端一张表 + 前端一份 TS 清单，新增模式改 2 处（注册项 + 模式实现）而非 8 处；脚手架/宏/基类模板暂不建，待 v1 后按真实新增需求再升级）

#### 形式域（模式以何形态存在于架构）

- **C0-4** 模式的物理形式统一：目录式（tot/multi_agent）与文件式（曾有的 supervisor/got/plan）并存——matrix §8 里程碑 1（阶段 A/B）已落地目录化；统一为"每模式自洽目录 + 生命周期 + 事件 + 配置 + 测试"的标准结构是否有残余例外，标准结构的"骨骼"（各模式都要有的共同骨架）应显性化。（已定案 2026-08-27，随 C0-3：目录化已无残余例外（[02-现状事实.md](02-现状事实.md) §二）；标准骨骼 = 五件套，以**注册表注册项为显性载体**（注册项齐全 = 五件套齐全的检查单）；multi_agent 为样板、tot/reflective 的组织差异属架构内部自由，不强制统一文件布局）
- **C0-5** 模式与数据驱动声明的边界：哪些模式"配置化"即可（Router 路由表 / Supervisor 池 / Plan 模板），哪些必须保留代码形态（ToT 探索策略）？声明化的边界以什么判定。（已定案 2026-08-27，C20 三张力推论：**配置面数据化、策略面代码化**——判定的边界线 = "是否含控制流决策"：路由表/子代理池规格/次数参数属数据（配置化）；探索算法/评分标准实现/收敛判定逻辑属策略（代码形态）；管线拓扑本身声明化（D15/D23 已定））
- **C0-6** 模式的繁殖成本：定义一个新模式当前需动几处（Rust 节点 → agent-commands → Tauri 命令 → 前端 composable/面板 → 文档/索引）？繁殖成本是否构成"广"的硬阻力，值不值得为它建脚手架。（已定案 2026-08-27，随 C0-3：现状 8 处（[02-现状事实.md](02-现状事实.md) §十）经**轻量注册表降为 2 处**（注册项 + 模式实现）；繁殖成本解除"广"的硬阻力；脚手架不建（v1 无新增计划，注册表已够））

#### 深浅域（覆盖够不够、该广还是该深）

- **C0-7** 覆盖充分性：对照真实任务形态图谱（问答/规划/研究/创作/分析/委派/探索/评审/记忆整理/多轮协商），当前 13 模式存在哪些盲区（如记忆组织、辩论/协商、多轮迭代式创作、工具链编排）？（已定案 2026-08-27：盲区清单（辩论/协商、记忆组织、工具链编排等）**记入 backlog 不进 v1**——注册表已定（C0-3），新模式增删改 2 处零阻力；v1 优先把已有 8 扩展模式经迹线投放到位，再谈补盲）
- **C0-8** 冗余与过广：哪些模式处于"有而无用"（GoT 相对 ToT 的增量是否值得独立存在？Router 与 Plan 入口义务是否重叠？）——瘦身候选清单。（已定案 2026-08-27：**GoT 保留独立**——多源聚合语义独特（Research 管线预设已依赖，A1 映射）、已共享 thoughts.rs 零重复成本、NodeType 刚完成清理不宜再动；**瘦身清单为空**（Router/Plan 义务清晰无重叠：判型入口 vs 规划阶段）；GoT 使用率随 C0-20 真实使用数据滚动观察，若长期闲置 v2 再议降级为 ToT 可选策略）
- **C0-9** 深度成色：每个模式的"深"以什么为参照（ToT 的四终止条件/beam 剪枝是深样板）；其余模式缺什么纵深；"浅而可用"与"深而完备"在当前产品阶段哪个是正确取向。（已定案 2026-08-27：**先广后深**——v1 把 8 扩展模式全部经迹线投放到位（投放本身是最大增量），深度只保 ToT 现状（四终止条件已是深样板）；深拓排序待 v1 真实使用数据（C0-20）后定——无用户反馈前深投是盲投）
- **C0-10** 广深的决策依据：产品选"能力广度更全"还是"少数杀手模式更深"，判据应来自用户任务矩阵（哪类任务频发）而非模式数量美学；谁来产出任务矩阵。（已定案 2026-08-27，随 C0-9：v1 判据 = 先广后深（投放优先）；任务矩阵基准 = C20 定位底色（通用 + 创作首场景，含创作任务不限于）；产出方式 = 方案文档阶段 Agent 起草、用户走查修订，此后作为深拓排序的依据）

#### 接触域（模式如何被产品触碰）

- **C0-11** 对外接触面统一：一个模式对外暴露的标准触点清单（入口命令 / 轨迹事件 / 配置面 / 错误语义 / 详图组件）应统一吗？触点未统一的模式（如 Router 只有命令无事件）如何补齐。（已定案 2026-08-27：勘察修正——Router 已有完整事件族，前提不成立（[02-现状事实.md](02-现状事实.md) §二）；标准触点 = **五触点清单**：① 入口命令（run_* 或手动命令）② 轨迹事件（B7 家族，全模式必接）③ 交接物（D23 ArtifactKind，全模式必产）④ 配置面（次数参数等，C0-5 数据面）⑤ 详图组件（A4，深水区模式）；②③ 为 v1 硬性补齐项（reflective 无独立命令面、tot 无独立策略文件属架构内部组织，不违触点）
- **C0-12** 接触的薄与厚：模式向外"讲什么"（决策与结果）vs"藏什么"（内部步骤细节）——薄接触（只见结果）与厚接触（全程可见）在哪些模式下各自成立（与 A0-12、B0-11 联动）。（已定案 2026-08-27，C20 锁定：**薄接触为默认**（summary + 物），厚接触按需（详图组件 = A4 按需展开）；分界线 = 交接物边界——物以内是"讲"（summary/理由），物以外是"藏"（节点内步骤细节，经细节事件按需查））
- **C0-13** 场景对模式的封装：用户入口是否应以"场景"（深度研究 / 头脑风暴 / 代码实验）而非"模式"命名——模式下沉为场景的底层拼块（与 A1 触发模型联动）。（已定案 2026-08-27：**v1 不做场景层封装**——入口只有迹线 + 命令菜单（能力语义分组）；世界观创作用既有领域面板/场景系统承载（C20 定位底色下首个场景的地位不变，只是不做预设封装）；场景层（深度研究/头脑风暴/世界观创作预设包 = 预设链 + 配置包）**v2 随模式市场/预设需求再定**；电梯陈述定稿通用版：**"你只管说，它自己会组织——而你能看懂它是怎么组织的。"**）

#### 耦合域（模式间松紧谱系）

- **C0-14** 合法耦合清单：允许的共享（shared 类型 / ReAct 内核 / 基础设施服务）与禁止的耦合（模式间直接调用）——规则靠文档约定还是 trait 边界（编译期）强制；现有 crate 边界（kernel 不依赖 patterns）已强制一级，模式之间的二级规则怎么定。（已定案 2026-08-27：二级规则 = **机制强制非文档**——① crate 一级已编译期强制（kernel 不依赖 patterns）② 模式间零直接引用由"shared 唯一共享点"结构性保证（现状零违约，[02-现状事实.md](02-现状事实.md) §九）③ 组合合法性由构图期 kind 校验拦截（D23）；三层机制已在，无需新增 trait 边界）
- **C0-15** 产品层对模式的依赖：命令层/前端按"模式写死"还是按"契约发现"（清单/注册表）——crate 拆分后引用面已收敛，是否趁势抽"模式清单"（Each 模式的入口/事件/配置注册表）以实现未来增删模式零改产品层。（已定案 2026-08-27，随 C0-3：**契约发现**——轻量注册表（后端一张静态表 + 前端一份 TS 清单，内容含名称/命令/事件族/ArtifactKind/配置默认值）；命令层与前端从注册表读模式元数据，不再按模式写死；注册表 = C0-11 五触点的结构化载体）
- **C0-16** 破坏性演进的最小化：改一个模式（接口/事件/配置变更）的耦合影响面如何画界（对外契约版本、前端向下兼容）——与 B0-23 演进稳定的模式侧。（已定案 2026-08-27，随 B0-23：模式侧契约 = 事件族 + ArtifactKind + 命令签名三面，全部 additive 版本化（只加不改，废弃 deprecated 标注）；影响面画界 = 触点清单（C0-11 五触点）即变更清单；前端向下兼容 = 事件消费向后兼容（新增字段不破坏旧解析））

#### 特征域（如何成为产品性格）

- **C0-18** 差异化记忆点：与主流对话式 AI 相比，哪几项能力（显式委派 / 思维探索可视化 / 评审收敛 / 多智能体黑板）能成为"用户一用就记得住"的差异点；哪些是必须有的标配（不值得当卖点）。（已定案 2026-08-27，C20 锁定：**一级差异点 = 自组织过程呈现**（判型→组队→迹线，竞品最大空白）；二级差异点 = 显式委派可视化（子 run 树，B22）+ 探索过程可视（ToT/GoT 详图）；标配不当卖点 = 记忆 / 工具 / 多模型 / 规划本身（行业人人有））
- **C0-19** 可传达的能力语言：如何用一句话说清产品能力（电梯陈述）；13 模式如何压缩成对外语言（如"计划-探索-委派-评审的自组织助手"）而不丢失细节的表达张力。（已定案 2026-08-27，随 C0-13：电梯陈述定稿——**"你只管说，它自己会组织——而你能看懂它是怎么组织的。"**；展开表述用链族语言（计划-探索-委派-评审）而非模式编号，仅在文档对应处附编号）
- **C0-20** 深广假设的试验方法：用什么手段验证"广/深"假设（任务矩阵走查 / 对比型验收 / 真实任务日志分析），避免按模式数量自嗨；验证周期与轮次。（已倾向 2026-08-27：**试验方法 = E19 验证基准承载**——① 三条真实任务（快问答/规划/委派）走完整管线 = 深度走查 ② B10 判型缓存落地后统计判型准确率 = 广度有效性数据 ③ 运行一段后活动日志分析（trace 通道已有）= 真实使用画像；任务矩阵由 Agent 起草、用户走查修订（C0-10）；不设固定周期，随 v1 落地后的真实使用滚动验证）

### 议题四：链路与组合研究 —— 约束、收敛、性质、程度、粒度、完整、接续、插入、长度

> 起步问题：链路/组合"受什么约束、如何收敛、是什么性质、组合多深多细、怎么闭环、怎么续接、能不能插、多长合适"；按关键词拆为研究子面（以下每条是研究问题，非解答）。本议题是"组合机制学"——链的形态选择会决定前端的叙事形态与后端的数据模型。

#### 约束域（组合的规矩）

- **D0-1** 合法路径定义：哪些链路是"合法的"（条件支路图谱）；合法性的判定与越界检测如何落地（声明式管线定义 vs trait 接口 vs 编译期断言 vs 测试枚举）——与 D15 已倾向的"条件支路"衔接确认。（D23 定案：边声明接受的 artifact kind，构图期硬校验不匹配即拒绝）
- **D0-2** 约束的软硬分级：组合约束是"非法即不允许"（硬）还是"允许但标注实验性"（软）？内核层与产品层的约束强度是否应分级。（D23 定案：双层——构图期 kind 匹配=硬，运行期物缺失=软降级）
- **D0-3** 组合合法性的可测性：合法路径集是否有枚举式测试（每支路一条用例）；"语义非法组合"（如 ToT 探索结果直接喂给 Supervisor 调度者）由谁拦截——编译期、运行时断言还是测试。（D23 定案：构图期校验即枚举测试点——每条非法组合一条拒绝用例）

#### 收敛域（链如何结束）

- **D0-4** 收敛条件谱系：各模式终止条件（ToT 四条件 / 评审阈值 / MultiAgent 三收敛 / 步骤耗尽 / 无进展循环检测）如何在管线级统一为"收敛判定"；"这件事做完了"由谁、按什么宣布。（已定案 2026-08-27，B0-4 推论：收敛判定 = run 终态出口 + reason 枚举（goal_reached / threshold_met / limit_reached / no_progress / aborted / degraded）；由编排器主循环宣布（OrchestratorEnd 扩展 reason 字段）；各模式内部终止条件向枚举映射（ToT GoalReached→goal_reached、ScoreConverged→threshold_met、MaxDepth/MaxThoughts→limit_reached、NoCandidates→no_progress；MultiAgent 三收敛同理），映射表随管线定义声明）
- **D0-5** 收敛失败递归：评审低分→回炉→再低分的"无进展收敛"判定归谁；与 B0-21 管线冻结检测的分工（"在推进但未收敛" vs "完全无响应"是两件事）。（已定案 2026-08-27：现有两道防线已够——"在推进但未收敛"（每轮 Refine 产出物=有进展）由次数上限收口（Refine 3 → limit_reached 正常收敛）；"完全无响应"由 B0-21 run 级冻结检测接管（v1 已定接）；两者分工清晰，无需新增机制）
- **D0-6** 用户与收敛：收敛结论（分数/结果）是否必须给用户"盖章"——用户可否反对收敛（"不行，再想"）？强迫收敛（无解也要给结论）与重试的权利边界。（已定案 2026-08-27：强迫收敛 = B0-4 超限=收敛（带部分结果与理由，不裸奔）；用户反对收敛 = v2 评审否决门（D21 四门之一）；v1 重试权 = 命令覆盖重发（A1 同机制，"不行，再想" = /命令 重发新 run））

#### 性质域（链的形态学）

- **D0-7** 组合结构类别：链应是"顺序段 + 条件支路 + 可选循环（评审回炉）"的组合，还是常备"并发扇出/汇聚"（多路探索、黑板协作、聚合）？结构类别的完整集合是什么。（D21 定案：顺序+条件+循环+门；图级 fork/join v1 不做，并发留节点内）
- **D0-8** 链的确定性与可变点：同请求同输入是否必走同一条链？模型判型参与的环节是"可变点"，其余是"铁轨"——可变点与铁轨的边界如何画，谁有权改道。（D21 定案：铁轨=声明支路；可变点=入口判型+门上决策+节点内策略）

#### 程度与粒度域（组合的规模参数）

- **D0-10** 嵌套深度：run 套 run（顶层→委派→孙委派，深度 3 已有上限）的语义；探索分支内嵌计划的合法嵌套；深度与资源预算的关系。（已定案 2026-08-27，随 B22：run 树子层级 ≤3（max_delegate_depth 语义直接映射）；探索分支内嵌计划 = 节点内结构（器），非 run 层嵌套；深度受既有上限约束，Token 预算 v1 不做（B0-6））
- **D0-11** 组合粒度：管线定义的最小单位是"阶段"（plan/execute/reflect）、"步骤"（计划项）还是"动作"（单次 tool call）？以"重规划"为例，粒度该在步骤级还是阶段级介入——粒度过细维护失控、过粗表达力不足。（已定案 2026-08-27，随 D23：管线定义粒度 = **阶段级**（与交接物同粒度）；步骤级是 phase 内细节（Execute 各步输出聚合为一个 Execution 物）；重规划 = 阶段级介入（PlanReplanned 整体替换计划））
- **D0-12** 阶段数上限：单请求链的"阶段数"是否有语义上限；多少阶段算"体面"、多少算"剧场"（与 A0-18 剧场感反模式联动）。（已定案 2026-08-27：**不设独立参数**——预设链静态决定（最长 5 阶段位：Plan→Execute(→ToT/GoT 探索工位)→Reflection→Refine），循环深度受既有次数上限约束（Refine 3 / 编排器 50 轮 / 无进展 10 次）；剧场感防线在前端折叠态（A2/A3）而非后端参数）

#### 完整域（链如何闭环）

- **D0-13** 入口出口完整性：入口是否必过 Route（或可跳过直达指定模式）？出口是否必收敛出一份"结论"？快问答的"默认链"（单节点）是否也算一条完整链。（已定案 2026-08-27：入口 = 判型必经——命令强制管线是判型链路的"强制档"（跳过 LLM 判型但不跳过管线选择，A1）；出口 = 必收敛出结论（B0-4 超限=收敛保证有产出，Degraded 物兜底）；快问答退化 run = 完整 run（B22：单阶段也是链））
- **D0-14** 断链补全：计划中间步失败 / 委派目标缺失 / 评审依赖的前段不存在时，链如何"续完"——降级、重规划、截断的判定与可见性。（D23 定案：软校验物缺失 → 声明式降级支路产出 Degraded 物，可见可追溯）

#### 接续域（链如何续接）

- **D0-16** 跨轮续接：同一话题多轮对话间，管线是否可跨轮续接（上一轮计划被本轮追加/修订）还是每轮独立链路；话题连续性的判定由谁认。（已定案 2026-08-27，随 D21/B22：每轮 = 独立 run；跨轮续接 = 链间经交接物引用——上一轮 Plan 物随会话上下文被本轮判型读取，计划追加/修订走 PlanReplanned 既有机制；话题连续性由判型链路在会话上下文中自然判断，不设专门机制）
- **D0-17** 中断后续跑：管线中途中止/失败后，恢复是"从头再来"还是"从断点续"——检查点粒度能否下沉到管线阶段级；用户"接着做"的入口。（已定案 2026-08-27，随 B0-7：v1 = 从头重跑（命令覆盖重发同机制，新 run 继承会话上下文即"接着做"）；断点续跑 v2（快照/restore API 为种子，B22 已定））
- **D0-18** 跨会话接续：换会话后是否还认得"未完成的计划/黑板"（归属与回看，与 B0-13/B0-17 联动）。（已定案 2026-08-27，随 B22/B0-13：v1 不认（run 树挂 session，无跨会话引用）；历史会话内计划可回看（已 SQLite 会话级持久化）；跨会话续做 = v2+ 与迹线回看一起设计）

#### 插入域（链能否插入、怎么插）

- **D0-19** 计划内插入：执行中动态追加步骤（ExecuteNode 已有 `<new_tasks>`）的合法性边界——谁允许追加（LLM 自主 / 用户要求 / 子任务发现）？追加是否可追溯（谁加的、为什么）。（已定案 2026-08-27：维持 `<new_tasks>` 现状——LLM/子任务发现自主追加合法（执行反馈动态触发的体现，A1 已含）；可追溯已解决（PlanReplanned 事件携带完整替换计划 = 改了什么一目了然）；用户要求追加 = 插话门（D0-20，v1 steer 队列化到节点边界））
- **D0-20** 用户中途插话：对话中用户"插话"（纠正方向 / 追加要求）是否中断当前链、注入新指令？插入点与当前步骤的冲突如何处置。（D21 定案：收口为插话门——v1 = steer 队列化到节点边界，不中断链）
- **D0-21** 阶段级插入：执行中能否插入"评审 / 探索"新阶段（临时加深）？插入的权限、成本与可见性。（已定案 2026-08-27：**v1 不做**——执行中不插入新阶段（保持声明化铁轨不被运行时打洞）；临时加深 = 命令覆盖重发（/tot /research 新 run）；v2 若做走门机制（"加深门"））

#### 长度域（链长由谁决定）

- **D0-22** 长度的决定者：链长由任务复杂度自适应（Plan 步数 / 探索深度）、用户指定（"简要/详细"）、还是预算（B0-6 Token）约束？三者冲突时的优先级。（已定案 2026-08-27，随 A1/B0-6：优先级 = 命令强制 > 判型自适应 > 次数上限兜底；Token 预算不进 v1（B0-6），无第三层冲突）
- **D0-23** 长度与深度的权衡：短链高对齐（快速直答） vs 长链深处理（彻底解）之间的表达——"再想想 / 更深入点"类用户动作如何延长链（触发评审 / 补充探索 / 加一次回炉）。（已定案 2026-08-27：v1 = 新消息触发新 run 判型（自然语言"再深入点"即形状干预信号）+ 命令覆盖（/tot /research 重发）；延长链全走"新 run"而非"运行中改链"——与声明化铁轨一致；v2 = 评审否决门 + "加深"快捷动作随门机制）
- **D0-24** 长度的可视预期：链长能否在入口处预告（Route 判型时提示"预计 N 阶段"）？与 A0-13 等待感管理的衔接。（已定案 2026-08-27：两时点预告——① 判型后迹线首段显示管线形状（链族名 = 阶段概貌）② PlanCreated 后计划全貌可见（精确长度预告的天然时点）；不做"预计 N 阶段"数字承诺（无可靠预估不承诺，A0-13 原则）；等待感衔接 = 折叠态"已学到 + 下一步"叙事（03 参照））

## 一、前端交互（UX：用户如何感知能力）

### A1. 触发模型：模式由谁触发？（钥匙 5/5）
- **状态**：已定案（2026-08-27 拍板）
- **问题**：目前 8 个扩展模式是用户手动挑面板（PlanPanel / OrchestratorPanel / MultiAgentPanel / RouterPanel），要求用户先学会 8 种模式才用得上能力，违背"提升交互感官"目标。
- **结论**：**自动为主 + 手动可指定**，四项细则一并定案：
  - **自动为主**：主对话区永远干净，判型决定 run 形状（B22）；快问答直接 ReAct 直答（退化 run，不渲染编排段 = C20 分级透明）；复杂任务编排段自动浮现。
  - **词汇映射（A3 四管线 = D15 链族的预设封装）**：Query = 快问答链（退化 run）；Research = 规划型链 + GoT 聚合位 + Reflection；Experiment = 规划型链 + Refine 迭代环；Compose = 规划型链 + Reflection——三者皆规划型链变体，差异只在 Execute 工位实现与可选深水区段；**委派型/求解探索型链不在预设内**，由执行反馈动态触发（Execute 中判定需委派→挂委派位；判为多解型→换 ToT 工位）。判型词汇表收敛为一张映射表，D15 管线定义是唯一拓扑源；未来加管线 = 加预设。
  - **手动入口：`/` 命令菜单 + 前缀机制复用**：输入 `/` 弹出模式菜单（按 C14 能力语义分组：探索/协作/规划/评审），选择即插入前缀；对后端复用既有 force_pipeline Chip 机制（跳过 LLM 判型），零新链路。
  - **判型可纠（v1）**：判型结果与理由在迹线首段可见（数据已有：RouterDecisionMade 携 reason）；判错时**命令覆盖**——用户 `/plan 重发`，旧 run 收拢、新 run 按指定形状重建；中途换链按钮留 v2（依赖 run 重建链路成熟）。
- **备选**：A. 用户显式选择（可控但打断）；B. 维持现状多面板（体验碎片）——均否决。
- **理由**：请求驱动暴露优于记背驱动；B10 判型链路（强制→LLM→关键词→兜底）+ B22（判型=run 形状）+ C20（分级透明）配套全部就位。
- **锁动**：C0-13（入口不按模式命名；"是否按场景命名"由其继续定）/ D0-22（命令 = 最高优先级的形状干预通道，优先级排序细节由其继续定）/ B10（判型缓存 + 可见可纠的落地形态确认）/ E18-M4（自动触发里程碑方向确认）

### A2. 投影形态：前端如何呈现模式链？
- **状态**：已倾向（待拍板）
- **问题**：模式链信息以什么形态呈现给用户？并列面板（按模式分栏）vs 一条管线轨迹（按请求组织）。
- **倾向**：**统一编排迹线 + 按需详图**。主对话区下（或内嵌于对话流）一条纵向迹线：路由判型 → 计划步骤 → 执行与委派 → 评审结果，**逐步展开、完成后收拢为折叠任务流 + 最终输出**（符合用户一贯展示偏好：任务流逐步渲染、最终折叠、不丢弃中间结论）；深水区模式（ToT 树 / GoT 图 / MultiAgent 黑板）作为迹线内可展开的详图。
- **备选**：B. 迹线 + 现有面板跳转（双 UI 体验）；C. 仅优化现有面板（仍是按模式分栏的旧心智）。
- **理由**：迹线以"一次请求"为组织单元，用户理解成本最低；与后端"生产管线事实"的模型天然对应（见 B7/B8）。

### A3. 迹线与对话流的布局关系？
- **状态**：待决
- **问题**：迹线放哪、何时折叠，才能不打断对话流又不藏信息？
- **倾向**：迹线作为对话流内的一条"编排段"（特殊消息单元：以请求为单位，可展开/折叠）；最终回答作为该段最后一条正常消息落回对话区。用户视角：发一句复杂请求 → 看到这条请求被"怎么处理"（轨迹）→ 得到结论；普通快问答不出现编排段（无感）。
- **理由**：保持主对话区"唯一入口"的干净；编排段只在被需要时出现（快问答不触发）。

### A4. 深水区模式（ToT/GoT/MultiAgent）如何呈现？
- **状态**：待决
- **问题**：树状思维、图聚合、黑板协作是信息密集型视图，全部塞进迹线会爆炸。
- **倾向**：迹线内只放"入口卡片"（如"已用思维树探索 3 条路径 · 展开"），点击展开为独立详图侧栏/浮层；详图复用现有多模式面板组件（ThoughtTree / MultiAgentBoard / GotGraph），但改为**从迹线事件驱动**而非独立面板常驻。
- **理由**：信息密度分层——迹线是索引，详图是内容；组件复用降低前端成本。

### A5. 用户干预能力做到什么程度？
- **状态**：待决
- **问题**：管线运行中，用户能否中止 / 跳过步骤 / 回退到某阶段？v1 做多少？
- **倾向**：**v1：仅"中止 + 暂停"**（复用现 long_task 看门狗/中止通道，后端已具备）；**跳过/回退/重跑指定步骤列为 v2**（涉及步骤级状态机与幂等，成本高）。
- **理由**：中止/暂停是"保命"能力，低成本；步骤级干预是"把控"能力，需单独设计。先保住安全底线。

### A6. 可解释性：为什么这次走了这条路？
- **状态**：待决
- **问题**：用户看到迹线，需要知道"为什么是 Router→Plan→委派"而不是"直接答"。
- **倾向**：迹线每段携带一句话理由（判型理由 / 委派选择 reasoning / 评审意见摘要）；理由由产出该阶段的节点提供（Router 已产出 reason；Supervisor AssignmentResult 已含 reasoning；Reflection 已含 issues）。
- **状态更新（2026-08-27，D23 联动）**：理由与结果的载体 = 交接物的 summary + kind 载荷（理由字段已类型化在物里），投影层拼装即可。
- **理由**：数据已存在，投影层拼装即可，成本低、信任增益大。

## 二、后端执行（引擎如何工作）

### B7. 后端如何"生产管线事实"？
- **状态**：已倾向（待拍板）
- **问题**：现在各模式事件异构（agent:event:plan_* / orch_multi / reflection:${sid} / NodeStart 等），前端要分别适配。统一管线轨迹需要统一事实来源。
- **倾向**：在现有事件流之上**新增统一"轨迹事件"家族**（`orchestration_trace`：pipe_started / phase_entered(phase, reason) / phase_result(phase, status, summary) / pipe_finished），由编排层（DefaultOrchestrator + 图节点入口）发出；各模式细节事件流**保留**（轨迹是骨架，细节按需查）。
- **状态更新（2026-08-27，D23 联动）**：phase_result 补充携带 `artifact_id + summary`（引用物而非内嵌全文）——事件轻、物权威；全部轨迹事件带 run_id（B22 已定）。
- **原因**：不推倒现有事件（面板已依赖），用"骨架事件 + 细节事件"双层并存实现渐进。

### B8. 编排上下文（Orchestration Context）要不要贯穿请求生命周期？
- **状态**：已定案（2026-08-27，随 B22 收口）
- **问题**：一次请求的当前阶段、计划、黑板、委派关系、评审结果散在各节点/存储里，迹线要拼装。
- **结论**：**需要，实体即 OrchestrationRun**（run_id / 管线形状 / 阶段指针 / 交接物区 / 决策记录）——定义与归属见 [B22](#b22-运行单元run-实体与-run-树钥匙-35含-b8-收口)。
- **原因**：这是"一请求一管线"的落地载体；也是重放/隔离（B11）的基础。

### B9. 失败降级策略？
- **状态**：待决
- **问题**：ToT 超时、子 Agent 失败、评审后重拆失败……管线如何降级而不让用户面对裸奔错误？
- **倾向**：每类降级在**管线定义中声明**（探索失败 → 降 ReAct 直答；委派失败 → 主 Agent 兜底重试；评审不达阈 → 回炉一次后仍低分则给出当前最优并说明）；降级动作作为迹线的一环向用户可见（"已降级为直接回答，原因：探索超时"）。
- **状态更新（2026-08-27，D23 联动）**：降级产出**一等 Degraded 交接物**（from / reason / partial）——降级在链上有实体痕迹，审计链不断裂；本条的完整降级策略仍待后续定案，物的载体已定。
- **原因**：降级是"能力体验"的最后一环，不可见降级 = 黑盒不可信。

### B10. Router 判型可靠度如何保证？
- **状态**：待决
- **问题**：自动触发依赖 Router 判型准确；判错会把快问答送进重型管线。
- **倾向**：复用现有 A3 四管线判型链路（强制管线 → LLM 判型 → 关键词 → 默认兜底），并在**请求级缓存判型结果**（同会话相似任务不重复 LLM）；判型结果与理由进轨迹事件首段，用户可见可纠。
- **状态更新（2026-08-27，A1 定案联动）**：可纠的 v1 落地形态确认——判型理由迹线首段可见 + 命令覆盖重发；A3 四管线↔链族映射表已定（见 A1），本条的判型缓存与可靠度验证细节继续研究。
- **原因**：链路已存在，只差"自动接线 + 缓存 + 可见"。

### B11. 多请求并发/隔离边界？
- **状态**：已定案（2026-08-27，随 B22 确认）
- **问题**：同一会话内用户连续发两条复杂请求，迹线与事件如何隔离？
- **结论**：**v1 顶层 run 按请求串行**（session 同时至多一个 active 顶层 run；发新请求时旧迹线收拢，新请求起新 run_id）；**节点内子 run 并发随节点语义**（MultiAgent / 委派已有并发）。事件按 run_id 路由，前端迹线按 run 树聚合。
- **原因**：串行 + run_id 隔离是先做对再促快的最小步。

### B22. 运行单元：run 实体与 run 树（钥匙 3/5，含 B8 收口）
- **状态**：已定案（2026-08-27）
- **问题**：一次"请求"在系统中的真实实体是什么？子任务/委派是否自成运行单元？嵌套与顶层的关系由什么界定（原研究区 B0-1，与 B8 编排上下文一并收口）。
- **结论**：
  - **run = 请求级编排上下文实体**：`OrchestrationRun { run_id / session_id / status / pipeline（判型选中的管线形状）/ 阶段指针 / 交接物区（计划 / 评审记录 / 委派映射 / 最优路径）/ 决策记录（判型理由 / 委派 reasoning）}`——B8 的载体即此。
  - **双入口统一**：send_message 内部也建 run——判型结果 = 管线选择 = run 形状；快问答 = **退化 run**（单阶段 react，不渲染编排段 = C20 分级透明）；A3 四管线 ↔ D15 链族的词汇映射细节留 B10 轮。
  - **显式子 run 树（Devin 嵌套模式）**：委派创建子 run——delegate 工具委派与 Supervisor 分配**均生成子 run 实体**（完整生命周期 / 耗时 / 交接物），挂父 run 节点之下；**MultiAgent 不拆**（对等协作整体 = D21「器」，无中心委派关系）；子 run 可再委派，**run 树子层级 ≤ 3**（现 max_delegate_depth 语义直接映射，超限照旧 ToolError）；**abort 父 run → 递归中止活跃子孙 run**。
  - **与 D21 的协调**：拓扑仍是单链（体不变）——run 树是"执行账本"的嵌套（谁被谁委派、执行多久），不是管线拓扑的分支；委派关系显式实体化，深化可审计辅气质（未来"接管子 run"有实体基础）。
  - **持久化：内存 + 懒持久**：run 实体驻 agent-commands 内存（HashMap 注册表）；仅**多阶段 / 深水区 run 懒写入 SQLite**（表结构 v1.5 定：新 runs 表或扩展 long_tasks，属数据模型决策届时确认）；纯退化 run 不落表；重启 = run 蒸发（会话历史只剩消息，可接受）；元数据持久化 + 迹线回看 + 断点续跑（快照 API 为种子）捆绑 v2。
  - **群聊**：每条回复 = 独立 run，同一规则，不引入特殊形态。
- **锁动**：B7（轨迹事件带 run_id）/ B8（转定案）/ B11（顶层串行 + 节点内并发确认）/ B0-2（并发三层：顶层串行 / 节点内并发 / 子 run 账本嵌套）/ B0-3（五出口状态机 Running→Completed|Aborted|Error|Timeout|Interrupted + abort 递归穿透；孤儿 run = 蒸发）/ B0-16（事件先落迹线、run 终态后写会话消息）/ B0-17（重启蒸发，无回写）/ D0-10（嵌套深度 = run 树子层级 ≤3）/ D0-18（run 树归属父会话）
- **依据**：[02-现状事实.md](02-现状事实.md) §三（无 run_id 缺口、事件仅 session 作用域）/ [03-外部参照.md](03-外部参照.md) §一.5（Devin 嵌套子会话树 = 最完整参照）/ C20（可审计辅气质深化）/ D21（拓扑单链与账本嵌套分层）。

## 四、链路/组合（模式之间怎么接线）

### D15. 组合协议：条件支路 vs 动态自由组合？
- **状态**：已倾向（待拍板）
- **问题**：模式交叉由什么约束——预设条件支路，还是运行时自由连？
- **倾向**：**分层约定 + 条件支路**。定义一族预设链路（按 Router 判型选择入口）：
  - 快问答 → ReAct 直答（不出现编排段）
  - 规划型 → Plan→Execute→(可选)Reflection/Refine 收敛
  - 委派型 → Supervisor 分配 或 SubAgent 委派 或 MultiAgent 黑板协作
  - 求解/探索型 → ToT（分支探索）→ 或 GoT（多源聚合）
  - 失败/低分反馈 → 回 Plan 重拆 或 Refine 迭代 或（仍不达）降级
  规则集中在**一份管线定义**（声明式），拒绝任意乱连；可测试、可解释。
- **备选**：B. 动态图自由组合（最强但黑盒难测）；C. 固定场景模板（简单不灵活）。

### D16. junction 判定谁负责？
- **状态**：待决
- **问题**："执行完要不要评审？评审低分要不要回炉？"谁来下这个判断。
- **倾向**：由**节点返回状态 + 管线定义的条件边**驱动（图宿主已支持条件边）：Execute 汇总结果 → 若配置了评审且结果非 trivial → 进 Reflection；Reflection 分数低于阈且未达迭代上限 → Refine/回 Plan；否则收敛。全部是声明在管线定义里的 if，而不是散落的 LLM 判断。
- **原因**：可测试、可向用户解释、可退避（关掉评审即绕过）。

### D17. 深水区探索（ToT/GoT）挂在管线哪个位置？
- **状态**：待决
- **问题**：探索类模式是"替代执行"还是"执行后的附加"？
- **倾向**：Router 判为"求解型/多解型"任务时，探索模式**替代**普通 ReAct 执行（ToT 分支探索在该步骤上展开），而非执行后再绕一圈；GoT 用于需要多源聚合的步骤（研究型）。即探索是"执行工位的一种实现"，被管线定义选中而非叠加。
- **原因**：避免"先执行再说要不要探索"的双重浪费；语义上探索就是解题方式本身。
- **状态更新（2026-08-27）**：D21「器」已确认本条倾向方向（探索=执行工位的一种实现），可随 D15 定案一并转正。

### D21. 链的性质：流水线为体、对话为门、树为器（钥匙 2/5）
- **状态**：已定案（2026-08-27）
- **问题**：一条链更像**流水线**（加工一件物，前段产物喂后段）、**对话**（演进而非预设）、还是**树/搜索**（多路径求优）？三种性质对前端叙事（A0-2）与数据模型（B0-13）的约束完全不同——"本议题最深的一条"（原研究区 D0-9）。
- **结论**：
  - **体（全局性质）= 流水线 / DAG**：一次请求 = 一条链——判型 → 阶段推进 → 交接物流动 → 收敛出结论；"为什么走这条路"由声明式管线定义回答（与 D15 咬合）。
  - **门（交互位点）= 对话性收口为协议化干预点**：门是构图时声明的（哪个节点后带什么门），非运行时任意插入。四门：**中止门**（abort 已有）/ **插话门**（steer 队列化到节点边界）/ 计划批准门（v2，借 ConfirmationBroker 实现而非 pause）/ 评审否决门（v2）。**v1 范围 = 中止 + 插话**。
  - **器（节点内部）= 树/图收纳为执行器结构**：ToT/GoT 多路径求优是"工位的机器结构"，对外只暴露入口卡 + 最优结果（A4 详图模式）；确认 D17 倾向——探索是"执行工位的一种实现"。
  - **对话性的另一半归宿**：跨轮续接（D0-16）= 链与链之间经交接物（计划已按会话持久化）引用/修订——链间对话性 ≠ 链的对话性质。
  - **图宿主级 fork/join 不进 v1**：并发留在节点内部（MultiAgent / ToT beam 已覆盖"多路"语义），与 B11 串行隔离一致；图级并行留 v2+。
- **三张力表态**（继承 C20）：声明化落为"支路与门都在管线定义里声明"——对话性以门的形式被声明化收编。
- **锁动**：A0-2（叙事=阶段推进，树段收入口卡）/ B0-13（交接物=核心持久化候选）/ D0-7（结构=顺序+条件+循环+门）/ D0-8（铁轨=声明支路，可变点=判型+门+节点内策略）/ D0-15（交接物类型化——钥匙 4 地基）/ D0-16（跨轮=交接物引用）/ D0-20（插话=门，v1 steer 队列化）/ D17（探索=执行工位，倾向获确认）
- **依据**：[02-现状事实.md](02-现状事实.md) §十一（串行 DAG 铁轨、交接物现状=state 内字符串）/ [03-外部参照.md](03-外部参照.md) §三.5（计划是一等公民：Windsurf 活计划 / ChatGPT 批准门 / 排队消息）/ C20 三张力表态。

### D23. 段间交接物：类型化信封 + 显式输出槽（钥匙 4/5）
- **状态**：已定案（2026-08-27）
- **问题**：前段产出什么"物"给后段——交接物的类型、校验与失败语义（"物"的契约甚至比"事件"更本质，原研究区 D0-15）。
- **结论**：
  - **类型化信封**：`HandoverArtifact { artifact_id, run_id, from_node, kind: ArtifactKind, summary, produced_at }`；`ArtifactKind` 枚举承载各段产出——`Plan(Vec<PlanItem>)` / `Reflection(ReflectionResult)` / `Routing(RouterDecision+reason)`（三个已有类型从事件载荷升格一等公民）/ `Execution{step_results,status}` / `Delegation{sub_run_id,task,output}`（挂接 B22 子 run 树）/ `Exploration{best_path,score,explored,term_reason}` / `Aggregation{content,sources}` / `Convergence{final,reason}` / `Degraded{from,reason,partial}`。类型驻 kernel types.rs（与 event.rs 承载模式事件形状同例）。
  - **显式输出槽**：`NodeResult` 增 `artifact: Option<HandoverArtifact>` 字段——节点在边界显式声明产出；主循环收到后①存入 run 交接物区②发 phase_result 事件（只带 artifact_id + summary，事件轻、物权威）。
  - **硬+软双层校验**：构图期硬校验（管线定义的边声明接受的 kind，不匹配即拒绝构图→非法组合在构图期暴露，每条非法组合一条拒绝用例）；运行期软校验（该到的物缺失→管线定义声明的降级支路接管，D0-14 断链补全语义）。
  - **一等降级物**：Degraded 为一等 kind——探索失败/委派失败/评审不达阈都产出物，降级在链上有实体痕迹，审计链不断裂（反模式 6"永不静默降级"的数据基础）。
  - **粒度裁定**：物 = 阶段/节点级（Execute 各步输出聚合为一个 Execution 物，步骤级是 phase 内细节）；终局结论 = run 的 final_message（已有），不另设"结论物"。
- **锁动**：D0-1（合法性=构图期 kind 校验）/ D0-2（软硬双层落定）/ D0-3（枚举测试点）/ D0-14（断链=物缺失→降级支路）/ B7（phase_result 带 artifact_id，升级）/ B9（Degraded 物，升级）/ B0-13（物=懒持久单位确认）/ A6（迹线段结果与理由=物的 summary）/ D0-11（管线定义粒度=阶段级，与物同粒度）
- **依据**：[02-现状事实.md](02-现状事实.md) §十一（PlanItem/ReflectionResult/RouterDecision 已类型化但藏于事件载荷）/ C20（可审计辅气质）/ D21（物=链的内聚单位）/ B22（run 交接物区容器已定，本条填内容）/ [03-外部参照.md](03-外部参照.md) §三.5（计划是一等公民）。
