# 请求头快照设计草案（阶段 3 · A2 补齐④）

> status: 已完成（2026-09-17 裁定 + 同日实施；评审通过，按建议采纳 D9-D14）
> 依据：[04-施工准备 §一 A2](04-施工准备.md)（补齐 ④：`request/header` 使每个请求是日志的纯函数）+ D1 裁定（四项全补；**本项改动面最大，须单独设计评审**）
> 上游参照：deepseek-harness 的 `request/header` 会话事件族——每个请求派发前把「请求头」写入 append-only 日志，配合消息日志使**任一历史请求可被逐字重建**
> 本文只做设计与裁定点收敛，**未动任何代码**

## 一、立项理由（为什么本项目需要）

现状：出问题时（"模型为什么这样回答/为什么超窗口/为什么路由到该管线"）只能靠 `info!` 日志与经验猜测——
- 请求的**系统提示词**（A4 收口后的 12 段组装结果）只在 `sessions.prompt_sections` 存**最新一份**，历史轮次的组装结果不可回溯
- 请求参数（模型 / temperature / max_tokens / thinking_level / 工具集）**完全没有留痕**
- 消息侧虽已有 `session_log`（不可变原文）+ `session_live`（活跃视图游标），但「**某次请求看到的是哪一版视图**」没有记录——重建缺一条边

补齐后：`(请求头快照 + session_log + 快照里的视图游标)` = **任一请求的纯函数重建**（诊断/复现/审计；也是 05-§2.2「请求派生前」语义的可观测化落点）。

## 二、快照内容定义（"除消息以外的一切"）

| 字段 | 内容 | 来源（现状落点） |
|---|---|---|
| `provider` / `model_id` | 实际生效的 Provider 与模型 | `ProviderConfig`（热切换后生效值） |
| `params` | temperature / max_tokens / top_p / top_k / thinking_mode / thinking_level | `AgentLoopConfig`（`build_prompt_options` 处直传） |
| `system_prompt` | 组装后的完整系统提示词（A4 收口 = `assemble_sections` 结果） | `PromptCallOptions.system_prompt_override` |
| `sections`（可选） | 结构化段清单（`Vec<PromptSection>` JSON）——比全文更可审计（能看清每段来源） | `AgentLoopConfig.prompt_sections` |
| `tools` | 工具名清单 + **schema 摘要哈希**（全量 schema 可选） | `PromptCallOptions.tools` |
| `purpose` | 调用用途：`main` / `compaction` / 其他旁路 | 新增字段（阶段 3 · D4 已加 `purpose`） |
| `view_cursor` | **消息视图游标**：消息条数 + 末条在 `session_log` 的坐标（重建的"缺的那条边"） | `session_live` 写穿时可见（`replace_messages` 的游标语义） |
| `request_seq` | 会话内请求序号（单调递增；与前端 trace 的 `seq` 口径对齐） | kernel 侧计数 |

**重建语义（验收定义，需拍板）**：给定 `(session_id, request_seq)` → 取该请求头 → 按 `view_cursor` 从 `session_log` 恢复消息视图 → 与 header 拼接 = **当次请求的等价重建**。
「等价」口径二选一：**(a) 字节级一致**（要求快照与派发零漂移，实现最重）或 **(b) 结构级一致**（消息正文/工具 schema/参数逐字段等值，允许序列化差异）。建议 (b)。

## 三、落点与写路径（三处关键选择）

### 3.1 存储载体（三选一）

| 选项 | 形态 | 优点 | 代价 |
|---|---|---|---|
| A. 新表 `request_headers` | `(session_id, request_seq, created_at, model, params_json, system_hash, tools_json, view_cursor_json)`；系统提示词等大对象**内容寻址**（`system_hash` → 首见时存全文，复用 raw 存储思路） | 语义独立、不污染视图同步事件；去重后体积可控（系统提示词只存一份） | 新增表（加法式，不动 `session_log/session_live`）；查询需 JOIN |
| B. `session_events` 加列 | 复用现有审计表，加 `detail TEXT`（可空 JSON） | 零新表；与既有审计流同序 | 视图同步事件（初始/追加/裁/改）与请求头混一列，语义混杂 |
| C. 文件落盘 | 按会话写 `{记忆根}/requests/{session}.jsonl`（追加式） | 实现最轻、与 raw/locks 同思路 | 与 SQLite 的会话生命周期解耦（删除会话需额外清理）；查询不便 |

**建议 A**（并复用 raw store 的内容寻址去重；`session_log/session_live` 不动）。

### 3.2 写路径时机（"崩溃后可重建"的强度选择）

- **s1 弱**：kernel 发事件 → 命令层异步落库（同 Plan 事件族/锁监听器模式）。窗口 ≈ 数 ms，崩溃时丢**最后一条**快照。
- **s2 中**：事件 → 同步追加到会话文件（`std::fs`，像压缩锁）→ 异步刷入 DB；崩溃后可由文件补齐。
- **s3 强**：派发前**阻塞等落库**（`await` 一次 INSERT，约 1–3ms/请求）。与主链路同步，语义最干净。

**建议 s2**：主链路零阻塞收益（写文件 < 0.1ms），崩溃强度足够（丢也不会丢正在飞的那条）。

### 3.3 采集点（kernel 侧唯一）

`run_react_loop` 的 `build_prompt_options` 之后、`call_llm_with_retry` 之前（阶段 3 · ① 把压缩放在这**之前**，两者顺序天然正确：快照 = 压缩后实际派发的内容）。旁路调用（压缩摘要等）**也走同一采集点**（`purpose=compaction`），口径统一。

## 四、验收（草案）

1. 单测：给定一次 run，`request_headers` 出现 `main` 一条；字段与 `PromptCallOptions`/config 一致
2. 重建测试：`(session_id, request_seq)` → 重建请求的结构级等值（消息视图按游标恢复）
3. 压缩交错场景：压缩前后各请求的快照各归其位（游标可区分视图版本）
4. 去重：同一系统提示词多次请求只存一份全文；`system_hash` 稳定
5. 不回归：主链路无额外可见行为（Tauri 命令不新增；前端零改动）

## 七、裁定结果与实施记录（2026-09-17）

**裁定（用户拍板：按建议采纳）**：D9 载体 **A**（新表 `request_snapshots` + 内容寻址去重 `request_blobs`）· D10 重建语义 **(b)** 结构级等值 · D11 写路径 **s2**（同步文件 WAL + 异步落库）· D12 **随会话级联删除** · D13 **旁路调用全收** · D14 **本期不做 UI**。

**实施修正（相对草案 §二 的「视图游标」）**：草案原写「游标 = 消息条数 + 末条在 `session_log` 的坐标」。实施期发现该口径有硬缺口——**在途消息在轮次结束写穿前不在 `session_log` 里**（写穿发生在 run 收尾），崩溃时「最后一条边」仍断。故改为记录**消息视图增量**本身：
- 上一条快照视图是当前视图的**前缀**（逐字段等值比对）→ 仅记新增消息（`Appended`）
- 否则（折叠 / 裁剪 / 回填 / 恢复等改写中段）→ 记全量视图（`Full`）

于是「任一请求可重建」不再依赖写穿时机，且（旁路）`material_ref` 补齐了压缩摘要指令的材料来源。

**落地**：

| 层 | 落点 | 说明 |
|---|---|---|
| kernel | `agent/request_snapshot.rs`（新增） | `RequestSnapshot`（header + `ViewUpdate::Appended/Full`）+ `capture_request_snapshot`；前缀判据 = **逐字段等值**（假前缀会静默损坏重建 → 宁可全量）；`OrchestratorEvent::RequestSnapshotCaptured` + `keys` 登记（`mode_of` 保持 Emit） |
| kernel 采集点 | `run_react_loop`（主链路，`set_messages` 之后 / 派发之前）；`generate_compaction_summary`（旁路，`purpose="compaction"` + `material_ref` = 折叠材料外置坐标） | 事件经总线**同步分发** → 监听器先落 WAL 再派发 |
| commands 存储 | `session_store`：`request_snapshots`（`snapshot_digest` 唯一键 → WAL 重放幂等）+ `request_blobs`（系统提示词 / 工具集内容寻址去重）；`reconstruct_request_view`（**纯函数**：全量重置 + 增量拼接；缺链拒绝重建）+ `RequestSnapshotRecord` 一并入 crate 公开面 |
| commands 写路径 | `request_snapshot.rs`（新增）：`RequestSnapshotListener`（同步追加 `{记忆根}/requests/{session}.jsonl`）+ `spawn_snapshot_flusher`（**装载期补齐** → 随通知增量刷入）+ `WalGate`（追加与截断互斥，保守不丢行）+ `remove_wal_file`（会话删除接线） | 不逐行 fsync：目标场景是**进程崩溃**（文件经 OS 页缓存存活），非整机断电 |

**验证**：kernel **259/259**（+3 采集契约：首条全量与 header 字段 / 增量与「全量+增量 = 视图」重建 / 折叠后回退全量 + 旁路带材料坐标；+2 前缀判据单测）· commands **180/180**（+5：存储往返与重建 / 去重与重放幂等与缺链拒绝 / 监听器追加与刷入 / 装载期坏行跳过 / 会话清理幂等）· src-tauri `cargo check` 全绿 · 前端零改动。

### 旁路入账扩展（D13 收尾，2026-09-17）

pattern 引擎的直调请求（不经 `AgentLoop` 采集点）纳入同一入账链：

| 层 | 落点 | 说明 |
|---|---|---|
| kernel 采集 | `GenaiBackend::prompt`：`purpose` 标签存在即视为旁路调用，**派发前**采集 | 主链路 `purpose=None`（由 AgentLoop 采集，避免双重入账）；压缩摘要走 `prompt_side_call`（已由 AgentLoop 采集 + 材料坐标），按标签显式排除 |
| kernel 构造 | `request_snapshot::build_bypass_snapshot` | 视图 = **本次实际请求消息**（backend 内部视图），**恒记全量**——与主链路 `state.messages` 视图不同构，不参与其增量比对 |
| kernel 链路锚点 | `request_snapshot::SnapshotChainAnchor`（`AgentLoop::new` 订阅本环 key） | 旁路行入链 → 本环增量基点置 `None` → 下一条本环快照必记全量。理由：重建链「`Full` 重置基底 / `Appended` 拼增量」，若旁路行插入后本环仍按旧基点记增量，重建会**静默错位**——不变式「重建基底 == 采集基点」。事件同源：桥接竞争丢事件时，行与重置一并缺席，链仍自洽 |
| 标签清单 | `router` / `reflection` / `refine` / `tot_expand` / `tot_score` / `tot_goal_check` / `got` / `orchestrator_complete` / `orchestrator_decide` / `orchestrator_react_step` | 10 个 pattern 直调点 + 编排适配器 3 方法；全部为 `agent.node_backend()`（会话同一 GenaiBackend 实例）→ 事件经 `BackendEventBridge`（on_any）到会话广播器 → WAL 监听器 |

**验证（扩展后）**：kernel **262/262**（+3：旁路快照形状与 header / 链路锚点只重置旁路行 / 旁路行入链后本环回退全量）· feature-gated（`--features llm-genai --offline`）291 通过 + 1 **既有失败**（`get_model_cloud_deepseek`，与本轮无关）——含新增接线测试（带 `purpose` 直调 → 采集先于派发；无标签不采集）· patterns **117/117**（+1 标签断言）· commands **180/180** · src-tauri `cargo check` 全绿 · 前端零改动（命令层事件转发对未识别事件为 catch-all 忽略）。

**已知边界（按「限范围」纪律留待后续）**：

1. 快照记录的是「请求**将要**发送的内容」；派发前失败（如无 Key）仍留痕，但**无结果字段**（失败诊断暂无）。
2. 重建覆盖「header + 消息视图」；系统提示词 / 工具经去重池还原（结构级等值，容忍序列化差异），**不保证字节级**。
3. 旁路行**恒全量**（无增量优化）：连续 pattern 调用（ToT/GoT 多轮）每条都重复整段视图，存储有冗余——正确性优先；如需压缩再引入「旁路专用基点」。
4. 编排适配器 `complete` 的系统提示词为**文本拼接**（kernel 系统槽位未走 `system_prompt_override`），快照的 `system_prompt` 字段为 `None`、系统文本在消息内——结构级等值不受影响。
