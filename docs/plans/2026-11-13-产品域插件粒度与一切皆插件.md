## 一、产品域插件粒度实测（任务三）

### 1.1 一句话结论

产品域的插件粒度**不是按「功能」划的，是按「侧栏有没有入口」划的**。
`kind: 'sprout' | 'utility'` 这一个字段决定了全部 41 个插件的形态，
而它只回答「贡献视图」还是「贡献 overlay」——不回答任何关于职责边界的问题。
结果是：**31 个插件严格等粒（各 1 个视图），10 个插件内部粒度相差 180 倍**
（`settings` 3943 行 vs `search` 22 行）。

### 1.3 六贡献位：机制齐了，覆盖不全

产品域插件 API（`apps/tauri/src/world/api.ts`）提供 7 个方法，归为五个平台级贡献位；
§4.2 的 `outline` 发现揭示了**第六个已实现但未提升的贡献位**（`form`）：

| 贡献位 | 方法 | 使用情况 | 覆盖度 |
|---|---|---|---:|
| 视图 | `registerView` | 31 个插件，各 1 个 | 31/31 sprout |
| overlay | `registerOverlay` | 10 个插件，共 13 个 | 10/10 utility |
| 实体类型 | `registerEntityV2` | 23 个插件，25 个类型 | 23/41 |
| 关系类型 | `registerRelationV2` | **0 个插件** | **0/41** |
| Facet | `registerFacet` | 1 个插件（`items`，2 个） | **1/41** |
| 能力 | `capabilities.register` | 1 个插件（`mindmap`，5 条） | **1/41** |
| （待提升）表现形式 | 无平台 API；`outline` 私有 `registerForm` | 1 个插件内部，11 种 | — |

**三个贡献位是空转的，一个贡献位是私有的。** 这是本次分析最重要的结构性发现之一：

- **关系类型贡献位 0 使用**：119 条关系定义全在 `entity-core/src/relations/`，
  分 5 个文件（index 102 / sproutTabs 7 / creature 4 / faith 3 / outlineLateral 3）。
  后四个文件的注释都写着「单独文件注册，避免膨胀已冻结的 relations/index.ts」——
  这是**集中登记与插件自治之间的妥协产物**，方向对但没走完。
- **Facet 贡献位被误用**：`weapons`/`apparel`/`items` 是 item 实体的三个 Facet 视图，
  正确做法是三个插件**各自注册**自己的 Facet，实际只有 `items` 注册了 2 个。
- **能力贡献位 1 个用户，且调用端不存在**（见 §3.3）。
- **表现形式贡献位被关在 `outline` 内部**（见 §4.2 的关键发现）——
  这是唯一一个「形态已经正确、只差提升」的贡献位。

### 1.4 三个「声明面」的空转

| 声明 | 应填数 | 实填数 | 后果 |
|---|---:|---:|---|
| `manifest.kind` | 41 | 13 | 28 个靠 `manifest.ts:22-25` 缺省兜底为 sprout；`validateManifest` 不校验该字段 |
| `manifest.domain` | 31（sprout） | 30 | `mindmap` 未声明（其 manifest 在独立 `manifest.ts`，漏了 domain） |
| `manifest.requires` | 10+（实际取服务的插件） | **1** | 只有 `timeline` 声明 `world.projectExtras`；装载器的依赖预检**基本没生效过** |

`requires` 空转是最该修的一条：dsh 侧 `inject` 是每个插件**必填**的核心声明，
它是「依赖声明即启动顺序」的唯一来源。产品域有这个机制但没人用，
导致插件与服务的真实依赖边在图上是不可见的。

### 1.5 插件身份的实际载体

41 个插件里只有 1 个（`mindmap`）有独立 `manifest.ts` 文件，其余 40 个把 manifest 内联在 `index.ts`。
manifest 的核心字段被 `validateManifest` 校验（id 形状 / version / description / requires /
domain / secondaryDomains / entityTypes），但 `kind` 不在校验范围。

**插件 id 命名已统一为 `official.*`**（41/41），这是好的一面：
与 dsh 侧的 `@deepseek-ai/dsh-*` 命名空间天然分域。

## 二、`kind` 二分不足以承载粒度管理（任务三的诊断）

### 2.1 现状

```
sprout  = 贡献侧栏视图（31 个）
utility = 纯 overlay/能力贡献，无侧栏入口（10 个）
```

这个二分在「入口形态」上是准确的（31 视图 + 13 overlay 严格互补，零例外），
但它**不承载任何职责信息**。同一个 `utility` 里有：

| utility 插件 | 行数 | 真实职责 |
|---|---:|---|
| `settings` | 3,602 | 平台管理面（能启停其他插件） |
| `entity-tools` | 628 | 两个死入口 + 一套重复的模板系统 |
| `data-tools` | 653 | 回收站 / 随笔 / 一致性报告三件套 |
| `theme-editor` | 915 | 主题编辑器（Quick/Pro/Code 三档） |
| `search` / `doc-export` / `import-export` / `templates` / `batch-edit` / `version-history` | 21~22 | 搬迁壳（实现全在共享包） |

### 2.2 缺失的维度

按 dsh 的粒度判据（详见 `01-dsh-plugin-granularity.md` §七），产品域 manifest 缺三样：

| 缺什么 | dsh 侧对应物 | 为什么需要 |
|---|---|---|
| **贡献类型枚举** | 无（靠 import 什么服务决定） | 现在 `kind` 混淆了「入口形态」与「贡献类型」；一个插件可同时贡献视图与 overlay 却只能二选一 |
| **服务依赖声明（实际使用）** | `export const inject = [...]` | `requires` 存在但 1/41 使用，依赖图不可见 |
| **配置模式** | `export const Config`（85 个 dsh 插件有） | 产品域插件无配置概念，行为只能硬编码 |

**结论**：`kind` 应拆成两个正交字段——
`contributions: ('view'|'overlay'|'entityType'|'facet'|'capability'|'form')[]`（能贡献什么）
+ `lifecycle: 'always'|'toggleable'`（能否被停用）。
现在的 `sprout|utility` 是这两个维度的错误折叠。

> 第六个贡献位 `form` 来自 §4.2 的 `outline` 发现——它是**已经被实现但没被提升**的贡献位。

## 三、产品域插件粒度的四个实质缺口

### 3.1 缺口一：入口可达性无保障

**实测：`official.entity-tools` 的两个 overlay 是死入口。**

| overlay id | 期望事件 | 全仓派发方 | 组件行数 |
|---|---|---|---:|
| `custom-rel-type` | `ws-open-custom-rel-type` | **0** | 376 |
| `entity-template` | `ws-open-entity-template` | **0** | 221 |

取证：`apps/` + `packages/` 全量搜索这两个 id，命中仅 4 类——
插件自己的注释、插件自己的登记、`Shell.vue:154` 的一句注释、两个测试文件。
两个测试只断言「登记了这两个 id」，**不验可达**。597 行代码运行时零触达。

**同类问题更广的形态：`ws-open-<id>` 是无类型约束的全局字符串事件。**
派发方写错 id 不报错，接收方不存在也不报错——失败模式是「点了没反应」。

**根因：入口注册有两套机制并存。**

| 机制 | 覆盖 | 评价 |
|---|---|---|
| `overlay.menu` 声明 → `AppMenu` 动态渲染 | 6/13 overlay | **正确**：入口随插件装载出现、随卸载消失 |
| 共享包硬编码 `ws-open-*` 事件名 | 7/13 overlay | **错误**：`ui-kit/ViewToolbar.vue:47-61` 写死 5 个 world 插件 id |

后者是**分层方向的实质破坏**：共享包 `packages/ui-kit` 知道了 5 个世界插件的具体身份。
后果有两个：① 插件卸载后工具条菜单仍在、点击静默失效；② 新增 overlay 时得去改共享包。

### 3.2 缺口二：状态获取有四套写法

「插件怎么取共享状态」这件事，仓里有四种并存写法：

| 写法 | 采用插件数 | 形态 |
|---|---:|---|
| 直接 `useXxxStore()` | 4（`settings` 18 处 / `custom` 1 / `mindmap` 1 / `field-matrix` 1 非 pinia） | 绕过服务目录 |
| `serviceAccess.ts` 独立文件 | 10 | 建了间接层 |
| `getWorldService('world.xxx')` 内联 | 若干 | 无文件、无声明 |
| 经 `GenericEntityView`/`SchemaRenderer` 取数 | 21 | 不需要直接取数 |

**同一件事四种写法，且第一种（直连）在 `settings` 里是 18 处。**
`settings` 直连有正当理由（它是设置页，要读写全部 store），但它也说明：
服务目录的边界没有被强制，只被「自觉遵守」。

### 3.3 缺口三：能力桥「装好了但没人打」

这是本次分析投入产出比最高的发现。

**建好的部分**（全部实测确认）：
- Rust 侧 5 条命令：`cmd_capability_register` / `list` / `invoke` / `result` / `unregister`
- ACL 按窗口 label 判定（`capabilities.rs`）
- 超时、审计、回执齐全
- 产品域登记 **17 条能力**（12 内建 + 5 mindmap）
- Agent 面（`dsh-plugin-worldsea-console`）登记 1 条

**断掉的部分**：
- **全仓没有任何代码调用 `cmd_capability_invoke`**
- 唯一提到它的地方是注释与 Rust 单元测试
- dsh 树 21,056 个跟踪文件零命中，`workspace-dist` 产物零命中

含义：Agent 让产品域「执行动作」（打开面板、触发导出、跑布局算法）的整条通路是断的。
现在 Agent 只能经 `dsh-plugin-worldsea` 直接读写 `worlddata/` 的 JSON 文件，
碰不到任何界面动作。

### 3.4 缺口四：类型注册不可回滚

`world/api.ts:107` 注释原文：

> 实体/关系/Facet 类型**有意不注销**（类型元数据长期可查，关系查询会引用），故不走 tracked。

视图与 overlay 随插件卸载回卷，类型不回卷。后果：
停用 `official.faith` 后，`faith` 实体类型仍在注册表里，只有侧栏入口消失。

这是既有口径「关闭芽 = 隐藏入口、保留实体」的机制根源，也是与 dsh 侧最根本的机制差异
（dsh 一切注册走 `ctx.effect`，卸载即全回滚）。

## 四、重新划分插件量（任务四）

### 4.1 划分原则：不按 `domain` 划，按「变更原因」划

**先说为什么不能按 `domain` 划。** `domain` 与「功能组」是两套正交轴，实测三个反例：

- `outline` 的 domain 是 `narrative`，但实现是画布（与 `drawing` 的 `tool` 同形态）
- `field-matrix` / `codex` / `gallery` 都是 `tool`，但它们是只读观测器，与 `mindmap`/`custom`（同为 `tool`）性质不同
- `narrative` 4 个插件 24,999 行（35.9%），`society`+`knowledge`+`geo`+`goods` 14 个插件仅 6,141 行（8.8%）

**按 domain 重划会把同类工具拆散、把不同类工具归一起。** `domain` 是内容分类轴，不该承载代码量均衡。

**采用的原则（三条，按优先级）：**

1. **一个插件 = 一个变更原因**（dsh 判据 3「业务分支必须落在独立包」的产品域版）
2. **单实现不拆**（dsh 判据 6「只有出现第二个 Provider 才拆」）——这是防止过度拆分的关键
3. **粒度目标是 500–1500 行的中段**（dsh 实测 p50=652 / p75=1413）

### 4.2 拆分候选（5 个，全部经子目录实测可行性）

| 插件 | 现状 | 内部结构实测 | 拆成 | 依据 |
|---|---:|---|---|---|
| `outline` | 12,305 / 73 | `board/` 12,111 行占 98%（`forms/` 3,984 · `components/` 3,539 · `composables/` 1,376 · `export/` 364）+ 根 `index.ts` 106 | ① `outline`（本体 + 实体类型）② **`outline-forms`**（11 种表现形式，3,984 行） | **forms/ 已自带私有插件注册表**（`registry.ts` 的 `registerForm`，注释原文：「新增一种表现形式 = 注册一个 FormDefinition，**不需要改编辑器代码**」）。这是全仓**除第二棵树之外唯一一处真正的插件式扩展点**，形态已经对了，只差提升为真插件 |
| `timeline` | 8,269 / 67 | `calendar/` 2,624（22 文件）· `components/` 2,902（20）· `composables/` 2,230（22）· 根 3 文件 513 | ① `timeline`（事件 + 组件）② **`timeline-calendar`**（历法内核，2,624 行） | 历法纯计算零 UI 依赖，且**已有第二个消费者**：`culture/FestivalCalendarView.vue` 复用它 → 符合 dsh 判据「出现第二个 Provider/Consumer 才拆」 |
| `tactical-board` | 4,774 / 28 | `composables/` 2,810（16）· `components/` 1,355（9）· 根 `TacticalBoardView.vue` | ① `tactical-board`（棋盘 UI）② **`tactical-engine-adapter`**（`composables/TacticalEngineJS.ts` 336 行 + 引擎绑定） | 引擎适配是「可替换能力」（wasm `tactical-engine` 可换实现）→ 符合 dsh 三角色判据 |
| `manuscript` | 4,081 / 24 | `components/` 2,369（11）· `composables/` 1,081（10）· 根 | ① `manuscript`（正文编辑）② **`manuscript-books`**（book 实体 + `BookGrid`/`BookInfoDialog`）③ `manuscript-phone-preview`（`PhonePreview.vue` 323 行） | 一个插件注册**两个实体类型**（book + manuscript），是唯一的多实体插件；手机预览 323 行是独立能力 |
| `settings` | 3,602 / 28 | `panels/` 2,632（22 文件）· `data/` 561（3）· 根 | **不拆成多个插件**（见下），但内部 `panels/` 已按 13 分类独立成文件 | 平台管理面，拆成可卸载插件语义荒谬 |

**`notebook` 不拆（更正）**：初判拟拆出 `migrations/`，实测该目录只有 **1 文件 / 45 行**，
拆了没有收益。`notebook` 的真实构成是 `components/` 2,331 + `composables/` 1,586，
是一个连贯的编辑器插件，**属于健康粒度**（5,064 行偏大但无内聚问题）。

**`outline` 的关键发现（本次分析最有价值的一条）**：
`board/forms/registry.ts` 是一个**自研的私有插件注册表**，形态与第二棵树完全同构——

```ts
export interface FormDefinition {
  form: string            // 唯一 id
  label: string
  icon: string
  kind: 'derived' | 'inline'
  defaultConfig: Record<string, unknown>
  configSchema: FormConfigField[]
  component: Component    // 组件引用
}
export function registerForm(def: FormDefinition): void   // 幂等注册
export function unregisterForm(form: string): boolean      // 可反注册
export function getAllForms(): FormDefinition[]
```

11 种表现形式（title / card / question / paragraph / script / sentence / table / tree /
progress / storyline / refs）各自独立注册在 `initializeForms.ts`（6 个）与
`initializeAggregateForms.ts`（5 个）。**这意味着 `outline` 早就在用插件思维组织代码，
只是这个注册表是私有的、不随插件启停、外界看不到。** 把它提升为平台级贡献位
（`api.registerForm()`）是「一切皆插件」最高性价比的一步。

**`settings` 的特殊处理**：`panels/` 下 22 个文件已按 13 分类独立
（`AppearancePanel` 13 行、`EditorPanel` 13 行、`LayoutPanel` 13 行等薄壳 +
`DetailSettingsPanel` 343、`IconsPanel` 341、`PluginsPanel` 322 等实体面板），
彼此零耦合。**保持为单个插件，不拆。** 唯一硬约束：`PluginsPanel` 读
`availablePlugins()` 全集，必须留在能读到全树清单的位置。

### 4.3 合并候选（2 组，经实测修正）

> **勘误（2026-11-13 22:15）**：本节初版写「4 个树视图重复 968 行、净减约 691 行」，
> **该结论是错的**。实测：`packages/canvas-engine/src/useTreeCanvas.ts`（457 行）早已是

## 五、「一切皆插件」的准确边界（任务六）

### 5.1 dsh 侧的实际程度（对照基准）

dsh 自称 "all-plugin Cordis agent harness"，实测后的准确表述是：

> **一切行为都是插件贡献，但不是每个包都是插件。**
> 373 个叶子包中 77 个（20.6%）既无 `default` 也无 `apply`，是库、装配清单或纯类型包。

dsh 的四层结构（无重叠、合计 373）：基础设施 106 / 能力 108 / 装配 26 /
表现（client）71 / experimental 横切 62。

关键机制（产品域可直接照抄的）：

| 机制 | dsh 形态 |
|---|---|
| 插件契约 | 函数插件 `name`+`inject`+`apply`；服务插件 `export default class`+`static inject`。**无注册表、无白名单** |
| 依赖声明 | `inject` 数组 → cordis fiber 挂起至服务就绪。**依赖声明即启动顺序** |
| 卸载 | 一切注册走 `ctx.effect` 并返回 disposer → **卸载即全回滚** |
| UI 扩展点 | `ctx.slots.register({ name, children })`，`children` 同时是渲染授权 |
| 装配 | YAML patch（`bundle/base` 9 行源码 + 444 行 patch）——**装配是数据不是代码** |
| 配置 | `export const Config`（85 个插件有），required 字段无默认值 |

### 5.2 产品域的边界判定

**判据（两条，缺一不可）：**
1. 它有没有「多份实现」的诉求？
2. 它变成插件后，卸载语义是否成立？

按这两条，产品域机制分三类：

#### 甲类 · 天然不是插件（树的地基，8 项）

| 机制 | 为什么不是插件 |
|---|---|
| 存储后端（`StorageBackend`/`FileStorageBackend`） | 单例、进程级、被所有插件依赖；实现切换是**环境判定**（Tauri vs 浏览器）不是用户选择 |
| schema 注册表（`entitySchemaRegistry`/`fieldRegistry`） | 注册是累积的、查询是全局的；「卸载不注销」是刻意设计 |
| 事件总线（`eventBus`） | 无状态中继，自己不需要生命周期 |
| 快捷键注册表（`useShortcuts`） | 冲突检测天然需要全集；用户覆盖存 localStorage |
| 主题令牌 / 样式层 | CSS 变量层叠顺序是全局一维的 |
| 项目/工作区模型 | 真源在 dsh，产品域只是镜像 |
| Tauri 命令面 + ACL | 进程边界，Rust 侧静态判定 |
| fs 监听（`useFsWatcher`） | 后端一个 watcher、前端引用计数；多实例会重复 emit |

**共同点：全局唯一 + 跨插件共享 + 生命周期长于任何插件。**
它们是 Cordis `Context` 的 `provide`，不是 `plugin`。

#### 乙类 · 必须变成插件才有意义（6 项）

视图 / overlay / 实体类型 / Facet / 能力 / **表现形式（待提升）**——即六个贡献位。
共同点：**「插件向平台注册一个可撤销的东西」，有 id、有归属、可卸载。**

其中表现形式（`form`）是唯一尚未提升为平台贡献位的：
`outline/board/forms/registry.ts` 已实现完整形态（`FormDefinition` + `registerForm` +
`unregisterForm` + 幂等 + 11 种注册），但它是 `outline` 私有的、不随插件启停、外界不可见。
提升它等于给产品域补上第六个贡献位。

#### 丙类 · 位置尴尬（现在是插件，但形状可疑，4 项）

| 插件 | 问题 |
|---|---|
| `settings` | 用「utility 常驻」规避了卸载语义不成立；本质是平台管理面 |
| `custom` | 视图容器，渲染其他插件的 component——组件引用不跨服务边界 |
| `field-matrix`/`codex`/`gallery` | `entityTypes: []` 的只读分析型芽，形状正确但语义窄 |
| `orchestration` | 执行端已退场，字段可填无消费者 |

### 5.3 差距表：产品域 vs dsh

| 维度 | dsh | 产品域 | 差距 |
|---|---|---|---|
| 插件契约 | `name` + `inject` + `apply`，无注册表 | `manifest` + `apply(ctx, api)`，有 `validateManifest` 校验 | **产品域更形式化**（不一定是坏事，但 manifest 字段空转要修） |
| 依赖声明 | `inject` 必填，fiber 挂起 | `requires` 可选，1/41 使用 | **实质差距** |
| 卸载语义 | 一切走 `ctx.effect`，全回滚 | 视图/overlay 回卷，类型不回卷 | **设计差异**（需明确契约，见 §5.5） |
| UI 扩展点 | slot + `children` 授权 | 视图注册 + `ws-open-*` 字符串事件 | **实质差距** |
| 装配 | YAML patch 是一等公民 | 无装配层概念 | **缺失** |
| 配置 | `Config` + schemastery | 无 | **缺失** |
| 分层纪律 | `AGENTS.md` 硬约束 + 脚本强制 | 有 `arch:check` 但无「插件不跨层」规则 | **部分** |
| 第三方插件 | plugin-manager/market 完整 | 有外部插件装载（`.worldsea/plugins/*.js`，约 1s 热装载） | **形态已具备** |
| 数量分布 | p50=652，双峰但中段厚 | 双峰极端，中段薄 | **需重划** |
| 贡献位覆盖 | 各贡献位均有多插件使用 | 5 个贡献位中 3 个空转 | **实质差距** |

### 5.4 「达到 dsh 程度」的具体含义

不是「把插件数做到 373 个」，而是**做到 dsh 的四条性质**：

1. **贡献位正交**：一个插件可以同时贡献视图 + overlay + 能力，各贡献位独立启停
2. **依赖图可见**：每个插件声明它消费哪些服务，装载器能画出依赖图并据此排序
3. **卸载可验证**：任一插件卸载后，它贡献的一切（视图/overlay/入口/能力）全部消失，无残留
4. **装配是数据**：产品形态变体（如「写作模式」「推演模式」）用配置表达，不用代码分支

产品域**已经做到 2 之外的机制、4 的零**，缺的是机制的**覆盖**与**验证**。

### 5.5 建议的明文契约（消除丙类歧义）

把「类型不可卸载」从隐含设计变成明文契约：

> **产品域插件契约（三条）**
> 1. **可卸载贡献**：视图、overlay、能力——随插件卸载全回滚，入口随之下线。
> 2. **不可卸载注册**：实体类型、关系类型、Facet——属于**平台登记面**，
>    插件是「首次登记者」而非「所有者」。停用插件只隐藏入口，不撤登记。
>    理由：类型元数据被关系查询与导出链引用，撤登记会让历史数据失去解释。
> 3. **依赖必须声明**：插件消费任何 `world.*` 服务，必须在 `manifest.requires` 声明；
>    装载器据此预检与排序。

这条契约一旦定下，`faith` 停用后类型仍在就不是 bug 而是设计。
