# Agent 底层能力基线 与 三阶段工程成熟度评估

> 缘起（2026-08-31）：三模式（深度思考 / 知识探索 / 任务执行）移除后，除世界观构建场景外，
> 我们的 Agent 最底层应当恒定呈现什么能力？对照 Prompt → Context → Harness 三阶段演进，
> 各阶段我们是否达到标准并成熟？
>
> 本文档为方向级文档：先立框架、逐层评估、给出底层能力清单与两项补课方向。
> 文档内不讨论代码技术实现话语，统一使用能力 / 机制 / 层面语言。

---

## 一、框架：三阶段是层层叠加，不是替代

参考 2026 年多方共识（OpenAI 官方论述、LangChain、Anthropic、《Context Engineering》论文、
智源/腾讯云/ThoughtWorks 等），AI 工程经历了三层抽象递进，每一层都是前一层的「地基」：

```
Harness Engineering（2026 主导） —— 管「让系统如何稳定运行」：运行环境
 └─ Context Engineering（2025 主导）—— 管「给模型什么信息」：信息环境
      └─ Prompt Engineering（2022-24 主导）—— 管「怎么说」：单条指令
```

| 层 | 控制粒度 | 本质 | 你设计什么 | 一句话局限 |
|---|---|---|---|---|
| Prompt | 单条消息 | I/O 优化 | 措辞、格式、示例、思维链引导 | 任务一复杂就失控 |
| Context | 单次调用 | 信息管理 | 上下文包：指令 / 记忆 / 工具 / 检索 / 历史压缩 | 信息到位，执行仍会跑偏 |
| Harness | 全生命周期 | 系统工程 | 执行循环、工具环境、状态管理、控制流、验证、反馈回路 | 衡量标准：Agent 无人监管完成正确工作 |

嵌套规则：**Harness 实现执行循环 → 循环每一步组装 Context → Context 内嵌 Prompt**。
每层不废弃前层，只是多了下层之上的杠杆。

## 二、逐层评估：我们的阶段成熟度

### ① Prompt 层 —— 判定：成熟（且已超纲）

我们早已脱离「写咒语」，进入**结构化、可编程的系统提示工程**（行业划分里属 2024 底-2025 的
Structured Prompt 阶段）：

- 一套常驻注入的规则体系：项目世界观定义 + 全局/项目双层规则 + 写作/设计/工具规范 + 协作约定，
  优先级显式声明，覆盖 Agent 行为的各个约束面
- 节奏型注入：长上下文背景知识按「全局计数 + 窗口合并」动态注入，避免每轮全量占用上下文
- 规则中途保存立即生效（配置变更实时传播到当前会话，不需重启）

Prompt 在项目里已被正确降格为 **Context 的最内层** —— 成熟。

### ② Context 层 —— 判定：半成熟（基础设施齐、核心信息能力未施工）

定义（Karpathy）：「把上下文窗口填进下一步恰好需要的信息——这是一门艺术与科学」。

| Context 组件 | 项目现状 | 判定 |
|---|---|---|
| 指令（系统提示） | 常驻规则体系 + 动态刷新 | ✅ 成熟 |
| 工具（描述与注入） | 大规模工具总线的注入与扩展（含技能、连接器） | ✅ 成熟 |
| 历史（保留/压缩/还原） | 会话消息持久化 + 刷新还原 + 上下文压缩；窗口占用语义已澄清 | 🟡 基建在、策略待校 |
| 记忆（短期/长期） | 短期对话记忆（窗口滚动）+ 长期实体记忆（知识图谱已有载体）；**记忆系统设计未展开** | 🟡 主缺口之一 |
| 检索（语义/混合） | 千万字级规模测算完成、混合检索方案已评定；**尚未施工** | 🟡 主缺口之二 |

**结论：Context 层的两个核心件（语义检索 + 记忆系统）正是此前挂起的「同源三件套」的一部分
（连同窗口阈值校准）。信息层是当前明牌缺口。**

### ③ Harness 层 —— 判定：基本成熟（项目重心，主体闭环，两处待证）

这一层是项目投入最重、工程化最高的面：

| Harness 能力 | 项目现状 | 判定 |
|---|---|---|
| 执行循环 | 思考→行动→观察的基础循环，内建速率限制 / 重试 / 软超时 / 看门狗 | ✅ |
| 计划-执行闭环 | 计划制定 → 确认 → 分步执行，计划随会话持久化 | ✅ |
| 编排骨架 | 统一编排引擎，覆盖十余种编排模式（计划执行 / 思维探索 / 思维树 / 主管调度 / 多智能体…），含分层记忆与内核级模型接入 | ✅ |
| 路由 | 多通道智能路由决策，决策过程归入过程可观测（不泄漏为正文） | ✅ |
| 过程可观测 | 全量事件流 + 动作段三类通道，且动作段可持久化、刷新后完整还原 | ✅ |
| 状态与恢复 | 长任务进度存点、会话持久化、中断恢复 | ✅ |
| 反馈回路 | 工具成败权威判定、失败自动重试、敏感操作确认 | ✅ |
| 工具系统层打通（MCP） | 配置化已完成、工具注入链路存在；**但未在真实系统层接触验证（前端 UI 未改动、Agent 后端未接真实环境），能力离真正打通还差**（2026-09-01 反馈补入） | 🟡 |
| 上下文管理 | 大上下文窗口阈值策略 + 压缩后按记忆恢复的协议 | ✅ |
| 业务验证机制 | 有自动化测试基线 + 计划收敛校验；**缺「独立验收器」对每步产物做验收（防『假装完成』）** | 🟡 |
| 稳定性实证 | 有多轮真机冒烟；**一批真机验收项（T10-T15）尚未集中执行** | 🟡 |

**结论：Harness 层主体闭环，行业前沿方向（2026 主导层）与我们重心重合。
三个待证点：① 业务产物验证闭环（独立验收器 / 防假结束）；② 真机稳定性的系统化实证；
③ MCP 真实系统层打通。**
补充观察（2026-09-01 用户反馈）：上述待证点基本都要基于**整个 Agent 系统的完善**才能收敛——
即最终都归到 Harness 层（最终阶段）的完善，而非单项孤立补课。

### 综合排序

```
成熟度：Prompt（成熟） > Harness（基本成熟） > Context（半成熟）
```

## 三、三模式移除后：Agent 底层恒定呈现的能力带

三模式移除剥掉的是**场景外壳**（模式选择、模式判型、阶段化展示），**不是能力本身**——
深度推理蕴含在执行循环与编排机制里、检索蕴含在工具集里、规划执行蕴含在计划-执行闭环里。

除世界观构建场景外，Agent 底层恒定呈现一条**通用主干能力带**（产品语言描述）：

```
目标层   理解意图 → 形成计划 → 与你确认
执行层   思考→行动→观察 的基础循环 + 大工具集（含技能与连接器，按需调用）
状态层   短期对话记忆（滚动窗口） + 长期记忆（图谱化实体载体） + 上下文压缩与还原
可靠层   失败自动重试 · 敏感操作确认 · 软超时看门狗 · 收敛判定 · 长任务可恢复
观测层   全量事件流 + 动作段持久化与还原 —— 过程可还原、可回放、可审计
扩展层   技能 + 连接器（配置化、热加载、规则动态刷新）
```

**产品定位呼应**：世界构建是上层场景；底层承诺是——**一条不区分模式、可靠执行 + 全程可观测 + 可恢复的通用 Agent 主轴**。任何上层场景（世界观构建、知识整理、任务交付…）都挂在这条主轴上。

## 四、我们要做的（两项补课方向）

> 两项均以「能力到位、可验证」为收口标准。下文每项按同一结构展开：
> **做什么 → 为什么 → 展开内容 → 做到什么程度**，力求直接可执行，不再停留在方向表态。

### 方向 A：补齐 Context 层 ——「记忆与信息供给」

背景：Context 层是当前唯一「半成熟」的层，缺口在信息核心（记忆系统 + 语义检索 + 窗口阈值校准），
恰与项目挂起的「同源三件套」重合。补齐后 Context 层从「基建齐」升级为「信息核心就位」。

#### A1 记忆系统设计展开

**做什么**：把「记忆」从载体（有东西能存）升级为机制（会写、会取、会更新、会遗忘），
并补齐规则体系中长期缺位的记忆说明件。

**为什么**：当前短期记忆靠窗口滚动、长期记忆只有图谱化实体载体——但「什么值得沉淀 / 什么该召回 /
冲突以谁为准 / 失效如何淘汰」没有成体系的规则。记忆是 Context 层信息核心的另一半，缺规则则一切靠实现层偶然行为。

**展开内容**：

1. **短期对话记忆 —— 保留 / 摘要 / 窗口策略**
   - 明确对话进行中哪些信息必须存活（用户意图、关键约束、待办、已确认决策），哪些可压缩为摘要，哪些随窗口滚动丢弃
   - 定义摘要触发时机与粒度：信息量到什么程度值得压成摘要，摘要后原细节如何降级处理
2. **长期实体记忆 —— 图谱化记忆的读写、沉淀与召回**
   - 写入：界定哪些类型的事实（实体、关系、观点、事件、决策）值得跨会话沉淀
   - 召回：新会话 / 新任务开始时带回哪些记忆、带多详细、按什么相关性排序
   - 更新与遗忘：同一实体新旧记忆冲突如何裁决；长期不用的记忆如何降权或淘汰
3. **落地形态：规则体系中的记忆说明件**
   - 记忆行为成为 Agent 恒定行为的显式约束，而非实现层偶然产物（此前一直缺位，等待本设计）

**做到什么程度**：记忆四环节（会写 / 会取 / 会更新 / 会遗忘）形成闭环，可回答
「Agent 记住了什么、为什么记得、什么被忘了」；记忆策略有显式规则可供审查与调整。

#### A2 语义检索落施工

**做什么**：把「项目里存在、但模型不知道」的知识，接入按需取回的能力，补齐信息缺口。

**为什么**：模型只知道自己训练过的东西；项目多年沉淀的规则、设定、历史决策、领域知识若不能按需取回，
Agent 只能「凭模型常识」作答——这正是 Context 层要解决的「给对的信息」问题的另一半。

**展开内容**：

1. **覆盖对象与编目**：界定哪些内容纳入可检索范围（项目知识、历史产物、沉淀规则…），统一编目，
   划清边界而非无限膨胀
2. **检索形态**：混合检索主线——精确命中与语义相近双通道并行、结果融合排序，保证「精确查得到、模糊找得对」；
   与智能检索路径共存（规模测算已完成：千万字级承载量处于该形态的适用区间）
3. **触发与使用**：需要时按需取回（现查现用），而非全量预载；检索结果作为「参考事实」注入，标注来源与可信度
4. **与记忆的分工**：检索回答「项目里有没有 / 是什么」，记忆回答「我们已记住了什么」，二者互补不重叠

**做到什么程度**：一个「模型没学过、但项目里已存在」的问题，能稳定取回正确材料；
检索结果参与回答或判断时，来源清晰可查。

#### A3 上下文窗口阈值校准

**做什么**：以「LLM 上下文窗口占用」为统一计量语义，校准压缩触发点与保留策略。

**为什么**：窗口语义此前已澄清（是 LLM 上下文窗口占用，而非对话条数等），但「何时预警、何时压缩、
压缩后保留什么」仍是经验值，缺一套可调、可验证的参数体系。

**展开内容**：

1. **统一口径**：全项目以窗口占用为唯一计量语义，消除各说各话
2. **阈值策略**：预警点 / 压缩点 / 压缩后保留策略三档可调；压缩不得牺牲关键信息（意图、决策、待办、记忆引用）
3. **还原保障**：压缩后能按既有路径（记忆 + 任务进度）无损接续
4. **参数可观测**：阈值调整有迹可循，可验证「更省窗口且不丢信息」

**做到什么程度**：窗口策略成为可调、可解释、可验证的工程参数；压缩后接续不丢上下文，用户无感知降级。

### 方向 B：夯实 Harness 层 ——「业务产物验证闭环」

背景：Harness 具备反馈回路与自动化测试基线，但缺**对每步业务产物的独立验收**——
LLM 自报「完成」不可全信，需要独立于执行的验收机制（防假结束、防以次充好）。

#### B1 每步产物的独立验收机制

**做什么**：计划内每一步的产物，交付后先经过独立验收环节，不通过则携带反馈重修（设上限）。

**为什么**：执行者的自我报告不可全信——「自报完成」与「真正达到标准」是两回事。
防假结束、防以次充好，只能靠独立于执行的验收。

**展开内容**：

1. **验收对象**：每步交付的业务产物（成果物 / 结论 / 交付物），而非内部过程痕迹
2. **验收时机**：产物形成 → 独立验收 → 通过才进入下一步
3. **验收标准**：按计划制定时即约定好的合格线判定，而非临场感觉
4. **重修回路**：不通过 → 携带具体验收反馈回炉重修；设重修上限，超限升级给你决策，不无限循环

#### B2 「完成」判定与验收解耦

**做什么**：任务是否收敛、步骤是否完成，由验收环节判定，而不是由执行体自判。

**为什么**：把「裁判」与「选手」分开——执行体负责做，验收环节负责判定；
否则完成与否永远取决于执行体的自我感觉。

**展开内容**：

1. **职责分离**：执行体只产出产物与过程记录，不拥有「宣称完成」的最终决定权
2. **判定依据**：基于可核验的产物状态（产物达标、约束满足、目标达成），而非主观陈述
3. **结果落地**：「通过」才进下一步、「不通过」进重修；全链路完成以验收链全绿为准

#### B3 验收可观测

**做什么**：验收结论与理由纳入过程可观测（动作段体系），可回放、可审计。

**为什么**：验收不能是黑箱——每一次「通过 / 打回」都要让用户能看到依据，否则验收本身也无法被信任。

**展开内容**：

1. **结论留痕**：每步验收形成独立记录（验收对象 / 结论 / 理由 / 重修次数）
2. **与轨迹衔接**：验收结论挂在对应步骤的动作段上，刷新还原后仍在
3. **可审计**：事后能完整回答「这一步为什么被判通过 / 为什么被打回」

#### B4 稳定性实证（真机验收批次）

**做什么**：将待验项目（真机验收批次 T10-T15）系统化执行，作为 Harness 层
「无人监管完成正确工作」的量化证据。

**为什么**：自动化测试基线证明「代码按预期行为」，真机实证才证明「在真实环境、真实模型、真实工具下
稳定完成业务」——后者才是 Harness 层的最终标准。

**展开内容**：

1. **批次范围**：覆盖本阶段交付线的真机走查项（编排双轨比对 / R6 动作段还原 / 断线恢复 / 三模式移除等，
   与集中测试清单合并执行）
2. **执行方式**：真实环境跑通完整业务链路，记录「目标 → 步骤 → 产物 → 验收」全链条
3. **证据形态**：每次实证产出可复读的记录（做了什么、产物是什么、验收过了吗），沉淀为稳定性证据库
4. **达标判定**：批次全绿 → Harness 层从「基本成熟」升级为「成熟（有实证）」

**做到什么程度**：任一待验项都能给出「链路跑通 + 产物达标 + 可复读证据」；批次收敛后 Harness 层达标定论。

## 五、成熟度路线

```
当前：Prompt 成熟 · Harness 基本成熟 · Context 半成熟
  │
  ├─ 方向 A（Context 补课）→ Context 从半成熟 → 成熟
  ├─ 方向 B（Harness 验证闭环）→ Harness 从基本成熟 → 成熟（含真机实证）
  │
  └─ 全层成熟后：底层主轴稳定，任何上层场景（世界观构建等）可在此之上直接生长，
       产品差异化 = 上层场景 × 稳固底层底盘
```

优先级建议（后续讨论拍板）：方向 A 与挂起的「③ 记忆系统设计」同源，可先行展开；
方向 B 中的真机实证与集中测试批次合并执行，验收机制作为 Harness 层的独立再立项。
