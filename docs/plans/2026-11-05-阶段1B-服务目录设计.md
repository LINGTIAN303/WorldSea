## 一、为什么这是 P0

`apps/tauri/src/world/tree.ts:28` 现在是：

```ts
export const WORLD_SERVICES: readonly string[] = ['world.info']
```

**只有一个服务。** 这导致：

2. `ctx.inject` 无可注入之物 → 空间轴（reactive coeffect）完全空转

**没有服务目录，就没有依赖图；没有依赖图，Cordis 就只是个「插件容器」而非「可组合框架」。**

## 二、命名约定（先定，避免后面返工）

### 2.1 命名空间划分

| 前缀 | 归属 | 例子 |
|---|---|---|
| `world.*` | 产品域世界语义 | `world.info` / `world.entities` |
| `dsh-*` | dsh 侧（不归本树） | `dsh-agent` / `dsh-session` |
| 其他 | 禁止 | — |

**规则**：本树的服务一律 `world.` 开头，与 dsh 侧的 `dsh-*` 天然分域。这条已生效（`WORLD_SERVICES` 现为 `world.info`）。

### 2.2 ★ P2 关键约定：服务名与能力 id 同构

用户 2026-11-05 拍板「未来会互相直接调用」，因此本目录**必须**与能力桥 id 对齐：

```
服务名（复数）：world.entities
能力 id（单数.方法）：world.entity.list / world.entity.put / ...
                    ↓ 同一个动作的两种调用形态
直接调用：ctx.get('world.entities').list()
桥调用：  invoke('world.entity.list', ...)
```

**对齐规则**：
- 服务名用**复数**（`world.entities`），表示「一类东西的集合」
- 能力 id 用**单数.方法**（`world.entity.list`），表示「对某个东西做一个动作」
- 二者共享同一份实现——服务是方法表，能力 id 是方法表的桥接暴露

**这样未来若合并成一棵树，能力调用可退化为 `ctx.get('world.entities').list()`，零改造。**

## 四、服务形态规范

### 4.1 服务暴露「方法表」，不暴露「store 实例」

```ts
// ✅ 正确
ctx.provide('world.entities', {
  list: () => entityStore.entities.value,        // 返回响应式数组引用，零拷贝
  get: (id: string) => entityStore.entityMap.get(id),
  put: (entity: Entity) => entityStore.create(entity),
  update: (id, changes) => entityStore.update(id, changes),
  delete: (id: string) => entityStore.remove(id),
})

// ❌ 错误
ctx.provide('world.entityStore', useEntityStore())
```

**理由**：
- 方法表可以加访问控制、加日志、加隔离
- store 实例暴露出去，就等于把内部结构钉死成公共契约

### 4.2 返回引用而非拷贝

`list()` 返回响应式数组**本身**（`entityStore.entities.value`），不是 `[...]` 拷贝。

**理由**：96 个文件直访 `useEntityStore` 的性能假设就是「拿到响应式引用」。改成拷贝会全面改变性能特征，是回归风险。

### 4.3 服务的生命周期

| 时机 | 动作 |
|---|---|
| 起树（`startWorldTree`） | `ctx.provide` 全部服务 |
| 拆树（`disposeWorldTree`） | `drops` 手动撤 + **root fiber dispose**（双保险） |

**⚠️ 更正一处此前的误判**：本文初稿曾写「`tree.ts:168-174` 的 `drops.push(context.provide(...))` 是多余的，Cordis 已经做了」——**这是错的**，实测证伪：

| 测试 | 结果 |
|---|---|
| root ctx **不** dispose，`provide` 后服务 | **仍在**（不会自动撤） |
| root ctx 不 dispose，手动调 `drop()` | 服务撤除 ✅ |
| 模拟 `tree.ts` 形态（只手动 drop，不 dispose root） | 服务正确撤除 ✅ |

**结论：`drops` 数组是必要的**，因为 `disposeWorldTree()` 原先从不拆 root。初稿的判断已在实测后更正。

### 4.4 ✅ 已施工：补 root fiber dispose（2026-11-05）

**发现的问题**：`disposeWorldTree()` 拆完插件、撤完服务后把 `ctx = null`，却**从未拆 root fiber**。这意味着任何直接挂在 root 上的 `ctx.effect`（非插件注册）永远不会被回收。

**实测确认的正确入口**（`Context` 上**没有** `dispose()` / `stop()`，只有 `ctx.fiber.dispose()`）：

| 测试 | 结果 |
|---|---|
| root 级 effect 被 `fiber.dispose()` 回收 | ✅ PASS |
| root `provide` 的服务被自动撤 | ✅ PASS |
| 子插件随 root dispose 一并回收（不逐个 dispose） | ✅ PASS（3/3） |
| dispose 后可重建新 Context | ✅ PASS |
| `drop()` 与 `fiber.dispose()` 同时调用 | ✅ 幂等，无异常 |

**落法**（`tree.ts:370-379`）：在 `drops` 之后追加 `void root.fiber.dispose().catch(...)`，保持同步签名（与既有 `void fiber.dispose()` 同口径）。

**回归锁**（`__tests__/tree.spec.ts` 新增 2 例，7 例全过）：
- 「拆树回收 root 级 effect」——**反证已做**：注释掉 `root.fiber.dispose()` → 精确报 `expected false to be true`；恢复后转绿。
- 「拆树后服务已撤（world.info 不可取）」——锁 drops 与 root dispose 的双保险结果。

## 十、✅ 第一个真实依赖落地：`world.projectExtras`（2026-11-05）

### 10.1 为什么新增第 7 个服务

在给插件挂真实 `requires` 前，先做了一次扫描，结果推翻了我原先的假设：

**42 个插件里，没有一个在 `apply` 里读应用共享态。**

原因是插件架构的固有形状：

| 层 | 做什么 | 用 Cordis 服务吗 |
|---|---|---|
| `apply(ctx, api)` | **注册**：`registerView` / `registerEntityV2` / … | ❌ 只**写**注册表 |
| Vue 组件（`.vue`） | **读**：`useEntityStore()` | ✅ 但要读，却跑在 Vue 组件树里 |

所以给 `outline` 硬挂 `requires: ['world.entities']` 是**假依赖**——声明在 `apply`，消费在组件，预检通过了但毫无约束力。

扫遍全仓，唯一在 `apply` 层真实消费应用级注册面的是 **`timeline`**：

```ts
registerPackSerializer(createTimelinePackSerializer())
registerProjectExtraProvider(timelineProjectExtraProvider)
```

而这两个原语是 `entity-core` 的**全局 Map 写入，没有撤销函数**——注册了就永久残留，正是「注册未走 effect」的典型病。

### 10.2 两处改动

**① `entity-core/src/core/projectExtras.ts`：让注册可撤销**

```ts
export function registerPackSerializer(serializer: Serializer): () => void {
  packSerializers.set(serializer.id, serializer)
  return () => {
    if (packSerializers.get(serializer.id) === serializer) packSerializers.delete(serializer.id)
  }
}
```

**身份校验是关键**：只有该 id 仍指向本次注册的实现时才删除。否则重载时旧实例的 disposer 会误删新实例的条目（HMR 高频场景下必踩）。

`registerProjectExtraProvider` 同构。

**② 新增 `world.projectExtras` 服务**

```ts
'world.projectExtras': {
  registerPackSerializer,
  registerProjectExtraProvider,
} satisfies WorldProjectExtrasService,
```

直通那两个原语，返回 disposer。

**③ `timeline` 改为声明的真实依赖**

```ts
export const manifest = {
  ...
  requires: ['world.projectExtras'],
}

export function apply(ctx: CordisContext, api: WorldPluginApi) {
  const extras = ctx.get('world.projectExtras') as WorldProjectExtrasService
  ctx.effect(() => extras.registerPackSerializer(createTimelinePackSerializer()))
  ctx.effect(() => extras.registerProjectExtraProvider(timelineProjectExtraProvider))
  ...
}
```

删掉了原来的模块级幂等布尔（`projectExtrasRegistered`）——**它存在的唯一理由是「注册了撤不掉，所以只能注册一次」**。有了可撤销的 effect，这个补丁就不需要了。

### 10.3 回归锁（`world-services.spec.ts` 13 例）

新增 3 例锁定真实依赖：
- `timeline` 源码里确有 `requires: ['world.projectExtras']`（读源码而非 import，避开 `.vue` 重依赖）
- 服务目录里确有该服务（声明与实际提供对得上）
- **从服务名单里抽掉该服务 → timeline 被拒**

### 10.4 反证

删掉 `timeline` 的 `requires` 声明 →

```
× 真实插件依赖：timeline 声明 world.projectExtras
  → timeline manifest 声明了 world.projectExtras 依赖
```

**精确命中，恢复后 13/13 转绿。**

### 10.5 这个发现对 `requires` 用法的修正

原先我以为「插件依赖数据」，实测后修正为：

> **在这个插件架构下，`requires` 的正确用法是「插件依赖基础设施」，不是「插件依赖数据」。**
> 依赖数据的是 Vue 组件（走 pinia），依赖基础设施的才是 `apply`（走 Cordis）。

这条认知解释了为什么 42 个插件里 `requires` 一直是死字段——**不是没人想用，是这个架构里 `apply` 层本来就没有数据依赖**。

`world.entities` 等服务仍然有价值（供未来在 `apply` 层做数据操作的插件用、供能力桥供数），但**不要为了「让 requires 看起来在工作」而给现有插件硬挂依赖**。

| 路径 | 写类操作做什么 |
|---|---|
| 能力 `world.entity.put`（旧） | `storage.putEntity(entity)` —— 直接落库：不校验、不归一化、不更新内存 |
| 服务 `world.entities.add()` | 校验 + 归一化 + 落库 + 更新内存 + 记撤销 |

`store.add()` 内部做 5 件事（`structuredClone` 防污染 / 封面色归一 / `validateEntity` / 落库 / 更新内存+撤销栈+通知 UI）。

**所以「能力改走服务」不是换数据源，是改行为。** 这正是必须先拍板的原因。

### 11.2 用户拍板（2026-11-06）

| # | 决策点 | 裁定 |
|---|---|---|
| 1 | 写类要不要加 schema 校验 | **C：加但降级**——服务失败时回退 storage 直写 + 打警告，避免 Agent 流程因校验变严中断 |
| 2 | 写类要不要跳过撤销栈 | **A：跳过**（`skipUndo: true`）——保护用户撤销历史（上限 20，Agent 批量写会挤掉真实操作） |
| 3 | 读类是否直接改 | **直接改**——读无副作用，服务比 storage 更接近 UI 真实所见 |

### 11.3 一个必须绕开的环

`tree.ts → api.ts → capabilities.ts`，若 capabilities 反向 import `tree.ts` 即成环（架构门禁 `ts-cycle` 会拦）。

解法：新增**服务访问器** `world/service-registry.ts`，树启动时把服务表寄存进去，能力桥从这里取。依赖方向单向：

```
tree.ts ──register──▶ service 表 ──get──▶ capabilities.ts
   └──▶ api.ts ──▶ capabilities.ts（不回头引 tree）
```

`clearWorldServiceTable()` 在拆树时调用，此后能力调用回退直连。

### 11.4 12 条能力的最终归属

| 类 | 能力 | 处理 |
|---|---|---|
| **读类（6）** | `world.views.list` · `world.project.current` · `world.schema.get` · `world.entity.list` · `world.entity.get` · `world.relation.list` | 经服务取数，回退直连 |
| **写类（5）** | `world.entity.put/update/delete` · `world.relation.put/delete` | 经服务（`source:'agent'` + `skipUndo:true`），失败降级 storage |
| **不经服务（1）** | `world.project.list` | 壳命令 `cmd_dsh_workspace_list`——dsh 工作区清单不属于世界语义 |

`world.entity.get` 特别处理：先查服务内存索引，**未命中再回退磁盘**——Agent 可能查不在当前视图里的实体。

### 11.5 顺带补的底层能力：`skipUndo` 普及

原先只有 `entityStore.update` 支持 `skipUndo`，`add` / `remove` / `relationStore.update` 都没有。写类能力要跳过撤销栈，必须补齐：

| 方法 | 改动 |
|---|---|
| `entityStore.add` | 加 `opts?: { skipUndo?: boolean }` |
| `entityStore.remove` | 同上（撤销块 + 回收站块两处守卫） |
| `relationStore.update` | 同上 |

改动量：2 文件 / +6 −6。
