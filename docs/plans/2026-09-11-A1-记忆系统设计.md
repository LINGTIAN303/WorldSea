## 〇、设计要点速览

一句话：**记忆 = 受治理的状态（governed state），不是「带检索的存储」**。本设计的重心因此落在**写入路径**（什么该成为持久状态、凭何权威、何时失效）而非检索算法。

六条主轴：

1. **双层架构**——`MemoryCenter`（SQLite）为 substrate，`MEMORY.md` 为 interface（D1）。
2. **三套「记忆」收敛为一套**——生产在用的 Rust A 套收编前端 localStorage KV（B 套），TS 框架包（C 套，已死）去留另定（D2）。
3. **写入四操作**——ADD / UPDATE / DELETE / NOOP，矛盾不覆盖只调和（甲1、甲2）。
4. **计量归一**——上下文 token 为唯一计量语义，采用 `memory-center-models` 的 tiktoken 路径（丙1）。
5. **压缩分五档**——四层压缩（相对归档阈值 60/75/85/95%）+ 完整归档（100%）兜顶（丙1 澄清、己2）。
6. **轨迹不可变 + 原文外置**——`messages` 从可变快照改为不可变追加；超长内容外置为文件、上下文只留路径锚点（丙2 阶段 B、己1）。

## 一、设计目标

### 1.1 四环节闭环

| 环节 | 现状 | 本设计交付 |
|---|---|---|
| **会写** | 只有 `record_turn` 追加 + 阈值 `archive` | 四操作写入 + 写前去重 + 档位控制写入策略 |
| **会取** | 每轮 `recall` 关键词命中 + 2000 token 注入 | 召回条数 / 注入预算随场景档位变化；语义检索前置接口 |
| **会更新** | **无任何更新路径** | 调和摘要（不覆盖）+ supersede 链 + `pinned` / `access_count` |
| **会遗忘** | **无任何淘汰** | 计量 → 软淘汰 → 硬删三级；**同时覆盖 DB 与磁盘外置文件** |

### 1.2 可回答三问（验收口径）

- **「Agent 记住了什么」**——库里所有条目可按项目 / 会话 / 层级枚举，UI 可审计（现 A 套 UI 面完全断开，见 §7.2）。
- **「为什么记得」**——每条带写入理由（`archive_reason`）、来源（session / hook）、标签（真标签维度，非被挪用的 `output_types`）。
- **「什么被忘了」**——淘汰有留痕（软删入回收站 + 硬删事件），不再是静默消失。

### 1.3 非目标（显式排除）

- **reflective（自我反思）不纳入 A1 范围**（丁2②）——只在 §4.4 约定一个写入接口，不把整个 reflective 拉进来。
- **语义检索施工本身不属 A1**——属 A2；A1 只定它的索引对象与 token 口径（戊1）。
- **知识图谱实体记忆的读写实现不属 A1**——甲0② 只定分工与桥接契约。

## 二、总体架构

### 2.1 双层架构（D1）

判据来自本轮外部调研：**「文件赢在 interface，数据库赢在 substrate」**——二者不是替代关系，不可混淆。

```
                    ┌─────────────────────────────────────────┐
   常驻每轮注入 ────▶ │  MEMORY.md   （interface）               │
                    │  · Agent 主动维护 · 用户不可直接编辑      │
                    │  · 精选常驻 · 贯穿全部会话                │
                    │  · 与四层分层正交，不占短/长期分类        │
                    └───────────────┬─────────────────────────┘
                                    │ 结构化写入（四操作，非自由文本）
                    ┌───────────────▼─────────────────────────┐
                    │  agent-memory 适配层                     │
                    │  · MemoryAccessor trait 实现             │
                    │  · 扩展库 memory_ext.db（加法，不改 vendor）│
                    └───────────────┬─────────────────────────┘
                                    │
                    ┌───────────────▼─────────────────────────┐
   按需召回 ────────▶ │  MemoryCenter SQLite （substrate）        │
                    │  · memories / hooks / raw_contexts        │
                    │  · 并发 · 审计 · 全量 · 语义检索基座       │
                    └──────────────────────────────────────────┘
```

**关键澄清（防止第四套命名）**：

- WorldSea 内部四层命名（Working / Episodic / Semantic / Procedural，丁4②）是**抽象度 + 作用域**维度；
- MemoryCenter 分层（Working → Archived → WeeklyMerged → MonthlyScored → Retained / Evicted）是**生命周期 / 成熟度**维度；
- 二者**不是同一维度、不可混用**；跨项目表述时不得互相替换。
- 「临时记忆」在两项目中均无出处——本设计**不引入**该词。

### 2.2 组件与数据流

```
一轮对话
   │
   ├─ ① 召回注入     build_prompt_options() ──▶ system_prompt_override（独立于 messages，天然免裁）
   │                    └ recall(top_k, 档位) ──▶ inject(预算, 档位)
   │
   ├─ ② 上下文记账    计量 = tiktoken(上下文 token)  ← 丙1
   │                    └ 超档 → 四层压缩阶梯（§5.2）
   │
   ├─ ③ 超长内容外置   单条 > 阈值 ──▶ 写外置文件 ──▶ 上下文留路径锚点  ← 己1、§6.3
   │
   ├─ ④ 轮次记录      record_turn() ──▶ 缓冲
   │
   └─ ⑤ 阈值归档      archive() ──▶ memories / hooks 落盘
                        └ pre_compress_hook ──▶ raw_contexts 全文快照  ← 接线 vendor
                        └ 写入四操作（去重 / 调和 / 淘汰）  ← 甲1、甲2
```

### 2.3 与实体记忆的分工与桥接（甲0②）

**分工**：

| 面 | 承载 | 内容形态 |
|---|---|---|
| 实体记忆 | 知识图谱 / entity store | **结构化事实**（实体、关系、属性） |
| 长期记忆 | MemoryCenter | **对话沉淀**（轮次、决策、意图、程序性经验） |

**现状**：两者**毫无桥接**——仅有三个弱连接：KB 实体关联 / `memory-archive` 的 `entityIds` 字段 / 场景 prompt 的实体摘要。

**桥接契约（本设计新增）**：

1. **记忆条目可携带实体引用**——写入时带 `entity_ids`，作为召回的过滤面与排序特征（此前标签维度不存在，与甲4 的真标签列一并落地）。
2. **实体变更 → 记忆写入源**——甲2 的调和摘要天然承接「同一实体新旧信息冲突」（如「某角色 2025-11 前设定为 A，之后改为 B」）。
3. **注入面合并**——实体记忆摘要与对话记忆摘要同处 `system_prompt_override`，但**来源分段标注**，不混淆。
4. **不合并存储**——甲0 选②而非③：两者保持各自载体，只做契约桥接。理由：实体记忆的读写路径已由 entity store 承载，合并会产生第二套写入语义。

**连带修正（反向发现第 1 条）**：底能文档 L136「长期记忆只有图谱化实体载体」与代码实况不符（真实生效的是 MemoryCenter SQLite）——本设计定稿后须同步修正该句。

## 三、契约层

### 3.1 数据模型：vendor 零改 + 适配层扩展库（甲4 收窄）

**约束（代码取证）**：

1. DB schema **无扩展点**——四表 DDL 硬编码在常量 `INIT_SQL`（`crates/vendor/memory-center-core/src/sqlite.rs:79-136`），仅 `run_v2_34_migrations`（`:144-164`）做列级幂等 ALTER；无 migration 注册表 / 无版本比对 / 无注入 DDL 的钩子。
2. `with_conn` 为**私有方法**（`crates/vendor/memory-center-core/src/sqlite.rs:278`）→ 适配层**无法**经公开 API 往同一个库加表。
3. 上游**无下游合并通道**——面向「直接依赖者」，扩展方式是 `Custom(String)` 变体；未见面向 fork 的 rebase 机制。

→ **完整重塑（改名 / 删列 / 合并表）= 与活跃上游永久结构分叉**，故甲4 由「重塑」收窄为**加法**。

**落地方案（首选 · 适配层独立扩展库）**：

```
{root}/projects/{project_id}/
   ├── memories.db          ← vendor 管理，DDL 一字不改
   ├── sessions/{sid}/raw_contexts/{hook_id}.txt   ← vendor raw_context（批次级，见 §6.3.1）
   └── memory_ext.db        ← 【新增】agent-memory 侧管理，本次全部新增概念落这里
```

`memory_ext.db` 表设计（新库，独立连接池，与 `memories.db` 以 `memory_id` / `hook_id` 做**软外键**——跨库不建 DB 级 FK，一致性靠应用层事务顺序保证）：

| 表 | 用途 | 关键列 |
|---|---|---|
| `memory_ext` | 补齐 trait 声明的 4 个死字段 | `memory_id` PK · `created_at`（记忆发生时点，非归档时点） · `access_count` · `pinned` · `summary_method`（Llm/Rule/None） |
| `hook_tags` | **真标签维度**（替代被挪用的 `tags` 列） | `hook_id` · `tag` · `tag_kind` |
| `supersede_chain` | 矛盾调和链（甲2） | `old_hook_id` · `new_hook_id` · `reason` · `decided_at` |
| `raw_ref` | 外置文件引用表（GC 依据，§6.3.2） | `content_hash` · `owner_kind`（context_anchor / archive） · `owner_id` · `pinned` · `stored_at` · `deleted_at` |
| `ext_meta` | 扩展库 schema 版本 | `schema_version` · `updated_at` |

**两处实现级细化（2026-09-11 施工时定，已落 `crates/agent-memory/src/ext.rs`）**：

1. **`raw_ref` 不落 `ref_count` 列**——改为**由 `COUNT` 派生**（主键三元组 `(content_hash, owner_kind, owner_id)` 天然去重）。理由：存储计数器会与行数据形成**第二个事实源**并可能漂移；派生计数在带索引的主键上代价可忽略且始终自洽。
2. **连接形态由「连接池」降为单连接**（`Mutex<Connection>` + WAL）——本库写入频率低（每轮至多数次）且单进程独占，单连接已够，省掉 `r2d2` / `r2d2_sqlite` 两条依赖边。后续若出现并发写压力，换回连接池是**局部改动**。

**对齐 `crates/agent-kernel/src/memory.rs` 的 5 处契约缺口**（§0.3 of 裁定清单）：

| 缺口 | 落地方式 |
|---|---|
| `MemoryRecallResult.created_at` 无落脚处 | `memory_ext.created_at` **增列**（补「记忆何时发生」语义） |
| `access_count` 恒 0 → 「会遗忘」无依据 | `memory_ext.access_count` 增列 + 召回时 `touch` 自增 |
| `pinned` 置顶能力不存在 | `memory_ext.pinned` 增列 + UI / 工具置顶入口 |
| `summary_method` 无落脚处 | `memory_ext.summary_method` 增列 |
| `raw_context_path` 恒 null | **不改列**——由「己1 接线 `raw_contexts`」自然填值（§6） |

> 备选方案（次选 · vendor 内仅加法）：沿用 `run_v2_34_migrations` 同款幂等写法，只在 vendor 内 `ALTER TABLE ADD COLUMN` / 新建表，**绝不改名 / 删列 / 合并表**。当扩展库跨库一致性成本高于收益时启用。目标不变：保住「未来重新拷贝上游仍可人工三方合并」的能力。

### 3.2 `MemoryAccessor` trait 扩展（甲1 四操作）

现 trait 共 7 方法（`crates/agent-kernel/src/memory.rs:22-87`）：`recall` / `inject` / `archive` / `get_archive_boundary` / `load_chunk` / `record_turn` / `delete_by_session_id`。**无 update / delete-by-id**。

新增方法**全部给默认实现**（返回 no-op / `Ok(None)`），保证 `NoopMemory` 与既有调用方零破坏：

```rust
/// 结构化写入（四操作）。op = Add / Update / Delete / Noop
/// 详细见 docs/details/注释/agent-kernel/memory.md
async fn write(&self, _entry: MemoryWriteEntry, _opts: MemoryWriteOptions)
    -> Result<WriteOutcome, MemoryError> { Ok(WriteOutcome::Noop) }

/// 按 hook_id 删除单条记忆（纠正用；现仅有按会话整删）
async fn delete_by_hook_id(&self, _hook_id: &str) -> Result<(), MemoryError> { Ok(()) }

/// 置顶 / 取消置顶（甲4 pinned；pinned 记忆永不参与自动淘汰）
async fn pin(&self, _hook_id: &str, _pinned: bool) -> Result<(), MemoryError> { Ok(()) }

/// 访问计数（甲3 淘汰依据；召回命中时调用）
async fn touch(&self, _hook_id: &str) -> Result<(), MemoryError> { Ok(()) }

/// 取回外置原文（己1；按虚拟路径或 hook_id）
async fn read_raw_context(&self, _session_id: &str, _hook_id: &str)
    -> Result<Option<String>, MemoryError> { Ok(None) }
```

新增类型：

```rust
pub enum MemoryWriteOp { Add, Update, Delete, Noop }         // 甲1：缺一即退化为 append-only
pub struct MemoryWriteEntry {
    pub content: String,
    pub kind: MemoryLayer,          // 丁4② 四层概念命名（仅 WorldSea 内部使用）
    pub entity_ids: Vec<String>,    // 甲0② 实体桥接
    pub tags: Vec<String>,          // 甲4 真标签
    pub source: ArchiveSource,
}
pub enum WriteOutcome { Added, Updated, Superseded, Noop }   // Superseded 对应甲2 调和
```

**写前检索契约（甲1 ③）**：`write` 内部先做相似度检索，**相似度 > 0.92 直接返回 `Noop`**（去重），避免扁平结构累积陈旧副本。

### 3.3 文件家族与 `MEMORY.md`（乙组）

| 文件 | 定位 | 用户可编辑 | 注入形态 | 归属裁定 |
|---|---|---|---|---|
| `MEMORY.md` | **Agent 主动维护的常驻 interface**；贯穿全部会话；与四层分层正交 | **否**（仅 Agent 通过结构化操作写） | **常驻注入（每轮）** | 乙1② / 乙2 / 乙3① |
| `project_memory.md` | MemoryCenter 正式约定（`AGENTS.md` §7 L190-229） | 标记外可写 | 不注入，反向写入闭环 | 乙2 |
| `AGENTS.md`（全局规则） | 既有规则体系 | 是 | 已注入 | — |
| `WORLD.md` | 既有节奏型注入 | 是 | 节奏型 | — |

**关键约束**：

1. **`MEMORY.md` 是 WorldSea 独有概念**，MemoryCenter 无对应物；与 `project_memory.md` 定位不同，**不可互替**（前者全局级 / 用户不可编辑 / 贯穿全部会话；后者项目级 / 用户可读可写）。
2. **`MEMORY.md` 内容边界 = 精选常驻**（乙1②）——只放跨项目的、稳定的、必须每轮在上下文里的少量条目。理由：它是**每轮常态成本**，必须高价值密度；其余留库中按需召回。
3. **澄清一处长期混淆**：`agent-memory` 的 2000 token 是**「召回注入」预算**，与常驻注入**不是同一个池子**。
4. **命名禁令**：落地文件家族时**避开 `agent_memory`**——该名现为前端 localStorage KV 键（`packages/agent-runtime/src/tools/memory-internal.ts:8`），而 D2 正要废弃它，同名不同介质会造成语义对冲。
5. **`session_memory.md` / `agent_memory.md` 均不存在**（两项目零命中）→ session 级直接用 MemoryCenter `standalone` 承载，**不引入 session 文件**。
6. **先行修复**：根 `project_memory.md` 已丢失 `MEMORY_CENTER:SECTION` 标记 → **反向写入闭环已断**；乙2 的「以文件为准」须先修此闭环（§7.3）。

## 四、机制层

### 4.1 写入：四操作 + 去重 + 矛盾调和（甲1 ③→②、甲2②）

**分期**（甲1 用户裁定 ③→②）：先补 **NOOP（写前去重）+ DELETE（纠正）**，**UPDATE 后置**——UPDATE 依赖甲2 的矛盾调和策略先定，且引入 LLM 调用成本。

**硬规则：矛盾不覆盖**。冲突信息**不作为 UPDATE 覆盖旧值**，而是生成一条**显式记录矛盾与时序的调和摘要**，原始双方**均保留**：

```
调和摘要示例：
「用户 2025-11 前使用 React，之后转 Vue」
  ├─ 保留 A 条：hook_id=xxx（2025-10，内容=React 方案）
  ├─ 保留 B 条：hook_id=yyy（2026-01，内容=Vue 方案）
  └─ 新增 C 条：supersede_chain(old=A, new=B, reason=时点转移)
```

依据：外部调研的 temporal arbiter 实践；且与 D1 咬合——**调和结论正是最该进 `MEMORY.md` 的那类内容**（跨项目、稳定、必须常驻）。

**成本控制**：调和需 LLM 调用（成本 / 延迟），**默认 auto 可关**（对应 dsh R2 同类风险）。

### 4.2 召回与注入（丁1 ②）

**档位联动**（`ScenarioMemoryPolicy` @ `crates/agent-kernel/src/scenario.rs:78-88`）：

| 档位 | 场景 | 注入预算 | 召回条数 | 写入策略 |
|---|---|---|---|---|
| `EntityRich` | worldbuilding / novel | 高 | 多 | 强沉淀（含实体关联） |
| `Standard` | general / design（缺省） | 中 | 中 | 标准 |
| `Light` | coding | 低 | 少 | 弱沉淀（避免稀释代码上下文） |

**取 ②+③**（用户裁定）：档位同时控制**注入预算 / 召回条数**与**写入策略（哪些内容值得沉淀）**，不止于数据意图透出。排在甲1–甲3 之后施工。

**软矛盾处置（用户裁定「可以收掉召回」）**：`coding` 为 `Light` 却仍把 `memory_recall` 列入工具清单（`crates/agent-kernel/src/scenario.rs:510`）——**收掉该工具**，使 Light 档位的「不召回」意图自洽。

**追加核实项**：这些 `tool_ids` 自述为「意图登记」（`scenario.rs:270-274` 注释），且 Rust 侧 `frontend_tool_bridge.rs` 未见 memory 工具桥接 → **白名单里列了，运行时未必可调**；D2 收编时一并核实。

### 4.3 遗忘与淘汰（甲3 ③→②）

**分期**：先补**计量与访问计数**（`access_count` 增列 + 写入路径），淘汰策略后置。理由：**没有真实 token 计量与访问频次，任何淘汰策略都是拍脑袋**。

**三级淘汰链**（参数起点取自 `memory-archive`，`packages/memory-archive/src/defaults.ts:24-28`）：

| 级别 | 判据 | 动作 | 起点参数 |
|---|---|---|---|
| 衰减评分 | 半衰期指数衰减 + 访问加权 | 更新 `decay_score` | `halfLifeDays = 30` |
| 软淘汰 | `decay_score < deprecatedThreshold` | 标记 deprecated（**入回收站**） | `deprecatedThreshold = 0.15` |
| 硬删 | 回收站到期 **且无引用** | 物理删除（DB 行 + 外置文件） | `trashRetentionDays = 7` · `deleteAfterDays = 90` |

**永久保护**：`pinned = true` 的记忆**永不衰减、永不淘汰**。

**必须覆盖两侧**：`raw_contexts` 表**与**磁盘外置文件——否则「遗忘」只忘了索引、没忘内容（§6.3.2）。

**调度基础设施缺口**：当前**无定时器**；② 需先接调度（日 / 周 / 月任务，参照 `memory-archive` 的 `scheduler` 配置）。

### 4.4 记忆策略、reflective 接口与四层命名

**丁1 · `memory_policy` 消费**：见 §4.2。

**丁2 · reflective 接口约定**（排除 A1 范围，但留接口）：用户定位 reflective 为「**记忆系统的一个内部小分支**——让 Agent 记住重复碰壁难题时的做法与解法，避免重陷同一次做法、避免污染上下文」。

### 5.0 量纲修正的实际落点（2026-09-11 施工）

**「数值要修正为 token（上下文窗口），字节是错误」** 这条裁定落到四处：

| # | 位置 | 修正前（字节口径） | 修正后（上下文 token 口径） |
|---|---|---|---|
| 1 | `agent-kernel` 主链路裁剪 | `HISTORY_BUDGET_BYTES = 160_000` + `content.len() + 32` 求和 | 删除该常量；改由 `ContextBudgetPolicy`（窗口 × 比率）推导 + 注入的估算器逐条计 token |
| 2 | 归档阈值（`agent-commands`） | 写死 `2000`（原为「让闭环可验证」，与设计口径无关） | `窗口 × 归档比率`（模型档案推导） |
| 3 | 系统提示词占比 | **完全漏算**（只累加 messages） | 一并计入（系统提示词 + 记忆注入 + 管线指引） |
| 4 | 消息结构开销 | `+32` **字节** | `+8` **token**（常数改名 `MESSAGE_STRUCTURE_OVERHEAD_TOKENS`） |

**裁剪触发点**：落在四层阶梯的**最高层（AutoCompact，归档阈值的 95%）**——当前唯一实现点，定位是「最后手段」；其余三层（Snip / MicroCompact / Collapse）待实现。[`ContextBudgetPolicy::tier_of`] 已提供分层判定，供后续逐层落地时复用。

**兜底取向**：模型信息缺失时 `window = 32_768`、比率 `0.25`（触发点约 7.8K token）。**宁可早裁，不可撑爆**——撑爆窗口是硬错误（API 直接拒绝），早裁只是效率损失。装配层应始终注入真实档案。

施工勘查查明该 crate **不在 WorldSea 仓库**（属独立项目 `D:\本地化AI\MemoryCenter`），且 `tiktoken-rs` 不在本机 rsproxy 缓存/索引中。用户裁定「联网没有问题（WorldSea 本就是联网应用）」→ 采用**方案 ①**：

- 源码逐行保持上游原样，只有 `Cargo.toml` 扁平化（与既有两个 vendor crate 同做法）
- 唯一功能性删减：**sentencepiece 可选依赖未随迁**（设计裁定「仅限本地部署模型」，且需尚未建设的「每模型 vocab 路径」设施）；保留同名 feature 以免上游合并冲突，启用会给出明确编译错误提示

- 验证：`cargo test --offline` → **116 passed / 0 failed**（含 tiktoken 系数校准、家族/型号注册表、序列化往返等）

**接入形态（闭包注入，星型拓扑兑现）**：

```
crates/agent-memory/src/model_profile.rs   ← 新增：模型 → (分词器 · 窗口 · 归档阈值)
        │  ModelProfile::resolve(model_id, provider_id, declared_window)
        │    · 注册表精确命中（含 *-latest 别名）→ 专家档案
        │    · 未命中 → 供应商/模型名推断家族 → 保守比率 0.25
        ▼
  ContextBudgetPolicy（agent-kernel）  +  ArchiveConfig（vendor）  +  TokenEstimator（闭包）
```

**关键约束「阈值单一来源」的落地方式**：注册表命中时**只取「比率」**（= 专家阈值 ÷ 专家窗口），再用**实际窗口**重算阈值；调用方声明的窗口更小时只缩放阈值、**比率不漂移**。这样避免了上游那类「两处兜底不一致 → 反馈断裂」的问题。

**原子性观察**：`memory-center-models` 是**整套 token 计量 + 模型注册表**，不只是分词器；WorldSea 只用到其中一部分（`ModelRegistry` / `ModelVariant` / `Tokenizer` / `build_token_estimator`），其余（家族元数据、工具调用格式、归档策略枚举）暂未消费但已就位。

**硬性动作**：清除一切以**字节**为阈值的单位写法——`HISTORY_BUDGET_BYTES` 这个名字本身就是错误的量纲声明，须改名并改为 token 语义。**归档阈值（2000）与上下文预算（160 000）同属上下文 token 语义，一并归一。**

**sentencepiece（用户裁定：仅限本地部署接入的模型）——需注意三处机制落差**：

1. feature 是**编译期**开关（启用后 Gemini/Qwen/Llama 家族 `default_tokenizer()` 切 `spm_or_char()`），而「仅限本地部署」是**运行期**选择 → **构建链的 cmake + C++ 代价全局一次性支付**（`crates/memory-center-models/Cargo.toml:36` 实为 **static 静态编译**，**不破坏单二进制**；默认关闭的理由是「避免强制 cmake + C++ 编译器」）。
2. `.model` 路径是**单个环境变量** `MEMORY_CENTER_SPM_MODEL_PATH` → **只能指向一份词表**；多个本地模型（如本地 Qwen + 本地 Llama）无法分别供给 → **WorldSea 须自建「每模型 vocab 路径」**。
3. **动机是刚需而非优化**：MemoryCenter 的字符级近似在中文场景**偏差可达 20–30%**（上游自述 `docs/sentencepiece-guide.md:7-13`），直接影响归档触发时机与 `threshold_ratio_percent` 精度——「160K / 400K 触发」实际可能在 112K–520K 间漂移。

**阈值单一来源（引以为戒）**：上游曾出现 `get_archive_threshold` 兜底 120K 而 `ArchiveConfig::default()` 兜底 400K 的**反馈断裂**（LLM 建议归档、Archiver 不触发），已修。**WorldSea 的阈值必须单一来源。**

### 5.2 四层压缩阶梯（相对归档阈值，非相对窗口）

**标尺澄清（关键）**：四层压缩的百分比是**「相对归档阈值」**，不是「相对整个窗口」。

换算（以 1M 窗口、归档比率 2/5 → 阈值 400K 为例）：

| 层 | 占**归档阈值** | 触发点 | 占**窗口** | 动作 | 信息损失 |
|---|---|---|---|---|---|
| 第一层 Snip | 60% | 240K | 24% | 删早期工具返回的超长原始数据，只保留摘要 | 无感 |
| 第二层 MicroCompact | 75% | 300K | 30% | 早期长对话 → 简短摘要替换 | 轻微 |
| 第三层 Collapse | 85% | 340K | 34% | 多轮早期对话 → 折叠成一条摘要消息 | 细节丢失、主线保留 |
| 第四层 AutoCompact | 95% | 380K | 38% | 全面压缩：system + 全局摘要 + 最近 3 轮 | 明显 |
| **完整归档** | **100%** | **400K** | **40%** | 清空上下文，交 MemoryCenter 完成索引 / 钩子 | 沉淀 |

**两条曾判定的冲突同时消失**：

- **时序冲突消失**：四层全在归档阈值之内 → **归档是阶梯终点，压缩先行**，不存在「归档先触发、四层够不到」。
- **0.80 协商上限冲突消失**：最高点仅占窗口 **40%**，远低于 MemoryCenter 的 `window × 0.8` → **无需偏离上游任何参数**（此前「必须取消 0.80 上限」的判断基于错误标尺，已撤回）。

**顺带核实**：用户原给的 120/150/170/190K 正是 **200K 归档阈值**的 60/75/85/95% → 那组数字是按 200K 归档预算标定的，换窗口 / 换比率时须等比放大。

**设计约束**：阶梯**不用绝对 K 值定义**，一律用**占归档阈值的比例**——原因见反面教材：Claude Code 的自动压缩阈值是硬编码 150,000（服务端），「对 200K 窗口即 75%，对 1M 窗口则变成 15%」（GitHub #34202 / #41037）。

### 5.3 归档阈值（窗口 × 比率）

| 项 | 事实 | 依据 |
|---|---|---|
| 阈值 = 窗口 × 比率 | 内置 15 型号专家区间 **0.20–0.50**；`custom`（未知模型）统一 **0.25** | `crates/memory-center-models/src/variant.rs:53-62` |
| 「2/5」已证实 | 原文「**Claude Opus 4.6 的 1M 窗口取 400K = 0.40**」；「DeepSeek V4 的 1M 窗口取 200K = 0.20」（MoE 超长上下文衰减快） | `variant.rs:59-61` |
| 兜底常量来由 | `FALLBACK_ARCHIVE_THRESHOLD = 400_000` 恰为 **1M × 0.40** | `core-logic/src/model.rs:24` |
| 轮次边界才检查 | 达阈值后，**若当前轮次未完成则等待** | `core-logic/src/archive.rs:7-9`、`:13-14`、`:199-202` |
| 浮动双档 | `threshold_ratio_percent`：**≥80 准备归档 / ≥100 立即归档** | `docs/onboarding/rules/catpaw-memory-center-archive.md:16-18` |
| 硬上限强制截断 | **1.5 倍阈值**强制截断并标 `truncated=true` | `archive.rs:206-209`、`core-logic/src/model.rs:34` |

**WorldSea 取值**：**归档比率 = 窗口 × 2/5**（与 Claude 长窗口优质模型档一致），可配置为 0.20–0.50 分档。

**与压缩阶梯的时序（按用户 PS 固化）**：① 四层压缩先行（阶梯内） → ② 达到归档阈值后**完整归档** → ③ 清空上下文 → ④ 交 MemoryCenter 做索引 / 钩子。

**归档与压缩的性质分工**：归档是「**沉淀 + 清空**」的兜底动作，压缩是「**手术式腾挪**」——归档兜最顶、压缩先行。

### 5.5 不可变事件日志（丙2 阶段 B）

**方案基线（回写修正后）**：dsh 硬伤①原文称「裁剪只动内存 → 刷新后旧消息又完整回来」——**与代码不符**。实况链路是**写穿**的：

```
run() 内 AfterRun 裁剪（mod.rs:646 → :732）
  → run() 返回 → 广播 AgentEnd（mod.rs:627 / 634）
  → Tauri 侧 flush_buffered_action_events（apps/tauri/src-tauri/src/commands.rs:321-325）
  → flush_action_events → persist_messages（crates/agent-commands/src/lib.rs:3240-3250）
  → store.replace_messages（:3217-3233）
```

`replace_messages` 是**全量替换**（`DELETE FROM messages WHERE session_id` + 逐条 INSERT，`crates/agent-commands/src/session_store.rs:509-525`）。

→ **实际后果比原文更严重**：被裁消息**被物理删除**，刷新后不会回来，**不可恢复**。

→ **方案基线**：**把可变快照改成不可变追加**（阶段 B）——在不可变事件日志上**追加 replace 记录**，而非删历史。与甲1 的四操作**同源**，一起做省一次返工。

### 6.2 锚点回填机制（用户定义）

**机制定义（用户原话固化）**：超长原始数据在压缩后的上下文里被「**一对前后锚点**」替代（**空容器位**）；**完整原文进归档（外置）**；待后三层执行后，**按序把压缩后的文本填回锚点之间**。

```
压缩前：  ... [ 超长工具原始数据 1200 token ] ...

第一层后：... ⟨锚点A⟩ [空容器位] ⟨锚点B⟩ ...

后三层执行后：... ⟨锚点A⟩ [压缩后的文本] ⟨锚点B⟩ ...

达到归档阈值：完整原文进归档 → 清空上下文 → MemoryCenter 索引
```

与 **Claude Code 的 Snip 占位符 + Context Collapse 读时投影**（原始消息永不修改、折叠决策记于独立 commit log、每次读时重放）同构。

**两条硬前置依赖（当前均不成立）**：

| # | 前置 | 现状 | 关联 |
|---|---|---|---|
| ① | 需要**不可变、可寻址**的 session 日志（锚点 = 稳定坐标） | `messages` 是**全量替换的可变快照** → **坐标不成立** | **丙2 阶段 B**（是锚点机制的**前置，非可选项**） |
| ② | 需要 session 日志保留压缩前的**完整原文** | `clamp_tool_result` **入库前**截断 → 原文从未落盘 | **己1①**（己1③ 是缓解不是解决） |

→ **顺序约束（硬）**：**丙2 阶段 B 与 己1① 必须排在「锚点回填机制」之前实现**，否则锚点无底座。

**解法的作用范围（用户定义）**：**不限于工具调用**——任何超长内容（超长 user 输入、大文件读取、长 assistant 正文）适用同一解法，无需按消息类型分别设计。

**泛化收益**：原文不再随 `messages` 行被删而消失 → **「内容丢失」降级为「位置丢失」**。

### 6.3 落地三项（本文档细化 · **已确认按建议采纳**）

> 这三项是**设计文档内细化**，不另开裁定条目（裁定清单 §6 已如此定位）。以下给出**建议方案 + 备选 + 依据**；**2026-09-11 用户裁定：三项均按建议采纳**。备选方案留档——如后续实测暴露问题可回溯，不必重新调研。

#### 6.3.1 外置文件粒度

**两个粒度不可互相替代，因为目的不同**：

| 粒度 | 目的 | vendor 现状 | 建议 |
|---|---|---|---|
| **条级**（每条超长数据 1 文件） | 解决 ① **入库前截断导致原文从未落盘**——为**锚点提供可独立回填的坐标** | ❌ 无（vendor 只有批次级） | **新增（轻量命名层）** |
| **批次级**（1 次归档 = 1 文件） | 解决 ② **压缩前完整快照**——`pre_compress_hook` 一次性写整段未摘要上下文 | ✅ 有（`{hook_id}.txt`） | **直接复用 vendor 代码** |

**建议方案（混合，两者并存而非二选一）**：

1. **条级外置**（新增）：触发条件 = **单条内容 > 阈值**（与 `clamp_tool_result` 同门阈值，建议共用常量）。
   - 命名：**内容寻址** `raw/{sha256 前 16}.txt`——同一超长内容重复出现天然去重；GC 可判定（§6.3.2）。
   - 理由：条级是**锚点机制的必要条件**（锚点需要独立、稳定、可回填的坐标）；批次级粒度太粗（一次归档跨多轮 / 多个工具结果，无法按条精确回填）。
2. **批次级归档**（复用）：`pre_compress_hook` 触发，沿用 vendor `write_raw_context(session_id, hook_id, content)` 与 `{hook_id}.txt` 命名。
   - 理由：这是 vendor 既有能力（未接线），复用零新代码。

**必须注意的落点差异（代码事实）**：vendor 有两套 `write_raw_context` 实现，**存储介质不同**：

| 实现 | 位置 | 介质 | 返回 |
|---|---|---|---|
| `SqliteStorage` | `crates/vendor/memory-center-core/src/sqlite.rs:1079-1102` | **`raw_contexts` 表内** | **虚拟路径** `sessions/{sid}/raw_contexts/{hook_id}.txt` |
| `LocalStorage` | `crates/vendor/memory-center-core/src/storage.rs:840-850` | **真实文件** `sessions/{sid}/raw_contexts/{hook_id}.txt` | 真实相对路径 |

→ WorldSea 当前用 `SqliteStorage`，其「文件」实为**表内存储 + 虚拟路径**。**用户解法要求的「单独一个文件承载」需要在 §6.3.3 明确是否改为真文件**——这是本项与 6.3.3 的耦合点。

**与戊1 的同步项**：文件落盘后，A2 的索引对象须明确是**文件内容**还是 **DB 摘要**，否则检索覆盖不到外置原文。

#### 6.3.2 生命周期与 GC

**问题**：归档清空后**文件仍在** → 无淘汰则无限增长。**甲3 的淘汰策略必须覆盖文件**（`raw_contexts` 表**与**磁盘两侧），否则「遗忘」只忘了索引、没忘内容。

**建议方案（三档生命周期 + 引用判定）**：

```
        写入 ──▶ [保护期]  ──▶ [软删·回收站]  ──▶ [硬删]
                   │              │ 7 天           │
                   │              └── 恢复 ──▶ 回保护期
                   │
                   └─ 保护条件（任一成立即不 GC）：
                      · pinned = true
                      · 被活跃引用（最近 N 轮 / 未完成计划步骤）
                      · ref_count > 0
```

**GC 判据 = 「两处引用都不存在」**：一个外置文件可能被 (a) **上下文锚点** (b) **归档记忆的 `raw_context_path`** 引用；**两处引用皆无**方可进入删除流程。引用计数落在 `memory_ext.db` 的 `raw_ref` 表（§3.1），**不依赖跨库 FK**。

**扫描对象是外置目录下的实际文件，不是 `raw_ref` 的行**（施工时定的关键分解）：引用被释放后该行即物理删除，该哈希在表中已查不到 → 因此判定接口是**谓词** `is_gc_eligible(hash)`（有效引用数 = 0 且无 pinned）**而非枚举**；GC 遍历磁盘文件逐个询问。硬删顺序为**先删物理文件、再清引用行**——反过来一旦清行成功而删文件失败，文件即成不可追溯的孤儿。

**三级参数（起点取自 memory-archive）**：

| 档 | 触发 | 动作 | 参数 |
|---|---|---|---|
| 保护期 | 有引用 / pinned / 活跃 | 不动作 | — |
| 软删 | `decay_score < 0.15` 且无引用 | 入回收站（`deleted_at` 打标，不物理删） | `trashRetentionDays = 7` |
| 硬删 | 回收站到期 **且** 仍无引用 | 删 DB 行（`delete_raw_context`）+ 删磁盘文件 | `deleteAfterDays = 90` |

**分期落地（与甲3 同步）**：

- **甲3 落地前（当前）**：**只增不删 + 容量闸门**——设总量上限，超限**只告警不删**，避免误删。
- **甲3 落地后**：接入三级淘汰链；`delete_raw_context`（vendor 已有）+ 文件删除。

**计量依赖**：GC 依据需要真实 token / 字节计量 → 依赖 丙1 落地。

**⚠ 与甲4 收窄的一致性**：`raw_ref` 落 `memory_ext.db`（适配层），**不动 vendor DDL** —— 与甲4「仅加法 / 适配层」方向一致，不冲突。

#### 6.3.3 落点与安全边界

**两个候选落点**：

| 落点 | 取回方式 | 优点 | 代价 |
|---|---|---|---|
| **app_data**（`{app_data}/worldsea/memory/...`） | LLM 需**专门读工具** | 与记忆库同域、天然私有、不受工作区权限污染 | LLM 不能直接 `read_file` 取回 |
| **工作区**（`{workdir}/...`） | LLM 可用**既有 `read_file`** | 取回顺手 | 受权限分级 / 沙箱（P0·P1）约束；污染用户项目目录；与 `agent-out` / `agent-tmp` 分区语义纠缠 |

**建议方案：落 app_data + 新增受控读工具**。

**理由（三条）**：

1. **语义归属**——原始上下文是**记忆系统的私有 substrate**，不是用户产物；落工作区会混入 `agent-out`（产物，需确认）/ `agent-tmp`（临时，免确认）语义，与实际性质（记忆底层）不符。
2. **用户边界**——乙1 已定 `MEMORY.md`「用户不可直接编辑」；外置原文同理应是用户不直接触碰的层。落用户工作区会被用户误删 / 误提交 / 手工清理。
3. **权限体系一致性**——落工作区会引入「记忆文件是否受沙箱约束」的新问题；落 app_data 则**天然在权限体系之外**，无新增判定面。

**取回路径**：新增受控读工具（建议名 `memory_read_raw`，或给既有 `load_chunk` 加 raw 分支），只读、不下发写权限。

**安全边界（五条硬约束）**：

| # | 约束 | 说明 |
|---|---|---|
| 1 | **目录硬隔离** | `memory/sessions/{sid}/raw/` 仅记忆子系统可读写；不暴露为工作区路径 |
| 2 | **LLM 只读** | 只开放读工具，**不开放写**（防止 Agent 篡改原始轨迹） |
| 3 | **大小闸门** | 单文件上限 + 总量上限；超限时**拒绝外置 → 退回截断（保头+保尾）**，保证功能不中断 |
| 4 | **隐私边界** | 外置文件可能含用户私有内容 → **不入 git、不参与导出**；删除后进入回收站（可恢复窗口 7 天） |
| 5 | **与沙箱对齐** | 若未来沙箱把 app_data 纳入约束，需显式声明该目录为**例外**（记忆子系统独占） |

**与「真文件 vs 表内虚拟路径」的耦合（见 6.3.1）**：若采用**真文件**（对齐 `LocalStorage` 语义），上述五条边界全部适用；若沿用**表内虚拟路径**（当前 `SqliteStorage`），则「文件」不存在，GC 只需处理 DB 行——安全边界简化为「不暴露读接口给写工具」。**建议取真文件**，理由：用户解法明确要求「单独一个文件承载」，且真文件让原文**不随 `memories.db` 损坏而丢失**，隔离性更强。

**与权限体系的同步**：本项需与已完成的 [权限分级与沙箱耦合设计](2026-09-03-权限分级与沙箱耦合设计.md) 对齐——确认 app_data 记忆目录在既有权限模型中的定位（当前未纳入）。
