## 一、总览矩阵

| # | 模式 | NodeType | 当前代码位置 | 实现形态 | 核心职责 | 底座依赖 | 复杂度 | 迁移难度 |
|---|------|----------|-------------|---------|---------|---------|--------|---------|
| 1 | ReAct | `React` | `agent/mod.rs`（内嵌） | **非节点**，AgentLoop 主循环 | 思考→工具调用→观察循环 | 全部（state/backend/tool/event/memory/loop） | 极高 | 高 |
| 2 | Plan | `Plan` | `plan.rs` | 单文件节点 | 任务分解为计划项 | state/backend/event | 中 | 低 |
| 3 | Execute | `Execute` | `plan.rs` | 单文件节点 | 逐步骤执行计划 | state/backend/event/tool | 中 | 低 |
| 4 | Reflection | `Reflection` | `reflection.rs` | 单文件节点 | 评审输出质量并评分 | state/backend/event | 中 | 低 |
| 5 | Refine | `Refine` | `reflection.rs` | 单文件节点 | 依据评审反馈修正输出 | state/backend/event | 中 | 低 |
| 6 | Router | `Router` | `router.rs` | 单文件节点 | 意图分类→路由分支 | state/backend/event | 中 | 低 |
| 7 | Supervisor | `Supervisor` | `supervisor.rs` | 单文件节点 | 中心化任务分配→子Agent | state/backend/event/tool + AgentLoop | 高 | 中 |
| 8 | SubAgent | `SubAgent` | **无节点实现**；`supervisor.rs`(Spec) + `agent-commands/subagent.rs`(Manager) | 工具委派，非 OrchestratorNode | 子Agent实例管理与委派 | AgentLoop/tool/event | 高 | 高 |
| 9 | ToT | `Thought` | `tree_of_thoughts/`（目录） | 目录节点 | 思维树探索+评分+收敛 | state/backend/event | 高 | 中 |
| 10 | GoT | `Graph` | `graph_of_thoughts.rs` | 单文件节点 | 思维图+多parent聚合 | state/backend/event + ToT类型 | 高 | 中 |
| 11 | MultiAgent | `MultiAgent` | `multi_agent/`（目录） | 目录节点 | 去中心化对等协作 | state/backend/event/tool + AgentLoop | 极高 | 高 |
| 12 | Memory | `Memory` | **无节点实现**；`memory.rs` 是 MemoryAccessor trait（基础设施） | 基础设施，非节点 | 长期记忆检索/注入/归档 | —（被其他模式依赖） | — | — |
| 13 | Custom | `Custom` | 无（枚举占位） | 用户自定义节点 | 扩展点 | 任意 | — | — |

### 关键发现

1. **13 个 NodeType 中仅 9 个有实际 OrchestratorNode 实现**
2. **ReAct 不是节点**——它是 AgentLoop 本身，与底座强耦合
3. **SubAgent 不是节点**——通过 `SubAgentManager` 注册 `delegate_to_sub_agent` 工具实现委派
4. **Memory 不是节点**——`memory.rs` 是 `MemoryAccessor` trait，属于底座基础设施
5. **GoT 依赖 ToT 的类型定义**（`ThoughtNode`、`ToTConfig`、`ToTError` 等），存在跨模式耦合
6. **Reflection 依赖 Plan 的工具函数**（`extract_json_object`），存在跨模式耦合
7. **Supervisor 和 MultiAgent 都直接依赖 AgentLoop**（创建子 Agent 实例），与底座耦合

## 二、各模式详细档案

### 1. ReAct（思考-行动-观察循环）

**如何起作用：**
ReAct 是 Agent 的基础运行循环。每轮：调用 LLM → 解析是否有工具调用 → 有则执行工具并推入 toolResult 消息 → 无则返回最终文本。循环直到 LLM 不再调用工具或达到最大迭代次数。循环内还织入了 Loop Engineering（限流/重试/软超时/看门狗）、Deep Mode 阶段判定、长任务 checkpoint、记忆闭环（recall→inject→record_turn→archive）、四管线路由决策。

**如何被使用：**
- **默认主链路**：`AgentLoop::run(user_input)` 直接触发，是所有会话的默认执行方式
- **被其他模式内嵌**：Supervisor 和 MultiAgent 创建的子 Agent 实例本质上都是 ReAct 循环
- Tauri 命令层 `cmd_agent_send` → `AgentCommandService::send_message` → `AgentLoop::run`

**有什么用：**
- 提供最基础的"LLM + 工具"能力，是所有复杂编排模式的原子单元
- 支持流式输出、工具调用、多轮对话、上下文管理
- 织入了工程化能力（限流/重试/超时/记忆/阶段追踪），是生产级 Agent 的基础

**应该如何用：**
- **简单任务直接用**：不需要复杂编排的对话、问答、单工具任务，直接走 ReAct
- **作为子 Agent 内核**：Supervisor/MultiAgent 委派的子任务，内部都是 ReAct 循环
- **不适合**：需要多路径探索（ToT/GoT）、需要先规划再执行（Plan-Execute）、需要多角色协作（MultiAgent）的场景
- **配置要点**：通过 `AgentLoopConfig` 控制 max_iterations、system_prompt、workdir 等

---

### 2. Plan（计划生成）

**如何起作用：**
`PlanNode` 接收用户输入，调用 LLM 将任务分解为结构化的计划项列表（`Vec<PlanItem>`），写入 `state.plan`。每个计划项含 id/title/description/status/order/output。LLM 输出经三级降级解析（直接 JSON → 代码块提取 → 首个 `[...]` 片段）。

**如何被使用：**
- 作为编排图的入口节点，后跟 `ExecuteNode`
- `AgentCommandService::run_plan_execute()` 中构造：`PlanNode → ExecuteNode`（可选 → Reflection ⇄ Refine）
- 配置项：`max_items`（最大计划项数）、`next_node_id`（跳转目标）

**有什么用：**
- 将复杂任务分解为可追踪、可逐步执行的子任务
- 前端可展示计划列表，用户可看到执行进度
- 每个计划项独立执行，失败可定位到具体步骤

**应该如何用：**
- **适合**：多步骤复杂任务（如"分析这个项目并生成报告"）、需要用户可见执行进度的场景
- **不适合**：简单单步任务（增加不必要的 LLM 调用开销）
- **最佳实践**：Plan 后必须跟 Execute；需要质量保证时可接 Reflection-Refine 循环
- 计划项数量建议控制在 3-8 个，过多会导致执行时间过长

---

### 3. Execute（计划执行）

**如何起作用：**
`ExecuteNode` 读取 `state.plan`，逐个执行 pending 状态的计划项。采用**内部循环**设计：一次 `execute` 调用跑完所有 pending 项（每项独立 LLM 调用并广播 `PlanStepUpdate` 事件），避免 Orchestrator 循环访问超阈值触发疑似死循环检测。执行结果写入对应计划项的 `output` 字段。

**如何被使用：**
- 紧跟 `PlanNode` 之后，作为编排图的第二个节点
- `run_plan_execute()` 中配置 `next_node_id`：refine=false 时为 None（执行完即结束），refine=true 时指向 "reflection"

**有什么用：**
- 按计划逐步执行，每步独立调用 LLM
- 每步执行状态实时广播，前端可展示进度
- 执行结果持久化到计划项，支持后续回顾

**应该如何用：**
- **必须与 Plan 配对使用**，不能单独存在
- 内部循环设计意味着 ExecuteNode 是一个"重型节点"，一次调用可能产生多次 LLM 调用
- **注意**：当前实现不支持单步失败后的跳过/重试策略，所有步骤串行执行

---

### 4. Reflection（评审/反思）

**如何起作用：**
`ReflectionNode` 评审上一条 assistant 输出（或 ExecuteNode 的最终输出），按预设维度（默认：正确性/完整性/风格）调用 LLM 进行评分（0-100）并列出问题和改进建议。结果写入 `state.reflections`。评分低于阈值时 continue 到 RefineNode。

**如何被使用：**
- 在 Plan-Execute 链路后作为可选质量关卡：`Plan → Execute → Reflection ⇄ Refine`
- `run_plan_execute(refine=true)` 时自动加入 Reflection 和 Refine 节点
- 配置项：`dimensions`（评审维度，可自定义）、`min_score`（合格分数线）、`next_node_id`

**有什么用：**
- 对 LLM 输出进行质量把关，识别事实错误、遗漏、风格问题
- 评分和问题列表可展示给用户，提供可解释性
- 与 Refine 配合形成自我修正循环，提升输出质量

**应该如何用：**
- **适合**：对输出质量要求高的场景（报告生成、代码审查、文案润色）
- **不适合**：实时对话、简单问答（增加延迟和 token 消耗）
- **最佳实践**：与 Refine 配对使用，设置合理的 max_iterations 防止无限循环
- 评审维度应根据任务类型定制，默认三维度不一定适合所有场景

---

### 5. Refine（自我优化/修正）

**如何起作用：**
`RefineNode` 依据 `state.reflections` 中最新的评审结果（问题列表+改进建议），调用 LLM 对原始输出进行修正。修正后 continue 回 ReflectionNode 重新评审，形成 Reflection⇄Refine 循环。收敛条件由 RefineNode 判断：达到 max_iterations、评分超过 min_score、或连续 no_improvement_rounds 轮无提升。

**如何被使用：**
- 与 ReflectionNode 配对，形成质量修正循环
- `run_plan_execute(refine=true)` 中配置：`reflection_node_id`（回跳目标）、`max_iterations`、`min_score`

**有什么用：**
- 基于评审反馈自动修正输出，无需人工干预
- 多轮迭代逐步提升质量，直到达到合格标准
- 收敛条件防止无限循环和 token 浪费

**应该如何用：**
- **必须与 Reflection 配对**，单独使用无意义
- **适合**：可量化质量的输出（文章、代码、方案）
- **不适合**：开放性创作（"更好"难以定义，可能过度修正）
- **注意**：当前收敛后最终输出写入 messages，但计划项的 output 字段可能未同步更新

---

### 6. Router（路由/意图分类）

**如何起作用：**
`RouterNode` 根据用户输入和候选路由目标（`RouteTarget`：id/name/description/keywords），通过路由策略（默认 LLM 意图分类，备选关键词匹配）决策走哪个分支。决策结果写入 `NodeResult.next_node_id`，由 Orchestrator 按图调度对应节点。支持 `force_pipeline` 强制路由（前端可指定走哪个管线）。

**如何被使用：**
- **编排图中**：作为分支入口节点，后跟多个目标节点
- **AgentLoop 内部**（A3 四管线）：`with_router()` 注入后，`run()` 在接收用户输入时先经 Router 决策管线，把管线指引写入 system prompt。这是 Router 的**非节点用法**，直接嵌入 ReAct 循环
- 策略可注入：`LlmRoutingStrategy`（默认）、`KeywordRoutingStrategy`、自定义

**有什么用：**
- 将不同类型的任务分发到专门的处理链路
- 减少不必要的 LLM 调用（简单任务走简单链路）
- 四管线模式（深度思考/快速问答/代码/创意）可根据意图自动切换系统提示词

**应该如何用：**
- **适合**：多场景混合的 Agent（既要聊天又要写代码又要做分析）
- **编排图用法**：Router 后跟多个处理节点，通过边连接
- **AgentLoop 内嵌用法**：通过 `with_router()` 注入，实现发送链路路由（不改图，只改 system prompt）
- **注意**：两种用法目前并存，架构上不统一

---

### 7. Supervisor（监督者/中心化调度）

**如何起作用：**
`SupervisorNode` 持有一组子 Agent 规格（`SubAgentSpec`：id/name/description/system_prompt/tools_whitelist/max_iterations）。执行时通过分配策略（默认 LLM 决策）选择最合适的子 Agent，改写任务描述后创建 `AgentLoop` 实例并运行。子 Agent 完成后将结果写入 state.messages，可进行多轮分配（max_rounds）。

**如何被使用：**
- `AgentCommandService::run_supervisor()` 构造单节点编排图：SupervisorNode 作为唯一节点
- 复用会话的 backend 和 ToolBus（通过 `AgentLoop::tool_bus()`）
- 配置项：`specs`（子 Agent 规格列表）、`max_rounds`、分配策略

**有什么用：**
- 中心化任务分配，一个 Supervisor 管理多个专长子 Agent
- 子 Agent 有独立的 system_prompt 和工具白名单，实现角色隔离
- 多轮分配可处理需要多专长协作的复杂任务

**应该如何用：**
- **适合**：任务可明确分类、各子 Agent 职责清晰的场景（如"代码专家+文案专家+分析专家"）
- **不适合**：需要紧密协作、频繁交互的场景（应使用 MultiAgent）
- **最佳实践**：子 Agent 的 description 要写清楚专长边界，便于 LLM 分配决策
- **注意**：当前子 Agent 复用主 Agent 的 ToolBus，工具隔离（tools_whitelist）尚未完全实现

---

### 8. SubAgent（子 Agent 委派）

**如何起作用：**
SubAgent **不是 OrchestratorNode**，而是通过 `SubAgentManager`（在 agent-commands 层）实现的工具委派机制。`SubAgentManager` 持有子 Agent 规格注册表和实例池（懒加载缓存），向主 Agent 的 ToolBus 注册 `delegate_to_sub_agent` 和 `list_sub_agents` 工具。主 Agent（ReAct 循环）在需要时调用委派工具，`SubAgentManager` 创建/复用 `AgentLoop` 实例运行子任务，结果作为 toolResult 返回主 Agent。支持委派深度限制（max_delegate_depth，默认 3）防止递归膨胀。

**如何被使用：**
- `AgentCommandService` 构造时创建 `SubAgentManager`，注册到主 Agent 的 ToolBus
- 主 Agent 通过工具调用触发委派，不是通过编排图节点
- `register_subagent_spec` 命令可动态注册子 Agent 规格
- `list_instances` 命令可查看子 Agent 实例状态（消息数、是否流式中）

**有什么用：**
- 让主 Agent 在 ReAct 循环中按需委派子任务，无需预定义编排图
- 子 Agent 实例可复用（缓存），避免重复创建开销
- 委派深度限制防止递归委派导致的资源爆炸
- 与 Supervisor 的区别：Supervisor 是编排图节点（显式调度），SubAgent 是工具（隐式调用，由 LLM 自主决定何时委派）

**应该如何用：**
- **适合**：主 Agent 需要自主判断何时委派子任务的场景（灵活、动态）
- **不适合**：需要严格控制执行流程的场景（应使用 Supervisor 编排图）
- **最佳实践**：子 Agent 规格的 description 和 system_prompt 要精确，避免主 Agent 误用
- **注意**：当前实现与 Supervisor 有功能重叠（都能创建子 Agent），架构上需要统一

---

### 9. ToT（Tree of Thoughts 思维树）

**如何起作用：**
`ToTNode` 在一次 execute 内构建完整的思维树。三个可替换策略：
- **探索策略**（`ExplorationStrategy`）：默认 BeamSearch，每层生成 branch_factor 个候选思维
- **评分策略**（`ScoringStrategy`）：默认 LLM 评分，对每个思维打分
- **目标检查策略**（`GoalCheckStrategy`）：默认 LLM 判断是否达到目标
执行流程：初始化根节点 → 逐层探索（生成→评分→剪枝保留 beam_width 个）→ 检查目标 → 达到或超 max_depth 后选最优节点输出。树结构存在 `Arc<RwLock<HashMap<String, ThoughtNode>>>`。

**如何被使用：**
- `AgentCommandService::run_tot()` 构造单节点编排图：ToTNode 作为唯一节点
- `with_default_strategies()` 便捷方法使用 LLM 策略三件套
- 配置项：`max_depth`、`beam_width`、`branch_factor`、`max_thoughts`、收敛阈值

**有什么用：**
- 多路径探索问题空间，避免单一路径的局部最优
- Beam search 平衡探索广度和计算资源
- 每步评分可解释，用户可看到思维树的展开过程
- 适合需要"多想几步"的推理、规划、决策类问题

**应该如何用：**
- **适合**：推理题、规划问题、需要多方案比较的决策（如"设计一个系统架构"）
- **不适合**：简单事实问答、创意写作（多路径反而稀释创意）
- **参数调优**：beam_width=2-3 适合大多数场景，branch_factor=3-5，max_depth=3-5
- **注意**：LLM 调用次数 = sum(每层节点数)，参数过大会导致极高延迟和 token 消耗

---

### 10. GoT（Graph of Thoughts 思维图）

**如何起作用：**
`GoTNode` 扩展 ToT，在思维树基础上增加**聚合操作**（Aggregation）：将多个高分思维节点合并为一个新思维（多 parent），形成图结构而非纯树。聚合策略（`AggregationStrategy`，默认 LLM 聚合）将多个源节点的内容综合为一个新思维。每层结束时可生成 aggregation_branch_factor 个聚合节点进入下一层。聚合阈值过滤低质节点，避免浪费 LLM 调用。

**如何被使用：**
- `AgentCommandService::run_got()` 构造单节点编排图：GoTNode 作为唯一节点
- `GoTConfig` 包装 `ToTConfig` + 聚合参数（aggregation_enabled/threshold/max_size/branch_factor）
- 复用 ToT 的类型定义（ThoughtNode、ToTConfig、ToTError、ToTTerminationReason 等）

**有什么用：**
- 比 ToT 更强的信息综合能力：多个思维路径可以交叉融合
- 聚合操作模拟"集思广益"，将不同角度的思考合并为更全面的方案
- 图结构允许思维节点被多次引用（非树状继承）

**应该如何用：**
- **适合**：需要综合多方面信息的复杂问题（如"制定商业计划"需要市场+技术+财务综合）
- **不适合**：线性推理问题（聚合反而引入噪声）
- **最佳实践**：aggregation_threshold 设为 70+，确保只有高质量思维参与聚合
- **注意**：当前 GoT 直接 import ToT 的内部类型，耦合度高，迁移时需解耦

---

### 11. MultiAgent（多 Agent 对等协作）

**如何起作用：**
`MultiAgentNode` 在一次 execute 内运行 N 个 AgentLoop 的去中心化协作。初始化：创建 N 个 AgentLoop + N 个 mpsc 通道 + SharedBlackboard（共享黑板）。按 topology（全连接/环形/星型）构建 sender 网络。注入初始消息启动协作，每个 Agent 循环：接收消息→思考→调用工具→发送消息给其他 Agent→写入黑板。循环直到收敛（目标检查策略判断或达到 max_rounds）。最后通过综合策略（SynthesisStrategy，默认 LLM 综合）从黑板和消息历史中生成最终输出。

**如何被使用：**
- `AgentCommandService::run_multi()` 构造单节点编排图：MultiAgentNode 作为唯一节点
- 复用会话的 backend 和 ToolBus
- 配置项：`specs`（Agent 规格列表）、`max_rounds`、`topology`、`blackboard_enabled`、`require_synthesis`
- `last_blackboard()` 可供命令层读取黑板快照

**有什么用：**
- 多角色对等协作，模拟团队讨论（如"产品经理+工程师+设计师"共同设计方案）
- 共享黑板实现信息共享，避免消息传递的信息丢失
- 拓扑可配置，适应不同协作模式
- 与 Supervisor 的区别：Supervisor 是中心化调度（一个管多个），MultiAgent 是对等通信（N 个互相讨论）

**应该如何用：**
- **适合**：需要多角色紧密协作、频繁交互的场景（头脑风暴、方案设计、辩论）
- **不适合**：任务可明确分步执行的场景（用 Plan-Execute 更高效）
- **最佳实践**：Agent 数量控制在 2-5 个，过多会导致收敛困难和 token 爆炸
- **注意**：当前是最复杂的模式（内部创建 N 个 AgentLoop + mpsc 通道 + 黑板），与底座耦合最深

---

### 12. Memory（记忆系统）

**如何起作用：**
Memory **不是编排模式节点**，而是底座基础设施。`MemoryAccessor` trait 定义长期记忆的核心操作：
- `recall(query, options)`：语义检索历史记忆
- `inject(results, options)`：将检索结果格式化为 system prompt 注入文本
- `record_turn(user, assistant)`：记录当前轮对话（归档前累积）
- `archive(source)`：触发归档（将累积对话转为长期记忆）
- `get_archive_boundary()`：获取已归档消息的边界索引
- `load_chunk(hook_id, chunk_id)`：按需加载记忆片段
- `delete_by_session_id(session_id)`：删除会话的全部记忆

三类记忆：短期记忆（`state.messages`）、工作记忆（`state.extra["workingMemory"]`）、长期记忆（通过 MemoryAccessor）。

**如何被使用：**
- **AgentLoop 内嵌**（阶段3 记忆闭环）：`with_memory()` 注入后，`run()` 开头 recall→inject（拼入 system prompt），结束时 record_turn→archive
- **编排节点可选访问**：`NodeContext.memory` 字段提供 `Option<&dyn MemoryAccessor>`，节点可按需调用
- 实际实现：`crates/agent-memory` 中的 `MemoryCenterAccessor` 适配 MemoryCenter

**有什么用：**
- 跨会话记忆：Agent 能记住之前对话中的关键信息
- 上下文压缩：归档旧消息，释放上下文窗口
- 语义检索：根据当前查询召回相关历史，而非全量加载
- 是所有需要"记忆"能力的编排模式的基础依赖

**应该如何用：**
- **作为底座能力注入**，不是独立使用的编排模式
- 通过 `AgentLoop::with_memory(Some(accessor))` 启用
- **注意**：当前 MemoryAccessor 是底座的一部分，但在 NodeType 枚举中有 `Memory` 变体（无对应节点），这是命名混淆

---

### 13. Custom（自定义扩展点）

**如何起作用：**
`NodeType::Custom` 是枚举中的占位变体，用于标识用户自定义的 OrchestratorNode 实现。任何实现了 `OrchestratorNode` trait 且 `node_type()` 返回 `NodeType::Custom` 的结构体都属于此类。

**如何被使用：**
- 当前代码中**没有实际的 Custom 节点实现**
- 理论上用户可实现 `OrchestratorNode` trait 创建自定义节点，加入编排图
- 是架构预留的扩展点

**有什么用：**
- 允许在不修改框架代码的情况下扩展新的编排模式
- 是"可扩"目标的关键设计点

**应该如何用：**
- 需要框架未内置的编排逻辑时，实现 `OrchestratorNode` trait
- 当前由于 NodeType 是封闭枚举，Custom 是唯一的扩展通道
- **架构问题**：封闭枚举 + Custom 占位的设计限制了扩展性，重构时应考虑 trait object 或注册表模式

## 四、当前架构问题汇总

### 问题 1：底座与模式边界模糊（最核心）

- AgentLoop 既是底座（state/event/backend/tool 管理），又是 ReAct 模式实现
- Router、Memory、Loop Engineering、Deep Phases 等能力直接织入 AgentLoop::run()
- 导致"离了 ReAct 就运行不了"，底座无法独立承载其他层

### 问题 2：模式实现形态不统一

- 9 个 OrchestratorNode 实现 + 1 个内嵌（ReAct）+ 2 个非节点（SubAgent/Memory）+ 1 个占位（Custom）
- 有的单文件（plan/reflection/router/supervisor/graph_of_thoughts），有的目录（tree_of_thoughts/multi_agent）
- 有的通过编排图使用，有的通过工具使用，有的内嵌在循环里

### 问题 3：NodeType 封闭枚举限制扩展性

- 新增模式必须修改 node.rs 的 enum
- Custom 占位是唯一扩展通道，但无法区分不同自定义模式
- 与"可扩"目标冲突

### 问题 4：模式间隐式耦合

- GoT 直接 import ToT 内部类型
- Reflection 借用 Plan 的 JSON 解析函数
- 公共工具函数（extract_json_array/object）散落在 plan.rs 中，应提取到公共层

### 问题 5：Supervisor 与 SubAgent 功能重叠

- 都能创建子 Agent 实例并运行
- Supervisor 是编排图节点（显式调度），SubAgent 是工具（隐式调用）
- 两套子 Agent 管理逻辑并存，规格定义分散（SubAgentSpec 在 supervisor.rs，实例管理在 agent-commands/subagent.rs）

### 问题 6：Orchestrator 与模式平级

- DefaultOrchestrator（DAG 执行引擎）和 PlanNode/ReflectionNode 等在同一目录层级
- 看不出"引擎驱动节点"的层级关系
- Orchestrator 本身也应该是底座的一部分，而非与模式平级

## 五、迁移难度评估依据

| 迁移难度 | 判定依据 | 对应模式 |
|---------|---------|---------|
| **低** | 纯 OrchestratorNode 实现，仅依赖底座基础能力（state/backend/event），无跨模式依赖，单文件 | Plan, Execute, Reflection, Refine, Router |
| **中** | OrchestratorNode 实现，但内部逻辑复杂（多策略/多状态/并发），或有跨模式依赖 | ToT, GoT, Supervisor |
| **高** | 非 OrchestratorNode 实现（内嵌/工具委派），与 AgentLoop 深度耦合，需要重新设计接入方式 | ReAct, SubAgent, MultiAgent |
| **—** | 基础设施或占位，不属于编排模式 | Memory, Custom |
