## 上篇 · 理论基线

## 一、总框架：九个划分维度

「大纲」不存在唯一标准。它的形态由九个维度共同张成——**同一维度内可以叠加多个取值**（例如「标题式 + 图解式 + 混合式」），维度之间近似正交。

| # | 维度   | 取值                                                   |
| - | ---- | ---------------------------------------------------- |
| 1 | 表现形式 | 标题式、句子式、段落式、表格式、图解式、卡片式、混合式、问题式、脚本式、超文本式             |
| 2 | 详细程度 | 一句话、粗略、标准、详细、句子、段落、逐字、扩展                             |
| 3 | 逻辑结构 | 线性、并列、递进、因果、时间、空间、问题—解决、对比、分类、总分、循环、矩阵、叙事弧、金字塔       |
| 4 | 用途场景 | 写作、演讲、教学、研究、项目、会议、读书、剧本、小说、论文、商业、营销、法律、培训、播客、视频      |
| 5 | 载体工具 | 纸质、Word、Excel、PPT、思维导图、大纲软件、卡片、白板、Notion、Obsidian、AI |
| 6 | 正式程度 | 非正式、半正式、正式、学术/行业标准                                   |
| 7 | 颗粒度  | 宏观、中观、微观                                             |
| 8 | 动态性  | 静态、动态/可重组                                            |
| 9 | 读者对象 | 自用、共享、公开                                             |

**§一·补：表现形式的实现映射（2026-10-19 核对）**

理论取值 **10 个**（段落式 2026-09-18 曾随 Q1 取消、2026-10-19 随 Q1′ 复活）与当前**实现的 9 种形式**对照：

| 理论取值 | 实现（form id） | 说明 |
| --- | --- | --- |
| 标题式 | `title` | 直接对应 |
| 句子式 | `sentence` | 直接对应（软上限 120 字，映射 `description`） |
| 段落式 | `paragraph` | **2026-10-19 复活（Q1′）**：`content` 作为形式专属内容字段回归（声明 / 唯一入口 / 2000 软上限） |
| 表格式 | `table` | 直接对应（行 = 节点） |
| 图解式 | `tree`（树式） | **映射未声明**：树是图解式的树状子集 |
| 超文本式 | `refs`（关联实体） | **映射未声明**：超文本的核心是跳转，徽章点击跳转即此语义 |
| 混合式 | 容器级能力 | 不单独建组件——同容器可叠多个形式，即混合式 |
| 卡片式 | `card` | 2026-10-19 实现（就地编辑：标题 / 摘要） |
| 问题式 | `question` | 2026-10-19 实现（就地编辑问句，字段 `properties.question`） |
| 脚本式 | `script` | 2026-10-19 实现（结构化三字段：场景 / 台词 / 动作，各自独立编辑） |
| （无对应） | `storyline`（线索式） | **实现自造**：按 `storylines` 聚合的统计看板 |
| （无对应） | `progress`（进度式） | **实现自造**：按 `status` / `wordCount` 聚合的进度看板 |

**结论**：清单内实现 **9**（2026-10-19 补齐卡片式 / 问题式 / 脚本式，并复活段落式）· **未实现 0** · 自造 **2**（线索式 / 进度式）。**理论取值已全覆盖。**
**纪律**：新增形式必须在此表登记映射关系——「理论取值」或「实现自造」二选一，不许再有第三个去处（这正是本次差异的来源）。

> **写入交互**不在本表范围：11 种形式中 **7 种可写**（标题 / 句子 / 卡片 / 问题 / 段落 / 脚本 + 树式行内）、**4 种纯只读**（表格 / 线索 / 进度 / 关联实体，通过「转到写入位置」解决）。
> 见 [表现形式写入交互规格](../2026-10-19-表现形式写入交互规格.md)（三档模型 + 逐形式定义）。

> **对系统的含义**：这九维不是「界面上的九个开关」，而是**同一份数据的九种投影**。把它们理解成字段会立刻撞上组合爆炸；理解成视图/渲染配置才不会。

## 二、大纲为何是大纲

### 2.1 五个必要条件

大纲之所以是大纲，是因为它是**对复杂未完成对象的「全局主干结构表示」**：通过省略细节、建立关系、规定顺序，为后续的生成、沟通、执行和迭代提供认知脚手架与约束条件。因此它必须**同时**满足五个条件：

| # | 条件    | 含义                            |
| - | ----- | ----------------------------- |
| 1 | 指向整体  | 覆盖的是一个完整对象：一篇文章、一场演讲、一个项目、一门课 |
| 2 | 捉住主干  | 只保留关键节点，省略大量细节                |
| 3 | 建立关系  | 不只是罗列，而是建立层级、顺序、并列、递进、因果等关系   |
| 4 | 可生成展开 | 能被展开成后续内容或行动                  |
| 5 | 可迭代修正 | 是动态的，可以增删改                    |

**公式**：`大纲 = 全局覆盖 + 主干省略 + 关系结构 + 生成能力 + 迭代接口`

> **原文勘误**：口述公式中「关系结构」出现两次（对应第 3 条件），按五条件一一对应关系，此处按五元组记录。

### 2.2 功能逻辑：底层同时做四件事

| # | 功能 | 说明                                 |
| - | -- | ---------------------------------- |
| 1 | 压缩 | 把复杂的「内容」压成「结构信息」，像压缩包——保留的是解压规则    |
| 2 | 排序 | 决定什么先讲、什么后讲、什么重要、什么次要              |
| 3 | 连接 | 建立父子、并列、因果、对比、时间、空间等关系             |
| 4 | 约束 | 为后续写作或执行设定边界：这里该放什么、不该放什么、写到什么程度算够 |

> **结论**：大纲不是内容的影子，而是**内容的生成规则**。

### 2.3 生成逻辑：处在「意图」与「成品」之间

底层链条：

```
目标 → 复杂素材 → 认知瓶颈 → 结构降维 → 大纲 → 展开生成 → 反馈修正 → 大纲迭代 → 成品
```

一句话：**用结构统摄内容，用主干带动细节**。

### 2.4 边界逻辑：六种近邻物为何不是大纲

| 近邻物  | 与大纲的区别                         |
| ---- | ------------------------------ |
| 清单   | 只有项目，没有层级和关系                   |
| 摘要   | 压缩内容，不生成结构                     |
| 目录   | 面向**已完成**内容；大纲面向**未完成**内容      |
| 草稿   | 已有表达；大纲是表达**前**的结构             |
| 计划   | 强调时间、资源、行动；大纲强调内容、逻辑、结构        |
| 思维导图 | 可以是大纲的一种形式；但若**只发散不收敛**，就还不是大纲 |

判别口径（四条同时成立才算大纲）：**面向未来、捉住主干、建立关系、可以展开**。

## 三、大纲承载什么

大纲把碎片信息转化为结构节点，并给出**关系**与**状态**的可操作概览。拆三层：整合碎片、关系概览、状态概览。

### 3.1 整合碎片

散落的信息本身是孤立的——一条笔记、一个例子、一个疑问、一个数据、一个灵感，它们**没有位置，也没有轻重**，所以无法直接使用。大纲做的六件事：

1. **捕获**：先承认这些碎片存在
2. **归类**：把相似碎片放到同一主题下
3. **归并**：合并重复，拆分混杂
4. **层级化**：确定谁统摄谁，谁从属于谁
5. **排序**：决定先后、主次、轻重
6. **定位**：让每个碎片知道「我属于哪一部分、我为什么在这里」

> **结论**：大纲不是把碎片收进仓库，而是给每个碎片一个**地址**和**角色**。

### 3.2 关系概览

大纲的核心不只是列出节点，而是建立关系，让碎片从「并列存在」变成「相互定义」。三类关系：

| 类型   | 内容                            |
| ---- | ----------------------------- |
| 纵向关系 | 父—子、总—分、目标—手段、抽象—具体           |
| 横向关系 | 并列、对比、递进、因果、时序、空间、问题—方案、论点—论据 |
| 跨层关系 | 依赖、引用、冲突、支撑、反驳、补充             |

有了关系，大纲就变成一张**关系地图**：从看一堆点，变成看一个有方向、有层级、有逻辑的网络。回答四问——**有什么、在哪里、怎么连、为什么连**。

### 3.3 状态概览

传统大纲偏静态结构；现代工作大纲、项目管理大纲、知识库大纲还承载状态信息。每个节点可标注六类状态：

| # | 状态类别 | 取值示例                    |
| - | ---- | ----------------------- |
| 1 | 认知状态 | 已知 / 未知 / 假设 / 争议 / 待验证 |
| 2 | 完成状态 | 未开始 / 进行中 / 已完成 / 搁置    |
| 3 | 优先级  | 核心 / 次要 / 可选            |
| 4 | 资源状态 | 有素材 / 缺素材 / 需数据 / 需采访   |
| 5 | 逻辑状态 | 自洽 / 冲突 / 有缺口           |
| 6 | 行动状态 | 待办 / 待决策 / 待确认          |

> 于是大纲不只是骨架，还是**仪表盘**：哪里已经扎实、哪里还是空的、哪里逻辑冲突、哪里需要补料——**到哪了、卡在哪、缺什么、下一步是什么**。

### 3.4 三者如何联动

```
碎片信息 → 节点化 → 关系化 → 层级化 → 状态化 → 概览化 → 可操作化
```

1. **节点化**：碎片变成可命名的条目
2. **关系化**：条目之间产生连接
3. **层级化**：连接分出主次
4. **状态化**：每个条目带上进度和属性
5. **概览化**：全局视图形成
6. **可操作化**：知道下一步该写什么、补什么、删什么、问什么

> 大纲不只是「整合碎片」，它把碎片变成**可导航、可判断、可迭代的系统**。

### 3.5 边界：大纲不是数据库

大纲承载整合、关系和状态概览，但**不应塞满所有碎片内容**。合理结构是三层：

| 层     | 职责                 |
| ----- | ------------------ |
| 素材库   | 保存原始碎片、引用、数据、案例    |
| 大纲    | **只保留节点、关系、状态和指针** |
| 成稿/执行 | 根据大纲展开生成           |

> 大纲是**索引层和控制层**，不是仓库本身；它让碎片可被调用，而不是把碎片全部背在身上。

## 四、总定义

> 大纲是**碎片信息的结构整合器、关系地图和状态仪表盘**；它把散落信息变成**有地址、有关系、有状态、可操作**的全局概览。

## 五、由理论推导的系统约束（整理项）

把上篇翻译成可检验的系统要求，供设计对照：

| #   | 约束                                        | 来源          | 可检验形式                |
| --- | ----------------------------------------- | ----------- | -------------------- |
| C1  | 必须支持**树形主干**且主干可省略（允许节点只有标题、无正文）          | §2.1-1/2    | 空节点是合法状态，不逼填内容       |
| C2  | 关系必须是**一等公民**，且不限于父子                      | §2.2-3、§3.2 | 横向/跨层关系可通过数据表达并在视图呈现 |
| C3  | 每个节点必须可携带**多类状态**（至少完成状态 + 逻辑状态）          | §3.3        | 状态是结构化枚举，不是自由文本      |
| C4  | 必须能**展开生成**到下游（成稿/执行），且展开是单向引用（大纲不背内容）    | §2.1-4、§3.5 | 节点存指针；正文落在成稿侧        |
| C5  | 必须支持**迭代**：增删改 + 重排 + 关系变更都可逆             | §2.1-5      | 撤销/回收站/移动不失真         |
| C6  | 九维中「表现形式/详细程度/逻辑结构」应是**同一数据的渲染维度**，不是数据类型 | §一          | 不因换表现形态而丢数据          |
| C7  | 「面向未完成对象」是**与目录/成稿的根本分界**                 | §2.4        | 大纲节点不是章节实体，二者是引用关系   |
| C8  | 系统必须能回答四问：**有什么、在哪里、怎么连、为什么连**            | §3.2        | 结构查询能力（可被 Agent 调用）  |
| C9  | 系统必须能回答四问：**到哪了、卡在哪、缺什么、下一步是什么**          | §3.3        | 状态聚合/概览视图            |
| C10 | 素材库与大纲分离：大纲只放**指针**                       | §3.5        | 大纲节点正文长度受限，长内容外置     |

## 八、画布形态可行性（Q0 · 2026-09-15 追加 · 未拍板）

**问题**：大纲芽的前端形态，能否是一个能容纳/承载本理论（上篇 §一–§四）的画布或白板？

**结论（本节的判断）**：能，但必须区分两种问法——
- **画布作为「大纲数据的一种投影视图」**：技术上可行，且项目已有三套成熟范式可直接复用（§8.1），成本低、风险可控。**推荐这条路**。
- **画布作为「大纲的容器本体」**（即画布成为大纲的唯一/主形态、节点位置成为事实来源）：与大纲的定义直接冲突——大纲的规定性来自**顺序 + 层级 + 约束**（§2.2），而自由画布的**空间位置默认无语义**。若让位置成为真相，就同时有了「位置」与「order」两套顺序真相，重蹈本芽既有的「层级双写」覆辙（§6.2）。

### 8.1 项目已具备的三种画布范式（取证）

| 范式 | 代表 | 数据归属 | 可复用性 |
| --- | --- | --- | --- |
| 纯视图画布 | `official.graph` 全局图谱 | **不注册实体**，读全实体 + 关系 | `apps/tauri/src/sprouts/official/graph/index.ts:24-32`（`toolbar: 'overlay'` 全屏画布 + 悬浮工具条） |

### 8.3 核心张力：位置的语义地位（三选一）

| 方案 | 含义 | 后果 |
| --- | --- | --- |
| (a) 位置=视图态 | 坐标只存本地布局（如 `ws-outline-layout` 的 expandedIds 模式），不入实体 | 安全、零数据模型改动；代价是「自由摆放」不跨设备/项目保留 |
| (b) 位置=可选字段，非真相 | 坐标存实体（如 `layout.x/y`），但顺序仍以 `order` 为准；布局算法读 order，用户微调覆盖坐标 | 需要明确「重排后坐标是否失效」规则，否则出现两个真相 |
| (c) 位置=真相 | 放弃 `order`，位置即顺序 | 与 §2.2「排序是基本功能之一」冲突；导出/Agent 侧需重新定义顺序语义 |

> 建议 (a)：大纲的顺序必须可被 Agent 与导出稳定读取（`get_structure` 已按 order 排序，`agentDataBridges.ts:401-415`），把位置留在视图态最不容易破坏既有链路。

### 8.5 与 Q1（定位边界）的耦合 —— 诚实说明

画布形态**无法完全独立于 Q1**：画布节点放不下长文，因此若画布成为主视图，节点必须指针化，这等于替 Q1 投了「A 纯结构层」或「B 限长梗概」的票。
可部分解耦的做法：把**节点卡片的渲染内容做成可配置**（标题 / 摘要 / 状态徽章 / 字数），画布只消费「指针」，不消费 `content` 全文。这样即使 Q1 未定，画布也能先落地。

1. **画布与列表的关系**：并列第四个页签（树/线索/进度/画布）｜画布为主 + 列表为辅｜独立成新芽
2. **画布档位**：A 层级树画布｜B 关系画布｜C 自由白板
3. **位置语义**：视图态（不入库）｜可选字段（非真相）｜入库为真相

### 8.7 方案 D：白板编辑器（用户构想 · 09-15 追加 · 未拍板）

**构想原话要点（负责人表述）**：
- 要的不是「大纲芽多一个页签」，而是**一个类似画布/白板的编辑器**——因为「各种表现形式如果用其他的（视图）就不能全部呈现出来」；
- **半自由的白板**：一块白板内部兼容**多种表现形式**；
- **编辑器之外可以有多个白板**：白板是多实例的；
- 白板**是实体，但与其他实体芽的实体性质不同**（非世界观对象，而是承载物）。

**含义**：这把大纲芽从「树视图」重新定义为「**结构承载物编辑器**」——白板 = 作品结构的容器实例，节点 = 结构单元，表现形式 = 节点的渲染配置。理论 §一 的九维里，「表现形式」由此从「视图选择」变为「节点/白板级配置」。

#### 8.7.2 关键设计分岔：节点数据放在哪一层

| 方案 | 结构 | 代价 |
| --- | --- | --- |
| **甲（推荐）** | 节点仍是 `outline_node` 实体；白板只存「节点 id → 位置 + 表现形式」的**布局层** | 需维护一致性（节点删除后布局残留）；换来：Agent 8 动作 / `parent_child` 关系 / 实体搜索 / 跳转正文**全部保留** |
| 乙 | 节点整体塞进白板内容 JSON（mind-elixir 模式：`mindmapDoc.ts:1-24` 独立文档 + `project_settings` KV） | 简单、灵活、无限自由；但**大纲节点脱离实体系统**——现有 Agent 工具、关系、搜索、跨视图复用全部要重做，且与既有 `outline_node` 数据不兼容 |

#### 8.7.3 遗留张力被这个方案自然化解

「位置属于**白板**，不属于**节点**」——同一节点可出现在多个白板、各有位置。于是：
- 位置语义问题（§8.3）不再是「选 a/b/c」，而是**结构上分开**：`order` 管语义顺序（实体侧），位置管空间呈现（白板侧）；
- §8.2 的「顺序」弱项因此可控：白板不承担顺序，导出与 Agent 读 `order`（`agentDataBridges.ts:401-415`），线性/时间轴等「顺序类表现形式」则作为**布局模式**存在。

#### 8.7.4 待澄清

1. **「半自由」的可操作定义**：① 自动布局 + 局部拖拽即锁定（未拖的跟随布局）② 分组/泳道内自由、组间由关系约束 ③ 网格吸附 + 手动微调
2. **表现形式的粒度**：节点级 `renderMode`（同一节点可切卡片/标题/段落/表格）｜白板级模板（一块白板一种基调）｜两者叠加
3. **白板与节点的归属关系**：白板容纳全部 `outline_node`｜每块白板可选范围（子树/线索）｜白板可否嵌套
4. **芽的身份**：改造现有 `official.outline`｜新建独立芽（如 `official.board`）｜两者并存

**架构问题（需拍板）**：上述能力位于 `apps/tauri/src/sprouts/official/module-builder/`，**属芽内私有、不在共享包**。大纲芽要复用它只有两条路：

| 路径 | 说明 | 代价 |
| --- | --- | --- |
| (i) 提升为共享包 | 抽到 `packages/`（如 slot-kit），两芽共用 | 架构变更（需拍板），会触及 module-builder 回归面 |
| (ii) 芽内照抄 | 快，改动隔离 | 重复实现；本项目已有「双份漂移」教训（marked / @tiptap 双清单、MentionPopover 副本） |

**映射到方案 D**：白板 = 根槽位（`free`/`grid`）；板内可画「区」= container 槽位（承担组间约束）；区内放「节点组件」= 节点 + 表现形式；**表现形式 = 组件的 typeId**；节点数据仍在实体侧（甲方案）。

**由此浮现的二级问题**：组件与节点的对应关系——
- ① 组件 = 节点 + 表现形式（1:1，一个组件代表一个节点，表现形式是它的渲染模式）
- ② 组件 = 可聚合多个节点的容器（1:N，组件本身是「区/组」）
- ③ 两者并存（组件可代表节点，也可代表一组节点）

负责人「各种表现形式…一个白板兼容多个表现形式」的表述更贴近 ①，但需明确拍板（见 §九-Q0b）。

#### 8.8.1 负责人判定（09-15 追加四）

1. **组件与节点 = ① 1:1（已定）**：一个组件 = 一个节点 + 一种表现形式。
2. **module-builder 的组件模型判定为「不可复用」→ 需自研**。即 §8.8 上表的「现成模型」只作为**参照与借鉴**，不作为复用来源；本节的能力缺口（`free` 排布 / `x`·`y` 未实现）随之降为背景信息——大纲白板将自建一套贴合「结构表达」的模型，而非沿用「页面搭建」的槽位语义。
3. **表现形式的前端 UI 形态需逐个研究敲定**：表现形式不是靠「注册一个组件类型」就能批量获得的能力，每一种（标题式 / 句子式 / 段落式 / 表格式 / 图解式 …）都需要单独设计其 UI 形态与交互。→ 故本轮工作的**前置产物**是「表现形式逐个定义」，而非直接进入施工。

### 8.10 后端抽象草案（09-16 · 依负责人「白板 / 容器 / 组件」三层澄清）

负责人 09-16 澄清三点：① 需求以**前端形态**描述，**后端抽象由技术侧负责**；② §8.9.1 第 3 点修正——白板上摆放的不是「组件」而是**容器**，**容器内的才是组件**，组件**承载表现形式结构**；③ 其余判定点授权技术侧拍板（判定与依据见 §8.10.5，可推翻）。

#### 8.10.1 三层定名与归属

| 层 | 前端形态 | 后端身份 | 承载内容 |
| --- | --- | --- | --- |
| 白板 board | 可缩放平移的画布，多块并存 | **实体** `outline_board`（与 `drawing` 同模式） | 元数据 + 视口 + 缩略图 + 布局体 |
| 容器 container | 画布上可拖动的框（**摆放单位**） | 布局体内的结构层，**非实体** | `nodeId` 指针 + 位置 + 尺寸 + 组件列表 |
| 组件 component | 容器内的结构单元 | 布局体内的结构层，**非实体** | 表现形式类型 + 配置 + 顺序 |

一句话：**布局体只记「哪个节点、什么表现形式、放在哪」**。

#### 8.10.2 数据落点与字段草案

白板实体 `outline_board`（`ownFields`，照 `drawing` 先例）：

| 字段 | 内容 |
| --- | --- |
| description | 白板说明（复用 trait） |
| viewport | `{ zoom, panX, panY }`（JSON 串） |
| thumbnail | 缩略图 asset URL |
| layout | 布局体 JSON 串（结构见下） |

布局体草案：

```ts
interface OutlineBoardLayout {
  version: 1
  sections: Section[]
  containers: Container[]
}

/** 区：人工划分，承担「组间约束」 */
interface Section {
  id: string
  title?: string
  rect: { x: number; y: number; w: number; h: number }
  arrange: 'free' | 'vertical' | 'horizontal' | 'grid'
  order: number
}

/** 容器：与大纲节点 1:1 */
interface Container {
  id: string
  nodeId: string                                   // 指向 outline_node 实体
  sectionId?: string                               // 所属区（无 = 直接摆在板上）
  pos: { x: number; y: number }
  size?: { w: number; h: number }                  // 未设 = 内容自适应
  collapsed?: boolean
  components: Component[]
}

/** 组件：承载某一种表现形式的结构 */
interface Component {
  id: string
  form: string                                     // 表现形式类型（自研注册表）
  order: number
  config?: Record<string, unknown>                 // 该形式的配置（表格列 / 图解方向 …）
}
```

**内容不入布局体**：组件不存内容，内容由「表现形式 × 节点字段/关系」派生（§8.10.4）。这样白板与实体之间**不存在内容双写**。

**落点选择（技术侧拍板）**：布局体放白板实体 `properties.layout`——与 `drawing.canvasData` 先例一致、单一真相源。若实测大板拖拽的写放大（实体更新 = 顶层浅合并 + properties 整体替换，`entity_commands.rs:338`）成为瓶颈，再迁移为「布局体独立存项目 DB KV」（`mindmapDoc.ts:26-29` 模式）。列为优化项，不在初期复杂化。

#### 8.10.3 与既有数据的关系（不破坏原则）

- `outline_node` 的 `parentId` + `order` 仍是**语义层级与顺序的唯一真相源**；白板只记呈现。位置与顺序彻底分离。
- **悬空容器**：节点被删后容器 `nodeId` 失效 → 技术侧拍板「**渲染为占位 + 提供显式清理入口**」，不静默删除容器（避免误伤用户排布）。
- **Agent 侧**：`outline` 8 动作不动；「把一批节点摆到白板上」这类白板级 Agent 动作另立挂账。
- **导出**：表现形式决定导出形态（§8.10.5-G），故导出需经「表现形式渲染」这一层。

#### 8.10.4 表现形式的抽象定义（自研注册表的规格）

每种表现形式必须给出五件事——这也是负责人要求「逐个研究敲定」的对象：

1. **内容映射**：读节点的哪些字段 / 关系
2. **结构**：生成什么结构（一行标题 / 一句话 / 子节点表 / 关系图）
3. **编辑能力**：能否就地改内容，改的是哪个字段
4. **配置项**：该形式可配什么（表格列、图解方向、缩进深度）
5. **导出形态**：导出 docx/md 时呈现成什么

首批建议 3 种（覆盖「最短 → 一句话 → 跨节点结构」三档）：**标题式**（`name` + 层级）、**句子式**（`description`）、**表格式**（`children[]`）。
**段落式 → 已取消（2026-09-18，随 Q1 裁定）**：它映射 `content`（长文本）。Q1 定为 **A 纯结构层**、`content` 已删除，故段落式**不再是待做项**；需要长文时走 manuscript（节点 ↔ 章节关联已打通）。

#### 8.10.5 A–G 七项判定（技术侧拍板 · 可推翻）

| # | 判定 | 依据 |
| --- | --- | --- |
| A 数据流向 | **先有节点，再在容器里配表现形式**；表现形式永远是节点数据的派生，无独立内容 | 保住甲方案（节点是唯一真相源），Agent 与导出天然一致 |
| B 重复出现 | **同一白板内一个节点只能有一个容器**；**跨白板可重复** | 容器是摆放单位，同板内重复会产生「同一节点两个位置」的歧义 |
| C 多板关系 | **白板是视图，不是内容分区**——多块白板 = 同一批结构的不同组织/用途；要限定范围就在板内用「区」表达 | 避免「内容被切开」的搬运与一致性负担 |
| D 表格式 / 图解式 | **渲染该节点的子树 / 关系**（一节点一容器，组件服务于该节点） | 与「容器:节点 = 1:1」自洽；跨节点排布由「多个容器」完成 |
| E 「区」来源 | **人工划分**（可拖框、可命名），不自动成组 | 「约束」是用户意图的表达；自动成组会与 `parentId`/`order` 形成两套结构语义 |
| F 与树视图 | **并存**：树 = 结构保真视图，白板 = 表现自由视图 | 大量节点、线性通读、可访问性仍是树/列表强项（§8.2）。属 UX 层级，若定为「白板为主视图」可推翻 |
| G 导出 | **表现形式决定导出形态** | 否则表现层与产物脱节，理论 §一 的「表现形态」落不到成品上 |

#### 8.10.6 施工前仍待办

1. **表现形式规格逐种填写**（按 §8.10.4 五件事）——前置研究产物
2. 白板实体命名与激活策略（`outline_board` 是否随 `official.outline` 一并激活）
3. 悬空容器的占位样式与清理入口（UI）
4. 性能预算：单板容器数上限、拖拽保存防抖时长、布局体体积上限

>

> 1. 在 `outline_node.ownFields` **声明**（可见、可校验、进字段矩阵）；
> 2. 有**唯一写入入口**（就地编辑或面板编辑），不靠"某处顺手写"；
> 3. 有**长度语义**（软上限 + 超出提示），不是无底洞。
