# 启动页跟随 dsh 就绪批计划

> 起因：用户走查「启动双窗缺陷修复」后提出两点（2026-11-04）：
> ① 从产品域首页切到 Agent 空间时 dsh 界面还没加载（404 占位）；
> ② 产品域侧的启动页感觉「丢失」了。
> 判定：两点**同源**——启动页的结束条件只反映产品域自己就绪，与 dsh 加载完全脱钩。

## 一、根因分析

### 1.1 两点问题同一根因

产品域启动页的结束判定是 `uiStore.markReady()`，而它只等 4 个本地阶段：

```js
backend(初始化核心) → project(恢复项目) → shell(装配界面) → bridge(系统桥接) → markReady()
```

**这 4 步全是产品域自己的工作，与 dsh 无关。** 而 dsh 是在壳的后台线程里独立 spawn、独立等就绪（壳侧 `READY_TIMEOUT` 达 **90s**）。两条链完全并行、没有汇合点。

于是：

- **问题 ①**：用户切到 Agent 空间时，dsh 可能仍在 spawn/就绪链上 → 看到 404/占位页。
- **问题 ②**：启动页在 `markReady` 后保留 750ms 即离场；而 `markReady` 距首帧只有本地阶段那点时间。**启动页并没有「丢失」，是离场太快**（尤其本地阶段快时，750ms 覆盖不掉启动页自身的入场动画）。

### 1.2 缺失的能力

**产品域窗无法知道 dsh 何时就绪**——`DshBridge` 存在 `app.manage()` 里，但没有任何查询命令或事件。这是本次要补的通道。

## 二、方案

### 2.1 新增 dsh 就绪态通道（壳侧）

新文件 `apps/tauri/src-tauri/src/dsh_ready.rs`：

- 三个状态：`pending`（未就绪/启动中）/ `ready`（桥已装配，页面可加载）/ `failed`（启动失败）；
- 单向推进、进程级单值（`AtomicU8`），不回落——运行中 dsh 退出由 `watch_child` 单独处置，不属启动问题；
- 新命令 `cmd_dsh_ready_state` 供页面轮询。

**就绪落点**：`dsh_shell::install` 的 `attach(...)` 成功之后立刻 `mark_ready()`（此刻桥已装配 = dsh 页面可以加载）；`Err` 分支 `mark_failed()`。

### 2.2 启动页等两者都就绪（前端）

`App.vue` 的 `runBoot()` 在本地四阶段之后插入汇合点：

```js
uiStore.setBootStage('agent')
await waitForDshReady()      // 轮询 cmd_dsh_ready_state
uiStore.markReady()
```

**三道出口**（任一即返回，绝不把用户锁在启动页）：

| 出口 | 行为 |
|---|---|
| dsh `ready` | 正常放行——这是主路径 |
| dsh `failed` | **立即放行**——失败已有专门错误页与系统通知，不在启动页干等 |
| 封顶超时 **15s** | 放行并 warn——dsh 慢启动不阻塞使用（壳侧上限 90s，此处远小于它） |

**命令缺失**（浏览器预览 / 旧壳）→ 静默当就绪。

### 2.3 新增启动阶段文案

`uiStore.bootStage` 联合类型增 `'agent'`；`SplashScreen.vue` 的 `BOOT_STAGES` 增一条 `{ key: 'agent', short: '内核', full: '等待 Agent 内核' }`。

否则等待期间进度会停在「系统桥接」，用户不知道在等什么。

### 2.4 为什么用轮询而非事件

一处实现、无需监听器生命周期管理（窗口隐藏/显示、页面重挂载都无需清理）。150ms 间隔 × 最多 15s ≈ 100 次 IPC，开销可忽略。

## 三、时序校验

关键问题：**工作台窗在等待期间是否可见？隐藏窗的 JS 定时器会不会被节流？**

实测确认**不会**：`App.vue` 的 `onMounted` 里先调 `cmd_workspace_first_paint`（壳显示预建窗），**之后**才 `void runBoot()`。所以整个等待过程都发生在**已可见的窗口**里，无后台节流。

时序：

```
Vue mount → first_paint(窗口显示,启动页可见) → runBoot 本地四阶段 → 等 dsh → markReady → 750ms 后启动页离场
```

## 七、首轮走查复盘（2026-11-04，**两个真因都不在上面的方案里**）

用户反馈「首启仍未见启动页动画」。排查发现两处**都属既有缺陷**，本条方案（等 dsh）并非当时的主要矛盾：

### 7.1 真因一：跑的是旧产物（工程口径问题）

产品域页面加载的是**已构建的 `apps/tauri/workspace-dist/`**（`workspace_dist.rs`：dev 下读实时产物，安装形态读 exe 同级），**不是源码**。

实测：改动前 `workspace-dist` 目录时间为 **11-03 03:01**，而我的源码改动在 **11-04 00:14** → **用户运行的是旧版本，所有前端改动均未生效**。

**构建命令**（`apps/tauri/workspace/vite.config.ts` 头注给的官方用法）：
```
cd apps/tauri && node node_modules/vite/bin/vite.js build --config workspace/vite.config.ts
```
> 注意：`apps/tauri/package.json` 的 `build`（`vue-tsc -b && vite build`）构建的是**主窗**，不是工作台。两者入口不同，别混。

### 7.2 真因二：`cmd_workspace_first_paint` 从未登记 ACL（既有缺陷，潜伏一个多月）

`capabilities/workspace.json` 引 `allow-product-domain` → `permissions/worldsea-product.toml`。该 ACL 文件采用**显式白名单**（未列即拒）。

而 `cmd_workspace_first_paint` 自提交 `0685eb8`（默认落地工作台那批）引入后，**从未登记进该表**。后果链：

1. 工作台页 `onMounted` 调 `invoke('cmd_workspace_first_paint')` → **被 Tauri ACL 拒绝**；
2. `App.vue` 当时写的是 `.catch(() => {})` —— **静默吞掉**，无任何日志；
3. 首绘门永不触发 → 工作台窗只能等 `startup_visibility()` 里的 **8 秒兜底超时**强制显示；
4. 表现：**启动后 8 秒内看不到任何窗口**，然后窗口直接出现在首页 —— 即用户说的「启动页丢失」。

**这解释了「启动页丢失」的真正原因**：不是离场太快，而是**窗口压根没被首绘门显示出来**。

**处置**：
- ACL 补登 `cmd_workspace_first_paint` 与 `cmd_dsh_ready_state`（§7.3 的新命令同样需要）；
- `.catch(() => {})` 改为**留痕 warn**——静默 catch 是这条缺陷潜伏一个月的直接原因，同类写法必须避免。

### 7.3 顺带修正的判定

| 原判断 | 修正后 |
|---|---|
| 「启动页离场太快（750ms 不够）」 | **不是**主因。真因是窗口未被显示（§7.2） |
| 「等 dsh 就绪可解决启动页看不到」 | 只解决**切过去 404**；启动页可见性另有 ACL 缺陷 |

### 7.4 复验清单（必须按此顺序）

1. **先构建产物**：`node node_modules/vite/bin/vite.js build --config workspace/vite.config.ts`（否则改源码无效）；
2. 确认产物含新特征：`grep -c "cmd_workspace_first_paint\|cmd_dsh_ready_state\|等待 Agent 内核" index-*.js` = 3；
3. 重启壳验证 §五 四项；
4. 若仍无启动页 → 看控制台是否有 `[App] 首绘门回报失败` 警告（有 = ACL 仍未生效，需查 capabilities 与 TOML 是否被正确打包）。

## 八、第三轮：启动页背景透明（2026-11-04，根因 = CSS shorthand 的 var() 失效回退）

修好 ACL 后启动页终于出现，但**背景是透明的**，透出未加载完的首页卡片（用户截图实证）。

### 8.1 排查过程（先排除，再定位）

在真实 Chrome 里对**构建产物**逐层验证，六项全部正常：

| 检查项 | 结果 |
|---|---|
| `.ws-splash` 规则是否在产物里 | ✅ 完整存在（含 scoped `[data-v-275a4be2]`） |
| CSS 变量能否解析 | ✅ `--color-primary` → `#8b87f8` 等全部成实值 |
| 最底层渐变是否不透明 | ✅ 解析为 `rgb(17,17,19)` |
| scoped 属性选择器是否命中 | ✅ 带属性才命中（对照实验证实） |
| `position: fixed` 的包含块 | ✅ `#app` 无 transform/filter/contain，不破坏 fixed |
| WebView2 是否支持 `color-mix()` | ✅ 156.0.4314.58，支持 |

### 8.2 根因：`var()` 的失效回退**整条属性**，而 fallback 救不了

原写法把不透明底和两层光晕塞进**同一条 `background` shorthand**：

```css
background:
  radial-gradient(... color-mix(in srgb, var(--color-primary, #7C3AED) 10%, transparent) ...),
  radial-gradient(...),
  linear-gradient(135deg, var(--color-bg-base, #0D0D0D) ...);   /* ← 不透明底在这层 */
```

CSS 规范的两条规则叠加成陷阱：

1. `var()` 在**计算值阶段**替换；
2. 替换后若该属性值无效 → **整个属性回退 initial**（对 `background` 即透明）；
3. `var(--x, <fallback>)` 的 fallback **只在变量未定义时生效**，**变量有定义但拼出无效值时救不了**。

于是只要任一层解析出 WebView2 不接受的值，**整条 background（含底部不透明层）一起作废** → 启动页透明。
这解释了「子元素（眼睛/标题/进度条）都正常渲染、唯独背景没了」——子元素用的是各自的独立属性，没有共享这条 shorthand。

### 8.3 修复

| 改动 | 说明 |
|---|---|
| 底色拆成 `background-color: #111113`（**硬值，不引用变量**） | 加载遮罩的最后保险必须无条件成立 |
| 渐变改由 `background-image` 承载 | 它整条失效也不影响上面的纯色 |
| 浅色主题硬值 `html[data-theme='light'] .ws-splash { background-color: #fafaf9 }` | 与深色成对，同样不依赖变量 |
| `@supports not (color: color-mix(...))` 降级 | 不支持混色的环境给纯渐变，观感朴素但绝不透明 |
| `html { background-color: #111113 }`（App.vue 根样式，硬值） | 更外层的兜底：连启动页都失效时也不透出桌面 |

### 8.4 验证（真实浏览器，对照实验）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 变量正常 | 不透明 | 不透明 |
| **四个主题变量全损坏**（历史 bug 场景） | **透明** | **仍不透明（rgb(17,17,19)）** |

修复后即使 `background-image` 整条作废（`bgImageValid=false`），`background-color` 仍生效——这正是原 shorthand 做不到的。

### 8.5 复验清单（在 §7.4 之后）

1. **先构建产物**（顺序不能省，见 §7.1）；
2. 重启壳，启动页应显示**深色不透明背景**，不再透出首页卡片；
3. 切换浅色主题再启动一次 → 背景为浅色（`#fafaf9`）。

> **通用教训**：把「必须成立的底色」与「可降级的装饰」分开写在不同属性上。
> 任何含 `var()` 的 shorthand 都可能因变量失效而整条作废，**不能把不可失败的一层压在它里面**。
