# 以其为基方向探究

> status: 已完成
> 方向定义（用户原话）：**「以其为基」——确认该项目是否有作为框架或基座的形态。**
> 前置事实：[本项目 Agent 现状盘点](01-本项目Agent现状盘点.md)（域内资产与硬边界）。
> 参照项目：deepseek-harness（`dsh`，TypeScript / Node、MIT、开发者预览期 `0.1.6-alpha.1`），本地路径 `.独立项/【参考项】deepseek-harness/`。
> 取证方式：四路只读探索；关键论断附 dsh 文件路径。未改任何代码。

## 零、结论

**dsh 具备完整且刻意的基座形态；但作为 WorldSea 的基座，它带来的是一次「双进程双语言」的结构性改变，而非一次框架替换。**

三句话概括：

1. **形态成立**：Cordis 全插件架构 + 命名 profile + 有序 patch 层，官方明示"没有特权核心可打补丁，一切从配置替换"（`dsh/docs/architecture.md`）；agent-loop 本身可换（`dsh/packages/README.md`）。基座能力完成度很高。
2. **三处硬约束**：① 运行时**必须是 Node**（可打包成单文件可执行，但消不掉 Node）；② 官方 Web UI 是 **React 18 + Cordis slots**，Vue 无法进入——它的 UI 扩展单位是"client 插件 + slot"，不是"渲染框架"；③ **对外承诺度低**：developer preview、SDK 协议无版本协商、wire 类型是构建期产物，"契约"多为 current-state 参考而非冻结规格。
3. **对 WorldSea 的推论**：能"以 dsh 为基"的部分只有 **Agent 引擎**（loop/工具/会话/配套能力），UI 与领域层必须自建自留；最终架构必然是 **Rust 主进程 + dsh Node 侧车**——与项目"单二进制部署"约束存在结构性张力，此张力是方向决策的核心事实。

**接入形态可行性排序**（详见 §二）：

| 形态 | 可行性 | 一句话 |
|---|---|---|
| 进程外 `--profile web`（HTTP + WS） | 可行（功能最全） | 数据面完整，但无冻结协议规格，Rust 侧需自写协议客户端并承担漂移 |
| 进程外 `--profile sdk`（JSON-RPC stdio） | 可行（表达力弱） | 协议极简（7 个方法/通知），**无逐字流式帧**，聊天体验有硬缺口 |
| ACP | 仅自动化 | 官方明示 automation-only，不能承载产品 UI；可当子代理执行器 |
| 嵌入进程 | 不可行 | 宿主必须 Node；除 `dsh` profile 外没有别的应用启动路径 |
| 复用/替换 UI 包 | 不可行 | React 硬编码；"复用 client 内核换 Vue 渲染层"无路径 |

## 一、基座形态评估（dsh 侧证据）

### 1.1 形态要素齐全

| 要素 | 内容 | 证据 |
|---|---|---|
| 无特权内核 | 一切皆插件：模型适配、工具注册表、会话日志、agent loop 都可从配置替换 | `dsh/docs/architecture.md` |
| 组合机制 | profile（命名组合，存于 Harness home）+ bundle（配置行与挂载代码的分发格式）+ 有序 patch 层（bundle 顺序 → profile patch → home patch → `--patch` overlay） | `dsh/docs/architecture.md`（Profiles and bundles） |
| 应用形态 | `web` / `headless` / `sdk` / `sdk-minimal` / `acp` 五个官方 profile；`dsh web` 是 `--profile web` 的别名 | `dsh/docs/architecture.md`（Application launch） |
| 第三方扩展 | `dsh plugin --profile <name> add <pkg\|git\|tarball>`（转发 pnpm，落 `$DSH_HOME/profiles/<name>`）；bundle/profile 由 `package.json` 的 `dsh` 字段声明 | `dsh/docs/user/develop/basic/publish.md`、`dsh/apps/cli/reference/README.md` |
| 扩展点地图 | 官方"新行为放哪里"映射表（换 loop / 加 provider / 加工具 / 换存储 / 换沙箱 / 加 UI 节点 / 加命令 / 运行时自改造） | `dsh/docs/architecture.md`（Where new behavior goes）、`dsh/docs/cookbook/extension-cookbook.md` |

| 许可 | MIT（Copyright 2026 DeepSeek）；vendored 包保留各自 upstream MIT；`THIRD_PARTY_NOTICES.md` 由生成器维护并在 CI 校验 | `dsh/LICENSE`、`dsh/vendor/README.md` |

### 1.2 官方声明的可替换面

| 目标 | 机制 |
|---|---|
| 换 Agent loop | loop 只依赖 Service Definition；`dsh-agent-loop` 可换 |
| 加模型 provider | `ctx.llm` 注册适配器 |
| 加工具 | `ctx.tools.register()`（原生 JSON-Schema 或 `defineTool`） |
| 换会话存储 | 实现 `SessionPersistence`（`create`/`open`/`stat`/`list`/`export`） |
| 改 prompt 组装 | `ctx.systemPrompt.section()` + `system-prompt/assemble` waterfall |
| 换沙箱/文件系统/子进程/shell/终端/LSP | 各自 `ctx.*` provider |
| 加 UI 节点 | 注册 `ConversationNodeDefinition` + keyed renderer（**React**） |
| 加设置卡片 / 人类命令 / 运行时自改造 | `ctx.settings` / `ctx.commands` / `ctx.dynamicCordisRunner` |

### 1.3 难以替换的部分（改造时的"地雷区"）

| 部分 | 说明 |
|---|---|
| Cordis 本体 | 已 vendored + fork（19 条本地修改，含 fiber 生命周期加固）；非普通 npm 依赖，跟随成本落在 dsh 自己的 fork 上 |
| Typert Remote 生成管线 | Remote 的 wire 形状（参数名、lookup 字段）是构建期 `tsc`/`tsdown` 产物，**只有 TS 消费者能直接复用**；非 TS 侧须手写对齐 |
| 会话日志格式 | JSONL v0→v1→v2 迁移链 + "committed generation never renamed/replaced/deleted"；接自有存储只能实现 `SessionPersistence` seam，不能改格式 |
| 浏览器壳与渲染框架 | `PLATFORM_MODULES` 静态表硬编码 React；`ui-renderer` 是唯一 ctx→React 集成层且被规定为业务组件不得绕过的边界 |
| Electron desktop 私有层 | 私有 Desktop Host + 版本化 framed byte pipes + `dsh-app://`；Electron 与 dsh 必须同版本（release identity 绑定） |

## 二、接入形态逐条评估（核心）

### 形态 A：进程外 `dsh --profile web`（HTTP + WS）——功能最全

**证据**：webserver 默认 `127.0.0.1:3080`（`dsh/packages/host/webserver/README.md`）；数据面 = `/api`（Remote unary，`POST /api/<namespace>/<method>`）+ `/api/remote.mux`（WebSocket，rpcId 双向）+ token→签名 cookie 鉴权 + Host/Origin trust fence（`dsh/packages/client/connection/README.md`、`dsh/docs/api-gateway.md`）。

**可行性**：高功能、低保证。
- 正面：覆盖会话、工具、设置、工作区、终端等全套 Host API；事件流（`session/event` 类）可订阅。
- 约束 1：**无独立协议规格发布**，`docs/api-gateway.md` 自称 current-state reference；wire 类型是构建期产物 → Rust 侧须按 descriptor 手写并承担上游漂移。
- 约束 2：cookie 刻意不带 `Secure`（loopback HTTP 发行形态）、无 logout；`--host 0.0.0.0` 被 CLI 拒绝、LAN 地址启动采样一次后不更新。
- 约束 3：index 渲染必经 `ctx.webServer.renderIndex`（注入 `window.__DSH_BOOT__` 与 `/plugins/??…` 脚本）；自建前端需容忍这些注入。

### 形态 B：进程外 `--profile sdk`（JSON-RPC stdio）——表达力弱

**证据**：client→server 仅 3 个方法（`initialize` / `session/prompt` / `shutdown`），server→client 仅 4 个通知（`session.event` / `session.status` / `subagent.started` / `subagent.finished`）（`dsh/packages/sdk/protocol/README.md`）；启动方式即 spawn `dsh --profile sdk` 子进程。

**可行性**：中高（Rust 侧实现换行分隔 JSON-RPC 客户端成本低），但：
- **无逐字流式帧**：通知集合里没有 `agent/assistant-stream`；只能等 `assistant/message` settlement 后用 `expandAssistantStream()` 展开紧凑流。对"逐字打字"的聊天 UI 是明显缺陷。
- 无 prompt 取消、无 per-prompt 结果、无 session close、无协议版本协商（`serverInfo.version` 恒为 `0.0.1` 且客户端不校验）。
- 放弃一轮 = 关闭运行时进程。

### 形态 C：ACP——不可作为产品基座

官方明示 "automation-only"，刻意省略 DSH 特有展示数据（cards/plans/titles/todos/terminals），"Choose it when automation should own the interaction; avoid it when a human needs DSH-specific presentation"（`dsh/packages/acp/acp/README.md`）。
**可用场景**：WorldSea 把 dsh 当**子代理执行器**（out-of-process delegation），而非产品基座。

### 形态 D：嵌入进程——不可行

所有形态都是 Cordis 插件树，宿主是 Node；`docs/architecture.md` 的 Application launch 明确除 `dsh` profile 外没有别的应用启动路径，且 `scripts/verify-application-entrypoints.ts` 会拒绝绕过 `dsh` 的 Node 应用入口。

### 形态 E：复用/替换 UI 包——不可行

- **不可复用**：`packages/client/web` 的 `PLATFORM_MODULES` 是静态共享模块表（React、Cordis），dynamic bundle 的 external 只能解析到该表；`ui-renderer` 是唯一把 bare observable 绑到 React 并拥有 React context 的包。**"复用 client 内核 + Vue 渲染层"无路径**。
- **整体替换 dist 有缝但代价极高**：`host/frontend-static` 只认一个配置 `distIndex`（assembly fact，理论可换成任意 dist），`host/webserver` 声明"不含 harness 概念、不服务文件"——但数据面（`/api` + `/api/remote.mux`）与注入面（`__DSH_BOOT__`）都由 dsh 的 client 体系拥有，Vue 端等于**手写一套 dsh 私有协议的客户端**，且无冻结规格。
- 官方对"自建 UI"的定位是合法路径（`Add UI or editor integration → drive ctx.agents and render from session/event`），但**官方推荐形态是写 client 插件（React + slots）**，不是换壳。

### 形态 F：打包与部署

| 项 | 事实 |
|---|---|
| Node 版本 | `^22.19.0 \|\| >=24.0.0`；CI 覆盖 22.19/24/26 |
| 包管理器 | `pnpm@11.7.0`；`dsh plugin` 依赖 PATH 上有 pnpm（普通运行不需要） |
| native addon | Linux `landlock-run` 静态可执行 + Node-API `system.node`（flock）；平台仅 Linux x64/arm64、macOS x64/arm64（**Windows 沿用既有 semaphore 实现**） |
| 其他原生件 | `node-pty`（Windows ConPTY addon）、ripgrep 与 mac `-spawn-helper` sidecar |
| 单文件可执行 | 技术上可行：Python SDK runtime 用 `@yao-pkg/pkg` 把 CLI 与封闭 Node 依赖树打成单文件原生可执行——**这只是把 Node 塞进可执行文件，不是去掉 Node** |
| Electron desktop | 不监听端口（`dsh-app://` + framed byte pipes）；发行目标仅 mac arm64/x64、win x64（**Linux 不是 Desktop 发行目标**） |
| 对 WorldSea 的推论 | 走此方向的终态必然是 **Rust 主进程 + dsh Node 侧车（单文件可执行）** 的双进程、双语言发行形态 |

## 三、若以 dsh 为基：WorldSea 的改造面

> 口径：**保留 = 原样自留**（dsh 不认识/无必要动）；**替换 = 交给 dsh**；**桥接 = 必须新建适配层**。

### 3.1 保留（自留资产）

| 资产 | 说明 |
|---|---|
| Vue 前端整体（Agent UI + 领域 UI） | dsh 的 UI 包全不可用；前端消费的**事件协议须重接**（自建协议客户端） |
| 实体 / 芽系统（28 个官方芽） | 与 Agent 引擎正交 |
| A2UI blocks 呈现层 | 需要把"结构化块"表达为 dsh 工具的事件/结果 |
| 八文件规则体系 | 可映射到 dsh 的 `agent-instructions` / context 机制（见桥接） |
| 场景装配语义 | 场景 → dsh preset/会话配置的映射须自建 |
| 长期记忆底座（agent-memory/agent-index/vendor） | dsh 无跨会话记忆系统 |
| 群聊引擎 | dsh 只有 subagent 委派，无多 Agent 会议抽象 |
| 权限三档语义 + 领域写保护 | dsh 的 approval/sandbox 是通用机制，领域约束须重新声明 |

### 3.2 替换（交给 dsh）

| 现有实现 | 被替换为 |
|---|---|
| ReAct 循环 + RunPhase | dsh agent-loop（或自定义 loop 插件） |
| LLM 后端（genai） | dsh `ctx.llm` 适配器（DeepSeek 适配器自带） |
| 工具总线 + FrontendToolBridge 双执行栈 | dsh `ctx.tools`（须把 7 个桥工具与领域工具注册为 dsh 插件工具） |
| 编排骨架（agent-patterns） | dsh 无直接对应；**这一段没有替代品**，需另行裁定（保留 / 用 dsh workflow / 放弃） |
| MCP 实现（rmcp） | dsh `mcp` 包（二选一，或保留 rmcp 走桥） |
| Skills 协议栈 | dsh `skill` 包（SKILL.md 同源） |
| 上下文压缩 | dsh compaction 系 |
| 会话日志/持久化 | dsh session + `SessionPersistence`（或实现 seam 接自有 SQLite——**格式不可改，须适配**） |

### 3.3 桥接（新建适配层，工作量的大头）

| 桥 | 内容 | 规模直觉 |
|---|---|---|
| 协议客户端（浏览器侧） | Vue 前端 ↔ dsh Host（`/api` + `/api/remote.mux`），含鉴权 cookie、rpcId 双向、恢复重试 | 大（一套私有协议客户端，且上游漂移） |
| 事件协议转换 | dsh `session/event`（含原本地流帧）→ 本项目 `turnModel.ts` 归约器 | 中—大（影响 8 类 ActionKind 与全部行段组件） |
| 领域工具注册 | 7 个桥工具 + TS 侧 200+ 领域的取舍重注册（实体 CRUD / content_search / KB / 芽写面） | 大（同时也是清理 TS 双轨的机会） |
| 数据桥接线 | dsh 工具执行 → `agentDataBridges.ts`（保持数据/UI 动作分路由） | 中 |
| 场景 → 配置翻译 | `Scenario` 8 装配面 → dsh preset / 工具集 / prompt 段 | 中 |
| 规则文件承接 | 八文件 → dsh instructions/context 机制（WORLD.md 节奏型注入需在工具出口挂点） | 中 |
| 记忆接线 | dsh 会话日志 → 长期记忆的上游输入；压缩事件 ↔ 归档 | 中（取决于 A1 已落地成果如何复用） |

## 四、代价与风险

### 4.1 与项目约束的结构性冲突

| # | 冲突 | 说明 |
|---|---|---|
| C1 | **单二进制 vs 双进程双语言** | 项目约束"Rust + 单二进制部署"；此方向终态 = Rust 主进程 + Node 侧车（pkg 单文件可执行），进程管理、生命周期、打包、更新、签名全部复杂化 |
| C2 | **前端主权 vs 协议从属** | Vue 前端可保留，但它从此消费的是 dsh 私有协议（无冻结规格、构建期 wire 类型）——**产品体验的上限被上游协议节奏绑定** |
| C3 | **领域深度 vs 通用基座** | dsh 的扩展点面向"通用 agent 产品"；本项目的场景/规则/记忆/A2UI 这些深度领域定制，在 dsh 里都属"外部插件"，开发体验官方自认较差（第三方写 UI 插件须自备打包链、bundle-purity gate 拒绝跨插件 value import） |

### 4.2 风险清单（不自动处理，供决策）

| # | 风险 | 影响 | 缓解建议 |
|---|---|---|---|

## 五、结论与建议（待拍板）

### 5.1 判定

**"有基座形态"成立；"以它为基"对 WorldSea 成立的只是「Agent 引擎层」。**

- 它是给两类人设计的基座：① 想快速获得一个完整 agent 产品（含 Web UI）的人；② 愿意用 React 写 client 插件的人。WorldSea 两类都不是——Vue + 深度领域定制。
- 因此本方向在 WorldSea 语境下的真实含义是：**把 Agent 引擎（loop/工具/会话/配套能力）外置给 dsh，WorldSea 保留产品层与领域层，通过进程外协议连接**。这是一次"引擎外置"架构，而非"框架替换"。

### 5.2 若继续推进：最小验证路径

```text
步骤 1（不改本项目）：
  用 dsh 自带 web profile 跑通一个真实任务（含工具调用），
  用抓包/日志记录 /api 与 remote.mux 的完整往返，评估协议复杂度

步骤 2（薄客户端验证）：
  写一个最小 Rust/Node 客户端，验证"外部程序能否完整驱动一次会话
  （发送 → 流式回读 → 工具确认 → 取消）"，明确流式帧能否满足聊天 UI

步骤 3（桥接可行性验证）：
  用 dsh 插件机制注册 1 个领域工具（如 entity_create），
  走通"dsh 工具执行 → WorldSea 数据桥"的完整回路

步骤 4（决策）：
  以步骤 1-3 的实测数据为输入，做方向终裁（含与提取融合的取舍）
```
