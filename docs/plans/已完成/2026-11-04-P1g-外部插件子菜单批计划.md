# P1-g：「外部插件」子菜单——按需列出并处置（2026-11-04）

> 交接文档 §4.4 最后一项可选项。解决「崩溃线索没指到真因时，用户无从下手」。

## 一、为什么需要

截至 P1-f，所有处置入口都**依赖崩溃线索**：线索指到谁，才能处置谁。但线索有固有边界
（P1-a §5.3：只覆盖路由崩溃，且只说明「崩溃那一刻谁在服务」）。

若线索指偏了、或宿主崩在非路由路径，用户就完全失去手动入口——只能去改 profile 文件。

## 二、形态

「视图」子菜单新增「外部插件」，二级结构：

```
视图
└─ 外部插件
   ├─ dsh-whale-widget
   │  ├─ 停用后重启
   │  └─ 卸载后重启
   ├─ dshmarket
   │  ├─ 停用后重启
   │  └─ 卸载后重启
   └─ …（只列外部插件，官方内置不出现）
```

- **按包名列，不按 entry 列**：与 P1-c 的 bundle 粒度一致（一个包可能展开成多个 entry）
- **已停用的标出来**（`名字（已停用）`），避免用户误以为操作没生效
- **不可移除的项置灰**（`removable=false`，通常是官方保护或使用中）
- **每次弹出前重建**：插件是运行期可变的（用户可能在别处装了/卸了），缓存只会说旧话。
  代价是每次弹菜单调一次宿主 API（本地管道，毫秒级）

## 三、改动

| 文件 | 改动 |
|---|---|
| `dsh_plugin_control.rs` | 新增 `external_bundles_for_menu()`（排序后的清单，桥不可达时返回空） |
| `dsh_plugin_remedy.rs`（新） | 从 control 拆出的流程编排：`remediate_suspect_and_restart` / `remediate_named_and_restart` / `finish` |
| `menu.rs` | 「外部插件」动态子菜单 + `parse_plugin_action()` 解析动态 id |
| `menu_tests.rs`（新） | 动态 id 解析的 4 例 |

**两个入口共用同一条流程**：`remediate_named_and_restart`（按包名，用户自己挑）与
`remediate_suspect_and_restart`（按线索）只在「目标从哪来」不同；确认、执行、通知、
重启全部走 `finish`。各自实现一遍迟早会不一致。

**动态 id 形如** `worldsea.plugin.<动词>.<包名>`。静态 `match` 分支无法枚举运行时才存在的
包名，故 `handle` 用前缀兜底 + `parse_plugin_action` 解析。

### 4.1 拆分与门禁拦截（过程中）

首版把流程编排也塞进 `dsh_plugin_control.rs`，行数涨到 **442**，被架构门禁拦下
（上限 400）。按职责拆出 `dsh_plugin_remedy.rs`：

- `dsh_plugin_control.rs` 270 行 —— 「怎么调宿主」
- `dsh_plugin_remedy.rs` 180 行 —— 「怎么问用户、怎么告知结果」

前者可单测，后者只在真机上有意义。**门禁拦得对**：那个文件本来就在做两件事。

### 4.2 反证发现了一条「假测试」

`parse_plugin_action` 首版只有 `scoped_package_names_are_kept_whole` 一例。
把实现从 `split_once` 改成 `rsplit_once`（明显错误）→ **该测试仍通过**。

原因：`@montersy123/dsh-skill-market` 这类包名里，最后一段恰好不是合法动词，所以
从右切只是「碰巧也没切中」。补 `the_verb_position_is_anchored_to_the_first_segment`
用包名本身以动词结尾的 id（`a/b.disable`）区分两种实现；再反证 → 新测试精准失败。

**教训**：反证不只是确认测试会红，它还会暴露「红不起来的测试」。

### 4.3 又一次构建缓存假失败

反证恢复后测试仍报 1 例红，源码核对无误，`cargo clean -p` 后全绿。

## 五、真机走查清单（用户手测）

> **走查结果：通过（2026-11-04，用户手测）**。

| # | 操作 | 预期 |
|---|---|---|
| 1 | 「⋯」→ 视图 → 外部插件 | 列出**全部外部插件**（当前 10 个），**不含**任何 `@deepseek-ai/*` |
| 2 | 展开任一插件 | 两项：「停用后重启」「卸载后重启」（不可移除的卸载项置灰） |

| 6 | 无崩溃线索时也能操作 | 全程不依赖崩溃线索（第 3/5 项即验证） |

第 1 项的「不含官方插件」是**安全属性**，务必确认。

## 六、遗留

- **未做「重新启用」入口**：菜单只列外部插件，但已停用的插件仍能列出来（标「已停用」）——
  下一步自然该给它「启用后重启」。本次没做是因为用户只要求「列出来处置」，
  且启用不涉及破坏性风险，价值低于其他项。
- **未做搜索/分组**：外部插件数量一多（比如 30 个）二级菜单会很长。当前 10 个可接受，
  真变长了再考虑分组或改成列表对话框。
