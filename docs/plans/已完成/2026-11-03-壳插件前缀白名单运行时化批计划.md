# 壳插件前缀白名单运行时化批计划（A 方案）

> 来源：跨仓交接件 [worldsea-shell-whitelist-runtime.md](worldsea-shell-whitelist-runtime.md)（由插件侧只读排查产出）。
> 本文把它转成本仓可施工的批计划：**保留原方案的骨架，补上 4 处决策裁定 + 4 处原文档未覆盖的实现约束**。
> 基线：`a71b4ba`（F6 追版 dsh-v0.2.1-rc.5 之后）；施工前请复核基线未变。

## 一、问题与目标

### 1.1 现象

第三方插件 `dsh-agents-visualization` 装进 web profile 后，设置页「规则」入口出现（客户端 bundle 走 `/plugins/`，在白名单内），但**三个 Tab 全部空态、零错误提示**——插件数据接口全部 `404`，一个请求都没到宿主。

### 1.2 根因

`apps/tauri/src-tauri/src/dsh_proxy.rs:75` 的 `PLUGIN_PREFIXES` 是**编译期手工记账簿**：

```rust
const PLUGIN_PREFIXES: [&str; 2] = ["/dsh-whale/", "/dsh-bili/"];
```

插件 API 前缀 `/dsh-agents-visualization/api` 不在表内 → `path_allowed` 返回 false → `:181-184` 直接 404。宿主侧其实**已正常注册该路由**，只是被壳挡在外面。

### 1.3 要修的是机制，不是那一条记录

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | 清单是手工记账，非可推导集合 | `PLUGIN_PREFIXES` 来源 = 「这台机器恰好装过什么插件」 |
| 2 | 失败模式已重复发生两次 | `dsh_proxy.rs:73` 注释「dsh-whale-widget 即此」；C1-b 批计划记 `/open-in-app/apps` 误杀 |
| 3 | 失败对插件开发者静默 | 页面只见 404；壳日志只在 debug 的 stdout，不落盘 |
| 4 | 代价错配 | dsh 插件是**运行时**装载（profile `node_modules` + bundle patch），白名单却在 Rust **编译期**写死 |
| 5 | 注释语义混淆 | `dsh_proxy.rs:55-60` 称白名单「枚举自 dsh 源码」——对 `ALLOWED_PREFIXES` 成立，对 `PLUGIN_PREFIXES` 完全不成立，二者却并列同表 |

> **关键洞察**（原文档提出，本批采纳）：插件代码本身就跑在宿主进程内（能读任意文件、能注册任意路由）。壳对插件命名空间做精确字符串匹配**不构成真正的安全边界**——它挡的是「页面被 XSS 后借道」，不是「恶意插件」。所以对插件前缀放宽，安全收益损失有限，摩擦成本却是全额。

### 1.4 目标

把「插件前缀」从 **Rust 编译期常量**改成**宿主上报的运行期数据**，并让「被壳拦下」这件事对插件**可辨认**。

## 三、方案

### 3.1 总体数据流

```
dsh 宿主启动 → webserver 路由表就位 → hello 帧携带 prefix 清单 → 壳接收并缓存为快照
                                                                            ↓
页面请求 → 壳闸门：越界 403 / 方法 405 / 命名空间判定 → 命中即转发，未命中试探转发 + 落档
```

`ALLOWED_PREFIXES`（dsh 内置路由）**保持静态不动**——它有客观来源、是安全基线，且不受 F6 追版影响（台账已记 `webServer.register` 调用点 14=14）。只有第三方插件命名空间这一段变成运行期。

### 3.2 不区分「插件 vs 内置」

让宿主上报**整张 prefix 路由表**（内置 + 插件一起），壳用它替换 `PLUGIN_PREFIXES` 的角色；`ALLOWED_PREFIXES` 作为**兜底底集**保留（防上报失败时页面完全不可用）。

这消掉了「谁是插件」这个无法可靠回答的问题（`node_modules` 里既有第三方也有 dsh 自带包）。

### 3.3 落点：两条改动

#### A-1 · dsh 侧上报（必须先进）

| 文件 | 改动 |
|---|---|
| `dsh/packages/host/webserver/src/index.ts` | 新增只读访问器 `listPrefixRoutes(): string[]`，导出 `this.prefixes` 的键。**只读、不改注册语义** |
| `dsh/packages/bundle/web-app/src/pipe-transport.ts` | `PipeCarrierOptions` 增 `readonly routePrefixes?: readonly string[]`；`HelloFrame` 增 `readonly routePrefixes?: readonly string[]`；`PipeConnection.start():269` 的 send 带上该字段 |
| `dsh/packages/bundle/web-app/src/index.ts` | `installPipeMode` 的 `installPipeCarrier({...})` 调用增参 `routePrefixes: ctx.webServer.listPrefixRoutes()` |

**时序要点（必须核实）**：`routePrefixes` 要在**连接建立时**求值，而不是在 `installPipeCarrier` 调用时求值一次。`PipeConnection` 是在 `createNetServer((socket) => new PipeConnection(...))` 里为**每条连接**新建的（`pipe-transport.ts:191-195`），而壳可能重连。故正确做法是把 `listPrefixRoutes` **函数**（而非数组快照）传进 carrier，在 `start()` 里调用。这样壳重连时拿到的是当下真值——**顺带解决了 D1 的一部分**。

#### A-2 · 壳侧消费

| 文件 | 改动 |
|---|---|
| `apps/tauri/src-tauri/src/dsh_pipe_io.rs:234-241` | hello 分支多读一个可选字段 `routePrefixes`（字符串数组），经 `hello_tx` 一并发回（通道类型从 `Result<u64, String>` 改为 `Result<HelloInfo, String>`） |
| `apps/tauri/src-tauri/src/dsh_pipe.rs:165-172` | `await_hello` 收 `HelloInfo`；`PipeClient` 保存快照（`Mutex<Vec<String>>` 或用 `arc_swap` 风格的原子替换；不新增依赖就用 `RwLock`） |
| `apps/tauri/src-tauri/src/dsh_pipe.rs` | 新增 `pub fn route_prefixes(&self) -> Vec<String>` 只读访问 |
| `apps/tauri/src-tauri/src/dsh_bridge.rs:108-119` | `ProxyCfg` 增 `plugin_prefixes: Vec<String>`（或持 `Arc<PipeClient>` 由 `path_allowed` 现读——见下方注意） |
| `apps/tauri/src-tauri/src/dsh_proxy.rs:106-117` | `path_allowed` 改为「静态底集 ∪ 运行期快照」，并实施 D1 的试探转发 |

**注意（freshness vs 简单性的取捨）**：`ProxyCfg` 目前是值结构、在 `prepare()` 里一次装配。若把快照**拷进** cfg，则只在 `prepare` 时取一次值，宿主后续变化不可见。既然 D1 已裁定「未命中试探转发」，快照过期**不再是致命问题**（最坏是落一次档 + 试探成功）。故**推荐**：cfg 持 `Vec<String>` 值拷贝，保持 `ProxyCfg` 的纯数据结构性质、测试可直接构造。不引入 `Arc` 共享可变状态。

### 3.4 闸门新语义（D1 的关键）

`path_allowed` 三态化，`proxy()` 相应分支：

| 判定 | 行为 |
|---|---|
| 命中 `ALLOWED_PREFIXES` 或 `/` / `/index.html` | 直接转发（现状不变） |
| 命中运行期快照（`PLUGIN_PREFIXES` 的来源） | 直接转发，**不落档**（正常路径，避免日志噪音） |
| **两者都不命中** | **试探转发一次** + 落档一行（`404（白名单外·已试探转发）` / 或转发后的真实状态码）；仅在转发**失败**或**返回 404** 时才向页面回 404 |

这样：
- 新插件**无需重启壳**即可用（D1 主路径解决）；
- 未知路径仍会被记录（可观测性不退化）；
- 页面侧体验从「静默 404」变为「能拿到真实响应」，且 2.6-2 让「真被拦」可辨认。

**负向保护必须保留**：`has_traversal`（403）与 `method_allowed`（405）在试探之前判定，不因白名单放宽而松动。`/etc/passwd` 等仍 404（宿主本来也不路由它）。

### 3.5 2.6-2 · 给页面的 404 带可辨认标记

`dsh_proxy.rs` 的白名单拒绝分支：当 `is_api`（`path_only.starts_with("/api/")`）或**请求携带 `accept: application/json`** 时，返回 JSON：

```json
{"ok":false,"code":"SHELL_PATH_BLOCKED","path":"/dsh-agents-visualization/api/..."}
```

`content-type: application/json; charset=utf-8` + `cache-control: no-store`。其余情况保持 `text/plain`（不污染资源语义）。

**实现要点**：`failure_response(status, wants_html, title, detail)` 现有签名不支持换 content-type。新增一个薄封装（如 `blocked_response(path_only)`）而不是改 `failure_response` 的四参签名——后者被 8 处调用，改签名会扩散。

### 3.6 fallback 兜底语义核对

`webserver/index.ts:561-567`：无 fallback 注册时宿主对未匹配路径直接 `404` 空体；`frontend-static` 在 web profile 里**已注册 fallback**（dist 兜底座）。故试探转发对任意路径都是安全的（要么命中真实路由，要么落到 dist 兜底座 → 通常 404）。**施工时需确认** web profile 下 fallback 确已就位（`dsh/apps/web` 或 bundle 装配），否则试探转发可能返回 200 + index.html（SPA 行为），那会让「未知路径」看起来像成功。

> 若确认 fallback 会把未知路径渲染成 index（SPA fallback），则**试探转发只对「疑似 API 面」生效**（路径含 `/api/` 或其上一段是单段命名空间），其余保持 404。这是本批唯一需要施工中实测确认的分支。

## 四、验收

### 4.1 单测

dsh 侧：
- `webserver.spec.ts` / `webserver-external.spec.ts`：`listPrefixRoutes()` 覆盖「内置 + 动态注册的插件路由」，且 `register` 的 disposer 生效后该前缀**从清单消失**（HMR 安全，符合 `packages/AGENTS.md` 的 disposal 要求）。
- `pipe-transport.spec.ts`：hello 帧含 `routePrefixes`；**不带该字段**时解析不报错（向后兼容）；连接建立**之后**新增的路由出现在**下一条连接**的 hello 里（验证函数式求值时序）。

壳侧（`dsh_proxy_tests.rs`）：
- `path_allowed` 新增「运行期快照内路径放行」用例。
- **保留并扩展** `allowlist_covers_enumerated_host_routes` 的负面断言：`/dsh-evil/widget.js` 若快照为空/未就绪，**试探转发后仍应是 404**（即不得因为「试探」而无条件放行成功）。这条是本批最重要的回归保护。
- 新增：越界 403 / 方法 405 在「未命中白名单」路径上**依然优先**（不能被试探转发短路）。
- 新增：API 面被拦时返回 JSON 且 `code == "SHELL_PATH_BLOCKED"`；非 API 面仍是 `text/plain`。

`dsh_pipe_tests.rs` / `dsh_pipe_test_host.rs`：
- 假宿主的 hello 增 `routePrefixes` 字段（`dsh_pipe_test_host.rs:84`）；新增「hello 不带该字段」的兼容用例。
- **兼容性红线**：宿主 hello **多字段**壳必须接受（现状 `dsh_pipe_io.rs:235` 只取 `version`，安全）；但**新增帧类型**会被 `dispatch` 的 `_ => false` 判为协议失序并**断链**（`dsh_pipe_io.rs:59-62, 328`）。本批**不得引入新帧类型**。

### 4.2 真机走查（用户手测）

| 场景 | 预期 |
|---|---|
| 装 `dsh-agents-visualization` 后打开设置页「规则」 | 三个 Tab **有真实数据**（全局级显示两份 AGENTS.md、第三方列出已装工具） |
| 在设置页**启用/禁用一个插件**（不重启壳） | 该插件接口**立即可用/立即失效**，无需重启（验证 D1） |
| 断点验证 | 把某插件从快照排除（或临时令 `listPrefixRoutes` 不返回它）→ 取消 `WORLDSEA_BRIDGE_OPEN=1` 后仍能用（试探转发生效），且日志有落档行 |
| 负向 | 页面 `fetch('/etc/passwd')` 仍 404；`fetch('/assets/../secret')` 仍 403；`PUT /anything` 仍 405 |
| 可辨认错误 | 人为让某 API 路径命中白名单拒绝分支 → 页面拿到 `{"ok":false,"code":"SHELL_PATH_BLOCKED"}`（非纯文本、非空态） |

4. **A-2**：壳侧 `dsh_pipe_io` → `dsh_pipe` → `dsh_bridge` → `dsh_proxy` 逐层接线 + 单测。

### 走查项设计错误的两处（本批必须留档，避免后续重复踩）

**#2：「启用插件 → UI 立即出现」不能用来验证闸门热生效。**
它受 `client-hmr` 制约，而 `apps/tauri/dsh-overlay.yml` **主动关闭了 `client-hmr`**（C1-b：`/plugins/events` 是 SSE 长连，而壳协议 `worldsea://` 的应答是缓冲体，无法透传流式响应）。官方 Electron 桌面端走原生 HTTP，SSE 可用，故其设置页能热更新——**这是壳刻意接受的既有差异，与本次白名单改造无关**。
用户观察「刷新后规则入口出现/消失、启用后仍需刷新」与此完全一致。
**正确的验证方式**是直接打插件 API（绕开 UI）：
```js
const r = await fetch('/dsh-agents-visualization/api/state'); console.log(r.status);
```

**#4：`fetch('/assets/../secret')` 在页面侧不可能产生越界路径。**
浏览器/URL 解析器在发请求前就消掉 `..` 段（实测：`/assets/../secret` 与 `/assets/%2e%2e%2f` 均归一化为 `/secret`），因此永远到不了壳的 `has_traversal` 分支。
`has_traversal` 的真实用途是挡**非浏览器来源**（wry 协议头、重定向等），已由单测 `traversal_rejected_403_without_forwarding` 覆盖。**走查项应从清单中移除**。

**#3 的取证要求**：`fetch()` 只要拿到任何 HTTP 响应（含 404/403）都是 `fulfilled`，故不展开 `Response` 就读不到状态码。正确写法：
```js
const r = await fetch('/etc/passwd');
console.log(r.status, r.headers.get('content-type'), await r.text());
// 预期：404 / application/json / {"ok":false,"code":"SHELL_PATH_BLOCKED",...}
```
该项已由单测 `unknown_prefix_probes_upstream_and_reports_blocked_api` 与 `blocked_response_shape_is_machine_readable` 双重覆盖。
