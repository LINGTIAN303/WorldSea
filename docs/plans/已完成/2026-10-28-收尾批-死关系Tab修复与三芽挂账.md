审计脚本 = 全芽视图 `relationType` 引用 × 注册表 schema 差集 + 方向校验（reverseDirection → 本芽实体类型须在 targetTypes，反之 sourceTypes）。结果：**8 个死类型 + 5 处方向不匹配**。

## 四、施工重大发现：显式关系声明被自动逆类型遮蔽（本批修掉唯一实例）

`defineRelation` 幂等守卫 + auto-inverse 组合存在系统性行为：**若 A→B 的 B 侧稍后还有显式声明，且 B 已作为 A 的自动逆类型注册（镜像类型更窄），则 B 的显式声明被静默跳过**。全 114 条声明模拟定位：仅 `owned_by` 一处中招——`owns`（character→item）的 auto-inverse 抢注了窄版 `owned_by`（item→character），显式完整版（item,building→character,organization）从未生效 → **buildings「所属势力」Tab 的 add 流与 schema 不符**（新守卫 spec 抓出，审计脚本的正则被嵌套 `}` 骗过而漏报——spec 用真注册表更准）。

**修复**：`owns` 源/目标端补全为 `['character','organization']` / `['item','building']`（原位就地改，与显式 owned_by 成镜像一致 → auto-inverse 与显式声明等价，幂等跳过无害）。`defineRelation` 机制本身**不动**（「未来双端显式声明必须镜像一致」写入 relations 注释文档警示）；检查 relationTypes 常量/inverseRegistry 的 OWNED_BY 注册无冲突。
