### 语义检索基线（R2 起点 · 2026-09-12 实测）

**运行方式**（`crates/agent-index` 下；Key 从环境变量读，不入命令历史）：

```text
SILICONFLOW_API_KEY=<key> cargo test --offline --test eval_retrieval -- --ignored --nocapture
```

端点 `https://api.siliconflow.cn/v1/embeddings` · 模型 `BAAI/bge-m3` · dim 1024 · 语料 8 份 fixture（考据/设定/剧情/代码/笔记）。

**结果**（索引状态 `files: 8, chunks: 8, vectors: 8, dim: 1024`——向量全部补齐）：

| 查询组 | 关键词通道（BM25-jieba） | 混合检索（BM25 ∪ 向量 → RRF） |
| --- | --- | --- |
| 改述型（10 条，与原文少字面重叠） | **5/10 = 50%** | **10/10 = 100%** |

**读法**：5 条关键词未命中（「什么样的周期会让航行更安全」「有哪些不能随便碰的古老造物」「主角是怎么变强的」「第一本书讲了个什么故事」「两个势力在争什么」）**全部由向量通道救回**；关键词已命中的 5 条在混合通道下一条未丢 → **RRF 融合无回退损失**。另一组关键词评测（20 条，离线断言 `hit@3 ≥ 90%`）维持全绿。

**用途**：该 10/10 即 **R2 各增强项（本地 embedding / 代码语法分块 / Reranker）的对照基线**；两组共同量化了「语义通道存在的必要性」（改述查询命中率 50% → 100%）。测试已加**回归断言** `hy_hits >= kw_hits`（保证混合通道在任何配置下都不会比关键词更差），仅在显式跑 `--ignored` 时生效。

### 记忆侧语义基线（A2-1 · 2026-09-12 实测）

文件侧基线的**另一半**：记忆侧此前只有假 Embedder 的单元测试，真实向量下的召回质量与去重阈值都没有基线。新增 `crates/agent-memory/tests/eval_semantic.rs`（12 条摘要口径语料 + 10 条改述召回 + 三类去重探针各 6 条；`#[ignore]` + 真实端点，Key 同文件侧）。

**召回（10 条改述查询）**：

| 通道 | hit@1 | hit@3 |
| --- | --- | --- |
| 关键词（BM25-jieba） | 7/10 | 8/10 |
| 混合（BM25 ∪ 向量 → RRF） | **10/10** | **10/10** |

**去重阈值标定（戊1 阈值 0.92）**：

| 探针类别（各 6 条） | top1 余弦 | ≥ 0.92 |
| --- | --- | --- |
| 同义改写（应判**重复**） | min **0.8131** / 中位 0.8673 | **0/6** |
| 同主题新事实（应判**不重复**） | max **0.6910** / 中位 0.5430 | 0/6 |
| 完全无关（应判不重复） | max 0.4665 / 中位 0.4170 | 0/6 |

→ **单阈值可分区间 (0.6910, 0.8131)**（余量 0.122）。当前 0.92 高于同义簇下界 0.11 → **真重复全部漏判、去重实际不生效**；**建议 0.75**（区间中点）。**根因**：0.92 是从「字符二元组 Jaccard」继承的数值，A2-1 换度量（余弦）时未重标定——完整推论见 [A1 设计 §4.1](2026-09-11-A1-记忆系统设计.md)「语义去重的阈值标定」。**两条契约断言**：混合 top3 ≥ 关键词 top3；同义簇下界 > 同主题簇上界（后者若不成立，说明「调阈值」不是可选项、需换判别方式）。

**R2-1 落地要点**：

- **API**：`chunker::BoundaryHint { Plain, Markdown, Code }` + `chunk_text_for(text, params, hint)`；`IndexPolicy::boundary_hint(path)` 按扩展名选择（md/markdown/rst/org → `Markdown`；rs/ts/tsx/js/jsx/vue/py/go/java/kt/c/h/cpp/hpp/cs/rb/php/swift/lua/sh/bash/ps1/sql/proto/gradle → `Code`；其余 → `Plain`）。
- **边界规则**：Markdown 行首 `#`（1–6 级；**围栏代码块内不生效**——否则 ```python 里的 `# 注释` 会被当标题）；代码**列 0** 的顶层声明前缀（`fn`/`pub`/`impl`/`struct`/`enum`/`trait`/`def`/`class`/`func`/`export`/`function`/`public`/… + 属性与文档注释 `#[`/`///`/`//`/`#`——它们语义上归属**后一个**声明，断在其前可让注释与声明同块）。含**词边界校验**（`impl` 不命中 `implement`）。
- **两条硬口径**：① **只提前、不推后**——边界只让块更早收尾，且要求已累计 ≥ `max_chars/2`（防碎块），故「单块不膨胀」「行覆盖连续」两条不变量不受边界逻辑影响；② **`Plain` 与 v1 逐字节一致**（零行为变化锚点，由 `plain_hint_is_byte_identical_to_legacy` 锁定）。
- **启发式的已知取舍**：无 AST——列 0 关键字匹配是跨语言近似，把方法误判为顶层边界只会让块更小，**不丢内容**。
- **索引随分块版本自动失效**（同批落地）：新增 `meta` 表 + `CHUNK_SCHEMA_VERSION`（当前 `2`）；打开库时版本不符即**整体作废**（清块 / 文件行 / **向量**——`chunk_id` 随分块规则变化，旧向量会成孤儿并与新块错配），由**下一次检索或同步全量重建**（`search` 自带懒同步）。**为什么必须有**：`sync()` 的增量 diff 只看 `size + mtime`，规则变了而文件没变时会判「未变更」→ 静默沿用旧分块，且**无任何外部症状**。代价 = 升级后首次检索触发一次全量重建（含重新向量化），属预期成本。
- **验证**：agent-index **22 单元 + 1 关键词评测**全绿，另 **1 规模压测**（`#[ignore]`，需数分钟）：较 R2 前的 9+1 增 12 项（边界分块 6 + 索引接线 1 + 扩展名映射 1 + 版本作废 1 + 元信息 1 + GC 2）；关键词评测（20 条离线）维持 `hit@3 = 20/20`；`Plain` 路径零行为变化。

### 文件侧索引生命周期 + 规模实测 + 冷启动修正（2026-09-12/13）

**① 孤儿索引库 GC（已落地）**

- **为什么必须另记 workdir**：库名是 `{目录名}-{workdir 路径 sha256 前 8 位}.db`，**哈希不可反解** → meta 表新增 `workdir` 与 `last_used_at` 两个键（`open`/`sync` 时刷新）。
- **三重条件同时满足才删**：工作区**不存在** + 超宽限期（`DEFAULT_PRUNE_GRACE_MS` = **30 天**）+ **非本进程活跃实例**（`active_index_paths()`）。宽限期专门覆盖「移动盘未插入 / 网络盘离线」这类**暂时不可达**——`Path::exists()` 对它们返回 false，会被误判成「已删除」。
- **保守取向**：本机制引入前建的库无 meta 记录 → **永不自动删**（手动删索引目录即可）；删除失败（被占用）不计入 `removed`，下轮巡检重试。GC 以**只读**方式打开库（不写 WAL、不改 mtime）。
- **接线**：并入既有 6 小时后台巡检（`ensure_memory_gc_task`，启动条件放宽为「记忆根 **或** 索引根存在」——否则「只配了工作区索引」会永不巡检，形成静默缺口）；另留手动入口 `run_workspace_index_gc()`。

**② 规模实测（2 万块量级 · `scale_benchmark_report`，假嵌入器 → 可重复、零 API 成本）**

| 阶段 | 实测 | 说明 |
| --- | --- | --- |
| 合成语料 | 500 文件 × 40 块 ≈ **19 500 块**（约 27 MB） | 生成 1.9 s |
| 扫描 | **4 ms** | 纯元数据，可忽略 |
| 读 + 分块 | **1 444 ms** | 边界感知分块，约 15 MB/s |
| **首建总耗时（同步 + 播种）** | **89.7 s** | 其中 **BM25 播种 83.6 s**、其余 **6.1 s**（扫描+分块+落库）；冷启动修正后**整体移到后台** |
| 向量补齐（后台） | **77.6 s** → 19 500 条（dim 1024 ≈ **76 MB** BLOB） | 渐进，不阻塞首次检索 |
| 检索延迟 | 关键词 avg **96.4 ms** / p95 103.3 ms ｜ 混合 avg **421.1 ms** / p95 441.6 ms | 20 次；混合含查询向量化 + 余弦 + RRF |

**瓶颈定位（消去法 + 对照实验）**：最初怀疑「逐条 `INSERT` 各自成事务 → WAL 每行 fsync」，遂把「**单文件一个事务**」作为对照项落地 → 总耗时仅 **108.4 s → 89.1 s（−18%）**，而分块实测 1.3 s、扫描 4 ms ⇒ **剩余 ≈ 86 s 归 BM25（jieba 分词 + 倒排表构建）**。事务优化保留（消除一处明确低效写法，无副作用）。

### 冷启动修正（2026-09-13 · 已落地）

**问题**：上述 89.7 s 的构建**原本发生在检索路径上**——① `open()` 同步全量播种 BM25（每次进程冷启动付一次）；② `search()` 内同步调用 `sync()`（首次即全量建索引）→ **首次检索阻塞约 90 s**，且按此线性外推，10 万块（千万字级目标）≈ **7–8 分钟**。

**解法（把构建整体移出检索路径，构建期间渐进可用）**：

| 落点 | 改动 |
| --- | --- |
| `open()` | **不再播种**关键词索引（只保留空索引）；就绪由后台预热完成 |
| `search()` | **从不等待构建**：未就绪 → 触发后台预热（`ensure_warmup`）并立即返回；已就绪 → 去抖过期时触发**后台**增量刷新（`spawn_sync`），本次用现有索引、新变更下次可见 |
| `ensure_warmup()` | 后台两阶段「**同步 → 播种**」，单飞幂等；失败复位标志、下次检索重试 |
| `index_file()` | **未就绪时跳过关键词写入**——否则首建会把 83.6 s 的分词**跑两遍**（sync 逐块一遍 + 播种一遍）。实测校正后首建的「非播种部分」仅 6.1 s，正是这条起效的证据 |
| `build_keyword_blocking()` | ① 全程持 `sync_lock`（防「读快照→替换」窗口里插入增量写入 → 内容被替换抹掉造成永久漏检）；② **锁外构建、锁内瞬间替换**（若全程持关键词写锁，83.6 s 会挡住并发检索——与「不阻塞」目标相悖）；③ 重复调用安全（整表替换，不叠加） |
| `rebuild()` | 关键词**同步**重建（显式动作，用户预期「点完即可用」） |

**呈现契约**（工具与面板如实告知，不假装成功）：`IndexStats` 增 `keyword_ready` / `keyword_built` → `workspace_search` 在未就绪时返回 note「工作区索引正在后台构建（已就绪 x/y 块）……请稍后重试」；配置面板「工作区索引」行显示「索引构建中 x/y」。**未就绪期间检索仍可用**：关键词通道为空、向量通道（若有）照常参与，故结果可能来自语义通道（note 会说明不完整）。

**测试**（2 项新增）：`cold_search_returns_promptly_then_recovers_after_warmup`（冷检索 < 500 ms 返回 + 触发预热 + 就绪后可检索 + 幂等）、`ready_search_refreshes_in_background`（就绪后新文件由后台刷新吸收，检索不阻塞、随后可见）。

**代价与遗留**：① 首次使用某工作区，**第一次查询拿不到全量结果**（索引在后台建），需模型/用户**重试一次**——这是「不阻塞」换来的显式取舍，已由 note 如实告知；② `open()` 后到就绪前的窗口内，关键词通道不可用（旧的「打开即完整可用」对 2 万块以上不再成立——那本来就是 83 s 的阻塞伪装成的「可用」）；③ 10 万块外推仍需 ≈ 7–8 分钟后台构建 → 若目标规模临近，还需「BM25 只索引标题级文本 / 倒排表增量持久化」等进一步缩短（未做，待目标规模实测后再评）。

**未覆盖**：真实端点的向量补齐吞吐（本次用假嵌入器以避开 API 成本与网络抖动）；磁盘占用上限（76 MB BLOB / 2 万块，线性外推 ≈ 380 MB / 10 万块）。

## 一、问题定义与规模测算

### 1.1 检索对象（WorldSea 场景的内容形态）

| 内容                       | 结构化程度       | 现有检索通道                         | 缺口                        |
| ------------------------ | ----------- | ------------------------------ | ------------------------- |
| 实体（角色/地域/组织…）            | 高（schema 化） | entity 语义工具 + embedding 索引（已通） | 无                         |
| KB/笔记本                   | 半结构化        | KB 语义索引（已通）                    | 规模上限（IndexedDB）           |
| 考据资料/散文件（workdir md/txt） | 低（散文为主）     | 仅 grep/read 纯文本                | **主缺口**——无语义通道、无全文索引      |
| 文稿（章节）                   | 低-中         | 无独立通道                          | 同上                        |
| **代码文件（编码场景）**           | 高（语法结构）     | grep 纯文本（符号精确，强项）              | 大库冷启动定位慢；语义级"这段代码做什么"检索缺失 |

**核心缺口 = workdir 非结构化内容（散文考据资料 + 代码）的语义/全文检索**。实体/KB 已有通道，不需要本评定重做。

**⚠ 编码场景维度（2026-08-30 用户补充，依据项目第一要素：以通用 Agent 为基础）**：WorldSea 兼顾通用编码场景（Skills 脚本/插件模块/用户以通用 Agent 干编程活），检索必须覆盖代码内容：

- **混合检索天然兼容代码**——BM25/grep 是代码符号检索的强项（arXiv 证据：BM25 全规模 scaling 最优；Claude Code 亦然），向量通道补"这段代码做什么"语义查询

- 对推荐方案的影响 = **零架构改动，三个实现注意项**：① 分块策略对代码文件按语法结构（函数/类）而非固定字数切；② FTS5 分词对标识符的处理（trigram 或 unicode61+大小写保真）；③ embedding 选型须含 code retrieval 能力——**Qwen3-Embedding 明确支持代码检索**（bge-m3 通用多语言亦可用），评定 §三.5 选型结论不受影响

### 1.2 规模测算（千万字级 = 10M 汉字 ≈ 7M tokens，按 500 字/块）

| 项                       | 10M 字                                                                                                                                 | 50M 字（5 倍冗余上限）             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| chunk 数（500 字/块）        | \~2 万                                                                                                                                 | \~10 万                     |
| 向量存储（1024 维 f32=4KB）    | \~80 MB                                                                                                                               | \~400 MB（int8 量化 \~100 MB） |
| FTS5 全文索引（文本 1-2 倍）     | 10-20 MB                                                                                                                              | 50-100 MB                  |
| 查询延迟（sqlite-vec top-50） | <50 ms（[GeminiDesktop 实测同量级](https://geminidesktop.app/en/blog/local-sqlite-vec-rag-gemini-desktop-2026)：50 万词→200MB 单文件→top-5 <50ms） | 同量级可维持                     |

**结论**：千万字级（甚至 5 千万字）落在 **SQLite 单文件甜点区内**（sqlite-vec 上限 \~10M 向量，我们在 1% 处）——**完全不需要专用向量数据库**（LanceDB/Chroma/Qdrant 均为过度设计）。

## 二、现状盘点（基建契合度）

1. **SQLite 基建现成**：Rust 侧 sqlx 多库（sessions 等），FTS5 为 SQLite 内置（零依赖），sqlite-vec 为单文件扩展（Tauri bundle .dll/.dylib，与"MCP 配置/规则文件"的单机文件哲学同构）。
2. **embedding 包现成但载体受限**：`packages/agent-runtime/src/embedding/`（IndexedDB 向量库）——WebView origin 配额限制 + 与磁盘文件体系脱节，**不宜承载 workdir 文件索引**（保留服务实体/KB）。
3. **Agent 工具面**：227 工具 + grep/read 纯文本（保留——精确符号定位仍有价值，见证据 §三.3）。
4. **文件监听**：useFsWatcher 已有——增量索引的触发器现成。

## 三、外部证据汇总（2026-08-30 查证）

### 3.1 混合检索 = 2026 共识（BM25 精确但字面 × 向量灵活但模糊）

- BM25 失败模式：词表不匹配（"car insurance" vs "vehicle policy"）；向量失败模式：**精确标识符/专名 near-miss**（OAuth2Provider 搜出 OAuthClientProvider）——两failure 模式互恰，RRF（排名融合，无 needscore 校准）或加权融合（可加 metadata 信号）合并（[StrataFS 深度文](https://stratafs.neullabs.com/blog/hybrid-search-bm25-vector-explained/)，2026-05）。

- 世界观场景的对应：考据资料充满专名（人名/地名/术语）→ 必须双通道；散文语义查询 → 必须向量。

### 3.2 sqlite-vec 是桌面甜点区

单 .db 文件 + 扩展 bundle + <5ms 冷启动 + 跨进程共享 + 量级上限 10M 向量；LanceDB 多文件目录在云同步下脆弱；Chroma 需常驻进程违背嵌入式哲学（同上 GeminiDesktop 文 + [SQLite 技术选型对照](https://github.com/davidamitchell/Research/wiki/2026-02-27-local-database)）。

### 3.3 **重量级证据：arXiv 2026-07 规模化研究**（《Which RAG Paradigm Wins at Scale?》，28 层嵌套语料梯子 1K→512K 文档受控实验）

- **BM25 在全部规模层定义低成本 Pareto 前沿，中规模起 accuracy 领先**——无 LLM 构造成本；

- **Agent+BM25（agent 调 BM25 工具的多轮循环）全规模最高 69.4 分**，对比裸文件 agent 36.9、原生 BM25 54.8——"agent + 检索工具"组合是最强形态；

- **图系 RAG 撞构造墙**：最重 builder 每索引 token 花 24.6 个生成 LLM token，跑完 2% 语料即停；可扩展变体在同层仍不如 BM25（[arXiv:2607.26497](https://arxiv.org/html/2607.26497v1)）。

- 印证首轮 Claude Code 证据（agentic search 弃 RAG）的适用边界：**纯文件 agent 在大规模散文上会掉分，agent 必须骑在结构化检索（BM25/混合）上**。

### 3.4 GraphRAG/LightRAG 系：本场景不建

- 经典 GraphRAG 索引成本 \~1000× 向量 RAG（LLM 读全库抽实体）；LightRAG 增量友好但仍是 LLM 抽取成本；LazyGraphRAG 便宜 700×但查询时才付 LLM 成本（[对比](https://dreaming.press/posts/2026-06-21-graphrag-vs-vector-rag.html)）。

- 判据："全局性问题是否在 query log 中被证明存在"——世界观产品的实体关系**已经有结构化承载**（entity store 的实体+关系图谱，天然免 LLM 抽取），考据资料的多跳需求未证明。**图系留待真实需求信号，不预建**。

### 3.5 embedding 选型（中文优先 + 本地路线）

| 模型                                   | 维度/上下文     | 中文表现                      | 本地可行性                                               | 备注                                                         |
| ------------------------------------ | ---------- | ------------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| **bge-m3**（BAAI，MIT）                 | 1024 / 8K  | recall \~88-91%           | 568M，fp16 1.4GB / Q8 0.7GB；MLX/llama.cpp/Ollama 均可跑 | **dense+sparse+colbert 三合一**——sparse 向量天然喂 BM25 式通道，单模型双索引 |
| **Qwen3-Embedding-0.6B**（Apache-2.0） | 1024 / 32K | MTEB multilingual No.1 系列 | 0.6B 轻量；4B/8B 为质量档                                  | MRL 降维（1024→512/256 不重嵌）；32K 上下文支持 late chunking           |
| nomic-embed-text-v2                  | 768 / 8K   | 中文弱                       | 极快（CPU 580 chunks/s）                                | 英文优先，不选                                                    |
| 云端 API（OpenAI 兼容/智谱等）                | —          | 视端点                       | 零运维                                                 | v1 快速可用路线（用户已配多 provider）                                  |

（[Apple Silicon 实测](https://contracollective.com/blog/local-embeddings-apple-silicon-nomic-bge-qwen3-m5-max-2026)、[Qwen3-Embedding](https://github.com/QwenLM/Qwen3-Embedding)、[中文 RAG 选型](https://blog.aihubplus.com/post/embedding-model-guide-2026/)，2026-06/07）

### 3.6 分块质量：Contextual Retrieval / Late Chunking（v2 增强，v1 不做）

- 朴素分块丢失上下文（代词/专名定义在别处）是隐形失败主因；**Contextual Retrieval**（每 chunk 前置 LLM 生成的文档级上下文）单独降 top-20 失败 35%，+BM25 达 49%，+reranker 达 67%（[RAG 策略综述](https://github.com/enflory/ingolmo/blob/main/rag-domain-knowledge-strategies/README.md)，2026-06）。

- **Late Chunking**（先整文档 forward pass 再按边界池化，bge-m3/Qwen3 的 8K-32K 上下文支持）零额外 LLM 成本获得同等上下文化效果。

## 五、推荐组合（分层架构）

```
L0  agentic search（既有 grep/glob/read）——精确符号/路径定位，保留不动
L1  混合检索工具（本评定核心）：
    SQLite 单库（workdir 级）= FTS5（BM25）+ sqlite-vec（向量）+ RRF 融合
    → 新工具 workspace_search(query, scope?, type?) → top-k + 分节摘要 + 路径引用
L2  质量增强（v2，按效果评测决定）：
    - Late Chunking（bge-m3/Qwen3 长上下文零成本上下文化）
    - 或 Contextual Retrieval（LLM 前缀，成本高一档、效果更强）
    - Reranker（Qwen3-Reranker-0.6B 本地 / 云端）按需
L3  图层：不预建——entity store 已是结构化关系承载；考据多跳需求出现再评 LightRAG
```

**embedding 供给分两期**：v1 云端 API（复用用户已配 provider 的 OpenAI 兼容 embedding 端点，快速闭环）；v2 本地选项（bge-m3 经 Ollama/OpenAI 兼容端点或 Rust ort 侧车）——离线场景补全。

**索引生命周期**：useFsWatcher 增量触发 → 分块 → 嵌入 → 写库；实体/KB 维持既有 embedding 通道不动。

## 六、分期路线（拍板后细化立项）

- **R1（v1 核心）**：sqlite-vec 扩展 bundle → 索引管线（watcher 驱动 + 全量重建命令）→ FTS5+向量 RRF 查询 → `workspace_search` 工具接入 227 工具面 + 流式区投影 → 云端 embedding。闭环 =「考据资料散文件可被语义+全文检索」。

- **R2（质量）**：本地 embedding 选项（bge-m3）/ Late Chunking / Reranker，逐项 A/B 评测。

- **R3（观望）**：图系/聚合类查询——以真实 query log 为触发条件。
