# 规则文件体系与 MCP 配置化设计（H5 八文件体系 + H6-③ 预设移除）

> 来源（2026-08-30）：用户在 [Harness 工程差距调研](./2026-08-30-Harness工程差距调研.md) P3 H6 拍板轮给出两大块新拍板——H5 规则工程从 v1 单文件升级为多文件体系、MCP 官方预设全部移除改配置文件维护。两者共同哲学：**文件化、用户与 Agent 共同维护、去 UI 中心化**（UI 只是快捷入口，文件才是唯一事实源）。
> 本文档承接两线的设计与施工记录。拍板内容为既定约束（不可回退），待设计点需讨论后施工。

## 一、项目定位背景（本设计的前提）

**第一要素（2026-08-30 确立，已写入** **[README.md](../../../README.md)）**：WorldSea 不止是世界观构建的 Agent 产品与 Harness 工程，更兼顾通用 Agent 的性质——**以通用 Agent 为基础、以通用 Harness 工程支撑的世界观构建产品**。

对本文的直接含义：规则文件体系不能只服务世界观场景（WORLD.md），要按通用 Harness 标准设计（AGENTS.md/RULES.md/TOOLS.md 与领域无关）。

### 2.2 通用拍板（适用于全部八文件）

1. 用户与 Agent 都可以维护与编辑，但**不是必须存在**（缺省文件 = 静默跳过，不注入、不报错）。
2. 主设置 → Agent 类 → **规则卡片面板**加入 UI，供用户快速写入内容。
3. **注入方式需要设计**；**内容不由我们负责填充**（内容所有权 = 用户与 Agent，开发者只定格式与机制）。

### 2.3 澄清结果（2026-08-30 用户回答，全部收口）

- ① 「七类」计数：按「七类规则文件 + WORLDSEA.md 系统级特例」归位（用户未反对，默认成立）。

- ② WORLD.md 注入粒度 = **节奏型重注入**：每处理 10 个同类实体，重新注入一次 WORLD.md 中该类相关段落。**目的（用户原话）**：让 Agent 的注意力尽量集中在 WORLD.md 内容上，以让 Agent 的执行能按照该文件内容进行动作。**衍生设计点（用户提出）**：同类与不同类是否真有必要隔离，有待评估 → §2.4 ⑧。

- ③ WORLDSEA.md 处置 = **应用内置资源**：打包进应用资源随版本发布，无文件系统可写实体；规则卡片面板中 WORLDSEA 卡只读展示；v1 ProjectRulesEditor 的读写逻辑随卡片面板改造迁移。

- ④ MCP 配置文件级别 = **全局单份**：放应用配置目录，跨项目共享（细节见 §3.3 ①）。

### 2.8 施工记录：WORLD.md 节奏型注入（2026-08-30 施工完成 ✅）

**分层实现**：

- **纯逻辑层** world-rules.ts（新增，可单测）：`extractWorldRuleSections`（`## 标题` 切节，标题匹配 typeKey/显示名——归一化 equals/互相 includes，匹配键 ≥2 字防误配；无匹配兜底全文）+ `WorldRulesTrigger`（全局计数器 + 窗口类型收集 + 触发归零）+ `clampTriggerThreshold`（1-150 夹取）

- **RulesPanel WORLD 卡**：新增「注入触发阈值」输入（1-150，默认 20）；note 更新为机制已上线描述

**测试**：world-rules.spec.ts 11 用例（阈值夹取/分节匹配 typeKey/label/宽松 includes/无匹配兜底/无标题兜底/空内容/多类型合并/计数器触发归零/阈值实时更新/窗口去重）。教训：测试「多类型合并」初版误依赖兜底路径（纯英文 typeKey 本就无法匹配中文标题——跨语言匹配必须经 label 映射，正是胶水层传 labels 的原因），已修正为显式传 labels 的真匹配断言。

### 3.3 待设计点（讨论后施工）
