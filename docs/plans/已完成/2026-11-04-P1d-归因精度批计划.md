# P1-d：归因精度——记最近 N 条路由（2026-11-04）

> P1-a 的收尾强化：把「崩溃瞬间的单点线索」扩成「崩溃前的一段轨迹」。
> 起于交接文档 §4.4 的可选项，用户选择「记最近 N 条路由」。

## 一、为什么单点不够

P1-a 用宿主 `last route:` 行报出「崩溃时正在服务的插件」。但**一行只回答一个瞬间**。
实测反例（P1-b 期间）：植入的插件自崩，而那行记着 `client-connection`——它只是崩溃
那一刻恰好在飞的无关请求。

单点无法区分这两种情形：

- 某插件在密集刷同一路由，最后一次请求时崩了 → **大概率是它**
- 一堆不相干请求里夹了这一次 → **大概率不是它**

## 二、方案

宿主保留**最近 5 条**派发记录（环形缓冲），崩溃时逐行写出；壳按到达顺序累积成 trail。

### 2.1 宿主侧（`dsh/`，G7 fork 条目）

| 文件 | 改动 |
|---|---|
| `host/webserver/src/index.ts` | 新增 `recentActivity()` + 导出 `ACTIVITY_HISTORY = 5`；`route()` 除单点 `activity` 外维护环形缓冲（满即 `shift()`） |
| `boot/app-boot/src/index.ts` | `FailLoudActivity` 返回类型 `string \| undefined` → `readonly string[]`；`for…of` 逐行写 |
| `apps/cli/src/profile-boot.ts` | 改读 `recentActivity()`，每条路由一行 |

**保留单点 `lastActivity()`**：既有调用方不受影响，且它是「崩溃瞬间」的权威答案。

**行格式不变**（仍是 `last route: <METHOD> <url> → <kind> route <path> → plugin <name>`），
只是**行数从 1 变成最多 5**。壳的解析器天然兼容。

### 2.2 壳侧

| 文件 | 改动 |
|---|---|
| `dsh_crash_attribution.rs` | `Suspect` 增 `trail: Vec<String>`；`begin()` 开新记录、`push_trail()` 追加；`observe_line` 靠 `ACTIVITY_TRAIL_LIMIT` 判定「上一轮是否已收满」 |
| `dsh_restart.rs` | 错误页在「崩溃前换过插件」时展示 `崩溃前依次服务过：A → B → A` |

**轨迹只在有信息量时显示**：全是同一个插件时 `plugin_trail()` 压缩成一项，正文不重复列名。

### 2.3 一个必须同步的常量

壳侧 `ACTIVITY_TRAIL_LIMIT = 5` 必须与宿主侧 `ACTIVITY_HISTORY = 5` 对齐——它不只用于展示，
还是「上一轮崩溃的记录是否已收满、这一条属于下次崩溃」的判定依据。**宿主改大它时这里必须跟改。**

## 三、验证

| 项 | 结果 |
|---|---|
| `cargo test --lib` | **187 passed**（+4） |
| `webserver` vitest | 25 passed（+1 环形缓冲例） |
| `app-boot` vitest | 15 passed in installFailLoud group（+2 多行例） |
| `npx tsc -b` | 0 |
| `pnpm gate` | 4 项全过，fork 16=16 |
| `cargo check` | 零警告 |

**反证**：删掉 `activityHistory.shift()` → 环形缓冲越界增长到 8 条，
`keeps a bounded ring of recent dispatches` 精准失败（期望 5 实得 8）。

### 3.1 端到端（真实宿主，实测输出）

隔离 `DSH_HOME` + 覆盖层植入一个会自造三次路由活动再自崩的插件，真实 stderr：

```
dsh: last route: GET /ring-crash/api/0 → prefix route /ring-crash/api → plugin ring-crash-plugin
dsh: last route: GET /ring-crash/api/1 → prefix route /ring-crash/api → plugin ring-crash-plugin
dsh: last route: GET /ring-crash/api/2 → prefix route /ring-crash/api → plugin ring-crash-plugin
```

**改动前只会有末行一行。** 三行同时出现即证明环形缓冲、多行输出、插件归属三者串通。

### 3.2 产物核对（§3.2 口径，防假阳性）

改 `dsh/` 后按 tsc → tsdown → 验证产物三步走，逐项 grep：

- `webserver/lib/index.js` 含 `ACTIVITY_HISTORY` / `activityHistory` ✅
- `app-boot/lib/index.js` 含 `for (const live of activity?.() ?? [])` ✅
- `apps/cli/lib/profile-boot-<新哈希>.js` 含 `recentActivity` ✅
  （**注意分片换名**：旧哈希文件已不存在，按旧文件名 grep 会假阳性）

## 四、一个过程中踩到的坑

首版探针让插件用 `fetch('http://127.0.0.1:<port>/…')` 自造路由活动，**不生效**——
管道模式宿主不监听 TCP，`port` 只是声明的 authority。改用 `ctx.webServer.dispatch()`
直接喂合成请求才成功。这与 §6 探针技法里「管道模式无 TCP 监听」是同一件事。

## 五、未做

- **不给 N 值加配置项**：5 是「够看出密集刷 vs 过路请求」的最小值，加配置只会增加
  cordis.yml 与壳常量的同步负担（§2.3 那个坑会变成 N 种）。真需要再改常量。
- **不推断因果**：轨迹只呈现事实序列，仍不主张「谁导致的崩溃」。这是 P1-b 期间
  定下的线，不因信息变多而松动。
