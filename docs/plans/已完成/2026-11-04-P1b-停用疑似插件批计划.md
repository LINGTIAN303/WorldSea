# P1-b：停用疑似问题插件后重启（2026-11-04）

> 用户原话：「壳侧能有个停止插件运行的重试方法……这两个方法都能有个手动确认的控件，
> 同时停止或卸载后能够尝试重新连接……这两个方法都仅限 dsh 侧宿主内安装的外部插件，
> 而不染指官方内置插件」。

本批做「停用」这一半；卸载与「由用户二选一」的完整控件形态不在本批。

## 一、开工前先验证（省得做完才发现不通）

| 事项 | 结论 |
|---|---|
| 壳能否调宿主的插件管理 API | **能**。`dsh_bridge::call_api` 已存在（自动带 cookie，与页面同链路） |
| `pluginManager/listPlugins` | 通。信封 `{type:'client-request', rpcId, method, payload:{args}}`；缺 `args` 会报 `Remote payload must contain exactly one plain-object args field` |
| `pluginManager/setPluginEnabled` | 通。返回 `changed:true, application:"applied"`，实测真停用了插件 |
| 判「内置 vs 外部」用什么 | **`moduleName` 前缀**（见 §2.1） |
| 停主的 entry 够不够 | **不够**（见 §2.2） |

## 二、两个推翻原假设的实测发现

### 2.1 `readOnlyReason` 不是内置判据

P1-a 的计划里曾把它当判据，**是错的**。实测清单里几乎所有官方内置插件也没有该字段：

```
include:llm      @deepseek-ai/dsh-llm        (无 readOnlyReason)
include:session  @deepseek-ai/dsh-session    (无 readOnlyReason)
include:storage  @deepseek-ai/dsh-storage    (无 readOnlyReason)
```

它只表示「不能经 profile patch 管理」。拿它判内置，会把官方插件当成可停用的外部插件。

**实际判据**：`moduleName` 以 `@deepseek-ai/` 开头 = 官方；`cordis:` 开头 = 框架自身；
其余（裸包名或第三方 scope）= 外部。

### 2.2 停主 entry 不会停掉子 entry

`dsh-plugin-wallpaper-engine` 一个 npm 包装出 **8 个 entry**。实测停主 entry 后：

| entryId | enabled | fiberPhase |
|---|---|---|
| `include:wallpaper-engine` | **false** | — |
| `include:wallpaper-engine-about-notice` | **true** | pending |
| …其余 6 个 | **true** | pending |

子 entry 只是变 `pending`（等父激活），仍算 enabled。崩溃若是某个子入口引起的，
停主 entry 止不住。→ **必须按家族整组停**（用户已拍板）。

## 三、归因可信度的降级（本批连带修正 P1-a）

P1-b 的端到端验证暴露了 P1-a 的一个假设问题：

**`last route` = 崩溃瞬间在服务的路由，不等于崩溃元凶**。

实测反例：植入的插件在启动 8 秒后自行抛错，但期间页面恰好在调 `/api/settings/describe`，
那行记的是 `client-connection`（官方内置，与崩溃无关）。真壳日志：

```
[DSH-SHELL] 归因：宿主崩溃时正在服务插件 client-connection /api/settings/describe（路由 prefix route /api）
```

**处理**（用户拍板选「诚实降级」）：

| 位置 | 改法 |
|---|---|
| 错误页文案 | 「崩溃时正在服务的插件：X」+「不一定是崩溃原因」，不再写「疑似问题插件」 |
| 菜单文案 | 「停用「X」后重启（崩溃时它在服务）」 |
| 日志 | 「宿主崩溃时正在服务插件 X」 |
| 测试 | 新增 `stop_page_does_not_claim_the_plugin_caused_the_crash` 守住这条线 |

同时保留原有的**硬防线**：停用侧只认外部插件，官方内置一律拒绝——上面那个反例正是被
这条防线挡住的（`client-connection` 是 `@deepseek-ai/*`）。

## 四、改动

### 4.1 新增 `dsh_plugin_control.rs`

| 能力 | 说明 |
|---|---|
| `list_plugins` | 经 `call_api` 调 `pluginManager/listPlugins` |
| `external_families` | 从清单挑出外部插件家族（排除官方/框架/已停用） |
| `family_root` | 按「基座本身也在册」归并同包家族 |
| `family_of` | 把崩溃归因的 fiber 名匹配到家族（兼容 `wallpaper-engine` 与 `dsh-plugin-wallpaper-engine` 两种写法） |
| `disable_family` | 整组逐个停用；任一失败即报错并带出已停列表（不掩盖半途状态） |
| `disable_suspect_and_restart` | 菜单动作全流程：取线索 → 读清单 → 定家族 → 停用 → 通知 → 重启 |

### 4.2 菜单（`menu.rs`）

「视图」子菜单新增一项，**弹出前动态刷新**：

- 有线索 → 「停用「<名>」后重启（崩溃时它在服务）」，可点
- 无线索 → 「停用疑似问题插件后重启（当前无崩溃线索）」，置灰

刷新时机是 `cmd_shell_popup_menu`（菜单是启动时构建的，而线索只在崩溃后出现；
不刷新就会「明明有线索却点不了」或「没线索却可点」）。

## 五、验证

| 项 | 结果 |
|---|---|
| `cargo test --lib` | 184 passed（P1-b 新增 8 例） |
| `cargo check` | 零警告 |
| `pnpm gate` | 4 项全过 |
| 壳构建 | 通过 |

**反证**：把 `family_root` 的「基座在册」判据改成恒真（`if true`）→ 4 例同时失败
（含「无关包不应归并」）。恢复后全绿。

### 5.1 端到端（真壳 + 真崩溃）

起真壳、植入一个会自崩的外部插件，实测链路：

1. 宿主崩溃 → `installFailLoud` 写 `last route:` 行 ✅
2. 壳 stderr 读取线程解析并记录 ✅（日志实证见 §三）
3. 崩溃 3 次 → 重试耗尽 → 错误页 ✅
4. **菜单停用动作未能在自动化中驱动**（需要真实点击 popup 菜单，无法从外部注入）

第 4 步的**能力本身**已在 §一 用真实 API 调用验证过（`setPluginEnabled` 返回
`applied`）；未自动化的是「菜单点击 → 该函数」这一段接线，属真机走查范围。

### 5.2 一个真实 BUG（反证逼出来的，已修）

`family_root` 最初只判「基座在册」，反证时发现会把 `dsh-plugin-worldsea-console` 与
`dsh-whale-widget` 顺着公共前缀归并成不存在的 `dsh` 家族——那会让「停一个」变成
「停一片无关插件」。

深查后确认：正常路径下 `known` 只含完整包名，剥不到 `dsh`；该失败只出现在反证态。
故最终**没有**保留多余的 `head == "dsh"` 守卫（无效防御不留），而是补了一条
`packages_sharing_only_the_dsh_prefix_are_not_one_family` 锁住真实行为。

## 六、真机走查清单（用户手测）

> **走查结果：通过（2026-11-04，用户手测）**。五步全过，含第 5 项「官方插件拒绝停用」的安全属性。

前置：壳 exe 已构建（`apps\tauri\src-tauri\target\debug\worldsea-tauri-app.exe`）。

| # | 操作 | 预期 |
|---|---|---|
| 1 | 正常使用，打开「⋯」菜单 → 视图 | 有「停用疑似问题插件后重启（当前无崩溃线索）」，**置灰不可点** |
| 2 | 杀宿主连续 3 次让重试耗尽 | 错误页出现；若崩溃时有活跃路由，正文含「崩溃时正在服务的插件：<名>」与「不一定是崩溃原因」 |
| 3 | 此时打开「⋯」→ 视图 | 该项变为「停用「<名>」后重启（崩溃时它在服务）」，可点 |
| 4 | 点它 | 系统通知报「已停用外部插件 X 共 N 个入口」→ 自动重启 → 页面恢复 |
| 5 | 若第 3 步点名的是官方插件（如 `client-connection`） | 点它应**拒绝**并通知「在外部插件里找不到 …（它可能是官方内置插件）」 |

第 5 项是本批的**关键安全属性**，务必验一次。

## 七、遗留

1. **只做停用，未做卸载**——用户原话包含卸载，但停用已能止血；卸载是破坏性操作，
   建议单独一批并加二次确认。
2. **归因精度有限**（§三）——若真机走查发现经常指到无关插件，可考虑在宿主侧增强：
   记录最近 N 条路由而非 1 条，或结合未捕获异常的调用栈。
3. **未做「列出全部外部插件让我选」**——用户选了菜单单入口；若实际用起来觉得不够，
   再补一个「插件清单」子菜单。
