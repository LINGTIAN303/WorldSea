# P1-a：崩溃归因——报出疑似问题插件（2026-11-04）

> 本批只做 P1 的第一步：**认出并报出**「刚才是哪个插件把宿主弄死的」。
> 停用/卸载该插件（P1-b）与停用后自动重连（P1-c）不在本批。

## 一、为什么需要

P0（宿主崩溃自愈）解决了「宿主死了页面变砖」，但用户看到的仍是笼统的「反复崩溃，已停止自动重启」。
问题在于**崩溃是进程级死亡，插件来不及上报自己是谁**，壳只能给一个无操作感的错误页。

宿主侧有一行现成线索：`installFailLoud` 崩溃时补写的 `last route:`。但它只到路由路径：

```
dsh: last route: GET /wallpaper-engine/media/x → prefix route /wallpaper-engine
```

**路径前缀 ≠ 包名**。`/wallpaper-engine` 是人写的命名空间，插件包可能叫 `dsh-plugin-wallpaper-engine`。
壳若要指名，只能维护一张映射表去猜——那既脆弱又会随插件变化失真。

## 二、方案：让宿主在崩溃时直接报出插件名

cordis 的每个插件有自己的 fiber，且**服务方法体内的 `this.ctx` 会被重绑定为调用方**（shadow 机制）。
故 `webServer.register()` 在注册那一刻就知道「这条路由是谁注册的」。

于是把归属记进路由表，崩溃时随诊断一起吐出：

```
dsh: last route: GET /wallpaper-engine/media/x → prefix route /wallpaper-engine → plugin wallpaper-engine
```

壳解析这一行就能精确指名。**不需要映射表，也不猜。**

### 2.1 关键验证（做之前先证明可行）

cordis 是否真能在服务方法内拿到调用方身份，是本方案的成败前提。实测探针（隔离环境）：

```js
// 服务方法内读 this.ctx.fiber.name
PROBE identities = [{"fiberName":"wallpaper-engine","entryName":"wallpaper-engine","entryId":"bc982e72:6a8655f2"}]
```

真 Loader 环境下三者一致：

| 字段 | 值 | 用途 |
|---|---|---|
| `fiber.name` | `wallpaper-engine` | 本批归因（写入 `last route:`） |
| `entry.options.name` | `wallpaper-engine` | `listPlugins()` 的 `moduleName` |
| `entry.id` | `bc982e72:…` | `setPluginEnabled` 要的 `entryId` |

**这条一致性是 P1-b 不断链的保证**：本批用 `fiber.name` 定位，下批用 `entryId`/`moduleName` 禁停，
两者指向同一个插件。

## 三、改动

### 3.1 宿主侧（`dsh/`，新增 G6 fork 条目）

| 文件 | 改动 |
|---|---|
| `host/webserver/src/index.ts` | 路由表值由 `WebRoute` 改为 `WebRouteEntry{route, plugin?}`；`register()` 读 `this.ctx.fiber.name` 记归属；`WebRouteActivity` 增可选 `plugin` |
| `apps/cli/src/profile-boot.ts` | `last route:` 行追加 ` → plugin <名>`；无插件名时保持旧格式 |
| `packages/boot/app-boot/tests/app-boot.spec.ts` | 补 2 例（`activity` 供应器此前零覆盖） |
| `host/webserver/tests/webserver.spec.ts` | 补 2 例 + `loadComposition` 增可选 `extra` |

**根 fiber 注册的路由不记归属**（`plugin` 整字段省略）：那是框架自己注册的，报出来会误导
用户去停用一个不存在的「插件」。

### 3.2 壳侧（`apps/tauri/`）

| 文件 | 改动 |
|---|---|
| `dsh_crash_attribution.rs`（新） | 解析 `last route:` → `Suspect{plugin, method, url, route}`；`DshCrashAttribution` 状态 |
| `dsh_shell.rs` | stderr 读取线程调用 `observe_line`（原来只 eprintln） |
| `dsh_restart.rs` | 重启耗尽时的错误页点名疑似插件；重启成功时清空归因 |
| `lib.rs` | 注册模块 + `.manage(DshCrashAttribution::default())` |

归因只对**已死的那个宿主**成立，故重启成功即清空——否则旧归因会挂在健康页面上误导下一次排查。

### 4.2 端到端（宿主侧真实崩溃，实测输出）

用隔离 DSH_HOME + 真 Loader 挂一个会在路由服务中崩溃的插件，实际崩溃时 stderr：

dsh: last route: GET /e2e-crash/api/x → prefix route /e2e-crash/api → plugin e2e-crash-plugin

**这是改动前拿不到的信息**——旧格式只到 `route /e2e-crash/api`。

## 五、偏差与遗留

### 5.1 壳侧链路已用「真实宿主行」贯通（2026-11-04 补）

初版只做到「宿主侧实测 + 壳侧单测」，缺一条完整的机械验证。补做后已闭合：

**① 拿到真实宿主产出**（隔离 DSH_HOME + 真 Loader 挂一个在路由服务中抛错的插件，
直接跑 `dsh --profile web --patch …`）：

```
dsh: fatal uncaught exception: Error: e2e crash from plugin handler
    at Timeout._onTimeout (…/cp/index.js:8:49)
dsh: last route: GET /e2e-crash/api/self → prefix route /e2e-crash/api → plugin e2e-crash-plugin
```

**② 把这一行作为测试输入**跑完整链（解析 → 归因 → 文案 → query → 协议页 HTML）：

`a_real_host_stderr_line_ends_up_on_the_error_page` 断言三件事同时到达页面：
插件名 `e2e-crash-plugin` · 崩溃时在服务的请求 `GET /e2e-crash/api/self` · 失败原因。

**③ 反证**：把解析出的 `plugin` 改成固定 `"unknown"` → **4 个测试同时失败**，
其中包含上述全链贯通用例。证明这条链真的被测试守住，而不是「看起来对」。

**仍然保留的边界**：机器验证走的是 `error_page_response()`（协议处理器入口），
不是 WebView 真渲染。窗口渲染由 `dsh_error` 的既有走查覆盖（P0 批 #4 已验证窗口栏与
「⋯」菜单在错误页可用），本批未改那条路径。

### 5.2 初版为何卡住（记录下来免得重踩）

初版试图用「临时往 `apps/tauri/dsh-overlay.yml` 加 `insert` 条目」驱动真实崩溃，失败。
排查结论与正确做法：

1. **overlay 插入本身是有效的**——用 `dsh --profile web --patch <file> --dump-config`
   能看到 `- id: e2e-crash-plugin` 出现在组合里（这条命令是诊断 overlay 的捷径）。
2. 失败在**参数位置**：`--patch` / `--dump-config` 都是 **launcher 标志，必须排在
   `web` 子命令之前**；放在后面会被当成 app 参数，报 `unknown option`。
3. 另一个坑：已用 `--profile web` 选过 profile 后，**不能再给 `web` 子命令**，
   否则 `too many arguments. Expected 0 arguments but got 1: web`。

正确的最小复现（不经过壳，直击宿主侧）：

```powershell
$env:DSH_HOME = <临时目录>
node dsh\apps\cli\lib\bin.js --profile web --patch <overlay.yml> --no-open --port 39411
```

### 5.3 归因的固有边界

宿主也可能崩在**非路由路径**上（启动期、后台任务、事件回调）。此时没有 `last route:` 行，
壳保持原文案、不臆造插件名——这是有意的：**宁可不指名，也不指错人**。

### 5.3.1 措辞降级（2026-11-04，P1-b 期间修正）

P1-b 的端到端验证暴露了本批一个过强的假设：**`last route` 是「崩溃瞬间在服务的路由」，
不等于「导致崩溃的插件」**。

实测反例：植入的插件在启动 8 秒后自行抛错，但期间页面恰好在调 `/api/settings/describe`，
那行记的是 `client-connection`——无关的官方内置插件。真壳日志：

```
[DSH-SHELL] 归因：宿主崩溃时正在服务插件 client-connection /api/settings/describe（路由 prefix route /api）
```

**故本批文案已全面降级**（用户拍板「诚实降级」）：

| 位置 | 旧 | 新 |
|---|---|---|
| 错误页 | 「疑似问题插件：X」 | 「崩溃时正在服务的插件：X」+「不一定是崩溃原因」 |
| 菜单 | 「停用疑似问题插件「X」后重启」 | 「停用「X」后重启（崩溃时它在服务）」 |
| 日志 | 「归因：…」 | 「崩溃时正在服务插件 …」 |

新增 `stop_page_does_not_claim_the_plugin_caused_the_crash` 守住此线。
**P1-a 的产出价值因此重新定义为「提供线索」而非「指名元凶」。**

### 5.4 `plugin` 与 `moduleName` 的等价性

本批实测两者相等（见 §2.1），但这是**当前形态**：`fiber.name` 取「最近的有名祖先」，
若将来插件的 fiber 名与包名分离，P1-b 需要一层核对。届时消费点在 `plugin-manager` 的
`listPlugins()`，不在本批。
