## 零、总体判断（先读这段）

三域差距不是一个性质，分层看：

| 域 | 一句话判断 |
|---|---|
| 工具域 | **契约差距最大**：dsh 是「定义即契约」（schema/输出/并发/超时/呈现全在定义上、流水线单一）；本侧是「能力即工具」（110+ TS 工具、契约轻、执行流水线硬编码）。但本侧有一项 dsh 都没有的强点：**裁剪前原文外置 + 坐标可读回**（`raw/{hash}` + `memory_read_raw`），与 dsh 的 spill policy 语义同构且更前置。 |
| Skill 域 | **主症结是元数据双源**：SKILL.md（正文 + 可选 frontmatter）与静态 TS `SKILL_REGISTRY`（data/*.ts）并存——改文件不影响索引、12/37 无 frontmatter、2 处字段名失配，dsh 则是 frontmatter 唯一事实源 + 严格校验。触发机制（渐进披露 + `load_skill` 三件套）已与 dsh 同构。 |
| MCP 域 | **主缺口是生命周期**：本侧连接「一次成型」（启动连一次、工具缓存一份、断开靠 drop），dsh 有重连退避、代际切换、list_changed、优雅关闭。命名/冲突/安全（环境清理）上本侧均有可对齐差距。 |

对齐不是照抄：dsh 的工具契约是为「一个通用编程 harness」设计的（PTC 呈现、run_code、browser-use 等），本侧是世界观构建产品（桌面 + 单二进制 + 领域工具 + [[双执行栈历史]]）。本清单已按「本项目为什么需要」逐项过滤，不适用者列入 §四 排除项。

## 二、对照矩阵（语义 / 契约 / 设计 三层）

### 2.1 工具域

| 层 | dsh | 本侧 | 判定 |
|---|---|---|---|
| 语义 | 工具 = 带完整契约的注册单元（三字段进模型 + 输出双投影 + 呈现纯函数）；分层作用域可见集 | 工具 = 可调用函数；可见性 = 白名单（静态基线 + 场景裁剪） | **部分同构**：可见性裁剪思想一致（restrict ≈ WhitelistToolBus）；契约密度差距大 |
| 契约 | name/description/parameters 单源白名单投影；结果判别联合 isError+错误码；output schema 校验；并发/超时/取消声明式 | 双栈两套结构（记录式 vs JSON Schema）；结果靠 `{\"error\"}` 约定；无并发声明；超时全局常量 | **有差距**（T1/T3/T5） |
| 设计 | 五段流水线 + guard 单调 + 外挂 policy（超时/spill）+ 失败关闭并发 + 取消贯通 | 审批/超时/裁剪硬编码在调用点（裁剪已迁 waterfall 第一例）；并行路径无超时；已建成事件总线可承接迁移 | **有差距但承接条件已备**（T4/T6；裁剪已对齐） |

### 2.2 Skill 域

| 层 | dsh | 本侧 | 判定 |
|---|---|---|---|
| 语义 | Skill = 可发现/可分层/可渐进披露的知识包；三角色缝合（Definition/Provider/Consumer）；`disable-model-invocation` 等策略在文件内声明 | Skill = 静态注册元数据 + SKILL.md 正文；应用层启停；无策略字段 | **有差距**（S1/S3） |
| 契约 | frontmatter 唯一事实源 + 严格校验（非法值丢弃、旧键报错）；目录只给 name+description（截断 500）；digest 身份 | frontmatter 可选（12/37 无）且与 registry.ts 双源；索引无长度约束；无校验 | **有差距**（S1/S2/S5/S6） |
| 设计 | watcher 热重载 + 分层覆盖 + catalog/body 生命周期分离 + pre-step 注入 | 无热更新 + 静态注册 + 启停重建；注入段 order 270（与 dsh 的 pre-step 位置策略不同但等效） | **部分同构**（S4 为可选增强） |

### 2.3 MCP 域

| 层 | dsh | 本侧 | 判定 |
|---|---|---|---|
| 语义 | server = 可重连、可代际切换的能力单元；工具命名是本地命名空间（不回解析） | server = 一次连接 + 一份工具缓存；命名可反解析（脆弱约束） | **有差距**（M1/M3） |

## 三、建议清单

### 3.1 工具域

#### T1 工具结果补判别字段（isError + 错误码）【对齐·契约】
- dsh：结果判别联合——`isError` 显式 + `error{message, info{name, code}}` 结构化错误码（UNKNOWN_TOOL/INVALID_TOOL_OUTPUT/ABORTED）。
- 本侧：失败靠 `{\"error\":..}` 约定 + `ToolCallEnd.status` 二值；模型与前端都靠形状猜测。
- 立项理由：失败语义不明会让模型对「重试 / 换路 / 放弃」判断不稳；前端呈现也缺统一判据。这是模型行为级差异，成本却很小。
- 改动面：kernel 结果构造 + 桥端失败映射 + 前端消费（加性）+ 契约测试。
- 建议：**做**（小-中，低风险，可并入任一批次）。

#### T2 输出 schema 校验 + render 双投影【对齐·契约】
- dsh：`value`(canonical) → `output.schema` 校验 → `render()` 产 content；畸形结果判 `INVALID_TOOL_OUTPUT`。
- 本侧：工具返回值直接进消息，无校验、无渲染层（前端按工具名自行解析）。
- 立项理由：防畸形结果进上下文有价值，但**本侧每个工具都要补声明**，成本与收益比远大于 T1（dsh 是强类型内建语言，本侧双栈补全成本高）。
- 建议：**降级为最小形态**——仅对「结果结构敏感」的工具（UI 四工具、entity_* 等）在桥端做轻校验并归入 T1 的 `INVALID_TOOL_OUTPUT` 码；完整双投影列远期。

#### T3 并发安全声明（isConcurrencySafe）【对齐·设计】
- dsh：只有显式 `true` 才并行，未声明一律排他（失败关闭）。
- 本侧：一刀切 `parallel_tool_calls && !any_needs_confirm`；写类工具（entity 写、文件写）并发存在竞态风险，只读工具又被人为串行。
- 立项理由：本侧实体/关系写入是真写（无事务层），并发写同实体可能互相覆盖；当前「全并行 + 审批强制串行」是粗放近似。默认排他是更安全的基座。
- 改动面：`Tool` trait 加方法（默认 false）+ 并行判定改造 + 桥 11 项与原生工具逐项标注 + 契约测试。
- 建议：**做**（中，安全收益明确；可与 T4 同批）。

#### T4 并行路径补超时与重试【修复】
- dsh：`timeoutMs` 由统一 policy 实施（串并行同规）。
- 本侧：`execute_tool_with_retry` 仅串行调用；并行路径直调 `call_tool_with_ctx`——**并行工具卡死会挂住整个 turn**，且与串行行为不一致。
- 立项理由：这是缺陷修复，不是新特性；并行路径正是长输出工具（终端/文件）走的路。
- 改动面：`agent/tools.rs` 并行路径补同一包装（或统一提取执行入口）+ 契约测试。
- 建议：**优先做**（小-中，硬缺陷）。

#### T5 桥工具 schema 单一事实源【对齐·契约】
- dsh：三字段单源 + 白名单投影（模型只见 name/description/parameters）。
- 本侧：桥 11 项 name/description/parameters 在 Rust 手工拷贝自 TS，**已实际漂移**（A1 元工具 schema 双份、TS 6 示例 vs Rust 3）；且它是「补桥」的硬前置（每加一项工具要维护两份）。
- 立项理由：漂移即 BUG（模型看到的 schema 与实际执行不符）；不解决它，T8/T9 每项都要付双份维护成本。
- 改动面：三方案取一——① TS 启动时向 Rust 上报桥工具定义（运行时同步）；② 构建期从 TS 生成 Rust 常量（脚本 + CI 校验）；③ 桥注册改为「TS 定义进 Rust 总线」的正式通道。方案 ①/③ 改动 Rust 注册时序（涉及会话装配点），② 最小侵入。**方案选择需拍板**。
- 建议：**优先做**（中；方案拍板后施工）。

#### T6 工具执行流水线迁移（审批/超时/日志 → 监听器）【对齐·设计】
- dsh：五段流水线（pre-execute waterfall → guard 单调 → execute → post-execute → finalize），审批/超时/日志均为可组合的监听器。
- 本侧：事件总线（阶段 1）+ waterfall（裁剪已迁、A3 输入准入已用）已就绪；审批判定 `maybe_require_confirmation` 仍硬编码在调用点、仅串行。
- 立项理由：承接既有建设成果——迁移后审批/超时逻辑可测试、可停用、串并行统一；且本侧权限体系（三档 + 规则引擎）本身比 dsh 复杂，**要的是「判定点单一 + 不可翻案」的原则，不是照搬**。
- 改动面：中-大（审批判定点迁移 + 串并行路径统一 + 与既有权限分级链路的适配）。注：审批此前被列为 B 级不夹带（方向一 04-§五），本轮若纳入需明确授权。
- 建议：**拆两步**——T6a 审批判定迁 `pre-execute`（做）；T6b 串并行执行统一入口（与 T4 合并回合）。若用户不愿动审批，可只做 T6b。

#### T7 裁剪阈值粒度【增强】
- dsh：spill 阈值 `maxInlineBytes` 由 policy 配置。
- 本侧：全局常量 12000；**但已带 locator（原文外置坐标 + memory_read_raw 可读回）——语义已与 spill 同构**，差异仅在粒度。
- 建议：**缓做**（低优先；如做，按工具类别给阈值，如终端输出 vs 实体查询）。

#### T8 补桥：`a2ui_show_entity` / `a2ui_show_relation`【新增·能力】
- dsh 无直接对应（其 `present` 是同类思想：交付物呈现工具）。
- 本侧：两工具在 `ALL_TOOLS_MAP` 里存在但不可达（非桥 11 项）；A2UI 画布回源刚闭合（`docs/plans/2026-09-17-A2UI画布回源持久化.md`）。
- 立项理由：LLM 现在无法「把某个实体画到画布上」——这是世界观产品最自然的呈现动作之一，且消费侧（画布 + 回源）已就绪。
- 依赖：T5（否则又添两份 schema）。
- 建议：**做**（小，在 T5 之后）。

#### T9 补桥第二批（output_* / kb_* 等）【新增·能力】
- 本侧：110+ TS 工具仅 11 项可达。其中对 LLM 价值最高的候选：`output_*`（13 个呈现工具，含 `output_choice` 让模型发起选择、`output_entity_card`）、`kb_*`（9 个知识库工具）、`memory_*`（TS 3 件，与 Rust 5 件重叠需先定去留）。
- 立项理由：模型「能说不能呈现」是当前体验短板；知识库写入（kb_write）是世界观构建核心动作之一。
- 依赖：T5 先行；且需逐项拍板取舍（本清单建议首批只选 `output_*` 与 `kb_*` 中确认在用者）。
- 建议：**分批做，先出候选清单**（与用户逐项过一遍）。

### 3.2 Skill 域

> **2026-09-17 拍板注记（范围重定义，见 §七 D3）**：① 排除 27 芽所属 Skills（后续随芽单独改动，本轮不动）；② 除芽所属外，本侧独立 Skills 数量「应为 0 个」；③ 本轮按 **Skills 协议规范**（agentskills.io / dsh 同源协议）建设——**发现面 + 创建/导入管理面一并纳入**。以下 S1-S6 为对照期建议，范围以 §七 裁定与补充调查结论为准（先查清再动手）。
