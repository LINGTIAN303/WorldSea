## 一、问题定义与规模测算

### 1.1 检索对象（WorldSea 场景的内容形态）

| 内容                       | 结构化程度       | 现有检索通道                         | 缺口                        |
| ------------------------ | ----------- | ------------------------------ | ------------------------- |
| 实体（角色/地域/组织…）            | 高（schema 化） | entity 语义工具 + embedding 索引（已通） | 无                         |
| KB/笔记本                   | 半结构化        | KB 语义索引（已通）                    | 规模上限（IndexedDB）           |
| 考据资料/散文件（workdir md/txt） | 低（散文为主）     | 仅 grep/read 纯文本                | **主缺口**——无语义通道、无全文索引      |
| 文稿（章节）                   | 低-中         | 无独立通道                          | 同上                        |
| **代码文件（编码场景）**           | 高（语法结构）     | grep 纯文本（符号精确，强项）              | 大库冷启动定位慢；语义级"这段代码做什么"检索缺失 |

**核心缺口 = workdir 非结构化内容（散文考据资料 + 代码）的语义/全文检索**。实体/KB 已有通道，不需要本评定重做。

**⚠ 编码场景维度（2026-08-30 用户补充，依据项目第一要素：以通用 Agent 为基础）**：WorldSea 兼顾通用编码场景（Skills 脚本/插件模块/用户以通用 Agent 干编程活），检索必须覆盖代码内容：

- **混合检索天然兼容代码**——BM25/grep 是代码符号检索的强项（arXiv 证据：BM25 全规模 scaling 最优；Claude Code 亦然），向量通道补"这段代码做什么"语义查询

- 对推荐方案的影响 = **零架构改动，三个实现注意项**：① 分块策略对代码文件按语法结构（函数/类）而非固定字数切；② FTS5 分词对标识符的处理（trigram 或 unicode61+大小写保真）；③ embedding 选型须含 code retrieval 能力——**Qwen3-Embedding 明确支持代码检索**（bge-m3 通用多语言亦可用），评定 §三.5 选型结论不受影响

### 1.2 规模测算（千万字级 = 10M 汉字 ≈ 7M tokens，按 500 字/块）

| 项                       | 10M 字                                                                                                                                 | 50M 字（5 倍冗余上限）             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| chunk 数（500 字/块）        | \~2 万                                                                                                                                 | \~10 万                     |
| 向量存储（1024 维 f32=4KB）    | \~80 MB                                                                                                                               | \~400 MB（int8 量化 \~100 MB） |
| FTS5 全文索引（文本 1-2 倍）     | 10-20 MB                                                                                                                              | 50-100 MB                  |
| 查询延迟（sqlite-vec top-50） | <50 ms（[GeminiDesktop 实测同量级](https://geminidesktop.app/en/blog/local-sqlite-vec-rag-gemini-desktop-2026)：50 万词→200MB 单文件→top-5 <50ms） | 同量级可维持                     |

**结论**：千万字级（甚至 5 千万字）落在 **SQLite 单文件甜点区内**（sqlite-vec 上限 \~10M 向量，我们在 1% 处）——**完全不需要专用向量数据库**（LanceDB/Chroma/Qdrant 均为过度设计）。

## 二、现状盘点（基建契合度）

1. **SQLite 基建现成**：Rust 侧 sqlx 多库（sessions 等），FTS5 为 SQLite 内置（零依赖），sqlite-vec 为单文件扩展（Tauri bundle .dll/.dylib，与"MCP 配置/规则文件"的单机文件哲学同构）。
2. **embedding 包现成但载体受限**：`packages/agent-runtime/src/embedding/`（IndexedDB 向量库）——WebView origin 配额限制 + 与磁盘文件体系脱节，**不宜承载 workdir 文件索引**（保留服务实体/KB）。
3. **Agent 工具面**：227 工具 + grep/read 纯文本（保留——精确符号定位仍有价值，见证据 §三.3）。
4. **文件监听**：useFsWatcher 已有——增量索引的触发器现成。

## 三、外部证据汇总（2026-08-30 查证）

### 3.1 混合检索 = 2026 共识（BM25 精确但字面 × 向量灵活但模糊）

- BM25 失败模式：词表不匹配（"car insurance" vs "vehicle policy"）；向量失败模式：**精确标识符/专名 near-miss**（OAuth2Provider 搜出 OAuthClientProvider）——两failure 模式互恰，RRF（排名融合，无 needscore 校准）或加权融合（可加 metadata 信号）合并（[StrataFS 深度文](https://stratafs.neullabs.com/blog/hybrid-search-bm25-vector-explained/)，2026-05）。

- 世界观场景的对应：考据资料充满专名（人名/地名/术语）→ 必须双通道；散文语义查询 → 必须向量。

### 3.2 sqlite-vec 是桌面甜点区

单 .db 文件 + 扩展 bundle + <5ms 冷启动 + 跨进程共享 + 量级上限 10M 向量；LanceDB 多文件目录在云同步下脆弱；Chroma 需常驻进程违背嵌入式哲学（同上 GeminiDesktop 文 + [SQLite 技术选型对照](https://github.com/davidamitchell/Research/wiki/2026-02-27-local-database)）。

### 3.3 **重量级证据：arXiv 2026-07 规模化研究**（《Which RAG Paradigm Wins at Scale?》，28 层嵌套语料梯子 1K→512K 文档受控实验）

- **BM25 在全部规模层定义低成本 Pareto 前沿，中规模起 accuracy 领先**——无 LLM 构造成本；

- **Agent+BM25（agent 调 BM25 工具的多轮循环）全规模最高 69.4 分**，对比裸文件 agent 36.9、原生 BM25 54.8——"agent + 检索工具"组合是最强形态；

- **图系 RAG 撞构造墙**：最重 builder 每索引 token 花 24.6 个生成 LLM token，跑完 2% 语料即停；可扩展变体在同层仍不如 BM25（[arXiv:2607.26497](https://arxiv.org/html/2607.26497v1)）。

- 印证首轮 Claude Code 证据（agentic search 弃 RAG）的适用边界：**纯文件 agent 在大规模散文上会掉分，agent 必须骑在结构化检索（BM25/混合）上**。

### 3.4 GraphRAG/LightRAG 系：本场景不建

- 经典 GraphRAG 索引成本 \~1000× 向量 RAG（LLM 读全库抽实体）；LightRAG 增量友好但仍是 LLM 抽取成本；LazyGraphRAG 便宜 700×但查询时才付 LLM 成本（[对比](https://dreaming.press/posts/2026-06-21-graphrag-vs-vector-rag.html)）。

- 判据："全局性问题是否在 query log 中被证明存在"——世界观产品的实体关系**已经有结构化承载**（entity store 的实体+关系图谱，天然免 LLM 抽取），考据资料的多跳需求未证明。**图系留待真实需求信号，不预建**。

### 3.5 embedding 选型（中文优先 + 本地路线）

| 模型                                   | 维度/上下文     | 中文表现                      | 本地可行性                                               | 备注                                                         |
| ------------------------------------ | ---------- | ------------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| **bge-m3**（BAAI，MIT）                 | 1024 / 8K  | recall \~88-91%           | 568M，fp16 1.4GB / Q8 0.7GB；MLX/llama.cpp/Ollama 均可跑 | **dense+sparse+colbert 三合一**——sparse 向量天然喂 BM25 式通道，单模型双索引 |
| **Qwen3-Embedding-0.6B**（Apache-2.0） | 1024 / 32K | MTEB multilingual No.1 系列 | 0.6B 轻量；4B/8B 为质量档                                  | MRL 降维（1024→512/256 不重嵌）；32K 上下文支持 late chunking           |
| nomic-embed-text-v2                  | 768 / 8K   | 中文弱                       | 极快（CPU 580 chunks/s）                                | 英文优先，不选                                                    |
| 云端 API（OpenAI 兼容/智谱等）                | —          | 视端点                       | 零运维                                                 | v1 快速可用路线（用户已配多 provider）                                  |

（[Apple Silicon 实测](https://contracollective.com/blog/local-embeddings-apple-silicon-nomic-bge-qwen3-m5-max-2026)、[Qwen3-Embedding](https://github.com/QwenLM/Qwen3-Embedding)、[中文 RAG 选型](https://blog.aihubplus.com/post/embedding-model-guide-2026/)，2026-06/07）

### 3.6 分块质量：Contextual Retrieval / Late Chunking（v2 增强，v1 不做）

- 朴素分块丢失上下文（代词/专名定义在别处）是隐形失败主因；**Contextual Retrieval**（每 chunk 前置 LLM 生成的文档级上下文）单独降 top-20 失败 35%，+BM25 达 49%，+reranker 达 67%（[RAG 策略综述](https://github.com/enflory/ingolmo/blob/main/rag-domain-knowledge-strategies/README.md)，2026-06）。

- **Late Chunking**（先整文档 forward pass 再按边界池化，bge-m3/Qwen3 的 8K-32K 上下文支持）零额外 LLM 成本获得同等上下文化效果。

## 五、推荐组合（分层架构）

```
L0  agentic search（既有 grep/glob/read）——精确符号/路径定位，保留不动
L1  混合检索工具（本评定核心）：
    SQLite 单库（workdir 级）= FTS5（BM25）+ sqlite-vec（向量）+ RRF 融合
    → 新工具 workspace_search(query, scope?, type?) → top-k + 分节摘要 + 路径引用
L2  质量增强（v2，按效果评测决定）：
    - Late Chunking（bge-m3/Qwen3 长上下文零成本上下文化）
    - 或 Contextual Retrieval（LLM 前缀，成本高一档、效果更强）
    - Reranker（Qwen3-Reranker-0.6B 本地 / 云端）按需
L3  图层：不预建——entity store 已是结构化关系承载；考据多跳需求出现再评 LightRAG
```

**embedding 供给分两期**：v1 云端 API（复用用户已配 provider 的 OpenAI 兼容 embedding 端点，快速闭环）；v2 本地选项（bge-m3 经 Ollama/OpenAI 兼容端点或 Rust ort 侧车）——离线场景补全。

**索引生命周期**：useFsWatcher 增量触发 → 分块 → 嵌入 → 写库；实体/KB 维持既有 embedding 通道不动。

## 六、分期路线（拍板后细化立项）

- **R1（v1 核心）**：sqlite-vec 扩展 bundle → 索引管线（watcher 驱动 + 全量重建命令）→ FTS5+向量 RRF 查询 → `workspace_search` 工具接入 227 工具面 + 流式区投影 → 云端 embedding。闭环 =「考据资料散文件可被语义+全文检索」。

- **R2（质量）**：本地 embedding 选项（bge-m3）/ Late Chunking / Reranker，逐项 A/B 评测。

- **R3（观望）**：图系/聚合类查询——以真实 query log 为触发条件。
