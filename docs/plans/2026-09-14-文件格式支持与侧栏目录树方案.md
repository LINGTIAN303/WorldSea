## 一、背景与现状（已有资产，勿重复造）

用户提出「笔记本芽增加 Docx/PPT/Excel 等格式，渲染、绘制」「侧栏承载真目录树」。摸底后发现项目已有大量地基，**问题不是"从零做"，而是"接线"**。

### 1.1 文件系统层（Rust 侧，能力已完整）

`apps/tauri/src-tauri/src/fs_commands.rs` 暴露：`cmd_fs_read`（支持 base64/utf-8 双编码）/ `cmd_fs_write` / `cmd_fs_list`（可选递归）/ `cmd_fs_delete` / `cmd_fs_stat` / `cmd_fs_mkdir` / `cmd_fs_copy` / `cmd_fs_rename` / `cmd_fs_search` / `cmd_open_in_explorer`；另有 `fs_watch_commands.rs` 提供文件监听。

写类入口的唯一防护是 `ensure_write_allowed` → `sensitive_dir_reason`（**系统敏感目录黑名单，非工作区隔离**）。

### 1.2 前端文件子系统（`apps/tauri/src/space/files/`，18 文件）

- **`FileTreeBrowser.vue` = 可直接内嵌的真目录树**：懒加载、面包屑、行内重命名（Enter/Esc/失焦提交）、新建文件/文件夹、上传、删除（带确认）、展开态按根路径持久化到 localStorage、`agent-tmp`/`agent-out` 分区 chip、在系统资源管理器中打开。
  props = `{ rootPath?: string|null, compact?: boolean, title?: string, mergedHeader?: boolean }`；`compact` 的注释原文即「左栏会话侧边栏内嵌时」。
  **已内嵌两处**：`space/chat/SessionSidebar.vue:140`（左栏）、`space/panels/PreviewPanel.vue:60`（右栏）。
- 同目录另有 `ProjectFilesPanel.vue`（组合树+预览+多标签）、`FileTabBar.vue` + `fileTabsStore.ts`（会话级多文件标签）、`FilePreview.vue`（预览/编辑/对比三态）、`CodeEditor.vue`（CodeMirror 6）、`CodeDiff.vue`、`fileIcons.ts` + `file-icon-data.ts`。

### 1.3 Office 图标已就绪

`space/files/file-icon-data.ts:66-72` 已含 `pdf→_f_pdf` / `doc,docx→_f_word` / `xls,xlsx→_f_excel` / `ppt,pptx→_f_powerpoint`（数据源 vscode-great-icons）。文件树里**已经显示正确的 Office 图标**。

### 1.4 `FilePreview.vue` 是格式能力的唯一落点

现支持五类：`image` / `markdown` / `html` / `code` / `text`（`previewKind()` @ `:419-425`）。**`BINARY_EXT`（`:157-161`）把 `pdf/doc/docx/xls/xlsx/ppt/pptx` 明确列为"不可预览"**，直接走「非文本二进制文件，暂不支持预览」分支 → 这就是要改的那张黑名单。

### 1.5 依赖现状（关键：已装但未声明）

已装于**根** `package.json`：`docx` ^9.6.1（生成）、`mammoth` ^1.12.0（docx 解析）、`jszip` ^3.10.1、`pdfjs-dist` ^5.7.284、`turndown` ^7.2.4。
**`apps/tauri/package.json` 未声明它们**（靠根 hoist 生效）—— 隐性契约，本方案顺手补齐。

已装但用途受限：

- `apps/tauri/src/composables/useFileExtract.ts` —— 用 mammoth（`:36-53`）与 pdfjs（`:56-90`）**只提取纯文本给 Agent 当上下文，不做渲染**；pdfjs 已 Worker 化（`:62-67`，注释记录了「`workerSrc=''` 会回退主线程同步解析、大 PDF 卡顿」这个已踩过的坑）；入参是 `File` 对象，接入 FilePreview 需从 base64 转 ArrayBuffer。
- `sprouts/official/manuscript/composables/useManuscriptExport.ts:41-67` —— **已能生成 docx**，但实现是 `stripHTML`（`:4-8`）后逐行成段，**丢掉标题层级 / 列表 / 加粗**。

### 1.6 关键架构事实：「项目 = 目录」

`space/workspace.ts` 定义三层语义（`:42-60` `resolveWorkspaceDir`、`:70-83` `resolveEntityDataDir`）：

- **普通项目**：`dirPath` 既是 Agent 工作区，也是实体存储父目录 → 实体落 `{dirPath}/entities`（`FileStorageBackend` 落 JSON 文件）
- **默认项目例外**：Agent 工作区 `~/.WorldSea/agent`，实体 `~/.WorldSea/worlddata`

→ **推论：笔记本的「笔记」本来就已经是磁盘上的真实文件**，只是位于受管理的 `entities/` 子目录 + 有索引。「真目录树」与「笔记」不是两套体系，是**同一棵树的两个部分**。这是三期方案的解题前提。

### 1.7 编辑器内核（TipTap）实际边界

`apps/tauri/package.json:45-49` 装了 `@tiptap/core` / `extension-mention` / `starter-kit` / `suggestion` / `vue-3`。
`useNoteEditor.ts` 实际启用：`StarterKit + Mention + SlashCommandExtension` —— **一个格式扩展都没装**（无 Table / Image / TaskList / CodeBlock）。

能力边界分三层：

| 层 | 结论 |
|---|---|
| 段落、标题、列表、引用、加粗、行内代码 | **够用**，`StarterKit` 已覆盖 |
| 表格、图片、任务列表、代码块 | **加官方扩展即可**（`@tiptap/extension-table` 等），非架构问题 |
| 分页（页边距 / 页眉页脚 / 分页符 / 页码 / 浮动对象 / 公式） | **根本不够**。TipTap 是流式文档模型，docx 是分页文档模型 |

**由此确立产品形态原则：预览走渲染器（只读、追保真）；编辑走 TipTap（内容编辑、导出而非存回）。两条路不混。**

## 二、一期 · 文件格式只读预览

### 2.1 落点

`space/files/FilePreview.vue`：从 `BINARY_EXT` 移除 office 项，`previewKind()` 扩展分发到新渲染器；每类渲染器若干行（docx/xlsx/pptx），pdf 复用既有 image/pdf 分支形态。

### 2.2 分格式方案

| 格式 | 方案 | 新依赖 | 说明 |
|---|---|---|---|
| docx | `docx-preview` → 渲染进容器 div | **`docx-preview`** | CSS-in-JS 保真渲染、分页模拟、内置 sanitizer。复杂表格/公式支持差、内存占用高（沿用 10MB 守卫） |
| xlsx | SheetJS 解析 → 原生表格组件渲染 | **`xlsx`**（SheetJS CE） | 只解析数据；样式不保证（CE 版导入丢样式，符合「设定表」定位） |
| pdf | `pdfjs-dist`（**已装**）→ canvas 分页渲染 | 无 | 照搬 `useFileExtract.ts:62-67` 的 Worker 化解法 |
| pptx | 探测本机 LibreOffice → `soffice --headless --convert-to pdf` → 复用 pdf 通路 | 无 | 桌面端天然可行；**必须先探测再降级** |

排除项见 §五。

## 四、三期 · 侧栏并列双 tab

### 4.1 做法

笔记本（以及后续其他芽）侧栏顶部加「笔记 / 文件」切换：

- **笔记侧**：现有 `FolderTree`（虚拟文件夹，localStorage）不动
- **文件侧**：**直接复用 `FileTreeBrowser`**（`compact` + `rootPath`），零新组件

零数据迁移、可逆、当轮可验收。

### 4.2 待定：根语义

| 选项 | 效果 |
|---|---|
| 项目目录 `{dirPath}` | 能力最全，但用户会看到 `entities/` 里一堆实体 JSON（那是内部存储格式） |
| 项目目录下某子目录（如 `notes/`） | 更干净，但少一层能力（看不到 Agent 的 `agent-tmp`/`agent-out`） |
| 由用户显式指定 | 最灵活，需新增配置面 |

**已拍板**：项目目录 `{dirPath}` + 对 `entities/` 等内部目录做视觉弱化（灰化/折叠），既不阉割能力也不误导。

### 4.3 前提：删除必须先可逆化（**不解决不开工**）

`cmd_fs_delete` 是**递归且不可逆**的，`FileTreeBrowser.onDelete` 的确认文案自己就写着「此操作不可撤销」；而 `ensure_write_allowed` 不做工作区隔离。

**冲突点**：笔记本芽刚于 `c7eefda` 把「删文件夹」做成**可撤销**（`asSingleUndoStep` 归并为单条撤销记录）。把不可逆的真删除摆进工作台芽，与芽内其他删除操作形成刺眼的不一致。

**已拍板：软删除进回收站** —— 复用既有 `trashStore`（`entityStore.remove` 已在用），与实体删除体验对齐。三期实现要点：

- 删除文件/目录 → 不调 `cmd_fs_delete`，改为「移入项目内回收站目录 + 记账」（复用 `trashStore` 或新建文件侧替身）
- 回收站提供「还原 / 永久删除」；永久删除才真正调 `cmd_fs_delete`，并保留二次确认
- 跨盘移动不可靠，故回收站目录须与源同盘（放项目目录下，如 `{dirPath}/.trash/`）
- 需与既有实体回收站（`trashStore`，90 天 GC）口径统一，避免两套回收站语义

## 五、明确不做（负向范围，避免反复讨论）

| 项 | 排除理由 |
|---|---|
| 嵌入 Univer 做 xlsx 保真编辑 | 重依赖；导入导出样式仅保持 80~85%；高级能力依赖 Univer Server / Pro。且产品定位是「设定表」非财务报表 |
| **Luckysheet** | **官方已停止维护**（继任者 Univer） |
| Microsoft Office Online Viewer | 需公网可访问 URL + 文件上传微软服务器 → 与「本地开发、不上线」原则及隐私边界冲突 |
| pptx 纯前端渲染 / 编辑 | 纯前端还原度差、排版易崩；业界无实用编辑方案 |
| docx「编辑后原样存回」 | 等价于在 Web 内自造分页排版引擎，目标本身不成立 |
| 让 TipTap 承担版式还原 | 流式文档模型 vs 分页文档模型，模型层不匹配 |
