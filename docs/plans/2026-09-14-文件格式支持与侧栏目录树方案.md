### 1.5 依赖现状（关键：已装但未声明）

已装于**根** `package.json`：`docx` ^9.6.1（生成）、`mammoth` ^1.12.0（docx 解析）、`jszip` ^3.10.1、`pdfjs-dist` ^5.7.284、`turndown` ^7.2.4。
**`apps/tauri/package.json` 未声明它们**（靠根 hoist 生效）—— 隐性契约，本方案顺手补齐。

已装但用途受限：

- `apps/tauri/src/composables/useFileExtract.ts` —— 用 mammoth（`:36-53`）与 pdfjs（`:56-90`）**只提取纯文本给 Agent 当上下文，不做渲染**；pdfjs 已 Worker 化（`:62-67`，注释记录了「`workerSrc=''` 会回退主线程同步解析、大 PDF 卡顿」这个已踩过的坑）；入参是 `File` 对象，接入 FilePreview 需从 base64 转 ArrayBuffer。
- `sprouts/official/manuscript/composables/useManuscriptExport.ts:41-67` —— **已能生成 docx**，但实现是 `stripHTML`（`:4-8`）后逐行成段，**丢掉标题层级 / 列表 / 加粗**。

### 1.6 关键架构事实：「项目 = 目录」

`space/workspace.ts` 定义三层语义（`:42-60` `resolveWorkspaceDir`、`:70-83` `resolveEntityDataDir`）：

- **普通项目**：`dirPath` 既是 Agent 工作区，也是实体存储父目录 → 实体落 `{dirPath}/entities`（`FileStorageBackend` 落 JSON 文件）
- **默认项目例外**：Agent 工作区 `~/.WorldSea/agent`，实体 `~/.WorldSea/worlddata`

→ **推论：笔记本的「笔记」本来就已经是磁盘上的真实文件**，只是位于受管理的 `entities/` 子目录 + 有索引。「真目录树」与「笔记」不是两套体系，是**同一棵树的两个部分**。这是三期方案的解题前提。

### 1.7 编辑器内核（TipTap）实际边界

`apps/tauri/package.json:45-49` 装了 `@tiptap/core` / `extension-mention` / `starter-kit` / `suggestion` / `vue-3`。
`useNoteEditor.ts` 实际启用：`StarterKit + Mention + SlashCommandExtension` —— **一个格式扩展都没装**（无 Table / Image / TaskList / CodeBlock）。

能力边界分三层：

| 层 | 结论 |
|---|---|
| 段落、标题、列表、引用、加粗、行内代码 | **够用**，`StarterKit` 已覆盖 |
| 表格、图片、任务列表、代码块 | **加官方扩展即可**（`@tiptap/extension-table` 等），非架构问题 |
| 分页（页边距 / 页眉页脚 / 分页符 / 页码 / 浮动对象 / 公式） | **根本不够**。TipTap 是流式文档模型，docx 是分页文档模型 |

**由此确立产品形态原则：预览走渲染器（只读、追保真）；编辑走 TipTap（内容编辑、导出而非存回）。两条路不混。**

## 四、三期 · 侧栏并列双 tab（2026-09-14 施工完成）

### 4.1 做法

笔记本（以及后续其他芽）侧栏顶部加「笔记 / 文件」切换：

- **笔记侧**：现有 `FolderTree`（虚拟文件夹，localStorage）不动
- **文件侧**：**直接复用 `FileTreeBrowser`**（`compact` + `rootPath`），零新组件

零数据迁移、可逆、当轮可验收。**已落地**（`NotebookView.vue`）：tab 状态全局 localStorage 持久化；`filesRoot = resolveEntityDataDir()`（普通项目 = dirPath，默认项目 = worlddata，与工作台实体同源）。

### 4.2 根语义

**已拍板**：项目目录 `{dirPath}` + 对 `entities/` 等内部目录做视觉弱化（灰化），既不阉割能力也不误导。**已落地**：`FileTreeBrowser.flatNodes` 对 root 下第一级 `entities` 标记 `muted`（opacity 0.55）；`.trash` 目录从树中**隐藏**（有独立回收站视图，双入口只会造成混乱 —— 实现时对「弱化」的边界补充：弱化针对 entities，`.trash` 走隐藏）。

### 4.3 前提：删除可逆化（已落地）

原拍板：**复用既有 `trashStore` 软删除**。**实现层修正（2026-09-14 实读 `trashStore.ts`）**：其 `TrashItem.data` 是 `Entity | Relation` 且存 localStorage，硬塞文件记录会污染类型 —— 改为「**磁盘即真相**」的专用实现（同语义、不同载体）：

**一期渲染器的两处关键取证**

1. **SheetJS 对无法识别的内容不抛错，会静默回落为 CSV/文本解析** —— 实测 8 字节垃圾 / 纯文本 / 空字节 / HTML 表格都会返回一张名为 `Sheet1` 的「表」（只有 zip 结构损坏才抛 `Unsupported ZIP file`）。若不设门槛，损坏文件或扩展名与内容不符的文本会被渲染成**看起来正常**的表。故 `XlsxPreview` 加 **ZIP 文件头门槛**（`PK\x03\x04`，OOXML 规范保证），并给加密文件/损坏文件明确文案。
2. **`.xls` 本轮不接** —— 该扩展名在实际数据里常是「HTML 表格改名」，SheetJS 对其宽容解析，与上一条「垃圾内容也被当成表」是同一个口子，无法用文件头确定性区分。故 `.xls` 留在 `BINARY_EXT`（诚实提示不可预览），待后续按 HTML/CFB 分支单独接。
