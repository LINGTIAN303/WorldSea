# P1-e：卸载二次确认（2026-11-04）

> 交接文档 §4.4 列的第二项可选项，用户选择「处理剩下的可选项」。
> 起于 P1-b 遗留：「卸载是破坏性的，现在只靠菜单里显式点作确认」。

## 一、为什么只给卸载加确认

判据是**可逆性**，不是「操作重不重要」：

| 动作 | 可逆性 | 确认 |
|---|---|---|
| 停用 | 再启用即可复原 | **不加摩擦** |
| 卸载 | 包被 `pnpm remove` 真的移除，恢复要重新安装 | **必须确认** |

给可逆操作也弹确认框，只会训练用户习惯性点「是」。

## 二、实现

用 `tauri_plugin_dialog`（已在 `lib.rs` 注册，此前壳侧未用过）的原生模态框，
经 `show_message_dialog` 的回调 + `mpsc` 通道拿结果：

| 要点 | 做法 |
|---|---|
| 按钮文言 | `OkCancelCustom("卸载", "取消")`——动词明确，不写「确定」 |
| 正文 | 带上包名 + 明说「会真的卸载（pnpm remove），需要重新安装才能恢复」+ 指路「只想不加载请用停用」 |
| 拿不到结果时 | **按取消处理**（超时 300s 或通道断开），绝不默认执行破坏性动作 |
| 执行线程 | 仍在后台线程，不阻塞菜单事件循环 |

配套把「取线索 + 定位包」抽成 `resolve_target()`（确认框需要先知道包名才能写清正文），
处置动作本身留在 `run_remediation()`。

**`needs_confirmation()` 落在枚举上**：这条差异是 `Remediation` 的语义，不是调用点的
临时判断。测试 `only_the_irreversible_action_asks_for_confirmation` 钉住它，
将来若加第三个动作（如「忽略」），会先被迫回答「它要不要确认」。

## 三、验证

| 项 | 结果 |
|---|---|
| `cargo test --lib` | **188 passed**（+1） |
| `cargo check` | **零警告** |
| `pnpm gate` | 4 项全过 |

**过程中的一处自我纠正**：首版 `Target` 结构里带了 `suspect` 字段，编译报
`field 'suspect' is never read`。处置只需要包名，缓存整条线索会让「谁在用哪个字段」
变模糊——删掉该字段而非加 `#[allow]`。

## 四、真机走查清单（用户手测）

| # | 操作 | 预期 |
|---|---|---|
| 1 | 崩溃线索存在时，菜单点「**停用**…后重启」 | **不弹任何对话框**，直接停用 → 通知 → 重启 |
| 2 | 崩溃线索存在时，菜单点「**卸载**…后重启」 | 弹出原生确认框：标题「确认卸载插件？」、正文含包名与「会真的卸载」、按钮为「卸载」/「取消」 |
| 3 | 第 2 步点「取消」 | 无任何变化；系统通知「已取消——未卸载 X」；插件仍在（可再启用） |
| 4 | 第 2 步点「卸载」 | 通知「已卸载外部插件 X」→ 自动重启；包从 `profiles/web/package.json` 的 `dependencies` 消失 |
| 5 | 崩溃线索指向官方插件时点任一处置项 | 弹通知「在外部插件里找不到 …（它可能是官方内置插件）」；**卸载也不该弹确认框**（定位阶段就失败了） |

第 1、5 项是「不加多余摩擦」的验收点；第 3 项是「拿不到确认就不动手」的验收点。

## 五、遗留

- **二次确认只覆盖卸载**：若将来加「批量处置」或「重置 profile」这类更重动作，
  应复用 `needs_confirmation()` 的判据（可逆性），而不是各写各的。
- **确认框是原生模态**：它开着时主窗口不可交互。这是有意的——破坏性动作期间
  不应允许用户在别处继续操作。
