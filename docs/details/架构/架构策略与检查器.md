# 架构策略与检查器

> status: **现行**（ZCode 能力内化 · P 线 P1-P3 + 余项，2026-09-21 落地）
> 依据：[03-首批批次计划](../../plans/已完成/2026-09-21-ZCode能力内化方向探究/03-首批批次计划-工程机器与会话权限.md)（P 线）；参照 ZCode `architecture-policy.yaml` + `architecture:check/context` 机制
> 面向：本项目全部代码改动（含 Agent 会话内改动）

---

## 一、是什么

| 件 | 路径 | 作用 |
|---|---|---|
| 架构策略 | `architecture-policy.json`（仓库根） | 模块登记（roots / manifest / requires 白名单——**Rust 与 TS 双栈**）；全局上限（400 行/文件，tests·spec 覆盖 1200） |
| 检查器 | `scripts/architecture/check.mjs` | **五类检查**（模块登记 / 文件规模 / Rust 依赖边 / TS 依赖边 / TS 包级环）+ `--changed` / `--update-baseline` / `--self-test`（10 例夹具） |
| 存量基线 | `architecture-baseline.json`（仓库根） | 超限文件行数冻结（只禁增长）+ 既有违规豁免（当前 8 处 TS 包级环） |
| 阅读包 | `scripts/architecture/context.mjs` | 按模块生成「文件清单 / 公开契约面 / 依赖 / 测试 / 文档指针」；落盘版在 `docs/reading-packs/` |

## 二、命令

```bash
pnpm arch:check                  # 全量检查（退出码 0=通过 / 1=有违规）
pnpm arch:check -- --changed     # 只查变更文件（新增/修改），其余检查全量
pnpm arch:check -- --self-test   # 夹具反证（10 例，不触碰本仓）
pnpm arch:context <module-id>            # 阅读包 → stdout
pnpm arch:context <module-id> --write    # 落盘 docs/reading-packs/<id>.md
```

## 三、三条治理规则（**流程约束**）

1. **改跨包/跨 crate 边界前**：先跑 `pnpm arch:check`，再 `pnpm arch:context <module-id>` 读目标模块（阅读包不是可选材料——领域问题先读包，不扒源码代偿）。
2. **新增模块 / 新增跨模块依赖（Rust 或 TS）**：先在 `architecture-policy.json` 登记（新模块登记 roots+manifest；新依赖边登记进 `requires`）——**未登记即检查报红**，登记本身即一次「有意识的决策」。
3. **行为变更先写/更新计划文档或 spec**：与既有计划文档惯例一致（`docs/plans/`），改完必跑 `pnpm arch:check -- --changed`。

## 四、检查项与处置

| 检查 | 规则 | 处置 |
|---|---|---|
| `registry` | 顶层模块目录（crates/\*、crates/vendor/\*、packages/\*、apps/\*、worldsea-core、tactical-engine）必须已登记；登记的 roots/manifest 必须存在 | 未登记 → 去 policy 登记；登记失效 → 修正或注销 |
| `file-size` | 新建文件 ≤ 上限（400；tests/spec 1200）；存量超限文件**只禁增长**（按基线冻结行数） | 超限 → 拆分；确需例外 → 走 §五 基线更新流程 |
| `rust-edge` | 模块的 path 依赖必须在 `requires` 白名单内；指向未登记目录即红 | 新增依赖 → policy 登记；跨层依赖 → 先评审（单向依赖原则） |
| `ts-edge` | TS 跨包依赖（`@worldsea/*` 与跨包相对导入）必须在 `requires` 白名单内（40 条现存边已登记） | 同 rust-edge：新增依赖先登记 |
| `ts-cycle` | TS 包级依赖不得成环（eslint 不管这个） | 拆环；短期无法拆 → 登记豁免（附理由），并计入挂账 |

## 五、基线维护与阈值

- **基线只冻结存量**：`--update-baseline` 会**重写**基线（files = 当前全部超限文件行数；other = 当前全部既有违规）。**基线上涨 = 债务上涨**——每次更新前先看 diff，确认新增豁免逐条有理由。
- 新增违规**不会**被自动豁免：不在基线内即报红。
- 存量文件**不得增长**：冻结行数 +1 即红（拆分或显式更新基线并在提交信息说明）。
- **阈值复核（2026-09-21 完成）**：实测分布——扫描 1555 个文件，>400 行 **218 个（≈14%**；>800 行 78 / >1500 行 22），集中在大头 tauri-app 64 / agent-kernel 23 / agent-runtime-ts 17 / agent-commands 15 / worldsea-core 14 / vendor 21；覆盖档 1200 使多数测试文件免触线。**结论：维持 400/1200**（存量冻结兜底；若新增文件频繁触线再调，调整须同步本文件）。
