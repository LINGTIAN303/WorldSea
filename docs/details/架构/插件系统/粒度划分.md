# 粒度划分

> 本文是**结论层**：41 个插件的大小分布、该拆还是该合、判据是什么、覆盖度如何。
> 完整推导与逐插件明细见 [计划文档](../../../plans/2026-11-13-产品域插件粒度与一切皆插件.md)；与 dsh 侧的对照见该文档 §五。
> 数字口径：`apps/tauri/src/world/plugins/` 下 ts+vue，排除 `*.spec.ts` 与 `__tests__/`，按 `Get-Content | Measure-Object -Line`（不含空行）计。

## 一、一句话结论

**产品域的插件粒度不是按「功能」划的，是按「侧栏有没有入口」划的。**

`kind: 'sprout' | 'utility'` 这一个字段决定全部 41 个插件的形态，而它只回答「贡献视图」还是「贡献 overlay」——不回答任何关于职责边界的问题。结果是 31 个 sprout 严格等粒（各 1 个视图），10 个 utility 内部粒度相差 190 倍（`settings` 3,602 行 vs `search` 19 行）。

## 二、粒度分布：双峰极端

| 行数区间 | 插件数 | 合计行数 | 占比 |
|---|---:|---:|---:|
| ≥ 3000 | 8 | 44,737 | **71.0%** |
| 1000–2999 | 6 | 8,556 | 13.6% |
| 500–999 | 11 | 7,565 | 12.0% |
| < 500 | 16 | 2,155 | 3.4% |
| **合计** | **41** | **63,013** | 100% |

前 5 名占 **53.6%**：`outline` 12,315 · `timeline` 8,282 · `notebook` 5,066 · `tactical-board` 4,776 · `manuscript` 4,083。

对照 dsh 侧（373 个叶包）：中位 652 行、p25=257、p75=1413、p90=3274，主峰在 500–1000 行。

**产品域缺的正是「1000–3000 行的中段」**——要么 5 个巨兽，要么 16 个 <500 行的小件。这是分布问题，不是数量问题。

## 三、六贡献位的覆盖度

| 贡献位 | 方法 | 用量 | 覆盖度 |
|---|---|---|---:|
| 视图 | `registerView` | 31 个插件各 1 个 | 31/31 sprout |
| 覆盖层 | `registerOverlay` | 10 个插件共 13 个 | 10/10 utility |
| 实体类型 | `registerEntityV2` | 23 个插件共 25 个类型 | 23/41 |
| 关系类型 | `registerRelationV2` | **0 个插件** | **0/41** |
| Facet | `registerFacet` | 2 个插件（`weapons` 1 个 · `apparel` 1 个） | **2/41** |
| 表现形式 | `registerForm` | 1 个插件（`outline`，11 种） | **1/41** |
| （跨面出口）能力 | `capabilities.register` | 1 个插件（`mindmap`，5 条） | **1/41** |

**四个贡献位是空转的。** 这是本次分析最重要的结构性发现：

- **关系类型贡献位 0 使用**：119 条关系定义全在 `packages/entity-core/src/relations/`，分 5 个文件（`index` 102 / `sproutTabs` 7 / `creature` 4 / `faith` 3 / `outlineLateral` 3）。后四个文件的注释都写着「单独文件注册，避免膨胀已冻结的 `relations/index.ts`」——这是**集中登记与插件自治之间的妥协产物**，方向对但没走完。
- **Facet 曾是误用**：`weapons` / `apparel` / `items` 是 item 实体的三个 Facet 视图，正确做法是三个插件各自注册自己的 Facet，而原先只有 `items` 顺手注册了 2 个。**2026-11-17 已归位**——`weapon` 归 `weapons`、`apparel` 归 `apparel`，`items` 只保留「item 实体挂载这两个 Facet」的声明（挂载与定义归属是两件事）。
- **表现形式刚提升**：`outline` 早在 2026-09 就实现了完整插件形态（id / 幂等 / 可反注册 / 11 种注册），但它是私有的——不随启停、外界不可见。2026-11-13 提升为平台第六贡献位。
- **能力只有 1 个用户**，且调用端直到 2026-11-13 才接通（见 [机制/能力桥](../机制/能力桥.md)）。

## 四、拆合判据：只有两条

这是本文最该记住的部分。判据与 dsh 一致：

1. **有没有第二个消费者 / 提供者？** 没有第二份实现或第二个消费方，就没有拆的理由。
2. **卸载语义是否成立？** 拆出来的东西独立卸载后，系统是否仍自洽？

**三类弱信号不能单独支撑拆合决策**：① 文件行数接近 ② 名字相似 ③ 存在双实现。2026-11-13 的初版判断正是栽在这三类信号上——5 项拆合判断撤回 4 项。

### 已撤回的四项（附实测事实）

| 原判断 | 实测事实 | 结论 |
|---|---|---|
| 4 个树视图重复 968 行，可抽公共件 | `packages/canvas-engine/src/useTreeCanvas.ts`（457 行）早已是共用内核；四份文件只做业务绘制样式（关系统→颜色映射、节点内容、边转换），是必要差异 | **撤回** |
| 历法被 `culture` 复用 → 有第二消费者 → 拆 `timeline-calendar` | `culture` 的 `FestivalCalendarView` 用自己的 composable，**零依赖** timeline 历法；历法 50 处引用全在 timeline 内部 | **撤回** |
| 两套模板系统并存 → 合为一套 | A = 用户模板库（存/取实体配置，pinia）；B = 项目脚手架（`WorldTemplate` 一键建 N 实体 + M 关系，10 个内置模板）。**不同功能** | **撤回** |
| `manuscript` 拆出 books / phone-preview；`tactical-board` 拆出引擎适配 | `book` 是 `manuscript` 的容器（同一条创作链的父子层），无外部消费者；wasm + `TacticalEngineJS` 是**降级对**（wasm 优先 / JS 兜底，同一接口），不是可替换能力 | **撤回** |

### 唯一成立的一项：提升而非拆分

`outline` 的 `forms/`（3,984 行，11 种表现形式）自带私有插件注册表，形态已正确——但「拆成独立插件」会引入一个新的插件 id 与一套启停语义，而真正的诉求是「其他插件也能贡献表现形式」。所以正确动作是**把注册表提升为平台贡献位**，插件数不变。

## 五、为什么不按 `domain` 划

`domain` 与「功能组」是两套正交轴，三个反例：

- `outline` 的 domain 是 `narrative`，但实现是画布（与 `drawing` 的 `tool` 同形态）
- `field-matrix` / `codex` / `gallery` 都是 `tool`，但它们是只读观测器，与 `mindmap` / `custom`（同为 `tool`）性质不同
- `narrative` 4 个插件 24,999 行（35.9%），`society` + `knowledge` + `geo` + `goods` 14 个插件仅 6,141 行（8.8%）

**按 domain 重划会把同类工具拆散、把不同类工具归一起。** `domain` 是内容分类轴，不该承载代码量均衡。

采用的原则（三条，按优先级）：

1. **一个插件 = 一个变更原因**
2. **单实现不拆**——防止过度拆分的关键
3. **粒度目标是 500–1500 行的中段**（dsh 实测 p50=652 / p75=1413）

## 八、「一切皆插件」的准确边界

判据与 dsh 一致：**贡献位内的才是插件，贡献位外的是平台地基。**

### 天然不是插件的（`Context` 的 provide）

| 机制 | 为什么不是插件 |
|---|---|
| 存储后端（`StorageBackend` / `FileStorageBackend`） | 单例、进程级、被所有插件依赖；「实现切换」是环境判定（Tauri vs 浏览器）而非用户选择 |
| schema 注册表（四套） | 注册是累积的、查询是全局的；卸载不注销是刻意设计 |
| 事件总线（`eventBus`） | 无状态中继，不需要生命周期 |
| 快捷键注册表（`useShortcuts`） | 全局键位冲突检测天然需要全集 |
| 主题令牌 / 样式层（`theme.css` / `style-kit`） | CSS 变量的层叠顺序是全局一维的 |
| 项目 / 工作区模型 | 真源在 dsh，产品域只是镜像 |
| Tauri 命令面 + ACL | 进程边界，由 Rust 侧静态判定 |
| fs 监听（`useFsWatcher`） | 后端一个 watcher、前端引用计数；多实例会重复 emit |

共同点：**全局唯一 + 跨插件共享 + 生命周期长于任何插件**。

### 位置尴尬的（现在是插件，但形状可疑）

| 插件 | 问题 |
|---|---|
| `settings` | 平台管理面而非功能贡献。做成插件后「设置」可被卸载 = 用户失去所有设置入口。`utility` 常驻语义救了它，但本质是用常驻规避「卸载语义不成立」 |
| `custom` | 视图容器，必须直连 `pluginStore.getView(id).component`——组件引用不跨服务边界，这是服务目录边界的真实反例 |
| `field-matrix` / `codex` / `gallery` | 不贡献实体类型（`entityTypes: []`），是只读分析型芽；形状正确但语义窄 |
| `orchestration` | 注册 `pipeline` 实体类型 + 3 个模板，但执行端（Rust Workflow 引擎）已随 E8 退场，字段可填无消费者 |

## 九、判据的通用形式

> **「一切皆插件」在产品域成立的范围 = 贡献位。**
> 凡是**不在这六个贡献位里**的机制——存储、注册表、事件、键位、令牌、项目模型、命令 ACL、文件监听——都不是插件，是 `Context` 的 provide。

当前代码已经按这条线长成了：`world/services.ts` 的 13 项服务全在 `context.provide`（`tree.ts:172-175`），41 个插件全部通过 `api.*` 注册。这条线是干净的。真正没走完的是**贡献位的覆盖不全**——`relationType` 0 个、`facet` 2 个（已归位）、`form` 1 个、`capability` 1 个。
