## 三、四条职责边界

| 边界 | 判据 |
|---|---|
| `ui/` vs `components/` | `ui/` 是**唯一实例的壳件**（Shell / TitleBar / Sidebar / 首页 / Splash）；`components/` 是**可多处实例化的通用件**（文件选择器、预览器、Tui 基础件） |
| `shell/` vs `composables/` | `shell/` 只放**与壳进程对接**的三件；`composables/` 放跑在页面内但跨视图的编排。这个分界靠文件名能看出来，不是目录约定文档定义的 |
| `core/` vs `composables/` | `core/` 只做 invoke 与 WASM 的封装，不含业务判断；有业务判断的进 `composables/` |
| `world/` vs 其余 | `world/` 内的一切都受插件树管理（可启停、可卸载）；`world/` 外的代码是树的地基，不随插件变化 |

## 四、几个值得知道的历史遗留

| 现象 | 说明 |
|---|---|
| `components/ui/Tui*.vue`（10 个基础件）与 `ui-kit` 的 `Ws*.vue` 并存 | 双份基础件，无迁移计划记录。新增组件应优先用 `ui-kit` |
| `stores/` 里 4 个是 2–7 行的 re-export 壳 | 僵尸层，可直接 import `entity-core`。保留是为了让旧的相对路径 import 不断 |
| 三套 `useTheme` 并存 | `components/ui/useTheme.ts`（应用壳三态）· `entity-core/composables/useTheme.ts`（强调色轴）· `composables/useTheme.ts`（4 行 re-export）。前两者职责不同（底色 vs 强调色），是设计而非重复，但**名字相同**极易误用——`App.vue` 同时 import 两者并各自改名 |
| `entity/` 只有 3 个文件 | 它只收「跨插件共享的实体关联算法」；单插件用的算法留插件内 |

## 五、新增代码该放哪

| 你要加的东西 | 放哪 |
|---|---|
| 一个新的侧栏功能 | `world/plugins/<新插件>/`，见 [插件协议](../../架构/插件系统/插件协议.md) |
| 一个跨视图复用的 UI 件 | `packages/ui-kit`（不是 `apps/tauri/src/components/`） |
| 一个只服务某个视图的组件 | 该插件目录内 |
| 一个跨视图的应用级编排 | `composables/` |
| 一次新的 Tauri 命令调用 | 经 `core/api/` 封装，不直接 `invoke` |
| 一个全局样式令牌 | `styles/theme.css`（唯一真源） |
