# 项目详情

> 本目录回答「系统是怎么组织的」。计划（要做什么）在 [plans](../plans/)，索引（有哪些文档）在 [index](../index/README.md)。
> 三层按**抽象层次**分，不按主题分：越往下越靠近代码。

## 三层分工

| 层 | 目录 | 回答什么 | 读者何时来 |
|---|---|---|---|
| 系统级 | [架构](架构/README.md) | 系统由哪些部分组成、它们怎么配合、边界在哪 | 接手项目、判断改动影响面 |
| 实现级 | [前后端](前后端/README.md) | 前端与后端各自怎么分工、目录与状态怎么划 | 动手改代码前定位落点 |
| 细节级 | [注释](注释/README.md) | 某个文件为什么这样写、踩过什么坑 | 改这个文件时 |

## 另有两类目录

| 目录 | 性质 | 说明 |
|---|---|---|
| [端分离](端分离/README.md) | 专题 | Web/CLI/Tauri 三端分离的成套探究，已收口为历史记录 |
| [截图](截图/) | 素材 | 证据类附件，不承载结论 |
| [memory-archive](memory-archive/README.md) | 专题 | 记忆归档线演进记录，该线已退场 |

## 阅读顺序建议

1. 先读 [架构/总览](架构/总览.md) —— 一页看清三层形态与顶层目录
2. 再按问题进 [架构](架构/README.md) 的对应分组
3. 要改代码时进 [前后端](前后端/README.md)
4. 要改某个具体文件时查 [注释](注释/README.md)

## 写作口径

- 结论先行，数字必须可复现（给出脚本或命令，不写「大约」）
- 文档与代码冲突时**以代码为准**，并在文档里标出过时处，不留两套说法
- 新增专题目录须带 `README.md` 作入口；层次层（架构 / 前后端 / 注释）按层聚合登记，不混入专题
