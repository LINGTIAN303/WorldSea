# 实体详情表单（地基批：字段控件归一 + 布局层 + 编辑单轨）

> 代码内简要注释见 `packages/plugin-sdk/src/detail/*.ts|vue`。本文承载「为什么」。
> 批次计划与裁定见 [实体详情表单地基与形态批计划](../../../../plans/2026-10-02-实体详情表单地基与形态批计划.md)。

status: 已完成（2026-10-02 批次 1a 地基段；弹窗与批量编辑并轨、DetailField 退役、设置面板 Tab 属 1a 余下段）

## 一、这一层为什么长这样

详情/编辑此前是**四套字段控件 + 两条写路径**：抽屉 `DetailField.vue`、弹窗 `EntityFormModal.vue` 内联分支、
`BatchEditModal.vue` 全原生 input、以及 `ui-kit/entity/InfoPanel.vue`（610 行死面——
`provideGlobalSelection()` 全仓零调用，挂在 `Shell.vue` 上但永不显示）。
新增一个字段类型要改四处，且三处的 `fieldType` 拼法各不相同。

地基段的做法不是「把四处改得一样」，而是**取消「四处」这个前提**：
类型归一 → 控件映射 → 单一控件件 → 单一内容件 → 载体只是外壳。

## 二、命名漂移在唯一一处吸收

`detail/fieldType.ts` 的 `normalizeFieldType()` 是**全仓唯一**把 `entity-ref` / `entity-refs` /
`multi-select` / `text-long` / `richtext` 折成规范名的地方；Rust 三处枚举
（`schema/types.rs` camelCase、`retrofit/intent.rs` 的 `richText`、`validate/entity.rs` 认 `"multi-select"`）
**不改**——改协议层不如在消费端做一次显式折叠，代价是一个别名表。

未识别的类型归一为 **`unknown` 而不是静默转 `text`**。这条是硬要求：静默转正是原缺陷的成因——
`timeline` 的 `parentId`（`fieldType: 'entityRef'`）落进 `DetailField.vue` 的兜底 `<input>`，
于是抽屉里**显示和编辑的都是裸实体 ID**；`plants` 的 `usage`（`multi-select`）与 `tags` 同理退化成纯文本。
`unknown` 在控件层渲染成只读文本 + 一枚「未支持类型」角标，让问题**可见**而不是被抹平。

守卫：`CONTROL_SPEC` 的键集合必须 === `NORMALIZED_FIELD_TYPES`（新增类型忘了配控件即测试报红）。

## 三、控件映射是数据，不是分支

`detail/fieldControlMap.ts` 把「类型 → 用哪种控件 / 是否整行 / 是否可写」摊成一张表，
`FieldControl.vue` 只按 `kind` 渲染。这样做的理由是：分支散在模板里就是「第四套实现」的诞生机制——
每处 `v-else-if` 的集合都不一样，漂移是必然。表是数据，能被测试穷举，也能被设置面板反向渲染。

`formula` 标为 `editable: false`：值由公式引擎算出，给输入框等于让用户写进一个下次重算就被覆盖的字段。

## 四、顶层字段的真值位置（幽灵行的根因）

`identifiable` trait 声明 `title` / `description` 两个 schema 字段，`taggable` 声明 `tags`，`visual` 声明 `coverImage`；
但 `Entity` 的这几个真值在**顶层**（`name` / `description` / `tags` / `coverImage` / `coverPosition` / `coverZoom` / `avatar`），
不在 `properties`。此前详情一律按 `properties[key]` 取值，于是**每个实体的详情都白挂 2-3 条恒为「—」的字段行**。

`detail/fieldAccessor.ts` 做唯一定位（`readFieldValue` / `buildFieldPatch`）；
`detail/draftKeys.ts` 再对接 `useEntityEdit` 的 `_name` / `_description` 草稿方言——
方言不统一掉是因为时间线自有详情直接吃 `editForm._name`（改造它属另一批面）。

`splitDraft()` 有一条要紧规则：`properties` 是**整体替换**语义，保存必须带上新旧合并后的全量，
否则会抹掉未编辑的字段（同类事故在大纲芽以 `loadByType` 收窄的形式出现过）。

## 五、布局层：三级合并取「整表替换」而非深合并

`detail/detailLayout.ts` 的合并顺序 = 芽声明默认 ⊕ 用户按实体类型覆写 ⊕ 抽屉即时态。
每级给的是**整个 order / 整个 hidden / 整个 groups**，缺省即继承上一级。

理由：用户覆写的是「这一类实体的详情长什么样」，不是「在芽默认第 3 位插一个字段」。
深合并会让三层交织到无法解释，设置面板也无法如实回显当前状态。

两条兜底比合并规则更重要：
- **缺失字段追加在末尾**——芽后加的字段不会被用户旧覆写吞掉（这是覆写机制最常见的坑）；
- **失效 key 剔除**——芽改名或删字段后，覆写里的幽灵 key 不炸也不占位。

未分组的字段自动归入「其它」组，所以芽只声明分组时不会漏字段。

## 六、持久化分键，且不进实体

`worldsea_detail_layouts`（`stores/detailLayoutStore.ts`）与弹窗字段预设的 `worldsea_field_orders` **分键**：
后者语义是「一类型多套命名预设」，前者是「详情长什么样」，混用会互相搅动。

**形态与布局配置一律不落实体 `properties`**。此前 `useEntityEdit` 把用户自定义字段以
`__customFieldDefs` 的 JSON 字符串塞进每个实体的 `properties`——字段定义随实体重复存、
无法按类型一致管理、还会跟着 .ws 导出包外泄。现改走**类型级 `fieldRegistry`**
（`addUserField` / `removeField` / `setOrder`，落 `worldsea_field_registry`，同类型所有实体共享）。
`splitDraft` 会丢弃 `_` 前缀内部键，`__customFieldDefs` 因此不再落库。

## 七、编辑态单轨

抽屉只有一条写路径：`useEntityEdit` 的 `editForm` 草稿 + `saveEdit` 一次提交。
`✏️ 编辑`＝整面板进草稿态；**双击字段＝进入同一草稿态并把焦点给该字段**（不再是「单字段独立写库」的第二条路）。
弹窗 `EntityFormModal` 归为**新建专用**（含模板预填），编辑存量实体的入口只留在抽屉。

顺带修掉一处存量缺陷：`openFormWithDefaults(defaults)` 造的预填实体 `id` 是空串，
而 `onFormSave` 原按「`editingEntity` 是否非空」判编辑——空 id 被送进更新分支去 `entityStore.update('')`，
既不记 undo 也命不中任何实体 ⇒ **表单关掉但实体根本不落地、连「已创建」提示都不弹**（唯一调用者是角色的模板创建）。
判据改为「有 id 才算编辑」，并由 `components/__tests__/genericEntityViewSaveMode.spec.ts` 锁住
（反证：判据改回非空判定 → 第 1 例报红 `update` 被调用）。

## 八、详情段外移与两级形态

`detail/EntityDetailForm.vue` 是**载体无关**的详情内容件：只认 `entity / fields / layout / editing / draft`，
不认自己装在抽屉还是页面里。这是为「L1 载体形态（抽屉 / 栏式整页 / 居中弹层 / 沉浸页 / 浮层小窗）」与
「L2 内容形态（分组 / 表格 / 段落 / 卡片摘要 / 时间轴）」预留的同一接缝——两级各自可插，互不牵动。

`EntityDetailPanel.vue` 因此退回薄载体（fixed 抽屉 + 拖宽 + tab 条 + 插槽转发）。
GEV 侧详情段的字段来源也从旧 `entitySchemaRegistry` 换成 `fieldRegistry.getFields()`
——**抽屉这才开始吃字段顺序**（此前只有弹窗吃），且用户加的字段自动出现在详情里。

## 九、已知边界（本批留白，勿当已完成）

- **`ws-navigate` 的参数语义有歧义**：`Shell.vue` 的 handler 把 `detail.view` 当**实体类型**用
  （查 schema → 取 pluginId → 找该 plugin 的视图），而图谱传的是**视图 id**（`'characters'`），
  九个子视图传的是 `detail.entityType`（handler 根本不读）。结果是三类调用者**都没能切到目标视图**，
  只有 `selectEntity` 生效。`EntityRefControl` 的跳转按 handler 现行读法发 `{ view: 实体类型, entityId, entityType }`
  以便今天可用；这条接缝本身待单独裁定（未擅动，属既有缺陷而非本批引入）。
- `DetailField.vue` 仍在（时间线自有详情直挂 6 处引用），未随批退役。
- `EntityFormModal` / `BatchEditModal` 的字段控件并轨未做：弹窗的 `entityRef` 存的是**名称串**、
  抽屉侧存的是 **id**，两者写语义不同，直接换控件会静默改保存行为——需先定 entityRef 的落库语义再并轨。
- 批量编辑的单条「编辑」仍走 `useDialog().prompt()` 逐条问名称/描述。
- 覆写 UI（设置面板「实体详情」Tab、L2 形态选择器）在批次 1b；1a 只交付读通与落盘。
