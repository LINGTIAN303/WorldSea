## 一、这批只做「编排」，不碰「载体」

两级形态模型里，本批是 **L2 内容形态**＝同一份字段数据在容器里怎么排（分组/表格/段落/摘要/时间轴）。
**L1 载体形态**＝详情装在哪种容器（右栏抽屉 → 栏式整页 / 居中弹层 / 沉浸页 / 浮层小窗）归批次 2。

两级都挂在 1a 抽出来的**载体无关内容件** `EntityDetailForm` 上，所以换编排不动容器、换容器不动编排。
这条界线是本批全部设计的前提——上一轮我曾把它理解反（把「形态种类」当成字段编排），据此把批次切成了 1a/1b/2 三段。

## 二、注册表：为什么在仓内注册、为什么只有一份默认值

范式沿用大纲白板的 `FormDefinition`（`apps/tauri/src/world/plugins/outline/board/forms/registry.ts`），
有意改掉两处：

1. **形态件在仓内注册，不开放给芽运行时注册**。芽能改的是 `detailLayout.contentForm` 这个 **id**，
   不是往详情面塞组件。否则「用户在设置里可选的形态」会变成「某个芽恰好注册出来的形态」，
   选择器的内容就不可预期了。（真要开放自注册，得先把图标/文案/配置项一并纳入契约，那是另一批的事。）
2. **只有 `configSchema`，没有并行的 `defaultConfig`**。大纲白板两份并存，迟早漂移；
   1a 的 fieldType 三套命名漂移就是同型事故。这里默认值由 `defaultContentConfig()` 从 schema 的
   `default` 派生，`resolveContentConfig(form, stored)` 只做「默认打底 + 存储覆盖 + 未定义键兜底」。

注册顺序即选择器顺序；`registerContentForm` 幂等（同 id 重复注册直接跳过，不覆盖）。

## 三、五种编排与它们的适用判定

| id | 名称 | kind | 吃什么 | 空态说实话 |
|---|---|---|---|---|
| `grouped` | 分组式 | **inline** | 芽声明的 `groups` + `order` | 「该实体没有可显示的字段」 |
| `table` | 表格式 | derived | 全部可见字段 → 字段/值两列（复用 `ui-kit/DataTable`） | 同上 |
| `narrative` | 段落式 | derived | 长文本族字段合并成篇，按空行切自然段 | 「没有长文本字段，换分组式或摘要式看更合适」 |
| `summary` | 摘要式 | derived | 短字段族压成「标签 值」属性牌 + 首段正文摘录 | 「还没有已填的短字段」+「另有 N 项属性未显示」 |
| `timeline` | 时间轴式 | derived | 时间族字段聚成一条轴 | 「没有日期字段，时间轴式对它没有意义」 |

**归类只有一处口径**（`formValues.ts` 的 `fieldFamily`）：`textarea`/`richtext` → 长文本；
`date` 类型**或约定 key**（`date`/`dateEnd`/`birthDate`/`deathDate`/`createdAt`）→ 时间；其余 → 短字段。
加「约定 key」这一路是因为 `datable`/`ageable` trait 给的日期在 schema 里是 `text`，
类型说明不了它是时间——不加这路，人物志的「生卒年」进不了时间轴。

## 四、派生型在编辑态回落分组式（写路径单轨不破）

1a 把编辑收敛成**一条行内单轨**（`useEntityEdit` 的草稿 + `saveEdit`）。若五种编排各自实现编辑，
等于把那条单轨又分叉成五条。所以 `kind` 就是这件事的闸门：

```ts
activeContentForm(form, editing)
// 未注册 id → grouped（芽写错 id 也得有东西渲染）
// editing && kind==='derived' → grouped
```

`EntityDetailForm` 分发时按这个函数选件，并在选择器下方如实说明「**×× 为只读呈现，编辑中暂用分组式**」。
注意高亮仍留在**用户选的形态**上（`layout.contentForm`），不是回落后的 `grouped`——否则用户会以为自己的选择被改掉了。

## 五、形态之间只差编排，不差控件与动作

`DetailFieldRow.vue`（标签 + 作用域「共享/仅本实体」+ 移除 × + `FieldControl`）是 1a 行渲染的原样外移，
五个形态共用。所以「表格式里不能改字段类型语义」「摘要式里字段可移除吗」这类问题不需要各形态再答一遍。
派生形态在编辑态不出现（见第四节），因此它们只用到只读分支；双击仍发 `enter-edit` 进编辑。

## 六、只读展示的口径（都不该是 1a 修过坑的复活路径）

`displayOf(field, value, nameOf?)` 是派生形态唯一的取文入口，三条特殊规则：

- **`entityRef` 解成实体名**：值存的是 id（裁定：entityRef 落库统一存 id），只读形态直接把 id 打上表格
  就是 1a 那个「裸实体 ID」缺陷的复活路径。解析注入在 `useFieldSource()`（唯一碰 `entityStore` 的一处，
  `formValues.ts` 保持纯函数），**解不出显示「引用已失效」而不是退回 ID**。
- **`image` 显示「已配图」**：路径串打在只读表格里是噪声，缩略图属载体职责（抽屉头部已有封面位）。
- **空值统一「—」**，且**摘要式滤掉空值牌**——一排「—」正是被点名要消灭的幽灵行；但不静默吞，
  末尾报「另有 N 项属性未显示」。

时间轴式**不按日期排序**，沿用用户排的字段序：`datable` 的日期常见「约 1420 年」这类非 ISO 串，
字典序会把它们排到错误位置还看起来很讲道理。

### 6.1 其余四个只读面：去语法留内容，不做真渲染

真渲染只给**段落式**（它存在的意义就是排版成篇）。分组式的行、表格式的值列、摘要式的牌与摘录、
时间轴式的节点要的是「一眼读得清这个字段是什么」，往里塞 `<h2>`/`<ul>` 只会把行高与牌的单行假定撑破。

所以这些面走 `fieldValue.stripMarkdownSyntax()`：`**粗**`→粗、`` `码` ``→码、`[名](链)`→名、
`![图](链)`→图、行首 `#`/`>` 去掉、行首 `- `/`* `/`+ ` 归成 `· `。接入点是**唯一一处**
`toDisplayText()`（分组式行、表格式值、摘要牌、时间轴节点、以及 `FieldControl` 的只读态都从它出），
摘要摘录另经 `narrativeSections(...).text` 走同一管道（先剥标签再去语法）。

三条边界，都是刻意的：

| 边界 | 为什么 |
|---|---|
| **编辑态不去语法**（走 `toInputText`，显示源文） | 清洗过的文本一旦回写就把用户的 markdown 标记吃掉了，不可逆 |
| **数字标号 `1.` 不动** | 它本来就可读，去掉反而丢信息 |
| **词内 `*` 与 `_` 不动**（`2 * 3`、`snake_case_id`、`C#`） | 成对强调要求内侧非空白；CommonMark 本身也不把词内下划线当强调 |

守卫在 `detail/__tests__/plainText.spec.ts`（13 例，一半是**不该动的别动**——把 `2 * 3` 啃掉比留星号更像 BUG）。
反证＝让 `stripMarkdownSyntax` 直接原样返回 → 5 例红。

### 6.2 段落式的正文渲染：复用主窗口同一 markdown 内核

`detail/richText.ts` 两条分支按**存储形态**分，不按字段类型表分：

| 存储 | 走法 | 为什么 |
|---|---|---|
| `textarea`/长文本（markdown 源或纯文本） | `renderFullMarkdown(text, null)` | marked 实例是 `{ gfm:true, breaks:true }`——**单换行也保留软断行**，正文里 `##`/`-`/`**` 变成结构而不是原样露出 |
| `richtext`（编辑器写出的 HTML） | `sanitizeMarkdownHtml(text)` 直渲 | 再过一遍 markdown 会把 `<p>` 里的 `*` 之类字符当语法误解析 |

两条**都过 DOMPurify**，所以不存在「裸 `v-html` 用户数据」的路径——这是这件事的全部要点，
守卫也就是 `richText.spec.ts` 里那组攻击载荷（`onerror` / `<script>` / `javascript:` / `<iframe>`）。

三个刻意的取舍：

- **import 走 `@worldsea/shared-ui/markdown/stream` 子路径**（为此在 shared-ui 的 exports 里加了一条），
  不是包根 `@worldsea/shared-ui/markdown`——包根会连带 `codeHighlight.ts`，把 Prism 核心 + 13 个语言组件
  一起拖进工作台首屏。
- **不 import 主窗口的 `markdown.css`**，段落式自己用 `:deep()` 补了十来行。那份是
  `.ws-agent-md`（Agent 气泡样式，含代码块外壳与 mention），详情面用不上，也不想让跨包 CSS 副作用扩散。
- **摘要式与表格式仍吃纯文本**（`narrativeSections` 同时返回 `raw` 与 `text`）：摘录与牌列要的是
  一行可截断的 plain，给它 HTML 反而要再剥一次。

## 七、配置与落盘

`DetailLayout` 多一个 `contentConfig: Record<string, unknown>`，与 `contentForm` 走同一套三级合并
（芽默认 ⊕ 用户按类型覆写 ⊕ 即时态，整表替换、后者赢），落在既有键 `worldsea_detail_layouts` 的
同一条记录里（不新增存储键）。切换形态**不清配置**：别的形态的键留在原地，本形态不消费它，切回来还在。
写入口 `useDetailLayout().setContentForm` / `setContentConfig`，本批只有前者被选择器调用（后者给 1b-2 的设置 Tab）。

内容件**不直写存储**：选择器只发 `change-form`，由载体侧（GEV）接线落盘——与 1a 的
「本件只发事件不直写」一致，批次 2 换载体时这条不用改。

### 芽声明这一层怎么接（`detailLayout` prop）

三级合并的「芽默认」原来没有入口，现补上：`GenericEntityView` 与 `SchemaRenderer` 各加一个
可选 `detailLayout?: LayoutSource` prop，GEV 把它作为 `useDetailLayout` 的第三个来源传进去。
schema 驱动的芽（走 `SchemaRenderer`）因此与直挂 GEV 的芽同一条路。

首批两枚样例（可复核、也可改）：

| 芽 | 声明 | 理由 |
|---|---|---|
| `characters`（CharacterList） | `contentForm: 'narrative'` | 角色详情以正文为主（描述/经历是长文本） |
| `items`（ItemView） | `contentForm: 'summary'` | 道具是短属性堆叠（类型/稀有度/材质…），一屏看全 |

声明常量放在各芽的模块作用域（`const DETAIL_LAYOUT: LayoutSource = {...}`），
**不要在模板里写对象字面量**——那会每次渲染换一次引用，把 `layout` 的 computed 白白搅动一遍。

守卫在 `components/__tests__/detailLayoutChannel.spec.ts`：四例分别锁「GEV 真的把声明传到了内容件的
`layout`」「用户覆写压得过芽声明」「SchemaRenderer 原样下传」「设置面写的覆写＝详情面读到的」。
反证＝摘掉 GEV 第三参 → 通道例红。

### 7.1 设置 ·「实体详情」Tab（批次 1b-2）

面板在 `apps/tauri/src/ui/settings/panels/DetailSettingsPanel.vue`，分类 id `detail`（Tab 栏第三项起）；
三张卡＝**内容形态** / **字段顺序与可见性** / **形态配置**。

四条落地约束：

1. **面板不自己拼合并**，一律走 `useDetailLayout(activeType, availableKeys)` 读与写。
   设置面与详情面因此共用同一条三级合并——若这里直接读 `store.overrides[type].contentForm ?? 'grouped'`，
   就会长出第二个「当前形态」的真值来源（1a 那四套字段控件正是这么长出来的）。
   守卫第 4 例锁的就是这条：`store.patch` 写的值，GEV 里的内容件必须读到同一个。
2. **实现放 app 侧而不是 ui-kit**：形态注册表在 plugin-sdk，而 `plugin-sdk → ui-kit` 已存在，
   面板若进 ui-kit 就成包间环（arch 门禁 `[ts-edge]` / 成环检查会点红）。
   基座类（`.set-card/.sc-head/.set-row/.set-chip/.set-toggle/.set-hint`）来自 `SettingsDialog`
   全局引入的 `ui-kit settings-panels.css`，app 侧面板直接可用。
3. **三契约齐守**：`search-query` prop + 每卡 `match(关键词)` 过滤 + `goToCard(i)` 暴露 +
   `@card-change` 上报左列高亮；`.sc-head` 的首个 `<span>` 是左列标题文本（第二个 span 放当前类型名，
   rail 不取它，卡面看得到）。**不发 `dirty`**——本面板每次操作即时落盘，`dirty` 在
   `SettingsDialog.close()` 里是「关窗后刷新视图」的信号，误发会触发无谓刷新。
4. **「恢复芽默认」只在确有覆写时出现**，且走 `useConfirm` 危险态；它清的是该类型整条覆写
   （形态 + 顺序 + 可见性 + 配置），与 `useDetailLayout.reset()` 同义。

配置卡是**按 `configSchema` 自动渲染**的（boolean→开关 / number→数字 / select→下拉），
新增形态或加一个配置项都不用改本面板——这条与 §二 的「默认值单源」是同一件事的两端。

布尔项翻的是**当前有效值**（`config[key] === false`），不是事件里 DOM 的 `checked`：
`:checked` 是单向绑定，DOM 态与存储态在程序化触发下会分家（这条是真机之外由测试抓到的，
`detailSettingsPanel.spec.ts` 的「摘要式按 configSchema 自动渲染」用例）。

可见性/顺序行只处理**类型级字段**：实体级 `properties.__fieldDefs` 的定义随实体走，
设置面没有「当前实体」，故不在这里出现（详情面里照常可加可转）。

### 7.2 命名预设与详情覆写的分轴（同日裁定）

两件事**不同轴**，别再互相搅动：

| 轴 | 存哪 | 管什么 | 编辑面 |
|---|---|---|---|
| 命名预设 | `worldsea_field_orders` | 一个类型的**字段基准序**（可多套命名档） | 弹窗只留**切换**；增删改在设置 Tab 第五卡 |
| 详情覆写 | `worldsea_detail_layouts` | **呈现层**：可见性 / 分组 / 内容形态 / 形态配置（+ 顺序作为基准序之上的局部覆写） | 设置 Tab 前四卡 + 抽屉里手选 |

**去掉的破坏**（原实现的真问题）：`loadPreset` 先 `fieldRegistry.resetToBuiltin(entityType)`
再只放回预设里存的字段快照 ⇒「存过预设之后新增的自定义字段」会在点「使用」时凭空消失；
而 registry 的字段集与顺序正是详情面可用字段的来源（1a 接的线），所以**弹窗里点一下会连带改掉详情的结构**。
反过来「按快照把字段补回来」也不成立——用户后来主动删掉的字段会被复活。两头都是意外，
所以口径收成一句话：**字段是类型级真值（`fieldRegistry`），预设只是一份命名的顺序档**。
`applyBaseOrder()` 的做法是：预设里已不存在的 key 跳过，registry 里预设没见过的新字段补在末尾。
（`PresetData.customFields` 保留键名只为读旧 localStorage 不炸，写入与消费都已停止。）

**收面**：原本三处都能改字段序（弹窗 preset-bar、ui-kit `LayoutManager`「布局管理」弹窗、设置 Tab），

- **种子必须剔掉合成的「其它」组**（`OTHER_GROUP.key === '__other'`）：拿解析结果直接当草稿，

## 十、L1 载体形态（批次 2 第一刀：注册表 + 栏式整页）

批次 2 做的是**容器**那一轴。这一刀只落两种载体：`drawer`（右栏抽屉，缺省）与 `column`（栏式整页），
其余三式（居中弹层 / 沉浸页 / 浮层小窗）等这一刀走查过再上——一次铺四种会同时改四种进出路径，
反证与走查面都太大。

### 10.1 契约：载体之间只差容器

`carriers.ts` 注册表与 L2 的 `contentForms.ts` 同构（仓内注册、幂等、缺省兜底），
区别只在注册的是**容器件**。两个容器必须逐一对齐属性、事件、槽名与暴露面，GEV 才敢用
一个 `<component :is>` 分发：

```
props  visible / entity / icon / title / subtitle / tabs / defaultTab / showEdit / editing / panelId / *Width
emits  close / edit / update:editing / tab-change
slots  header（scoped entity,editing）+ 按 tab.id 的动态槽 + default
expose switchTab / activeTab        // GEV 的快捷键切页要靠它
```

对齐不是靠自觉，而是靠**两处共用实现**兜住：标签页状态与拖宽逻辑在 `detail/useDetailChrome.ts`，
外壳样式（`.dp-header`/`.dp-tabs`/`.dp-content`/关闭与拖宽把手…）在 `detail/carrier-chrome.css`，
两载体各自带 `.dp-shell` 类吃这份全局规则（**必须挂前缀**：这是全局 CSS，不加前缀会染别处同名类）。
各自 scoped 里只留真正独有的部分——抽屉的 `position: fixed` + 遮罩 + 滑入动效，栏式的在流内宽度。
抽屉因此从 270 行降到 139 行。

> 为什么不容许两个容器各写一份：1a 之前「四套字段控件」就是四个容器各写一遍开始的。
> 契约一旦靠自觉，加第三种载体时就会长出第三种行为差异。

### 10.3 只有 split 型载体才动布局

.gev-root--split .entity-grid { min-width: 0; }              /* 否则网格撑住不缩 */
.gev-root--split :deep(.detail-column) { margin-top: -20px; margin-bottom: -20px; height: auto; }

负 margin 是为了让分栏柱**出血到窗口边**（`.gev-root` 自带 20px padding）。分栏时机要看 `selectedEntity`：
只在 `splitCarrierOpen` 里判断是不够的——没选中实体时根容器不该提前变向。

### 12.2 三种载体的定位口径

- **沉浸页靠父容器**：GEV 与时间线的根容器加 `position:relative`，载体本身 `absolute; inset:0`。
  不用 `fixed` 铺满窗口——那会盖掉窗口栏与视图工具条，边界不可控；也不会"关掉"列表，只是压在下面。
- **浮层小窗坐标不落盘**：窗口尺寸会变，存过坐标下次开可能直接跑到屏幕外。
  首次打开落右上（`innerWidth - 宽度 - 24`，y=72），之后由用户拖；拖动只做位置写入，
  宽度仍走 `useResizable`（已按帧合并）。
- **居中弹层的上界要按视口收**：`min(900, innerWidth*0.9)`，在载体内算一次，不逐帧读。
