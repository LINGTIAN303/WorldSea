## 一、这批只做「编排」，不碰「载体」

两级形态模型里，本批是 **L2 内容形态**＝同一份字段数据在容器里怎么排（分组/表格/段落/摘要/时间轴）。
**L1 载体形态**＝详情装在哪种容器（右栏抽屉 → 栏式整页 / 居中弹层 / 沉浸页 / 浮层小窗）归批次 2。

两级都挂在 1a 抽出来的**载体无关内容件** `EntityDetailForm` 上，所以换编排不动容器、换容器不动编排。
这条界线是本批全部设计的前提——上一轮我曾把它理解反（把「形态种类」当成字段编排），据此把批次切成了 1a/1b/2 三段。

## 二、注册表：为什么在仓内注册、为什么只有一份默认值

范式沿用大纲白板的 `FormDefinition`（`apps/tauri/src/world/plugins/outline/board/forms/registry.ts`），
有意改掉两处：

1. **形态件在仓内注册，不开放给芽运行时注册**。芽能改的是 `detailLayout.contentForm` 这个 **id**，
   不是往详情面塞组件。否则「用户在设置里可选的形态」会变成「某个芽恰好注册出来的形态」，
   选择器的内容就不可预期了。（真要开放自注册，得先把图标/文案/配置项一并纳入契约，那是另一批的事。）
2. **只有 `configSchema`，没有并行的 `defaultConfig`**。大纲白板两份并存，迟早漂移；
   1a 的 fieldType 三套命名漂移就是同型事故。这里默认值由 `defaultContentConfig()` 从 schema 的
   `default` 派生，`resolveContentConfig(form, stored)` 只做「默认打底 + 存储覆盖 + 未定义键兜底」。

注册顺序即选择器顺序；`registerContentForm` 幂等（同 id 重复注册直接跳过，不覆盖）。

## 三、五种编排与它们的适用判定

| id | 名称 | kind | 吃什么 | 空态说实话 |
|---|---|---|---|---|
| `grouped` | 分组式 | **inline** | 芽声明的 `groups` + `order` | 「该实体没有可显示的字段」 |
| `table` | 表格式 | derived | 全部可见字段 → 字段/值两列（复用 `ui-kit/DataTable`） | 同上 |
| `narrative` | 段落式 | derived | 长文本族字段合并成篇，按空行切自然段 | 「没有长文本字段，换分组式或摘要式看更合适」 |
| `summary` | 摘要式 | derived | 短字段族压成「标签 值」属性牌 + 首段正文摘录 | 「还没有已填的短字段」+「另有 N 项属性未显示」 |
| `timeline` | 时间轴式 | derived | 时间族字段聚成一条轴 | 「没有日期字段，时间轴式对它没有意义」 |

**归类只有一处口径**（`formValues.ts` 的 `fieldFamily`）：`textarea`/`richtext` → 长文本；
`date` 类型**或约定 key**（`date`/`dateEnd`/`birthDate`/`deathDate`/`createdAt`）→ 时间；其余 → 短字段。
加「约定 key」这一路是因为 `datable`/`ageable` trait 给的日期在 schema 里是 `text`，
类型说明不了它是时间——不加这路，人物志的「生卒年」进不了时间轴。

## 四、派生型在编辑态回落分组式（写路径单轨不破）

1a 把编辑收敛成**一条行内单轨**（`useEntityEdit` 的草稿 + `saveEdit`）。若五种编排各自实现编辑，
等于把那条单轨又分叉成五条。所以 `kind` 就是这件事的闸门：

```ts
activeContentForm(form, editing)
// 未注册 id → grouped（芽写错 id 也得有东西渲染）
// editing && kind==='derived' → grouped
```

`EntityDetailForm` 分发时按这个函数选件，并在选择器下方如实说明「**×× 为只读呈现，编辑中暂用分组式**」。
注意高亮仍留在**用户选的形态**上（`layout.contentForm`），不是回落后的 `grouped`——否则用户会以为自己的选择被改掉了。

## 五、形态之间只差编排，不差控件与动作

`DetailFieldRow.vue`（标签 + 作用域「共享/仅本实体」+ 移除 × + `FieldControl`）是 1a 行渲染的原样外移，
五个形态共用。所以「表格式里不能改字段类型语义」「摘要式里字段可移除吗」这类问题不需要各形态再答一遍。
派生形态在编辑态不出现（见第四节），因此它们只用到只读分支；双击仍发 `enter-edit` 进编辑。

## 六、只读展示的三个口径（都是 1a 修过的坑）

`displayOf(field, value, nameOf?)` 是派生形态唯一的取文入口，三条特殊规则：

- **`entityRef` 解成实体名**：值存的是 id（裁定：entityRef 落库统一存 id），只读形态直接把 id 打上表格
  就是 1a 那个「裸实体 ID」缺陷的复活路径。解析注入在 `useFieldSource()`（唯一碰 `entityStore` 的一处，
  `formValues.ts` 保持纯函数），**解不出显示「引用已失效」而不是退回 ID**。
- **`image` 显示「已配图」**：路径串打在只读表格里是噪声，缩略图属载体职责（抽屉头部已有封面位）。
- **空值统一「—」**，且**摘要式滤掉空值牌**——一排「—」正是被点名要消灭的幽灵行；但不静默吞，
  末尾报「另有 N 项属性未显示」。

时间轴式**不按日期排序**，沿用用户排的字段序：`datable` 的日期常见「约 1420 年」这类非 ISO 串，
字典序会把它们排到错误位置还看起来很讲道理。

## 六·补 段落式的正文渲染：复用主窗口同一 markdown 内核

`detail/richText.ts` 两条分支按**存储形态**分，不按字段类型表分：

| 存储 | 走法 | 为什么 |
|---|---|---|
| `textarea`/长文本（markdown 源或纯文本） | `renderFullMarkdown(text, null)` | marked 实例是 `{ gfm:true, breaks:true }`——**单换行也保留软断行**，正文里 `##`/`-`/`**` 变成结构而不是原样露出 |
| `richtext`（编辑器写出的 HTML） | `sanitizeMarkdownHtml(text)` 直渲 | 再过一遍 markdown 会把 `<p>` 里的 `*` 之类字符当语法误解析 |

两条**都过 DOMPurify**，所以不存在「裸 `v-html` 用户数据」的路径——这是这件事的全部要点，
守卫也就是 `richText.spec.ts` 里那组攻击载荷（`onerror` / `<script>` / `javascript:` / `<iframe>`）。

三个刻意的取舍：

- **import 走 `@worldsea/shared-ui/markdown/stream` 子路径**（为此在 shared-ui 的 exports 里加了一条），
  不是包根 `@worldsea/shared-ui/markdown`——包根会连带 `codeHighlight.ts`，把 Prism 核心 + 13 个语言组件
  一起拖进工作台首屏。
- **不 import 主窗口的 `markdown.css`**，段落式自己用 `:deep()` 补了十来行。那份是
  `.ws-agent-md`（Agent 气泡样式，含代码块外壳与 mention），详情面用不上，也不想让跨包 CSS 副作用扩散。
- **摘要式与表格式仍吃纯文本**（`narrativeSections` 同时返回 `raw` 与 `text`）：摘录与牌列要的是
  一行可截断的 plain，给它 HTML 反而要再剥一次。

## 七、配置与落盘

`DetailLayout` 多一个 `contentConfig: Record<string, unknown>`，与 `contentForm` 走同一套三级合并
（芽默认 ⊕ 用户按类型覆写 ⊕ 即时态，整表替换、后者赢），落在既有键 `worldsea_detail_layouts` 的
同一条记录里（不新增存储键）。切换形态**不清配置**：别的形态的键留在原地，本形态不消费它，切回来还在。
写入口 `useDetailLayout().setContentForm` / `setContentConfig`，本批只有前者被选择器调用（后者给 1b-2 的设置 Tab）。

内容件**不直写存储**：选择器只发 `change-form`，由载体侧（GEV）接线落盘——与 1a 的
「本件只发事件不直写」一致，批次 2 换载体时这条不用改。

### 芽声明这一层怎么接（`detailLayout` prop）

三级合并的「芽默认」原来没有入口，现补上：`GenericEntityView` 与 `SchemaRenderer` 各加一个
可选 `detailLayout?: LayoutSource` prop，GEV 把它作为 `useDetailLayout` 的第三个来源传进去。
schema 驱动的芽（走 `SchemaRenderer`）因此与直挂 GEV 的芽同一条路。

首批两枚样例（可复核、也可改）：

| 芽 | 声明 | 理由 |
|---|---|---|
| `characters`（CharacterList） | `contentForm: 'narrative'` | 角色详情以正文为主（描述/经历是长文本） |
| `items`（ItemView） | `contentForm: 'summary'` | 道具是短属性堆叠（类型/稀有度/材质…），一屏看全 |

声明常量放在各芽的模块作用域（`const DETAIL_LAYOUT: LayoutSource = {...}`），
**不要在模板里写对象字面量**——那会每次渲染换一次引用，把 `layout` 的 computed 白白搅动一遍。

守卫在 `components/__tests__/detailLayoutChannel.spec.ts`：三例分别锁「GEV 真的把声明传到了内容件的
`layout`」「用户覆写压得过芽声明」「SchemaRenderer 原样下传」。反证＝摘掉 GEV 第三参 → 第一例报红。

## 八、已知边界（留白，勿当已完成）

- **芽默认只落了两枚样例**（`characters`/`items`），其余 25 芽未声明＝首开仍是分组式。
  要不要给更多芽定默认属产品判断，按需在 1b-2 一并复核。
- 形态选择器落在**内容件顶部**（不是抽屉 header 的既有工具条里），这样批次 2 的四种载体自动都有；
  代价是详情正文第一行多了一条横排按钮。
- 9 个子视图硬编码 detail 卡的收编仍未做（计划 §3.6 本批不做清单）；`TimelineView` 的自有详情面
  用的是 `EventDetailFields`（1a 余下段），**不消费本批形态**——它没有 `contentForm` 概念。
- 字段排序/可见性的覆写 UI 与「恢复芽默认」归 1b-2。
- 段落式渲染的是 markdown 与已存 HTML，**代码块不高亮**（刻意不引 Prism）；代码块外壳样式
  （`.ws-code-block`/`.ws-code-copy`）来自主窗口那份 CSS，详情面没带——所以代码块显示为朴素 `<pre>`。
  要在详情里做高亮/复制按钮，属独立一笔，别顺手加。
