## 二、为什么这事值得单独裁（风险，不是猜测）

1. **单向 / 双向语义分叉**：ERS 建的是双向关系（`createBidirectional`），AutoLinkSuggestions 建的是
   `putRelation` 的单向记录。同一个「A 属于 B」从两个入口建出来，图上是一根边还是一个箭头，取决于用户点了哪。
2. **缓存一致性**：`relationStore` 是内存态真源。`storage.putRelation` 绕开它 ⇒ 新建的关系不进 store，
   详情里的关联条目要等下一次 `loadAll` 才看得见；用户观感就是「加了但没出现」。
3. **删除确认口径不一**：URP 的删除带 `deleteWithConfirm`（含关系影响面提示），
   而 AutoLink 建的边没有任何入口能删（它不在 URP 的 `getConnected` 视图里就没有删除按钮）。
4. **详情形态改造会牵动它**：批次 1b/2 换内容与载体时，关系区是唯一还没有统一口径的部分。
   若不先裁这三件的归属，L2/L1 形态会在「关系区该放在哪个 tab / 哪种形态下还留不留得下」上反复返工。

## 三、留给裁定的三个问题（本批不代答）

- 关系区的**唯一写入口**是谁：URP 承载「列 + 删」并把「加」委托给 ERS（即把四个芽的绕行收掉），
  还是保留各芽按关系类型定制的 tab（概念的「矛盾」确实需要专属文案）？
- `AutoLinkSuggestions` 的 `storage.putRelation` 是否改为走 `relationStore` / `createBidirectional`
  ——这是**行为变更**（会开始产生双向边），需要用户确认口径而不是顺手改。
- 字段 `autoLink`（如角色的 `race` → `species`）与手工关联在同一条关系上如何共存：
  字段值变了，关系跟着变还是并列存在？现在两条路径互不知情。

## 四、本批与它相关的一处连带改动

1a 把详情段外移到 `EntityDetailForm` 时，URP / ERS / AutoLinkSuggestions **一行未改**，
